Lead Capture That Can't Fail — Tool Routing, Dead Air & Defense-in-Depth

A test caller told Max "you have no listing in Montreal" — but there was one. Pulling that thread unravelled three live problems at once: a model downgrade that broke the agent's tool routing, a week of leads silently saved as Unknown because the agent stopped firing its lead tool, and seventeen seconds of dead air on a phone call. This is a forensics-heavy session: we hit the live database, replay real phone calls from the VAPI API, kill a wrong hypothesis with evidence, and then rebuild lead capture so it works even when the AI misbehaves. Plus a bonus: a "data corruption" bug that turned out to be our own terminal lying to us.

🔴 Advanced ⏱️ ~90 min read / build 📋 Requires: Sessions 08–10 (French STT, deploy pipeline, latency tuning)

This was a pure diagnose-and-repair session. No new feature was requested — instead, real test calls surfaced misbehaviour, and each symptom turned out to have a different root cause. The exact words that kicked it off:

By the end of the session we had:

  • Proven the backend was innocent for the "no Montreal listing" complaint — by calling the live endpoint ourselves and watching it return the listing correctly — and traced the real cause to a model downgrade (last session's gpt-4o) that broke the agent's multi-step tool routing.
  • Reverted all five lease agents back to gpt-5.2-chat-latest and re-deployed them.
  • Retracted a wrong diagnosis: a "corrupted" 11½ → 11Â½ in the database turned out to be our own Windows terminal mis-decoding correct UTF-8. No data was ever broken.
  • Discovered that every lead for a full week had been saved as a useless Unknown placeholder, because the agent had stopped calling its submit_lease_lead tool — and proved it by replaying real calls from the VAPI API.
  • Rebuilt lead capture with defense in depth: a prompt rule (primary), a VAPI structured-data extraction plan that mines the lead from the transcript at end-of-call (safety net), and the existing Unknown row as a last-resort floor.
  • Eliminated dead air by giving the lookup tools a deterministic request-start filler that VAPI speaks the instant a tool fires — instead of hoping the model remembers to.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Diagnose a voice-agent complaint by isolating each layer (database → backend → VAPI config → model behaviour) and testing them independently.
  • Replay a real phone call from the VAPI call API and read exactly which tools the model invoked.
  • Form and falsify a debugging hypothesis with evidence rather than guesses — and recognise when your "obvious" cause is wrong.
  • Explain why a blocking tool plus an empty filler list produces dead air, and fix it with a request-start message.
  • Build defense-in-depth data capture so a flaky AI can't lose a lead, using VAPI's analysisPlan.structuredDataPlan.
  • Spot a measurement artifact — when your tooling, not the system, is what's broken.

🧠 Concepts Introduced This Session

Ten ideas carry this session. Concepts 1–4 are about finding the bugs (isolation, tool dispatch, call forensics, falsification). Concepts 5–8 are the fixes (dead air, request-start, structured extraction, defense in depth). Concepts 9–10 are the two smaller-but-sharp lessons (measurement artifacts, tolerant matching).

1 · Layer isolation: test each layer before you blame it

Plain-English explanation. A voice agent is a stack of independent layers: the database (does the data exist and is it correct?), the backend API (does the endpoint return the right answer?), the VAPI config (is the right model/prompt/tools live?), and the model's behaviour (did the AI choose to do the right thing?). When something goes wrong, the amateur move is to guess which layer is broken. The professional move is to test each layer in isolation, cheapest and most-certain first, until exactly one of them fails.

Why we need it (for CRM specifically). The caller said "no listing in Montreal." That sentence could be caused by any layer: maybe the row is missing (database), maybe the search endpoint has a bug (backend), maybe the wrong agent answered (config), or maybe the AI just said the wrong thing (behaviour). If you "fix" the search endpoint when the real problem is the model, you've wasted hours and changed nothing the caller experiences.

How it works (analogy). An electrician tracing a dead outlet doesn't rewire the whole house. They test the bulb, then the outlet, then the breaker, then the panel — one component at a time, with a meter, until the meter reads wrong at exactly one spot. Each test rules out a layer. We do the same with curl against the live API and SQL against the live DB.

Jargon decoder.

  • layer / tier — one independently-testable stage of the system (DB, API, config, model).
  • isolation test — a check that exercises exactly one layer so a pass/fail points at that layer alone.
  • curl — a command-line tool that sends an HTTP request and prints the raw response; perfect for testing an API layer without the UI or the phone in the way.

Annotated command — testing the backend layer directly. Instead of guessing whether find_units works, we called it ourselves with the exact query from the logs:

$ curl -s "https://tenant-management-mvp.onrender.com/leasing/find-units?manager_id=28c43c77...&query=Montreal" { "found": true, # the backend DID find it "count": 1, "units": [{ "flat_number": "STDTEST02", "address": "48 Avenue Libre, Montreal, Quebec", ... }], "available_cities": ["Dehradun","Laval","Montreal","Ranchi"] }

found: true at the backend layer is a verdict: the database has the row, and the API returns it. Whatever told the caller "no Montreal listing" lives above this layer — in the model. One command eliminated two whole layers.

🔑 Key Concept — a green test is half the answer

Proving a layer works is just as valuable as proving one is broken. The Montreal found: true didn't fix anything — but it slammed the door on "the data is missing" and "the endpoint is buggy," leaving only the model. Most debugging time is wasted suspecting innocent layers; isolation tests acquit them fast.

2 · How a VAPI "tool" reaches the model (name vs function.name)

Plain-English explanation. Max can do things in the world — look up units, search inventory, save a lead — through tools. A tool is a little contract: a name, a description (so the model knows when to use it), a set of parameters, and a URL to call. VAPI hands these tool definitions to the language model on every turn. When the model decides to use one, it emits the tool's name; VAPI matches that name to a tool and makes the HTTP call.

Why we need it (for CRM specifically). Max has three lease tools — find_units (look up by place), search_listings (filter by size/budget), and submit_lease_lead (save the lead). Whether a lead gets saved depends entirely on the model choosing the right tool at the right moment. Understanding how the model "sees" these tools is the difference between guessing and knowing why it picked one over another.

How it works (analogy). Think of tools as labelled buttons on a vending machine. The model reads the labels (the name + description) and presses one. VAPI is the machine wiring that connects each button to a specific product (the URL). If two buttons had the same label, the model couldn't tell them apart — a fact that becomes a key red herring in Bug 3.

Jargon decoder.

  • tool / function call — a structured action the model can request instead of just talking.
  • apiRequest tool — VAPI's newer tool type that calls an HTTP URL directly (vs the older "function" type routed through a webhook).
  • top-level name — the identifier the model actually emits and VAPI dispatches on (e.g. find_units).
  • nested function.name — a legacy sub-field; in our config it is the same literal string "api_request_tool" on every tool (this looks alarming but is harmless — see Bug 3).
  • blocking vs async — whether the model waits for the tool's result before continuing (see Concept 5).

Annotated code — the shape of a lease tool.

{
    "type": "apiRequest",          # newer VAPI tool type: calls a URL directly
    "name": "submit_lease_lead",   # THE identifier the model emits + VAPI dispatches on
    "async": True,                 # don't make the model wait for the response
    "function": {
        "name": "api_request_tool",   # legacy sub-field; identical on ALL tools (harmless)
        "description": "Capture the prospective tenant as a lead before ending the call.",
    },
    "url": f"{backend_url}/voice/lease-lead-direct?call_id={{{{call.id}}}}&phone={{{{customer.number}}}}",
    "method": "POST",
    "body": { "type": "object", "required": ["caller_name", "qualification_status"], "properties": { ... } },
}
⚠️ Warning — a returned tool name is the model's choice, not VAPI's

When you read a call log and see find_units was called, that means the model chose to emit find_units. The tools are just options on a menu; the model orders. So "the wrong tool ran" is almost always "the model picked the wrong tool" — a behaviour problem — not a wiring problem. Keep that distinction sharp; it saves you from rewiring things that work.

3 · Call-object forensics: replaying a phone call from the API

Plain-English explanation. Every call VAPI handles is stored as a structured object you can fetch back over the API. It contains the full message timeline — what the caller said, what Max said, and crucially every tool call the model made, with its arguments. Instead of trusting a human's memory of a call, you replay the machine's own record.

Why we need it (for CRM specifically). "It took my details but didn't log the lead" is a feeling. The call object turns it into a fact: it showed the model called find_units(query="Laval") five times and never once called submit_lease_lead. That single observation collapsed a fuzzy complaint into a precise behaviour bug.

How it works (analogy). A plane's black box doesn't argue about what the pilot "probably" did — it has the actual control inputs. The VAPI call object is Max's black box: pull it after an incident and read the real inputs.

Annotated commands — the forensic sweep. We fetched the specific call, then swept the last 25 to build a timeline:

$ # 1) pull ONE call and list the tool calls the model emitted $ curl -s "https://api.vapi.ai/call/019ef540-..."> -H "Authorization: Bearer $KEY" # messages[].toolCalls[].function.name ==> [tool_call] name='find_units' args={"query": "Laval"} # x5, never submit_lease_lead $ # 2) sweep the last 25 calls: which DISTINCT tools did each one use? 2026-06-23 asst=c76a69ea distinct=['find_units'] # broken 2026-06-18 asst=dc53d48d distinct=['find_units'] # broken 2026-06-16 asst=c76a69ea distinct=['find_units','search_listings','submit_lease_lead'] # healthy! 2026-06-11 asst=c76a69ea distinct=['find_units','search_listings','submit_lease_lead'] # healthy!

That sweep is the whole case in four lines: the agent used all three tools through 2026-06-16, then only find_units from 06-18 onward. A regression with a date. Now you know when it broke, which tells you what change to look at.

📖 Deep Dive — turn anecdotes into time series

One broken call is an anecdote; twenty calls plotted by date is data. The moment we saw the clean split at 06-16/06-18, the search space collapsed from "anything about the agent" to "whatever was deployed between those two dates." Bisecting by time is one of the most powerful debugging moves there is — it's the same idea as git bisect, applied to production behaviour instead of source code.

4 · Forming and falsifying a hypothesis

Plain-English explanation. A hypothesis is a guess about the cause. The discipline that separates debugging from flailing is this: don't go looking for evidence that your guess is right — go looking for evidence that would prove it wrong. If you can't kill the hypothesis, it survives. If one fact kills it, you drop it instantly, no matter how attractive it was.

Why we need it (for CRM specifically). Investigating the missing leads, we found a juicy suspect: all three tools share the same nested function.name = "api_request_tool". "Aha — name collision! The model can't tell them apart!" It's a clean story. It's also wrong, and believing it would have sent us rewriting tool configs for hours while the real cause sat untouched.

How it works (analogy). A detective who only collects evidence confirming their favourite suspect convicts innocent people. A good one actively asks "what would prove this person didn't do it?" — an alibi. We hunted for the collision hypothesis's alibi, and found three.

The three alibis that killed the "name collision" theory:

AlibiWhat it proves
The shared function.name has existed since May (git history), including on 06-16 when all three tools worked.A constant can't cause a change. If it were the cause, the agent would never have worked.
The model emitted the literal name find_units in the call object — not api_request_tool.VAPI dispatches on the unique top-level name, not the shared nested one. The collision field is ignored.
OpenAI rejects duplicate function names with a 400 error; yet find_units worked fine.If the shared name reached the model, nothing would work at all. Something works ⇒ names aren't colliding.
🔑 Key Concept — "it worked before" is a scalpel

The single most useful question in a regression is: "what is different now versus when it worked?" Anything that was the same in the working state cannot be the cause — by definition. The shared function.name was identical on 06-16 (working) and 06-23 (broken), so it was instantly exonerated. Hold every suspect up against the last known-good state; constants are innocent.

5 · Blocking vs async tools, and where dead air comes from

Plain-English explanation. A tool can be blocking (the model stops and waits for the result before it says or does anything else) or async (the model fires the tool and keeps talking while it runs in the background). A blocking tool is the right choice when the model needs the answer to continue — but it has a cost: while it waits, if nothing has been said, the caller hears silence. On a phone call, silence reads as "the line dropped."

Why we need it (for CRM specifically). find_units is blocking (async: False) because Max needs the lookup result to know what to say next. The plan was for the model to speak a "one moment" phrase before firing the tool. But the model isn't reliable about that — on the failing call it fired find_units first and said nothing, producing 17 seconds of dead air. The caller said "Hello?" twice.

How it works (analogy). A receptionist who needs to check a file can either say "one moment, let me look" and then walk to the cabinet (you know they're working), or silently walk off mid-sentence (you think they hung up). Same wait, opposite experience. The words before the pause are the whole difference.

The failure, from the real transcript:

Caller (+11.9s): I just saw your listing in Laval. So what do you have there? Hello? [ find_units fires — blocking — and Max says NOTHING ] Caller (+28.4s): Hello? # ~17s of silence; caller thinks the line died Max (+29.1s): Let me check that in my system. One moment please. Got it...
⚠️ Warning — "the model will say the filler" is not a guarantee

Relying on a language model to reliably perform a timing-sensitive action ("speak before you call the tool") is fragile. Models are probabilistic; on some turns they'll fire the tool first. If the cost of the rare miss is high (a caller hanging up), don't rely on the model — make the platform do it deterministically (next concept).

6 · request-start messages: deterministic filler

Plain-English explanation. VAPI lets each tool carry a messages list. A message of type request-start is spoken automatically by VAPI the instant the tool fires — no model involvement at all. Put a "one moment" phrase there and a blocking tool can never again produce dead air, because the platform always says something the moment the wait begins.

Why we need it (for CRM specifically). It moves the filler from "the model hopefully remembers" to "the platform guarantees." Per VAPI's own docs, a configured request-start message is more reliable than asking the LLM to generate the phrase. We added one to find_units and search_listings — the two lookup tools the caller waits on.

How it works (analogy). It's the automatic "Your call is important to us" that plays the instant you're put on hold — the human agent doesn't have to remember to say it; the phone system does. Reliable because it's not a person's job.

Jargon decoder.

  • messages (on a tool) — phrases VAPI can speak at tool lifecycle moments (start, delayed, failed).
  • request-start — the message spoken the moment the tool call begins.
  • content — the literal text spoken; it is read in the language it is written, so we make it bilingual to cover both English and French callers.
  • blocking: false — on the message, means "speak this, but don't make the tool wait for the speech to finish."

Annotated code — the deterministic filler.

# VAPI speaks this the INSTANT the (blocking) tool fires — no model involvement, no dead air.
"messages": [{
    "type": "request-start",                  # lifecycle moment: tool just started
    # one short bilingual string (EN then FR) so either caller hears a wait phrase immediately.
    # content is read in the language it's written, so we include both — matches Max's "Hi. Bonjour." style.
    "content": "Let me check that in my system, one moment. Un instant, je vérifie ça.",
    "blocking": False,                         # don't hold the tool waiting for the speech to finish
}],
💡 Tip — pair the platform filler with a prompt that stops double-speak

If VAPI now always says "let me check," but the prompt also tells the model to say it, the caller hears it twice. So we changed the prompt's "say a checking phrase" instruction to "the system says it automatically — don't announce the lookup, just keep the conversation flowing." Deterministic mechanism + a prompt that defers to it = clean, single, reliable filler.

7 · Structured data extraction at end-of-call

Plain-English explanation. VAPI can run an analysis pass after a call ends: you give it a schema (the fields you want — name, budget, move-in date, …) and it reads the whole transcript and fills those fields in, returning them in the end-of-call report. This means you can recover the structured lead from what was said, even if the model never called the save-the-lead tool during the conversation.

Why we need it (for CRM specifically). The whole crisis was that the model stopped calling submit_lease_lead, so the structured lead was never built mid-call. Structured extraction is a second, independent path to the same data: it doesn't care whether the model behaved — it just mines the finished transcript. That's the difference between "leads if the AI cooperates" and "leads, period."

How it works (analogy). Imagine an interviewer who's supposed to fill in a form during the meeting but keeps forgetting. So you also record the meeting and have an assistant fill the form from the recording afterwards. Two independent chances to get the form filled; you only need one to succeed.

Jargon decoder.

  • analysisPlan — VAPI's post-call analysis config block on the assistant.
  • structuredDataPlan — the sub-block that extracts typed fields from the transcript per a JSON schema.
  • end-of-call report — the webhook VAPI sends after a call; the extracted data arrives at message.analysis.structuredData.
  • schema — a typed description of the fields to extract (string, number, enum, …) plus a per-field description that guides the extractor.

Annotated code — the extraction plan (trimmed).

_LEASE_STRUCTURED_DATA_PLAN = {
    "enabled": True,                       # turn the post-call extraction on
    "schema": {                            # the lead fields we want pulled from the transcript
        "type": "object",
        "properties": {
            "caller_name": {"type": "string", "description": "Caller's full name. Empty if never given."},
            "qualification_status": {      # an enum constrains the model to valid values
                "type": "string", "enum": ["qualified", "not_qualified", "unmatched"],
                "description": "qualified if a unit was discussed and no hard disqualifier; else ...",
            },
            "budget_max": {"type": "number", "description": "Max monthly rent stated, in dollars. 0 if not stated."},
            "move_in_timeline": {"type": "string", "description": "Preferred move-in date/timeframe. Empty if none."},
            "occupants": {"type": "integer", "description": "People who will live in the unit. 0 if not stated."},
            "unit_of_interest": {"type": "string", "description": "Unit/street/city chosen, exactly as spoken."},
            # ... employment, landlord_aware, pets, disqualifying_reason, notes ...
        },
    },
    "messages": [{                         # a system prompt that steers the extractor
        "role": "system",
        "content": "Fill every field from what the caller actually said. Use empty string for "
                   "unknown text and 0 for unknown numbers — never guess. budget_max/occupants are numbers.",
    }],
}
📖 Deep Dive — the transcript has no UUIDs

One honest limitation: the transcript contains spoken words, never internal IDs. The caller says "the place on Chemin du Lac," not the listing's UUID. So unit_of_interest captures the spoken text, and the backend resolves it to a real listing_uuid best-effort (a unique substring match against the manager's active listings). When the text matches exactly one listing, we link it; otherwise we keep the words and leave the link null. Structured extraction recovers human facts perfectly and machine identifiers approximately — design around that.

8 · Defense in depth: don't trust one mechanism with critical data

Plain-English explanation. Defense in depth means protecting something important with multiple independent layers, so that if one fails, another still catches it. For data you cannot afford to lose, you never rely on a single mechanism — especially not one as probabilistic as "the AI will remember to call the tool."

Why we need it (for CRM specifically). A lost lead is lost revenue — the worst possible failure for this product. So lead capture now has three layers, in priority order: (1) the model calls submit_lease_lead mid-call; (2) if it doesn't, VAPI's structured extraction builds the lead from the transcript at end-of-call; (3) if even that yields nothing, we still write a bare Unknown row so the manager at least sees a call happened. A call_id de-duplication check ensures whichever layer fires first wins, so we never double-save.

How it works (analogy). A bank vault doesn't rely only on the door lock. There's the lock, plus a time delay, plus motion sensors, plus a guard. Each is independent; a thief has to beat all of them. Our lead has the tool, the extractor, and the floor row — three locks on the same vault.

LEAD CAPTURE — three independent layers (first one to fire wins, deduped by call_id) during the call ─────────────▶ ① submit_lease_lead tool → POST /voice/lease-lead-direct [richest: model-built] │ (model didn't fire it?) at end of call ──────────────▶ ② structuredDataPlan → /voice/lease-eoc-webhook reads │ message.analysis.structuredData [complete: transcript-mined] │ (no structured data?) last resort ─────────────────▶ ③ "Unknown" placeholder row → so a call is never invisible [floor: proof-of-call]
🔑 Key Concept — the floor can only go up

Before this session, layer ③ was the only layer that ever fired — every lead was "Unknown." After it, ③ is the last resort. Critically, adding layers ① and ② cannot make things worse: in the absolute worst case (both new layers fail) we still write the same "Unknown" row we wrote before. Defense in depth is safe to add precisely because each layer only ever improves on the floor beneath it.

9 · Measurement artifacts: when your tool is the bug

Plain-English explanation. Sometimes the thing you're measuring is fine and your measuring instrument is what's wrong. A "broken" reading that only appears through one tool — and vanishes when you check another way — is a measurement artifact, not a real defect.

Why we need it (for CRM specifically). Mid-investigation we "found" data corruption: a Quebec apartment size stored as 11½ was coming back as 11Â½ — the classic look of double-encoded UTF-8 (a real, common bug). We almost wrote a database migration to "fix" it. Then we checked the raw bytes and they were perfect. The Â was being injected by our own Windows terminal, which decoded the API's correct UTF-8 as a different character set. The data was never broken; our viewer was.

How it works (analogy). A thermometer reading 200°C in a room that feels normal isn't a fire — it's a broken thermometer. Before you evacuate (write a migration), check the temperature a second, independent way (raw bytes).

Jargon decoder.

  • UTF-8 — the standard way to encode text (including ½) as bytes; ½ is the two bytes C2 BD.
  • cp1252 / Latin-1 — an older single-byte Windows encoding; it reads the byte C2 as the visible character Â.
  • mojibake — garbled text from decoding bytes with the wrong encoding (½ → Â½).
  • xxd / hex dump — shows the literal bytes, bypassing any character-set interpretation.

Annotated command — the byte check that exonerated the data.

$ curl -s ".../find-units?...&query=Montreal" | grep -o '"quebec_size":"[^"]*"' | xxd 00000010: 31 31 c2 bd 22 0a # 31 31 = "11", c2 bd = ½ in correct UTF-8. NOT corrupt.

The bytes c2 bd are textbook-correct UTF-8 for ½. The database, the API, and VAPI were all fine; only python -m json.tool piped through the Windows console had mis-rendered them. We retracted the "corruption" diagnosis on the spot.

10 · Tolerant matching: normalize before you compare

Plain-English explanation. Humans say the same thing many ways: "four and a half," "4½," "4 1/2," "4.5." If your code compares with exact string equality, all those near-identical inputs miss each other. Tolerant matching means: run both sides through a normalizer that collapses the variations into one canonical form, then compare the canonical forms.

Why we need it (for CRM specifically). The lease search filtered Quebec apartment size with exact equality (quebec_size == "4½"). If the agent ever passed "4 1/2" or "4.5", the listing would silently drop out of results. We replaced the exact match with a normalized one so all spellings of the same size match.

How it works (analogy). A good librarian searching for "McDonald" also finds "MacDonald" and "Mc Donald" — they mentally normalize spelling variants before matching. The normalizer is that librarian, in code.

Annotated code — the normalizer.

def _normalize_quebec_size(s: str) -> str:
    # Canonicalize a Quebec size so "4½", "4 1/2", "4.5" all compare equal.
    if not s:
        return ""
    s = s.strip().lower().replace("Â", "")      # strip a stray Â defensively (see Bug 2)
    s = s.replace("1/2", "½").replace(".5", "½")  # collapse the half-room spellings to one glyph
    return s.replace(" ", "")                     # drop spaces: "4 ½" == "4½"

Then the search filter compares _normalize_quebec_size(stored) == _normalize_quebec_size(query) instead of raw equality — fragile exact match becomes forgiving.

💡 Tip — normalize on both sides, always

A classic half-fix is normalizing only the user's input but comparing against raw stored values (or vice-versa). If either side can contain a variant, normalize both. The symmetry is what guarantees "4 1/2" typed today matches "4½" stored last month.

🐛 Bug Journal

Four bugs, four different root causes — a model regression, a fake corruption, a behavioural regression, and a timing failure. This is the heart of the session.

🐛 Bug 1 — "You have no listing in Montreal" (but we did)

🚨 The Symptom

A test caller asked about Montreal in English. Max replied that there were no Montreal listings — yet a real, active Montreal listing (STDTEST02, 48 Avenue Libre) existed. The backend log showed the agent firing find_units with odd queries:

GET /leasing/find-units?...&query=Montreal 200 OK GET /leasing/find-units?...&query=11%201/2 # a SIZE, not a place GET /leasing/find-units?...&query= # empty query

🔍 The Diagnosis

We isolated the backend layer (Concept 1) by calling find_units?query=Montreal ourselves: it returned found: true with the listing. So data and API were innocent. The log's smoking gun was the second query: query=11 1/2 is a Quebec size. find_units only matches places (city/street/building); it deliberately does not match sizes. Searching a size through it always returns nothing — which the model then voiced as "no listings." The model was using the wrong tool for the job and never advancing to search_listings (which does filter by size). When the user mentioned they'd downgraded the model last session, the cause clicked into place.

🧠 The Root Cause

Last session's latency fix swapped the lease LLM from gpt-5.2-chat-latest to the lighter gpt-4o. The lease flow is a long, multi-step tool-routing spec (look up place → ask size → then filter with search_listings). The lighter model was materially worse at following that spec: it conflated the tools and stalled in the lookup step. This was the exact asymmetric downside we flagged in Session 10 — speed bought at the cost of behavioural quality. (We also confirmed the user's "prompt cut" was never deployed — the live prompt was the full 15,308 chars — so the prompt was not a contributor.)

🔧 The Fix

"model": {
    "provider": "openai",
    "model": "gpt-4o",                 # BEFORE: lighter/faster but mis-routes the multi-step tool flow
    "model": "gpt-5.2-chat-latest",    # AFTER:  restores reliable tool routing (the behaviour we need)
    ...
}

Then the idempotent push redeployed all five lease agents, and we verified the live model field server-side.

🛡️ The Lesson

An asymmetric trade-off isn't theoretical until it bites — and then it bites in production, on a real caller. A cheaper/faster model is only "free" if it preserves the behaviour you depend on; for a long tool-routing flow, model capability is the feature. When you take a speed-for-quality bet, instrument it (replay calls, watch tool usage) so you catch the regression before a customer does. And always isolate layers first: one curl saved us from "fixing" an innocent endpoint.

🐛 Bug 2 — The data corruption that wasn't (11Â½)

🚨 The Symptom

While inspecting the Montreal listing's JSON, the Quebec size came back looking double-encoded:

$ curl -s ".../find-units?...&query=Montreal" | python -m json.tool "quebec_size": "11Â½" # expected "11½" — looks like classic UTF-8 mojibake

This is the exact signature of a real, common bug (UTF-8 text accidentally decoded as Latin-1 and re-encoded), so it was completely believable. The initial diagnosis flagged it as data corruption introduced by a listing-edit path, and proposed a backfill migration.

🔍 The Diagnosis

Before writing a migration against production data, we verified two independent ways (Concept 9):

  1. Read the database directly via the Supabase SDK and printed codepoints: ['0x31','0x31','0xbd'] = 1,1,½. Clean. No Â (which would be 0xC2 as a separate codepoint).
  2. Read the live API as raw bytes with xxd: 31 31 c2 bd. The c2 bd is correct UTF-8 for ½.

Both the stored data and the wire bytes were perfect. The only place the Â appeared was through python -m json.tool rendered in the Windows terminal.

🧠 The Root Cause

The Windows console's default code page (cp1252) decoded the API's correct UTF-8 bytes with the wrong character set. UTF-8 encodes ½ as the two bytes C2 BD; cp1252 reads byte C2 as the visible glyph Â and BD as ½ — producing the phantom Â½. The corruption was generated by the act of viewing. The database, the FastAPI response, and VAPI all handled the bytes correctly end-to-end. The instrument was the bug.

🔧 The Fix

The fix was to not change the data at all — and to retract the corruption claim. The only code we wrote was defensive: the new _normalize_quebec_size strips a stray Â just in case a real one ever sneaks in, and we recorded the gotcha as a persistent memory so it never re-derails an investigation:

Verify raw bytes before declaring UTF-8 corruption. On Windows, piping an API
response through `python -m json.tool` (or print) decodes it as cp1252, turning
correct UTF-8 (C2 BD = ½) into a phantom "Â½". Confirm with `curl | xxd` and by
printing codepoints from the DB before writing any migration. Only 0xC2 actually
present in storage is real mojibake.

🛡️ The Lesson

When a defect appears only through one viewing path, suspect the path before the data. The cost of being wrong here was asymmetric and nasty: a "corruption fix" migration would have rewritten correct rows based on an illusion — turning a non-bug into a real one. The senior move is to confirm with an independent instrument (raw bytes) and, when the data is fine, to have the discipline to do nothing. Knowing when not to act is as valuable as any fix.

🐛 Bug 3 — A full week of leads logged as "Unknown"

🚨 The Symptom

After a successful-feeling test call — Max collected the caller's name (Pranav Raj), budget, move-in date, employment, occupants, pets — the manager saw no usable lead. The lease_leads table held only a placeholder:

most recent lease_leads rows: 2026-06-23 name='Unknown' status=unmatched notes="[end-of-call fallback] Transcript: ..." 2026-06-23 name='Unknown' status=unmatched 2026-06-18 name='Unknown' status=unmatched ... every recent call was an "Unknown" fallback — no real names, budgets, or qualification ...

🔍 The Diagnosis

We replayed the actual call from the VAPI API (Concept 3). The message timeline showed the model calling find_units(query="Laval") five times — at the budget step (where search_listings was due) and twice at the handoff (where submit_lease_lead was due) — and never calling submit_lease_lead. So the structured lead was never built mid-call; only the end-of-call Unknown fallback ever fired. Sweeping 25 calls placed the regression precisely: all three tools healthy through 06-16, only find_units from 06-18.

The red herring (and how we killed it). The obvious suspect was the shared function.name = "api_request_tool" across all three tools. We almost committed to it — then falsified it (Concept 4): it had been shared since May (including 06-16 when tools worked), the model emitted the unique top-level find_units (so dispatch uses that, not the shared field), and OpenAI would 400 on genuinely-duplicate names yet find_units worked. Three alibis, hypothesis dead.

🧠 The Root Cause

A prompt regression deployed around 06-17 (the Quebec-sizing / banded-confirmation work). That change (a) enriched find_units so it now returns full unit data — rent, size, beds, address — making it look like a do-everything tool, and (b) grew the prompt large enough to bury the submit_lease_lead instruction. The model learned to lean on find_units for everything and to narrate the closing line ("I'll get that to the team") instead of actually firing the lead tool. Both gpt-4o and the reverted gpt-5.2 exhibited it, confirming it was the prompt/tool framing, not the model.

🔧 The Fix — defense in depth (three layers)

(1) Prompt — make lead capture a hard rule and stop the model treating find_units as the finish line:

- ALWAYS call submit_lease_lead exactly once before the call ends — it is the ONLY tool
  that records the lead; find_units and search_listings only look things up and never capture a lead
- A call that ends without submit_lease_lead has FAILED. Do NOT call find_units/search_listings to wrap up.

(2) Safety net — VAPI's structuredDataPlan extracts the lead from the transcript at end-of-call (Concept 7), and the rewritten webhook builds a complete lead from it:

analysis = message.get("analysis") or {}
structured = analysis.get("structuredData") or {}          # fields VAPI mined from the transcript
if structured:                                             # SAFETY NET: build a COMPLETE lead
    lead_payload = {
        "caller_name": structured.get("caller_name") or "Unknown",
        "budget_max": _pos_num(structured.get("budget_max")),       # numbers parsed defensively
        "move_in_timeline": (structured.get("move_in_timeline") or "").strip() or None,
        "occupants": _pos_int(structured.get("occupants")),
        "qualification_status": structured.get("qualification_status") or "unmatched",
        "qualifying_answers": {...},                                # employment / landlord / pets / unit text
        # listing_uuid resolved best-effort from spoken unit_of_interest (transcripts carry no UUIDs)
        ...
    }
else:                                                      # FLOOR: only if nothing was extracted
    lead_payload = {"caller_name": "Unknown", "qualification_status": "unmatched", ...}
# dedup by call_id means if submit_lease_lead already saved during the call, this skips entirely
db.table("lease_leads").insert(lead_payload).execute()

(3) Floor — the original Unknown row remains as the last resort, so a call is never invisible. A call_id dedup ensures whichever layer fires first wins.

🛡️ The Lesson

Two lessons braided together. First, don't fall in love with your first hypothesis — the function.name theory was elegant and wrong; only actively trying to falsify it saved hours of misdirected work. Second, don't trust a probabilistic component with non-negotiable data. "The model will call the tool" is a hope, not a guarantee; for revenue-critical data like leads, add an independent, deterministic capture path so the system succeeds even when the AI doesn't. The prompt fix raises the odds; the structured-extraction net makes the outcome certain.

🐛 Bug 4 — Seventeen seconds of silence

🚨 The Symptom

On the same test call, Max went dead silent right after the caller's first question, for long enough that the caller repeated "Hello?" twice, thinking the line had dropped:

Caller (+11.9s): ...what do you have there? Hello? Caller (+28.4s): Hello? # ~17 seconds of nothing Max (+29.1s): Let me check that in my system. One moment please...

🔍 The Diagnosis

The gap lined up exactly with the first find_units call. That tool is blocking (async: False) because Max needs the result to continue (Concept 5). Its messages list was empty — by an earlier design choice to let the model speak the "one moment" phrase itself for bilingual flexibility. But on this call the model fired the tool first and spoke after the result returned. With a blocking tool and no platform-level filler, that ordering produces raw silence for the whole lookup.

🧠 The Root Cause

The filler was the model's responsibility, and the model is probabilistic about when it speaks relative to a tool call. The design relied on the LLM to perform a timing-sensitive action reliably; it doesn't. The empty messages list meant there was no deterministic backstop, so the one time the model got the ordering "wrong," the caller got 17 seconds of nothing.

🔧 The Fix

Move the filler from the model to the platform — a deterministic request-start message on the lookup tools (Concept 6), plus a prompt edit so the model no longer also announces the lookup (avoiding double-speak):

# BEFORE: empty — relied on the model to speak a filler before the blocking call
"messages": [],

# AFTER: VAPI speaks this the instant the tool fires — deterministic, bilingual, no dead air
"messages": [{
    "type": "request-start",
    "content": "Let me check that in my system, one moment. Un instant, je vérifie ça.",
    "blocking": False,
}],
The system AUTOMATICALLY speaks a short bilingual "one moment" phrase the instant any lookup
starts. You do NOT need to announce the lookup or say "let me check" yourself — saying it too
would double up. Instead, keep the conversation flowing and use the result the moment it arrives.

🛡️ The Lesson

If a behaviour is timing-critical and its failure is expensive (a caller hanging up), don't delegate it to a probabilistic agent — make the deterministic platform own it. The model is great at deciding what to say; it's unreliable at guaranteeing when. Match each responsibility to the component that can actually guarantee it. And when you move a job to the platform, update the prompt so the two don't collide (the double-speak guard).

🐛 Why so many bugs this session?

Unlike a green-field feature session, this one was almost entirely modifying existing, deployed behaviour — the surface with the most integration points to fail. Three of the four bugs were regressions (something that used to work), which is exactly where time-bisecting ("what changed since it worked?") and layer isolation pay off most. The fourth wasn't even a real bug — a reminder that "found a bug" should itself be a falsifiable claim.

🧯 Troubleshooting / Common Errors

The push said "5 updated" but the new field isn't live

A VAPI PATCH can accept a payload and silently drop a field it doesn't recognise (e.g. if analysisPlan wasn't mapped in _to_vapi_payload). Always re-fetch the assistant and assert the field is present. If it's missing, check that the snake_case config key (analysis_plan) is mapped to the camelCase payload key (analysisPlan) in the deploy script.

Leads still save as "Unknown" after deploying

Three things to check, in order: (1) Did the backend deploy to Render? The EOC webhook code that reads structuredData is backend, not VAPI config. (2) Is analysisPlan.structuredDataPlan.enabled actually true on the live assistant? (3) Did the call even produce a transcript? An immediate hang-up yields nothing to extract — that's a legitimate Unknown.

The caller hears the "one moment" phrase twice

That's the double-speak case: VAPI's request-start filler and the model both said it. Make sure the prompt's system-check section tells the model the filler is automatic and it should not announce lookups. Both halves of the fix must ship together.

"Â½" or other accented junk in a terminal

Almost always a console encoding mismatch (Concept 9), not real data. Verify with curl | xxd (look for c2 bd = correct ½) or by writing the output to a UTF-8 file and opening it in an editor, before you believe the data is broken.

"It worked yesterday" — where do I even start?

Bisect by time. Find the last known-good moment and the first known-bad one, list every deploy/change between them, and suspect those only. Anything unchanged across that boundary is innocent. For voice agents, the VAPI call API gives you a timestamped behaviour history to pin the boundary precisely.
