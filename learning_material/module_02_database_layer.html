Section 1 — What You Are Building

session.py is the gateway to the database. It creates two Supabase clients — one that respects Row Level Security (RLS) for user-facing routes, and one that bypasses it for webhooks and admin operations. Every route handler that reads or writes data gets one of these two clients injected via FastAPI's dependency system.

Two clients created ONCE at module import time (singletons): ┌─────────────────────────────────────────────────┐ │ _anon_client (uses SUPABASE_KEY) │ │ → Respects RLS │ │ → Used with get_authenticated_db (Module 03) │ │ → User sees only their own manager's data │ └─────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────┐ │ _service_client (uses SUPABASE_SERVICE_KEY) │ │ → Bypasses ALL RLS │ │ → Used in webhooks (Stripe, VAPI) │ │ → Used in admin operations │ │ → Sees ALL data across ALL managers │ └─────────────────────────────────────────────────┘

Section 2 — Concept Deep-Dives

Row Level Security (RLS) — PostgreSQL's per-row access control

Row Level Security is a PostgreSQL feature that adds a WHERE clause to every query automatically, based on who is running the query. When enabled on a table, a policy defines which rows each user can see or modify. Without RLS, every authenticated user can read every row in the database.

How it works conceptually

-- Without RLS: any authenticated user can do this
SELECT * FROM complaints;  -- returns ALL complaints from ALL managers

-- With RLS policy: "manager_id = auth.uid()"
SELECT * FROM complaints;  -- PostgreSQL silently adds:
-- WHERE manager_id = '<current user UUID>'
-- Returns only THIS manager's complaints

How auth.uid() gets the current user

Supabase Auth sets a session-level variable request.jwt.claims that PostgreSQL can read via auth.uid(). When you call db.postgrest.auth(token) in Python, the anon client includes the JWT in every subsequent PostgREST request. PostgREST passes it to PostgreSQL as a session variable — and PostgreSQL's RLS policies read it via auth.uid().

The service-role key bypasses RLS entirely

Supabase's service-role key carries a special JWT claim ("role": "service_role") that PostgreSQL recognizes as a superuser bypass. RLS policies are simply not evaluated. This is what makes it dangerous — and why it must never reach the frontend.

Try it yourself — see RLS in action

In Supabase SQL editor, run:

-- Enable RLS on a table
ALTER TABLE test_table ENABLE ROW LEVEL SECURITY;

-- Create a policy: users only see their own rows
CREATE POLICY own_rows ON test_table
  USING (user_id = auth.uid());

Success: After applying the policy, querying via the anon key (with a user JWT) returns only rows where user_id matches the logged-in user. The service-role key still returns all rows.

Supabase Python SDK — PostgREST query builder

The Supabase Python SDK wraps HTTP calls to the PostgREST REST API. You don't write SQL — you chain method calls that build a query. PostgREST translates them to SQL and runs them against PostgreSQL.

Common query patterns (standalone example)

from supabase import create_client

db = create_client("https://xxx.supabase.co", "your-key")

# SELECT * FROM complaints WHERE status = 'pending' ORDER BY created_at DESC
result = (
    db.table("complaints")
    .select("*")
    .eq("status", "pending")
    .order("created_at", desc=True)
    .execute()
)
rows = result.data   # list of dicts

# INSERT INTO complaints (...) VALUES (...) RETURNING *
new = (
    db.table("complaints")
    .insert({"flat_number": "101", "category": "water"})
    .execute()
)
created = new.data[0]   # the inserted row

# UPDATE complaints SET status='resolved' WHERE uuid='...' RETURNING *
updated = (
    db.table("complaints")
    .update({"status": "resolved"})
    .eq("uuid", "some-uuid")
    .execute()
)

# DELETE FROM complaints WHERE uuid='...'
db.table("complaints").delete().eq("uuid", "some-uuid").execute()

# JOIN: select complaints with nested appointment data
result = (
    db.table("complaints")
    .select("*, appointments(*)")   # nested select = JOIN
    .execute()
)

Key methods reference

MethodSQL equivalentNotes
.select("*")SELECT *Comma-separated column names to limit fields
.eq("col", val)WHERE col = valChain multiple for AND conditions
.ilike("col", "%val%")WHERE col ILIKE '%val%'Case-insensitive search
.in_("col", [a, b])WHERE col IN (a, b)Note the underscore — in is a Python keyword
.order("col", desc=True)ORDER BY col DESC
.limit(n)LIMIT n
.maybeSingle()LIMIT 1Returns None if no row, dict if one row, error if multiple
.execute()(sends the HTTP request)Must always be the final call

Always chain .execute() last. Without it, the query is never sent. The SDK is lazy — it builds the query object without running it until .execute() is called.

Why NOT SQLAlchemy with Supabase

SQLAlchemy is Python's most popular ORM. It lets you write Python code (not SQL) to query a database. So why doesn't this project use it?

Problem 1: SQLAlchemy bypasses RLS. SQLAlchemy connects directly to PostgreSQL via a connection pool. It doesn't know anything about Supabase Auth, JWT tokens, or auth.uid(). Running a query via SQLAlchemy means RLS doesn't activate — you'd see all rows for all managers, not just the current user's data. You'd have to manually add WHERE manager_id = ? to every single query — which is exactly what RLS automates.

Problem 2: Connection pooling conflicts. Supabase uses PgBouncer for connection pooling in transaction mode. SQLAlchemy's session-level configuration doesn't survive PgBouncer transaction mode, causing subtle failures.

What models.py is doing here: It was written during the prototype phase when the app used SQLite locally. The current codebase never imports from models.py in any live route. It exists as a historical artifact and can be ignored.

Section 3 — Line-by-Line Walkthrough

File: backend/app/db/session.py

from supabase import create_client, Client
from app.config import settings
Client is the type hint for a Supabase client object. Importing it here lets you annotate function return types and use IDE autocomplete on the client object in route files.
if not settings.SUPABASE_URL or not settings.SUPABASE_KEY:
    raise ValueError("SUPABASE_URL and SUPABASE_KEY must be set in environment variables")
This guard runs at module import time (i.e., when Uvicorn starts). If the env vars are missing, the server fails immediately with a clear error rather than crashing on the first database call with an opaque SDK error. Fast fail makes the root cause obvious.
_anon_client: Client = create_client(settings.SUPABASE_URL, settings.SUPABASE_KEY)
create_client() creates the Supabase client using the anon key. This client respects RLS. It's a module-level variable (created once at import time). The leading underscore in _anon_client signals "private to this module — access via the get_db() function, not directly."
_service_client: Client | None = None
if settings.SUPABASE_SERVICE_KEY:
    _service_client = create_client(settings.SUPABASE_URL, settings.SUPABASE_SERVICE_KEY)
The service client is optional — it's only created if SUPABASE_SERVICE_KEY is set. This allows the app to run in limited mode without the service key (useful for read-only development). The Client | None type hint means it can be either a Client or None — routes that need the service client check for None and raise an error.
def get_db() -> Client:
    return _anon_client

def get_service_db() -> Client:
    if _service_client is None:
        raise ValueError("SUPABASE_SERVICE_KEY is not configured")
    return _service_client
These are dependency functions — they're passed to FastAPI's Depends() in route signatures. get_db() just returns the singleton anon client. get_service_db() guards against the service key being missing.

Why functions instead of exporting the variables directly? Because Depends(get_db) is how FastAPI knows to inject a DB client — it calls the function for you. Exporting _anon_client directly would work but would bypass FastAPI's dependency injection system and make testing harder.

File: backend/app/db/models.py — Why it exists but isn't used

This file defines SQLAlchemy ORM models for the original schema. It was the database layer during the prototype. Notice that the models define tables that have since been replaced in Supabase:

class Tenant(Base):
    __tablename__ = "tenants"
    id = Column(Integer, primary_key=True)         # legacy int PK
    name = Column(String(100), nullable=False)
    phone = Column(String(20), unique=True, nullable=False)
    unit_id = Column(Integer, ForeignKey("units.id"))
    # ... etc
The live Supabase tenants table uses uuid as the primary key (not id), has flat_uuid instead of unit_id, and has many more fields. Never use these model classes in new code. They're kept here because removing them would require updating the Alembic migration history — a low-priority cleanup task.

Section 4 — Why This Design

Decision: Two global clients vs. one client per request

ApproachProsCons
Two module-level singletons (chosen)Zero connection overhead per request; predictable memory; simpleThread-safety concern (mitigated because postgrest.auth() is called per-request in get_authenticated_db)
New client per requestPerfect isolation; no shared state concernsSupabase client creation is slow (DNS lookup, SSL handshake); 100 req/s = 100 clients created/destroyed
Connection pool (SQLAlchemy)Efficient; well-tested; battle-hardenedBypasses RLS; conflict with Supabase's PgBouncer; requires manual WHERE manager_id

The key insight: The anon client singleton is safe because get_authenticated_db (Module 03) calls db.postgrest.auth(token) on every request — this sets the JWT for that request's PostgREST calls only. It's effectively per-request scoping even with a shared client object.

Decision: Supabase SDK vs. direct PostgreSQL (psycopg2/asyncpg)

ApproachProsCons
Supabase SDK (chosen)RLS automatic; Storage + Auth same SDK; simpler for CRUDHTTP overhead vs. raw PostgreSQL; limited query expressiveness
asyncpg / psycopg3Full SQL power; async-native; fastest Python PostgreSQL driverMust implement RLS token passing manually; must manage connection pool

Section 5 — How It Connects

session.py │ ├── get_db() → _anon_client │ │ │ └──► get_authenticated_db (Module 03) │ │ calls db.postgrest.auth(jwt_token) │ └──► injected into user-facing routes │ (complaints, flats, tenants, buildings, ...) │ └── get_service_db() → _service_client │ └──► webhooks: voice.py, payments.py └──► admin: vapi_provisioning.py └──► subscription checks: subscription.py

Data flowing IN: settings.SUPABASE_URL and settings.SUPABASE_KEY / SUPABASE_SERVICE_KEY — the connection credentials from config.py.

Data flowing OUT: Two Client objects that all route handlers depend on. The anon client is always used via get_authenticated_db() (never directly). The service client is used directly in webhook routes and admin operations.

Section 8 — Exercises

Easy Write a function that fetches a row by UUID

Problem: Write a standalone Python function get_complaint(db, uuid: str) -> dict | None that fetches a single complaint by UUID and returns it as a dict, or None if not found.

Hints

Use .maybeSingle() instead of .execute() — it returns None if no row is found, instead of an empty list. Filter with .eq("uuid", uuid).

Solution 
from supabase import Client

def get_complaint(db: Client, uuid: str) -> dict | None:
    result = (
        db.table("complaints")
        .select("*")
        .eq("uuid", uuid)
        .maybeSingle()
        .execute()
    )
    return result.data   # None or dict

Success: calling with a valid UUID returns a dict; calling with a non-existent UUID returns None (not an empty list, not an error).

Medium Add a third client function for read-only access

Problem: Add a get_readonly_db() function in session.py that returns the anon client but raises an error if someone tries to call .insert(), .update(), or .delete() on it. This is a conceptual exercise — implement it using Python's __getattr__ wrapping.

Hints

Create a wrapper class that proxies all attribute access to the underlying client but intercepts .table() and returns a restricted table object that blocks mutation methods.

Solution 
class ReadOnlyClient:
    def __init__(self, client: Client):
        self._client = client

    def table(self, name: str):
        tbl = self._client.table(name)
        def block(*args, **kwargs):
            raise PermissionError("Read-only client — mutations not allowed")
        tbl.insert = block
        tbl.update = block
        tbl.delete = block
        return tbl

def get_readonly_db() -> ReadOnlyClient:
    return ReadOnlyClient(_anon_client)

Success: get_readonly_db().table("x").select("*").execute() works; get_readonly_db().table("x").insert({}).execute() raises PermissionError.

Hard Implement a query helper with automatic RLS token injection

Problem: Currently, every route that uses the anon client must first call get_authenticated_db (which sets the JWT). Write a context manager with_rls(token: str) that temporarily injects the JWT into the anon client and removes it after:

with with_rls(token) as db:
    result = db.table("complaints").select("*").execute()
Hints

Use contextlib.contextmanager. Call _anon_client.postgrest.auth(token) on enter, and clear it (auth(None)) on exit. Use a try/finally to ensure cleanup even on exceptions.

Solution 
from contextlib import contextmanager

@contextmanager
def with_rls(token: str):
    _anon_client.postgrest.auth(token)
    try:
        yield _anon_client
    finally:
        _anon_client.postgrest.auth(None)   # always clear token

Note: This approach has a race condition in async code — two concurrent requests could overwrite each other's tokens. The project avoids this by using FastAPI's Depends(get_authenticated_db) which calls auth(token) per request before each query chain. This exercise is conceptual — the context manager pattern is cleaner but breaks under concurrency.

Success: The context manager sets the auth token on entry and clears it on exit, even if an exception occurs inside the block.
