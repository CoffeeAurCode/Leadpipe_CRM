The Always-200 Rule

Critical VAPI rule: Every VAPI webhook endpoint MUST return HTTP 200, even on errors.

If your endpoint returns 4xx or 5xx, VAPI interprets it as a fatal failure and kills the active call session. The tenant gets disconnected mid-complaint. From the VAPI dashboard, the call shows as "Failed".

The correct pattern: catch all exceptions, return a JSON response with an error description, but always with HTTP 200.

Step 1: Event Type Filtering — MUST Be First

Why this MUST be first: VAPI fires many webhook events per call — status-update, transcript, speech-update, and more. These intermediate events do NOT contain call_id or other metadata. If you try to extract call_id before filtering, you'll crash on None for most events. The event type check is the gate — everything else runs only for final events.

Step 2: Call Metadata Extraction (Priority-Based Fallback)

VAPI's webhook payload structure has changed across SDK versions. The three-level fallback chain handles all known variants. This was discovered through actual incidents where new VAPI releases sent data in a slightly different location.

Step 3: Transcript Extraction

We extract only role == "user" messages from the formatted transcript. We don't need the agent's own speech (role "assistant") for complaint extraction — the tenant's words are what matter.

Step 4: Confirmation Detection

A complaint is only created when the tenant explicitly confirmed their submission. The VAPI agent calls submit_complaint only after asking "Just to confirm, this is for flat 204, a plumbing issue... Is that correct?" and the tenant says "yes". The webhook detects this confirmation by looking for the submit_complaint tool in the payload.

Step 7: Idempotency Check

Why idempotency matters for webhooks: VAPI may re-send the same event if it doesn't receive a timely 200 response (network hiccup, slow server startup). Without this check, you'd get duplicate CallLog rows and duplicate Complaint records for the same call. The call_id UNIQUE constraint on the call_logs table enforces this at the DB level too — but checking first avoids an unnecessary INSERT attempt.

Step 10: Complaint Creation Flow

Why HTTP instead of calling the DB directly?

The complaint route (POST /complaints) does several things beyond a simple INSERT: it links the flat, looks up the tenant UUID, handles RLS, checks for existing complaints, and triggers notification side effects. Duplicating all that logic in the webhook would create a maintenance burden.

The known downside: This HTTP call will break with gunicorn multi-worker deployments (worker A's webhook calls worker B's /complaints endpoint — works in dev, can fail in production with internal routing). For production scale, replace with a direct service function call. The code comment acknowledges this.

Module-level call status timestamp

The frontend polls this endpoint every 3 seconds. When the timestamp changes (a new call has ended), it refreshes the complaints and appointments data. This is a lightweight alternative to WebSockets or SSE for this use case.

Outbound Call Endpoint

Why asyncio.to_thread? The VAPI Python SDK uses synchronous HTTP calls internally (no async support). FastAPI runs on an async event loop. Calling a synchronous function that blocks for 2-5 seconds from an async handler would block the entire server, preventing other requests from being processed. asyncio.to_thread() runs the blocking call in a thread pool, freeing the event loop.

Bugs & Fixes

Bug 1: tool-calls event processed without submit_complaint → duplicate CallLog

Symptom: Multiple CallLog rows with the same call_id.

Root cause: The agent calls other tools during a call (Verify_phone_number, check_availability). Each triggers a tool-calls event. The early webhook processed ALL tool-call events.

Fix: The webhook always checks for submit_complaint specifically. Only that tool creates a complaint. All other tool-call events are still processed to create the CallLog (which uses the idempotency check), but no complaint is created.

Bug 2: call_id extracted before event type check → NoneType crash on intermediate events

Symptom: AttributeError: 'NoneType' object has no attribute 'get' on most webhook events.

Root cause: Code tried to do message.get("call", {}).get("id") on intermediate events that have no "call" key.

Fix: Event type filtering is now STEP 1 — before any metadata extraction. Only final events (tool-calls, end-of-call-report) reach the metadata extraction code.

Bug 3: VAPI showing call as "Failed" in dashboard

Symptom: VAPI dashboard marks calls as failed. Tenants report the call dropped suddenly.

Root cause: A DB error (Supabase network timeout) raised an exception in the webhook. The exception propagated to FastAPI which returned HTTP 500.

Fix: Wrapped the entire function in try/except and return 200 even on errors. The error is logged but the VAPI session is not killed.

Exercises

Easy   Why does the voice webhook use get_service_db and not get_authenticated_db?

VAPI webhook calls arrive from VAPI's servers, not from a logged-in user. There is no JWT token in the request. get_authenticated_db reads the Authorization: Bearer header and would fail with a 401 or 403 if the header is missing. get_service_db uses the service role key (from the server's environment variable) which bypasses RLS and works without a user JWT.

Easy   What is the purpose of _last_call_ended_at being module-level (not in a database)?

The frontend polls GET /voice/call-status every 3 seconds. Storing this in a DB would require a write on every call end and a read every 3 seconds — unnecessary overhead for a simple "has anything changed?" signal. Module-level is faster (in-memory) and sufficient for single-worker deployments. The known limitation: it resets on server restart and doesn't work correctly with multiple server workers (Gunicorn multi-process). For production with multiple workers, this should be stored in Redis or the DB.

Hard   The HTTP call to /complaints inside the webhook will break with multiple Gunicorn workers. Design a solution that doesn't have this problem.
Show solution

Problem: Worker A handles the webhook. It makes an HTTP call to localhost:8000/complaints. With Gunicorn + 4 workers, localhost:8000 round-robins between all workers. The request may land on worker B which has a different DB session context. This can cause race conditions or the authenticated DB client not being set up correctly.

Solution — direct service function call:

Extract the complaint creation logic from the route handler into a service function that accepts a DB client:

# backend/app/services/complaint_service.py
async def create_complaint_from_voice(complaint_data: dict, db: Client) -> dict:
    # Same logic as POST /complaints but as a direct function
    flat_no = complaint_data["flat_number"].strip().upper()
    flat = db.table("flats").select("uuid, id").eq("flat_number", flat_no).execute()
    # ... rest of complaint creation ...
    result = db.table("complaints").insert(payload).execute()
    return result.data[0]

# In voice.py webhook, replace the httpx call with:
complaint = await create_complaint_from_voice(complaint_data, db)
complaint_id = complaint["id"]

This eliminates the HTTP call entirely. The service function uses the same db client that was injected into the webhook handler. No inter-worker communication, no network overhead, no timeout risk.
