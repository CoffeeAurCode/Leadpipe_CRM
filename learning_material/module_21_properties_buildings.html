Section 1 — Data Hierarchy and Navigation Model

The Properties page manages a three-level hierarchy: Property Group → Building → Flat. The UI mirrors this hierarchy with a drill-down navigation pattern: click a group to see its buildings, click a building to see its units. Three top-level "views" (Properties / Buildings / Units) give managers flat lists for their respective levels.

PropertiesPage navigation states: TOP-LEVEL VIEWS (view switcher tabs): ┌─────────────┬─────────────┬─────────────┐ │ Properties │ Buildings │ Units │ │ (groups) │ (all flat) │ (all flat) │ └─────────────┴─────────────┴─────────────┘ DRILL-DOWN (click a group in Properties view): Properties → [click Sunrise Estate] → Buildings of Sunrise Estate → [click Tower A] → Units of Tower A → [click unit] → FlatDetailModal DRILL-DOWN (click a building in Buildings view): Buildings → [click Tower A] → Units of Tower A → [click unit] → FlatDetailModal State variables that drive all of this: viewMode: 'properties' | 'buildings' | 'units' selectedProperty: PropertyGroup | null (drill-down level 1) selectedBuilding: Building | null (drill-down level 2) selectedFlatUuid: string | null (opens FlatDetailModal)

Two loading states: loadingMain is true during the initial page load (while property groups are fetched). loadingDrill is true when fetching data for a drill-down (clicking a group → fetching its buildings). This separation matters: while drill-down data loads, you still want to show the top-level list in the background — not replace the entire page with a spinner.

Two delete states: Similarly, deletingProperty and deletingBuilding are separate to allow one delete to be in progress while the other button is still available (and to show the right loading state on the right button).

Five data arrays: The page maintains different arrays for each context:
  • propertyGroups: loaded once, persists across view changes
  • buildings: all buildings flat list for the Buildings view tab
  • allUnits: loaded lazily only when Units tab is selected
  • buildingUnits: units for the currently drilled-in building — reset when navigating back
  • propertyBuildings: buildings for the currently drilled-in property — reset when navigating back

Part B — Data loading with useCallback

const loadPropertyGroups = useCallback(async () => {
    try {
        setLoadingMain(true);
        const data = await fetchPropertyGroups();
        setPropertyGroups(data);
        setError(null);
    } catch (err) {
        setError(t('properties.failedLoad'));
    } finally {
        setLoadingMain(false);
    }
}, []);
Why useCallback for data loaders?: These functions are passed to useEffect dependency arrays and to child components (e.g., handleBuildingAdded calls drillIntoProperty(selectedProperty) which calls the API). Without useCallback, a new function reference is created on every render, which would cause useEffect cleanup/re-run cycles. With useCallback(fn, []) (empty deps), the function is created once and reused.

Event-driven refresh: The page also listens for the 'refresh-properties' custom event (dispatched by the onboarding tour after creating data) to reload the list: 
useEffect(() => {
    const handler = () => { loadPropertyGroups(); loadBuildings(); };
    window.addEventListener('refresh-properties', handler);
    return () => window.removeEventListener('refresh-properties', handler);
}, [loadPropertyGroups, loadBuildings]);
This is the same cross-component event pattern used throughout the app (see Module 08's refresh-appointments pattern).

Part C — Drill-down navigation

const drillIntoProperty = useCallback(async (property) => {
    setSelectedProperty(property);
    setPropertyBuildings([]); // clear stale data immediately
    setLoadingDrill(true);
    try {
        const buildings = await fetchPropertyBuildings(property.id);
        setPropertyBuildings(buildings);
    } catch (err) {
        console.error('Error loading property buildings:', err);
    } finally {
        setLoadingDrill(false);
    }
}, []);
Clear stale data before fetching: setPropertyBuildings([]) immediately clears the previous building list. Without this, clicking "Sunrise Estate" would briefly show the buildings from the previously selected property while the new data loads. Clearing immediately ensures the user sees a loading spinner rather than stale data.

selectedProperty set before the async fetch: The property is set in state synchronously (before the await). This ensures the breadcrumb "Properties / Sunrise Estate" renders immediately while buildings are loading — no layout shift between clicking and the breadcrumb appearing.

Part D — The buildingLookup memo

const buildingLookup = useMemo(() => {
    const map = {};
    for (const b of buildings) map[b.id] = b;
    return map;
}, [buildings]);
The Units view shows "context chips" on each unit card — the building name and property type. Units from the API contain building_id but not the building object. The lookup map converts O(n) lookups (scanning the array for matching ID) to O(1) lookups (hash map access) for each unit card. For 200 units across 20 buildings, this is a significant speedup during render.

Part E — Optimistic UI updates in handlers

const handlePropertyGroupAdded = (newProperty) => {
    setPropertyGroups(prev => [newProperty, ...prev].sort((a, b) => a.name.localeCompare(b.name)));
};

const handleBuildingAdded = (newBuilding) => {
    setBuildings(prev => [newBuilding, ...prev].sort((a, b) => a.name.localeCompare(b.name)));
    if (selectedProperty) drillIntoProperty(selectedProperty);
};
Optimistic update: When a new property group is created, the modal calls onSuccess(newProperty) with the newly created object (returned from the backend). Instead of refetching the entire list, we insert the new item into the existing state array and sort it — this is immediate, no API round-trip needed.

Sort after insert: [newProperty, ...prev].sort(localeCompare) — prepend then sort. The resulting list is in alphabetical order. localeCompare handles locale-specific character ordering correctly (accented characters, etc.).

Refresh the drill-down after adding a building: If the user is currently viewing a property's buildings and adds a new building to that property, drillIntoProperty(selectedProperty) re-fetches the buildings list to include the new one. We can't just push to propertyBuildings because the new building might not have all the fields (like property_type_name) that the backend computes.

Part F — Delete handlers

const handleDeleteProperty = async () => {
    if (!window.confirm(
        `Delete "${selectedProperty.name}" and ALL its buildings, flats, and tenants?\n\nThis cannot be undone.`
    )) return;
    setDeletingProperty(true);
    try {
        await deletePropertyGroup(selectedProperty.id);
        setPropertyGroups(prev => prev.filter(p => p.id !== selectedProperty.id));
        setSelectedProperty(null);
        setPropertyBuildings([]);
    } catch (err) {
        alert(err.message || t('properties.failedDeleteProperty'));
    } finally {
        setDeletingProperty(false);
    }
};
Confirmation dialog for destructive actions: window.confirm() blocks execution until the user clicks OK or Cancel. This is the simplest possible confirmation UI — no custom modal needed. The message explicitly lists what will be deleted ("buildings, flats, and tenants") so the user understands the cascade scope.

Filter-based deletion from local state: After the API call succeeds, filter(p => p.id !== selectedProperty.id) removes the deleted group from local state without refetching the entire list. Navigation state is also cleaned: setSelectedProperty(null) and setPropertyBuildings([]) navigate back to the top-level list.

Section 3 — AddPropertyModal.jsx (Adding a Unit/Flat)

This modal creates a new flat unit. Despite being called "AddPropertyModal" (legacy naming), it creates a flat record, not a property group. The name reflects that in the original design, "property" referred to individual units. It was renamed to a hierarchy model later but the component name wasn't updated.

Part A — Address auto-fill from parent context

useEffect(() => {
    if (isOpen && initialAddress) {
        setFormData(prev => ({ ...prev, address: initialAddress }));
        setAddressAutoFilled(true);
    }
}, [isOpen, initialAddress]);
When the modal is opened from a building's context (user clicked "Add Unit" while inside a specific building), the parent passes initialAddress — the building's address concatenated with the property name. This pre-fills the address field so the user doesn't have to type it again. The addressAutoFilled flag shows an "auto-filled" hint below the field and is cleared if the user modifies the address.

Part B — Image handling

const handleImageChange = (e) => {
    const file = e.target.files[0];
    if (file) {
        if (!file.type.startsWith('image/')) {
            setError('Please select an image file'); return;
        }
        if (file.size > 10 * 1024 * 1024) {
            setError('Image must be less than 10MB'); return;
        }
        setFormData({ ...formData, image: file });
        setImagePreview(URL.createObjectURL(file));
        setError(null);
    }
};
Client-side validation before upload: The file type and size are checked immediately after selection — before any network call. This gives instant feedback without wasting bandwidth uploading files that will be rejected anyway.

URL.createObjectURL(file): Creates an in-memory URL representing the file's binary data. Setting this as the src of an <img> shows a preview immediately — no upload needed. The URL stays valid until the page navigates away or until you call URL.revokeObjectURL(). For images selected in a modal, the URL lives until the modal unmounts.

Note: This modal handles image selection and upload differently from AddBuildingModal. Here, the image file is stored in form state and sent as part of a multipart POST to /flats (the backend handles the Supabase Storage upload). In AddBuildingModal, the ImageUploadField component uploads the image immediately and stores the resulting URL in form state.

Part C — Form submission with FormData

    const handleSubmit = async (e) => {
        e.preventDefault();
        setLoading(true); setError(null);

        try {
            const formDataToSend = new FormData();
            formDataToSend.append('flat_number', formData.flat_number.trim().toUpperCase());

            if (formData.address) formDataToSend.append('address', formData.address.trim());
            if (formData.floor_number) formDataToSend.append('floor_number', formData.floor_number);
            if (formData.bedrooms) formDataToSend.append('bedrooms', formData.bedrooms);
            if (formData.bathrooms) formDataToSend.append('bathrooms', formData.bathrooms);

            if (assignTenant) {
                formDataToSend.append('tenant_name', formData.tenant_name.trim());
                formDataToSend.append('tenant_phone', formData.tenant_phone.trim());
            }

            if (initialBuildingId) formDataToSend.append('building_id', initialBuildingId);
            if (formData.image) formDataToSend.append('image', formData.image);

            await createProperty(formDataToSend);
            resetForm(); onSuccess(); onClose();
        } catch (err) {
            setError(err.message || 'Failed to create property');
        } finally {
            setLoading(false);
        }
    };
FormData construction: All optional fields are conditionally appended. If formData.address is empty, nothing is appended — the backend receives no address field and treats it as null. This is cleaner than sending address="", which might be stored as an empty string rather than null in the DB.

.trim().toUpperCase() on flat_number: Flat numbers are always stored uppercase and trimmed. This normalization happens client-side (for immediate UX consistency) and also server-side (the backend route does the same). Defense in depth — if one layer is bypassed, the other catches it.

Conditional tenant fields: The "Assign Tenant" checkbox controls whether tenant name and phone are included. If assignTenant is false, these fields are not appended to FormData even if the user typed in them (the fields are hidden anyway, but this is an extra guard). The backend creates the flat without a tenant if these fields are absent.

Part D — The AnimatePresence tenant section

<AnimatePresence>
    {assignTenant && (
        <motion.div
            initial={{ opacity: 0, height: 0 }}
            animate={{ opacity: 1, height: 'auto' }}
            exit={{ opacity: 0, height: 0 }}
            className="grid grid-cols-2 gap-4 pl-6 overflow-hidden"
        >
            {/* tenant name + phone inputs */}
        </motion.div>
    )}
</AnimatePresence>
AnimatePresence: Framer Motion wrapper that detects when children are removed from the React tree and plays their exit animation before actually removing them from the DOM. Without AnimatePresence, the exit prop has no effect — the element vanishes instantly.

Height animation: 0 → 'auto': Animating from height: 0 to height: 'auto' creates a smooth expand/collapse effect. The 'auto' value is special — Framer Motion measures the element's natural height and interpolates to it. This wouldn't work with pure CSS transitions (which can't animate to height: auto).

overflow-hidden: Required during the height animation. Without it, content would be visible outside the collapsing element during the exit animation (the content clips to the element's height only with overflow hidden).

Section 4 — AddBuildingModal.jsx

Fetching property types on open

useEffect(() => {
    if (isOpen && propertyTypes.length === 0) {
        fetchPropertyTypes()
            .then(setPropertyTypes)
            .catch(() => { });
    }
}, [isOpen]);
Lazy loading on modal open: Property types (Residential, Commercial, etc.) are only needed when the modal is open. Fetching them at page load would waste a network request. The propertyTypes.length === 0 guard prevents re-fetching if the modal is closed and reopened — the types are cached in component state until the component unmounts.

.catch(() => {}): Silently swallows the error. If property types fail to load, the select dropdown shows only "Select type" — the building can still be created without a type. This is a good tradeoff: the property type is optional; failing to load the types list shouldn't block building creation.

Submit handler — JSON body (not FormData)

    const handleSubmit = async e => {
        e.preventDefault();
        if (!form.name.trim()) { setError(t('building.nameRequired')); return; }
        setLoading(true); setError(null);
        try {
            const payload = { name: form.name.trim() };
            if (form.description) payload.description = form.description.trim();
            if (form.address) payload.address = form.address.trim();
            if (form.image_url) payload.image_url = form.image_url.trim();
            if (form.property_type_id) payload.property_type_id = form.property_type_id;
            if (initialPropertyId) payload.property_id = initialPropertyId;

            const newBuilding = await createBuilding(payload);
            reset(); onSuccess(newBuilding); onClose();
        } catch (err) {
            setError(err.message || t('building.failed'));
        } finally {
            setLoading(false);
        }
    };
JSON body vs FormData: Unlike AddPropertyModal (which uses FormData for image upload), this modal uses JSON. Why? The image URL is handled by ImageUploadField, which uploads the image to Supabase Storage separately and returns a URL string. The modal only needs to send that URL string in JSON — no binary file upload needed at submit time.

onSuccess(newBuilding): The parent's handleBuildingAdded receives the newly created building object (returned from createBuilding). This is the optimistic update pattern — insert into local state immediately, no re-fetch needed.

Section 5 — ImageUploadField.jsx

A reusable component that handles: drag-and-drop, click-to-upload, client-side validation, immediate local preview, upload to backend, and error handling. It's used in AddBuildingModal and can be used anywhere an image needs to be uploaded.

Part A — Client-side validation

const ALLOWED_TYPES = ['image/jpeg', 'image/jpg', 'image/png', 'image/webp'];
const MAX_SIZE_MB = 5;
const MAX_SIZE_BYTES = MAX_SIZE_MB * 1024 * 1024;

const validate = (file) => {
    if (!ALLOWED_TYPES.includes(file.type)) {
        return t('imageUpload.invalidType');
    }
    if (file.size > MAX_SIZE_BYTES) {
        return t('imageUpload.tooLarge', { size: (file.size / 1024 / 1024).toFixed(1), max: MAX_SIZE_MB });
    }
    return null; // null = no error
};
Return null for success: The convention is null means valid, any string is an error message. This avoids a boolean + separate error message — one return value conveys both.

Size calculation: MAX_SIZE_BYTES = 5 * 1024 * 1024 = 5 MB. The error message shows the actual file size in MB: (file.size / 1024 / 1024).toFixed(1). This tells the user "Your file is 7.3 MB, maximum is 5 MB" rather than a generic "File too large."

Part B — The processFile function

const processFile = useCallback(async (file) => {
    if (!file) return;

    const validationError = validate(file);
    if (validationError) { setError(validationError); return; }

    const localUrl = URL.createObjectURL(file);
    setPreview(localUrl);
    setError('');
    setUploading(true);
    onUploadStart?.(); // notify parent: disable submit button

    try {
        const { url } = await uploadImage(file, entityType);
        onUploadComplete(url);
        setPreview(url); // replace blob URL with permanent Supabase URL
    } catch (err) {
        setError(err.message || t('imageUpload.failed'));
        setPreview(currentImageUrl || null); // revert preview
        onUploadComplete(''); // clear in parent so old URL isn't accidentally submitted
    } finally {
        setUploading(false);
    }
}, [entityType, currentImageUrl, onUploadComplete]);
Immediate preview before upload: The blob URL is set as the preview source before the upload starts. The user sees the image immediately — no waiting for the server. This is the "optimistic preview" pattern.

onUploadStart?.(): Optional chaining call — if the parent passed an onUploadStart prop, call it; otherwise do nothing. This notifies the parent (e.g., AddBuildingModal) that an upload is in progress so it can disable the submit button. Without this, the user could submit the form before the upload completes, sending an empty URL.

Two-phase preview: First we show the blob URL (local file), then after upload we replace it with the permanent Supabase URL. The user doesn't see any change — both URLs resolve to the same image. But the form state now holds the permanent URL, which is what gets stored in the database.

Upload failure cleanup: On error: show the error message, revert the preview to whatever was there before (or null if this is a new upload), and call onUploadComplete('') to tell the parent the upload failed (clear any previously set URL). This prevents the form from submitting with a stale URL from a previous successful upload.

Part C — Drag-and-drop handling

<div
    onClick={() => !disabled && !uploading && inputRef.current?.click()}
    onDragOver={(e) => { e.preventDefault(); if (!disabled) setIsDragging(true); }}
    onDragLeave={() => setIsDragging(false)}
    onDrop={handleDrop}
    className={cn(
        'relative rounded-xl border-2 border-dashed transition-all duration-200 overflow-hidden',
        isDragging ? 'border-primary bg-primary/5 scale-[1.01]'
                   : 'border-border hover:border-primary/50 hover:bg-secondary/50',
        (disabled || uploading) && 'pointer-events-none opacity-70',
    )}
>
e.preventDefault() in onDragOver: Required to allow dropping. Browsers prevent drops by default — calling preventDefault() during dragover signals that this element accepts drops.

isDragging visual feedback: When something is dragged over the drop zone, the border turns primary color and the background gets a subtle tint (bg-primary/5 = 5% opacity primary color). A subtle scale increase (scale-[1.01]) adds a "ready to receive" cue. This feedback tells users the drop zone is active.

pointer-events-none opacity-70: When disabled or uploading, the drop zone is visually dimmed and interaction is prevented. pointer-events-none removes all mouse event handling — clicks, drags, and hover effects won't fire.

Section 6 — Sub-components Pattern in PropertiesPage

PropertyGroupCard — the cover image card 
function PropertyGroupCard({ property, onClick }) {
    const coverImage = property.image_url ||
        'https://images.unsplash.com/photo-...';  // fallback Unsplash image
    return (
        <motion.div
            whileHover={{ y: -2 }}
            onClick={() => onClick(property)}
            className="bg-card border border-border rounded-xl overflow-hidden cursor-pointer group"
        >
            <div className="relative h-40 overflow-hidden">
                <img
                    src={coverImage}
                    onError={e => { e.target.src = fallbackUrl; }}
                    className="w-full h-full object-cover group-hover:scale-105 transition-transform duration-300"
                />
                <div className="absolute inset-0 bg-gradient-to-t from-black/60 via-transparent to-transparent" />
            </div>
        </motion.div>
    );
}

Image zoom on hover: group-hover:scale-105 on the <img> makes the cover image zoom in slightly when the parent card is hovered. The overflow-hidden on the wrapper clips the zoomed image to the card boundary — without this, the image would overflow the card edges.

Gradient overlay: bg-gradient-to-t from-black/60 via-transparent to-transparent — a gradient that goes from 60% opacity black at the bottom to transparent at the top. This makes text (the building count badge) readable on any background image without blowing out the image colors.

whileHover={{ y: -2 }}: Subtle lift effect on hover. The card moves 2px upward, giving a "hover to interact" affordance. Combined with the box-shadow classes, this creates a clear interactive feedback.

CardGrid — staggered animation wrapper 
const CardGrid = ({ children, columns = 'grid-cols-1 sm:grid-cols-2 lg:grid-cols-3' }) => (
    <motion.div
        initial="hidden"
        animate="visible"
        variants={{ hidden: { opacity: 0 }, visible: { opacity: 1, transition: { staggerChildren: 0.06 } } }}
        className={cn('grid gap-5', columns)}
    >
        {children}
    </motion.div>
);

const cardVariants = { hidden: { opacity: 0, y: 16 }, visible: { opacity: 1, y: 0 } };

Variants and staggerChildren: Framer Motion's variant system propagates animation commands down the component tree. When the CardGrid animates from "hidden" to "visible", child components that also have "hidden" and "visible" variants animate automatically. staggerChildren: 0.06 delays each child's animation start by 0.06 seconds, creating a cascade effect.

Each child card is wrapped in a <motion.div variants={cardVariants}>, which inherits the parent's animation command. No initial/animate props needed on children — the parent drives everything.

Section 7 — Common Bugs & Fixes

Bug: After adding a building, the building list shows the old data

Symptom: User adds a building from the Properties view (inside a property group). The modal closes successfully, but the building doesn't appear in the property's building list until the page is manually refreshed.

Root cause: handleBuildingAdded updates buildings (the flat list for the Buildings tab) but doesn't refresh propertyBuildings (the list shown in the current drill-down view). The user is looking at propertyBuildings, which wasn't updated.

Fix: In handleBuildingAdded, also refresh the drill-down view if a property is selected:

const handleBuildingAdded = (newBuilding) => {
    setBuildings(prev => [newBuilding, ...prev].sort((a, b) => a.name.localeCompare(b.name)));
    if (selectedProperty) drillIntoProperty(selectedProperty); // re-fetch for drill-down
};

Bug: Image preview shows previous selection after clearing

Symptom: User selects an image, sees the preview, clicks the X button to clear it, then the preview disappears. But when selecting a new image (same file as before), the preview doesn't update.

Root cause: The browser caches file inputs. If the same file is selected twice in a row, the onChange event doesn't fire the second time because the input value hasn't changed from the browser's perspective.

Fix: Reset the input value after processing the file:

const handleFileChange = (e) => {
    const file = e.target.files?.[0];
    if (file) processFile(file);
    e.target.value = '';  // Reset so same file can be re-selected
};

Bug: "AddPropertyModal" creates a building instead of a unit

Symptom: (Legacy naming confusion) A developer reading the code sees AddPropertyModal and thinks it creates a Property Group. They try to use it for that purpose and get wrong behavior.

Root cause: Legacy naming from when "property" meant an individual unit. The component was later renamed conceptually but not in code.

How to remember the mapping:

  • AddPropertyGroupModal → creates a Property Group (top level)
  • AddBuildingModal → creates a Building (middle level)
  • AddPropertyModal → creates a Flat/Unit (bottom level, confusingly named)
In a future refactor, AddPropertyModal should be renamed AddUnitModal or AddFlatModal.

Bug: Clicking "Back" from a building shows stale property buildings

Symptom: User is in Building A's units, clicks back → sees Property X's buildings (correct). Clicks on Building B → sees Building B's units. Clicks back → sees Building A's units (wrong — should see Property X's buildings).

Root cause: backFromBuilding only clears selectedBuilding and buildingUnits. It doesn't re-fetch propertyBuildings, which might have been modified while the user was viewing Building B's units (e.g., if another tab added/deleted a building).

Fix for most cases: The current implementation is correct because propertyBuildings is fetched when the property is first drilled into, and the stale data issue only occurs if the DB changed while the user was navigating. For a production app, add a refresh on the back navigation:

const backFromBuilding = () => {
    setSelectedBuilding(null);
    setBuildingUnits([]);
    // Optional: refresh property buildings list
    if (selectedProperty) drillIntoProperty(selectedProperty);
};

Module 21 — Key Takeaways

  • Three-level hierarchy drill-down: implemented via selectedProperty and selectedBuilding state; the render function returns different JSX based on which selection is active.
  • Clear stale data immediately before async fetch: setPropertyBuildings([]) before await fetchPropertyBuildings(...) prevents showing old data while new data loads.
  • Optimistic updates: insert new items into local state immediately after creation — no full re-fetch needed. Sort after insert ([new, ...prev].sort(...)).
  • useCallback for data loaders: prevents new function references on every render, which would invalidate useEffect dependency arrays and cause infinite loops.
  • FormData for file+field submission: only omit Content-Type header so the browser sets the multipart boundary automatically.
  • Immediate blob URL preview: show the image before upload using URL.createObjectURL(file), then replace with the permanent URL after upload completes.
  • onUploadStart callback: prevents form submission while image is uploading — the parent disables the submit button in response.
  • AnimatePresence + height animation: enables smooth expand/collapse of conditional form sections. Requires overflow-hidden on the animated element.
  • Drag-and-drop: requires e.preventDefault() in onDragOver to allow dropping — browsers block drops by default.
  • Reset file input value after processing to allow re-selecting the same file: e.target.value = ''

Section 9 — Why This Design

Decision: Cascading fetches (group → buildings → units) vs. one nested payload

ApproachProsCons
Fetch each level on selection (chosen)Initial load is light; a manager with 40 buildings only pays for the one they open; each fetch maps to one obvious endpointClick-depth latency (three clicks = three round-trips); more loading states to manage
One nested mega-responseSingle request; instant drill-down after loadPayload grows with portfolio size; any change anywhere invalidates the whole tree; PostgREST triple-nesting gets fragile

Decision: Direct-to-Storage upload from the browser

ApproachProsCons
Browser → Supabase Storage, save URL via API (chosen)Image bytes never transit the FastAPI server — no upload size/timeout config, no server bandwidth cost; Storage RLS policies still gate writesTwo-step commit (upload, then save URL) can orphan files if step 2 fails; bucket policies become part of your security surface
Upload through the backendOne transaction-ish flow; server-side validation of file contentsServer becomes a file proxy; large uploads tie up workers
Senior takeaway: modal state (which modal is open, editing what) lives in the PAGE component, not in the modals. Modals receive props and callbacks — they're dumb. This keeps “what is the user doing right now” answerable from one component's state, which is exactly what you need when debugging a stuck dialog.

Section 10 — Checkpoint ✓

Run the full hierarchy through the UI:

  1. Create a property group → a building inside it → a unit inside that. Expected: each appears immediately in its panel without a manual refresh.
  2. Upload a building image. Expected: the image renders, AND the file exists in the Supabase Storage bucket (check the dashboard), AND the building row holds its public URL.
  3. Watch the Network tab while drilling down. Expected: one fetch per level as you click — not one giant fetch up front (that's the cascading design working).
  4. Delete the test group. Expected: children vanish with it (Module 05's cascade, seen from the UI side).
