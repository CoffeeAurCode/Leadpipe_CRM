Section 1 — What You Are Building

Complaints and appointments form a linked two-table system. A complaint represents a tenant's reported issue (water leak, noise, etc). An appointment is the scheduled visit to resolve it. One complaint can have one appointment. The complaint is the parent; the appointment is the child.

Relationship ──────────── complaints table appointments table ───────────────────── ────────────────────────────── uuid PK uuid PK id int PK (legacy) complaint_uuid FK → complaints.uuid flat_uuid FK → flats.uuid flat_number (denormalized copy — for VAPI speed) tenant_uuid FK → tenants.uuid appointment_date datetime category (water|electricity...) status (scheduled|cancelled|attended|completed) status (pending|in-progress|resolved) priority (low|medium|high) VAPI tool endpoints on /appointments: GET /appointments/view → list appointments for a flat (by flat_number) PATCH /appointments/update → reschedule (query params, not body) PATCH /appointments/cancel → cancel (idempotent) GET /appointments/availability → check if a time slot is free These MUST be registered ABOVE the dynamic /{appointment_id} route.

The module also covers core/constants.py — the single source of truth for allowed complaint categories and statuses, used both for API validation and for AI extraction (covered in Module 09).

Section 2 — Concept Deep-Dives

Named FK JOIN in Supabase — !fk_appointments_complaint_uuid

When two tables have more than one FK relationship between them, PostgREST doesn't know which one you mean when you write select("*, appointments(*)"). You must name the specific FK constraint.

python# The appointments table has multiple relationships to complaints:
# - appointments.complaint_uuid → complaints.uuid  (FK name: fk_appointments_complaint_uuid)
# - appointments.complaint_id  → complaints.id     (FK name: fk_appointments_complaint_id)

# WRONG — ambiguous, PostgREST raises an error
db.table("complaints").select("*, appointments(*)").execute()

# CORRECT — use the specific FK constraint name
db.table("complaints").select("*, appointments!fk_appointments_complaint_uuid(*)").execute()

The FK constraint name is defined in your Supabase schema SQL. You can find all FK names in the Supabase dashboard under Database → Tables → click the table → Constraints, or by running SELECT conname FROM pg_constraint WHERE contype = 'f' in the SQL editor.

Error message: When you have ambiguous FK relationships and don't specify the name, Supabase returns "Could not embed because more than one relationship was found". If you see this error, add the !fk_name qualifier.

Flattening Nested JOIN Results

Supabase's PostgREST JOIN returns a nested structure. Complaints returns appointments as an array inside each complaint. The route handler flattens this into a single-level dict for a cleaner API response:

python# Raw DB response structure (after join):
# {
#   "id": 1, "category": "water", ...,
#   "appointments": [{"appointment_date": "2025-06-01T10:00:00", "status": "scheduled"}]
# }

# Flattened output structure (what the API returns):
# {
#   "id": 1, "category": "water", ...,
#   "appointment_date": "2025-06-01T10:00:00",
#   "appointment_status": "scheduled"
# }

complaints = []
for complaint in response.data:
    complaint_data = {**complaint}  # shallow copy

    appointments = complaint.get('appointments', [])
    if appointments and len(appointments) > 0:
        appt = appointments[0]  # take first appointment only
        complaint_data['appointment_date'] = appt.get('appointment_date')
        complaint_data['appointment_status'] = appt.get('status')
    else:
        complaint_data['appointment_date'] = None
        complaint_data['appointment_status'] = None

    complaint_data.pop('appointments', None)  # remove nested array
    complaints.append(complaint_data)

Why flatten? The frontend expects a flat dict, not a nested array. It makes template rendering simpler: complaint.appointment_date instead of complaint.appointments[0]?.appointment_date.

Denormalized flat_number on Appointments — Why?

The appointment's link to a flat goes through the complaint: appointment → complaint → flat_uuid → flat_number. That's 3 joins to get the flat number. VAPI needs the flat number to look up appointments (it comes from the voice conversation — the tenant says their flat number). Doing 3 joins per VAPI call adds latency.

Solution: store flat_number as a denormalized column directly on the appointments table. It's set at insert time from the complaint's associated flat. VAPI then queries appointments directly by flat_number with zero joins:

python# At complaint creation: extract flat_number from the complaint's flat and store it
appt_response = db.table("appointments").insert({
    "complaint_uuid": created_complaint["uuid"],
    "flat_number": created_complaint.get("flat_number"),  # denormalized copy
    "appointment_date": appointment_date,
    "status": "scheduled"
}).execute()

# At VAPI query: one simple indexed lookup
db.table("appointments").select("*").ilike("flat_number", flat_number).execute()

The downside: if a flat is ever renumbered, the denormalized flat_number on historical appointments becomes stale. This is an acceptable trade-off for an MVP — renumbering flats almost never happens in practice.

Soft Delete vs Hard Delete

The DELETE /appointments/{id} endpoint doesn't actually delete the row. It sets status = "cancelled". This is called a soft delete.

ApproachProsCons
Hard delete (remove row)Clean, no orphaned dataCan't audit history, can't un-cancel
Soft delete (status = cancelled)Full history, reversibleMust filter cancelled records in every query

For appointments, soft delete is the right choice: the manager might want to see past cancelled appointments, or accidentally cancelled something and needs to reactivate it. The status machine for appointments is:

scheduled → cancelled (DELETE or PATCH /cancel) scheduled → attended (PATCH /{id} with status=attended) scheduled → completed (set by VAPI end-of-call webhook) cancelled → scheduled (PATCH /{id} with status=scheduled — "reactivate")
VAPI Availability Check — 1-Hour Slot Model

The GET /appointments/availability endpoint checks if the manager is free at a requested time. Every appointment is assumed to take exactly 1 hour. Two appointments conflict if their 1-hour windows overlap.

python# Requested slot: 10:30
# Any existing appointment A conflicts if: A - 1hr < 10:30 < A + 1hr
# Example: A=10:00 → window (9:00, 11:00) → 10:30 is inside → UNAVAILABLE
# Example: A=11:00 → window (10:00, 12:00) → 10:30 is inside → UNAVAILABLE
# Example: A=09:00 → window (8:00, 10:00)  → 10:30 is outside → AVAILABLE
# Back-to-back: A=09:30 → window ends at 10:30, requested starts at 10:30
#   gt(window_start) and lt(window_end) → strictly outside → AVAILABLE

requested_dt = datetime.strptime(normalized_date, "%Y-%m-%d %H:%M:%S")
window_start = (requested_dt - timedelta(hours=1)).strftime("%Y-%m-%d %H:%M:%S")
window_end   = (requested_dt + timedelta(hours=1)).strftime("%Y-%m-%d %H:%M:%S")

result = (
    db.table("appointments")
    .select("id")
    .eq("status", "scheduled")   # only scheduled appointments block time
    .gt("appointment_date", window_start)  # strictly greater than
    .lt("appointment_date", window_end)    # strictly less than
    .execute()
)

The strict inequalities (gt, lt rather than gte, lte) allow back-to-back bookings: a 10:00 appointment ending at 11:00 does not block an 11:00 appointment. The window is open-ended on both sides.

Fail-safe: If the DB query throws an exception, availability returns "unavailable". This is intentional — never let an error silently allow a double-booking. Fail closed, not open.

core/constants.py — Single Source of Truth for Allowed Values

Categories and statuses are defined once and imported everywhere. This prevents the category "Electricity" in the DB constraint, "electricity" in the validator, and "ELECTRICITY" in the AI extractor from silently diverging:

python# core/constants.py — the canonical list
ALLOWED_CATEGORIES = [
    "water", "electricity", "cleaning", "noise",
    "maintenance", "security", "other"
]

class ComplaintStatus(str, Enum):
    PENDING = "pending"
    IN_PROGRESS = "in-progress"
    RESOLVED = "resolved"

ALLOWED_STATUSES = [status.value for status in ComplaintStatus]
# → ["pending", "in-progress", "resolved"]

Used in 3 places: the Pydantic schema validator (below), the AI extractor (Module 09), and the DB CHECK constraint. Change the constants file and all three update together.

ComplaintStatus(str, Enum) inherits from both str and Enum. The str inheritance means each enum value IS a string — ComplaintStatus.PENDING == "pending" is True. This allows the enum to be stored in the DB and compared to plain strings without conversion.

Idempotent Cancel — Why It Matters

VAPI might call the cancel endpoint twice for the same appointment if the first call timed out or the network was unreliable. Without idempotency, the second call returns 400 ("cannot cancel an already-cancelled appointment"), which the voice agent treats as an error and confuses the caller.

python# Idempotent cancel: silently succeed if already cancelled
if apt.get("status") == "cancelled":
    return VapiAppointmentCancelResponse(id=apt["id"], status="cancelled")
    # ↑ returns 200 immediately, no DB write, no SMS, no error

if apt.get("status") == "completed":
    raise HTTPException(400, detail="Cannot cancel a completed appointment")
    # ↑ completed IS an error — the work is done, you can't undo it

The pattern: idempotency for retryable states (cancelled twice = fine), hard error for terminal states (can't cancel completed).

complaint.py — @field_validator for status

pythonfrom pydantic import BaseModel, field_validator

class ComplaintBase(BaseModel):
    category: str
    priority: Optional[str] = "medium"

@field_validator('status') is the Pydantic V2 way to validate a single field (V1 used @validator('status')). The @classmethod decorator is required — validators are class methods that receive the raw value before it's assigned to the model. Raising ValueError triggers Pydantic's validation error machinery.

Section 4 — complaints.py Walkthrough

POST /complaints — create with optional linked appointment

python@router.post("", response_model=ComplaintResponse, status_code=201)
async def create_complaint(
    complaint_data: ComplaintCreate,
    background_tasks: BackgroundTasks,
    user=Depends(require_active_subscription), db=Depends(get_authenticated_db)
):
    complaint_dict = complaint_data.model_dump(mode='json')

    # appointment_date is NOT a complaint column — extract before insert
    appointment_date = complaint_dict.pop("appointment_date", None)

    # UUID-based reference (preferred path)
    if complaint_data.flat_uuid:
        flat_check = db.table("flats").select("uuid").eq("uuid", str(complaint_data.flat_uuid)).execute()
        if not flat_check.data:
            raise HTTPException(status_code=404, detail="Flat not found")

    # Legacy path: flat_number → look up flat_uuid
    elif complaint_data.flat_number:
        flat = db.table("flats").select("uuid").eq("flat_number", complaint_data.flat_number).execute()
        if flat.data:
            complaint_dict['flat_uuid'] = str(flat.data[0]['uuid'])

    # Auto-assign tenant_uuid from the flat if not explicitly set
    if complaint_dict.get('flat_uuid') and not complaint_dict.get('tenant_uuid'):
        tenant = db.table("tenants").select("uuid").eq("flat_uuid", complaint_dict['flat_uuid']).execute()
        if tenant.data:
            complaint_dict['tenant_uuid'] = str(tenant.data[0]['uuid'])

    complaint_dict.pop("tenant_id", None)  # strip deprecated field

    response = db.table("complaints").insert(complaint_dict).execute()
    created_complaint = response.data[0]

    # Create linked appointment if appointment_date was in the request
    if appointment_date:
        appt_response = db.table("appointments").insert({
            "complaint_uuid": created_complaint["uuid"],
            "flat_number": created_complaint.get("flat_number"),  # denormalized
            "appointment_date": appointment_date,
            "status": "scheduled"
        }).execute()

        # Notify manager — non-blocking, runs after response is sent
        if appt_response.data:
            background_tasks.add_task(
                notify_manager_appointment_scheduled,
                appt_response.data[0]
            )

    return created_complaint

The appointment_date field is defined in ComplaintBase schema for convenience — callers can send a complaint and its first appointment in a single request. But appointment_date is NOT a column in the complaints table. It must be .pop()-ed from the dict before the DB insert, then used to create a separate row in the appointments table.

Section 5 — appointments.py Walkthrough

GET /appointments/availability — 1-hour slot model

python@router.get("/availability", response_model=VapiAvailabilityResponse)
async def vapi_check_availability(
    appointment_date: str = Query(...),
    db: Client = Depends(get_db),  # anon/service-role — no JWT from VAPI
):
    try:
        # VAPI sends "T" separator; DB expects space separator
        normalized_date = appointment_date.strip().replace("T", " ")
        requested_dt = datetime.strptime(normalized_date, "%Y-%m-%d %H:%M:%S")

        window_start = (requested_dt - timedelta(hours=1)).strftime("%Y-%m-%d %H:%M:%S")
        window_end   = (requested_dt + timedelta(hours=1)).strftime("%Y-%m-%d %H:%M:%S")

        result = (
            db.table("appointments")
            .select("id")
            .eq("status", "scheduled")
            .gt("appointment_date", window_start)  # strictly after T-1hr
            .lt("appointment_date", window_end)    # strictly before T+1hr
            .execute()
        )
        if result.data:
            return VapiAvailabilityResponse(status="unavailable")
        return VapiAvailabilityResponse(status="available")

    except Exception as e:
        print(f"[ERROR] vapi_check_availability: {e}")
        return VapiAvailabilityResponse(status="unavailable")  # fail-safe

PATCH /appointments/update — reschedule via query params

python@router.patch("/update", response_model=VapiAppointmentUpdateResponse)
async def vapi_update_appointment(
    background_tasks: BackgroundTasks,
    flat_number: str = Query(...),
    id: int = Query(...),                       # integer PK — easier for VAPI to extract
    new_appointment_date: str = Query(...),
    db: Client = Depends(get_db),
):
    normalized_flat = flat_number.strip().upper()

    # Fetch appointment by BOTH id AND flat_number — prevents cross-tenant access
    apt_resp = (
        db.table("appointments")
        .select("*")
        .eq("id", id)
        .ilike("flat_number", normalized_flat)
        .execute()
    )
    if not apt_resp.data:
        raise HTTPException(404, detail="Appointment not found")

    apt = apt_resp.data[0]
    if apt.get("status") == "completed":
        raise HTTPException(400, detail="Cannot reschedule a completed appointment")

    # Normalize date: VAPI sends T-separator, DB expects space
    normalized_date = new_appointment_date.replace("T", " ")

    update_resp = (
        db.table("appointments")
        .update({"appointment_date": normalized_date})
        .eq("id", apt["id"])
        .execute()
    )

    # Notify tenant asynchronously
    if flat_uuid := apt_resp.data[0].get("flat_uuid"):
        background_tasks.add_task(notify_tenant_appointment, flat_uuid, "rescheduled", normalized_flat, db, normalized_date)

    updated = update_resp.data[0]
    return VapiAppointmentUpdateResponse(id=updated["id"], new_appointment_date=updated["appointment_date"])

The double-filter .eq("id", id).ilike("flat_number", normalized_flat) is a security measure: if VAPI sends an appointment ID that belongs to a different flat (perhaps a bug or a confused LLM), the query returns nothing. This prevents one tenant accidentally viewing or modifying another tenant's appointment.

PATCH /appointments/{id} — manager update with notifications

python@router.patch("/{appointment_id}", response_model=AppointmentResponse)
async def update_appointment(appointment_id: int, appointment_data: AppointmentUpdate, background_tasks: BackgroundTasks, ...):
    update_data = appointment_data.model_dump(exclude_unset=True, mode='json')

    response = db.table("appointments").update(update_data).eq("id", appointment_id).execute()
    updated = response.data[0]

    flat_uuid = updated.get("flat_uuid")
    flat_number_val = updated.get("flat_number", "")

    # If date was changed → notify tenant of reschedule
    if "appointment_date" in update_data and flat_uuid:
        background_tasks.add_task(
            notify_tenant_appointment, str(flat_uuid), "rescheduled",
            flat_number_val, db, updated["appointment_date"]
        )

    # If status was changed → send appropriate notification
    if "status" in update_data and flat_uuid:
        _status_event_map = {
            "cancelled": "cancelled",
            "attended":  "attended",
            "scheduled": "reactivated",  # re-scheduling cancelled apt
        }
        event = _status_event_map.get(update_data["status"])
        if event:
            background_tasks.add_task(notify_tenant_appointment, str(flat_uuid), event, flat_number_val, db)

    return updated

The _status_event_map dict maps DB status values to notification event names. The notification service uses event names to select the right SMS/email template. "scheduled" → "reactivated" handles the case where a manager un-cancels an appointment by setting it back to scheduled.

Section 6 — Real Bugs We Hit

Bug: appointment_date was stored in the complaints table, causing schema errors

Symptom: POST /complaints with an appointment_date returned a Supabase error: "column appointment_date of relation complaints does not exist".

Root cause: appointment_date is a field in the ComplaintCreate schema but NOT a column in the complaints DB table. The code was doing complaint_dict = complaint_data.model_dump() and inserting the whole dict including appointment_date.

Fix: .pop("appointment_date", None) before the DB insert to extract it first, then use it to create the separate appointments row:

pythoncomplaint_dict = complaint_data.model_dump(mode='json')
appointment_date = complaint_dict.pop("appointment_date", None)  # extract before insert
db.table("complaints").insert(complaint_dict).execute()  # appointment_date no longer in dict
Bug: Ambiguous FK — PostgREST couldn't determine which relationship to use

Symptom: GET /complaints returned a 500 with the error "Could not embed because more than one relationship was found for 'complaints' and 'appointments'".

Root cause: The appointments table has TWO foreign keys pointing at complaints: complaint_uuid and the legacy complaint_id. Using select("*, appointments(*)") was ambiguous — PostgREST couldn't pick one.

Fix: Use the explicit FK constraint name in the select:

python# BEFORE (ambiguous)
db.table("complaints").select("*, appointments(*)").execute()

# AFTER (unambiguous — names the specific FK)
db.table("complaints").select("*, appointments!fk_appointments_complaint_uuid(*)").execute()
Bug: VAPI reschedule matched /appointments/{appointment_id} instead of /appointments/update

Symptom: VAPI's reschedule tool call reached GET /appointments/{appointment_id} and returned a single appointment as JSON, which the LLM tried to parse as a reschedule response — it was completely confused.

Root cause: PATCH /appointments/update was registered below PATCH /appointments/{appointment_id}. FastAPI matched "update" as the appointment_id path parameter.

Fix: Move ALL VAPI tool endpoints (/view, /update, /cancel, /availability) to the top of the appointments.py file, before the dynamic /{appointment_id} routes. Added a comment block explaining the ordering requirement.

Bug: Double SMS notification on VAPI cancel

Symptom: Tenants received two "your appointment has been cancelled" SMS messages.

Root cause: VAPI retried the cancel tool call (it thought the first call failed due to a timeout). Without idempotency, the second call hit the cancel endpoint, found the appointment in "scheduled" state (the first update hadn't committed fast enough), and sent another SMS.

Fix: Add the idempotency check at the top of the cancel handler. If status == "cancelled" already, return 200 immediately without triggering another notification:

pythonif apt.get("status") == "cancelled":
    return VapiAppointmentCancelResponse(id=apt["id"], status="cancelled")
    # ↑ no background_tasks.add_task — no second SMS

pythonfrom pydantic import BaseModel, field_validator, ConfigDict

class ComplaintBase(BaseModel):
    category: str
    priority: Optional[str] = "medium"
    appointment_date: Optional[str] = None
    description: str
    status: str
    source: str = "AI_AGENT"

    @field_validator('category')
    @classmethod
    def validate_category(cls, v):
        from app.core.constants import ALLOWED_CATEGORIES
        normalized = v.strip().lower()
        if normalized not in ALLOWED_CATEGORIES:
            raise ValueError(
                f"Invalid category '{v}'. "
                f"Allowed: {', '.join(ALLOWED_CATEGORIES)}"
            )
        return normalized  # return the normalized value, not the original

    @field_validator('status')
    @classmethod
    def validate_status(cls, v):
        from app.core.constants import ALLOWED_STATUSES
        if v not in ALLOWED_STATUSES:
            raise ValueError(
                f"Invalid status '{v}'. "
                f"Allowed: {', '.join(ALLOWED_STATUSES)}"
            )
        return v

The validator returns normalized (the lowercase version) — Pydantic stores the returned value, not the original input. So if the caller sends "Water", the complaint is stored as "water" — consistently lowercase everywhere in the system.
