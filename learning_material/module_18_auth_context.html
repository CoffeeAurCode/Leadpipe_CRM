Section 1 — The Auth Flow End-to-End

The authentication system has three layers: the Supabase client singleton (created once), the React context that makes session state available to every component, and the auth page that handles sign-in UI. Understanding how these connect is the foundation for every protected route in the app.

GOOGLE OAUTH PKCE FLOW: Browser Supabase Auth Google │ │ │ │── signInWithOAuth() ────────▶ │ │ │── Redirect to Google ───────▶ │ │ │ │◀─────────────────────────── Google redirects back with code │ (?code=xyz in URL) │ │ │ │── supabase detects code ────▶ │ detectSessionInUrl:true │── Exchange code for tokens ──▶ │ │◀─── JWT (access_token + refresh_token) │ │ │── onAuthStateChange fires ──▶ │ event: 'SIGNED_IN' │ │ session: { access_token } │ │ │ │ (INITIAL_SESSION also fires when client first loads) │ AuthGate reads session → renders App (authenticated) or AuthPage (unauthenticated)

Section 2 — lib/supabase.js Line-by-Line

This 12-line file is the most important file in the entire frontend. Every other file that touches auth or DB goes through this singleton.

import { createClient } from '@supabase/supabase-js'

export const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY,
  {
    auth: {
      detectSessionInUrl: true,
      flowType: 'pkce',
    },
  }
)
Singleton pattern: This file creates exactly one Supabase client for the entire application. All imports of supabase from anywhere in the codebase get the same instance. This matters because the client manages the session token, WebSocket subscriptions, and auth state — if you created multiple clients, they would each maintain separate state and could get out of sync.

VITE_SUPABASE_URL: The public Supabase project URL, e.g., https://xyzabc.supabase.co. This is safe to expose in client code (it's not a secret).

VITE_SUPABASE_ANON_KEY: The "anon" (anonymous) key, also known as the public API key. It's a JWT with "role": "anon" embedded. Despite appearing in client-side code, it's safe to expose because Row Level Security (RLS) policies on the database enforce what the anon role can access.

detectSessionInUrl: true: After Google OAuth redirects the user back to the app, Supabase puts the session tokens in the URL fragment (#access_token=...) or as a query parameter (?code=...) in PKCE mode. This option tells the Supabase client to look for and consume these URL parameters on initialization.

flowType: 'pkce': PKCE (Proof Key for Code Exchange) is a more secure OAuth flow than the older implicit flow. The difference:
  • Implicit: Access token delivered directly in URL fragment. Anyone who can see the URL (browser history, server logs, referrer headers) can steal the token.
  • PKCE: Authorization code is delivered in URL (short-lived, useless alone). Client exchanges code for tokens using a secret verifier stored in the browser's session storage. The token is never in the URL.
In 2024, PKCE is the recommended flow for all browser-based OAuth. Supabase made it the default in their SDK v2.

Section 3 — context/AuthContext.jsx Line-by-Line

React Context lets you share state across the entire component tree without passing props through every intermediate component. The auth context makes session, user, and signOut available anywhere with useAuth().

Part A — The ensureManagerProfile helper

async function ensureManagerProfile(user) {
    try {
        const { data } = await supabase
            .from('manager_profiles')
            .select('id')
            .eq('user_id', user.id)
            .maybeSingle();

        if (!data) {
            await supabase.from('manager_profiles').insert({
                user_id: user.id,
                name: user.user_metadata?.full_name || user.email?.split('@')[0] || 'Manager',
                phone: user.user_metadata?.phone || null,
            });
        }
    } catch (err) {
        console.error('Failed to ensure manager profile:', err);
    }
}
Why this function exists: When a user signs up with email/password, the auth page creates their manager_profiles row explicitly. But when a user signs in with Google OAuth for the first time, they bypass the sign-up form entirely — there's no code path that creates their profile row. This function fills that gap.

.maybeSingle() — returns a single row or null (never throws if no rows found). This is the idiomatic way to check existence. Using .single() would throw an error if the row doesn't exist, requiring a try/catch to check existence.

Fallback chain for name: user.user_metadata?.full_name (from Google) → user.email?.split('@')[0] (local part of email, e.g., "john.doe") → 'Manager' (guaranteed fallback). The ?. optional chaining safely handles null/undefined without throwing.

Why the outer try/catch: Profile creation is non-critical. If it fails (RLS, network blip), the user can still log in and use the app — they'll just have a missing profile row. Swallowing the error here prevents a broken profile upsert from blocking the entire sign-in flow.

Part B — The AuthProvider component

export function AuthProvider({ children }) {
    const [session, setSession] = useState(null);
    const [user, setUser] = useState(null);
    const [loading, setLoading] = useState(true);
    const profileChecked = useRef(false);
loading: true initially — prevents the "flash of unauthenticated content" where the app briefly shows the login page before the session is loaded. While loading is true, the app renders a spinner instead of either the login page or the authenticated app.

profileChecked ref — this is a subtle but critical bug prevention mechanism. Without it, the profile creation would run on every SIGNED_IN event — including token refreshes (which fire TOKEN_REFRESHED, but in some edge cases also SIGNED_IN). A ref doesn't trigger re-renders when changed, making it the right tool for this "did we already do this?" guard. See the Bug section for what happens without it. 
    useEffect(() => {
        const { data: { subscription } } = supabase.auth.onAuthStateChange(
            (event, session) => {
                setSession(session);
                setUser(session?.user ?? null);

                if (session?.user && !profileChecked.current) {
                    profileChecked.current = true;
                    ensureManagerProfile(session.user);
                }
                if (!session) {
                    profileChecked.current = false;
                }

                if (event === 'INITIAL_SESSION') {
                    setLoading(false);
                }
            }
        );

        return () => subscription.unsubscribe();
    }, []);
onAuthStateChange — Supabase's event emitter for auth state. It fires for every auth lifecycle event. The events you'll encounter:
EventWhen it firesSession value
INITIAL_SESSIONOnce, when the Supabase client finishes initializing (including detecting a session from URL or localStorage)Session if logged in, null if not
SIGNED_INAfter successful login (email/password or OAuth redirect)New session
TOKEN_REFRESHEDWhen the access token is refreshed (automatically, before expiry)Updated session with new token
SIGNED_OUTAfter supabase.auth.signOut()null
Why only set loading false on INITIAL_SESSION: This event fires exactly once, after the client has checked all possible session sources (localStorage, URL hash). Before it fires, you cannot know whether the user is logged in or not. Setting loading: false on any earlier event (or before this callback) would cause the app to flicker — briefly rendering the login page even for a logged-in user.

Profile check logic: Only runs if (1) there's a user, AND (2) we haven't checked yet for this session (profileChecked.current === false). When the user signs out, profileChecked.current is reset to false so the check will run again on their next sign-in.

Cleanup: subscription.unsubscribe(): React's useEffect cleanup runs when the component unmounts. Without this, the subscription would persist after unmount, causing memory leaks and potentially firing state updates on unmounted components. 
    const signOut = async () => {
        await supabase.auth.signOut();
        // Redirect handled by onAuthStateChange → AuthGate
    };

    return (
        <AuthContext.Provider value={{ session, user, loading, signOut }}>
            {children}
        </AuthContext.Provider>
    );
}
signOut() only calls Supabase — it doesn't manually update state or redirect. Why? Because supabase.auth.signOut() triggers the SIGNED_OUT event, which fires onAuthStateChange, which sets session: null. The AuthGate component (in App.jsx) watches the session and renders the login page when session === null. Clean separation: the context manages state changes, the gate decides what to render.

Context value shape: The object { session, user, loading, signOut } is what any component gets when calling useAuth(). Providing both session and user as separate values is convenient: some places need the full session (to extract the JWT for API calls), others just need user.id or user.email.

Part C — The useAuth hook

export function useAuth() {
    const context = useContext(AuthContext);
    if (!context) {
        throw new Error('useAuth must be used within an AuthProvider');
    }
    return context;
}
The guard check if (!context) catches a common developer mistake: using useAuth() in a component that isn't wrapped by AuthProvider. Without this guard, the hook silently returns null and the destructure const { session } = useAuth() would throw a different, confusing error ("Cannot destructure property 'session' of null"). The explicit error message "must be used within an AuthProvider" tells the developer exactly what to fix.

Section 4 — components/AuthPage.jsx Line-by-Line

Part A — State and setup

export default function AuthPage() {
    const { t } = useTranslation();
    const [mode, setMode] = useState('login'); // 'login' | 'signup'
    const [email, setEmail] = useState('');
    const [password, setPassword] = useState('');
    const [name, setName] = useState('');
    const [phone, setPhone] = useState('');
    const [loading, setLoading] = useState(false);
    const [googleLoading, setGoogleLoading] = useState(false);
    const [error, setError] = useState(null);
    const [message, setMessage] = useState(null);
Separate loading and googleLoading: Two loading states for two different async operations. When the user clicks "Continue with Google", googleLoading shows a spinner on the Google button while loading remains false. If both shared one state, clicking Google would also disable the email form button, creating a confusing UX.

mode state instead of a separate component: Login and signup share 90% of their UI. Using a mode string and conditional rendering (show name/phone fields only in signup mode) is simpler than two separate page components.

Part B — Email authentication handler

    const handleEmailAuth = async (e) => {
        e.preventDefault();
        setLoading(true);
        setError(null);
        setMessage(null);

        try {
            if (mode === 'signup') {
                if (!name) { setError(t('auth.nameRequired')); setLoading(false); return; }

                const { data, error: signUpError } = await supabase.auth.signUp({
                    email, password,
                });

                if (signUpError) { setError(signUpError.message); setLoading(false); return; }

                if (data.user) {
                    const { error: profileError } = await supabase
                        .from('manager_profiles')
                        .insert({ user_id: data.user.id, name, phone: phone || null });
                    if (profileError) console.error('Profile creation error:', profileError);
                }
                setMessage(t('auth.accountCreated'));
            } else {
                const { error: signInError } = await supabase.auth.signInWithPassword({
                    email, password,
                });
                if (signInError) { setError(signInError.message); setLoading(false); return; }
            }
        } catch {
            setError(t('auth.unexpectedError'));
            setLoading(false);
        }
    };
Sign-up flow vs sign-in flow: Sign-in is simple — call signInWithPassword, get back an error or a session (session triggers onAuthStateChange, which renders the app). Sign-up has an extra step: after creating the auth user, immediately create the manager_profiles row.

Why not use a Supabase trigger instead: Triggers (DB-level functions that run after INSERT on auth.users) would be the "correct" approach for auto-creating profiles. But triggers require database access beyond what the Supabase dashboard easily exposes, and they're harder to debug. Doing it in application code is more transparent.

data.user check after signUp: Supabase can return a user object even when email confirmation is required (the user exists but is unconfirmed). The profile row is created regardless — when the user confirms their email and signs in, the profile will already be there.

Loading state not reset on success: After successful sign-in, onAuthStateChange fires and causes a re-render that replaces AuthPage with the authenticated app. Resetting loading to false would cause a brief flicker. On error, setLoading(false) is called explicitly before the early returns.

Part C — Google OAuth handler

    const handleGoogleAuth = async () => {
        setError(null);
        setGoogleLoading(true);
        const { error } = await supabase.auth.signInWithOAuth({
            provider: 'google',
            options: {
                redirectTo: window.location.origin,
            },
        });
        if (error) {
            setError(error.message);
            setGoogleLoading(false);
        }
    };
signInWithOAuth redirects the browser — it doesn't return a session. It redirects the user to Google's consent screen, which redirects back to redirectTo after sign-in. The function only returns an error if the initial redirect itself fails (invalid provider config, network error).

redirectTo: window.location.origin: Sets where Google redirects back to after authentication. window.location.origin evaluates to the current page's origin (e.g., https://app.example.com in production, http://localhost:5173 in dev). This URL must be whitelisted in both Supabase (Auth > URL Configuration > Redirect URLs) and in the Google Cloud Console (OAuth 2.0 > Authorized redirect URIs). If it's not whitelisted, Google returns "redirect_uri_mismatch" error.

setGoogleLoading(false) only on error: On success, the page navigates away. On error, we need to re-enable the button.

Section 5 — Concept Deep-Dives

React Context — when to use it, when not to

Context solves prop drilling: passing data through many component layers just so a deeply nested component can access it. Auth state is the canonical use case — every protected component needs to know who's logged in.

Without Context (prop drilling): App → Layout → Sidebar → UserAvatar (needs user.name) App → Layout → MainContent → Header → UserMenu (needs signOut) App → Layout → MainContent → Profile → ProfileForm (needs user.email) → You'd need to pass user/signOut as props through 3 levels of components that don't need the data themselves With Context: AuthProvider wraps the whole tree. UserAvatar calls useAuth() directly — gets user.name. UserMenu calls useAuth() directly — gets signOut. ProfileForm calls useAuth() directly — gets user.email. → No prop drilling. Components are decoupled.

When NOT to use context: for data that only one subtree needs (use props or local state), for frequently changing values (context re-renders ALL consumers on every change — use Zustand or useState+props for high-frequency updates like mouse position or animation state).

PKCE flow — what the "code verifier" actually does

PKCE stands for "Proof Key for Code Exchange." The mechanism:

  1. Browser generates a random code_verifier string (stored in sessionStorage)
  2. Browser hashes it: code_challenge = base64url(SHA256(code_verifier))
  3. Browser sends code_challenge to Supabase when starting OAuth
  4. Google redirects back with a one-time code
  5. Supabase exchanges the code for tokens — but also requires the original code_verifier
  6. Browser sends both code + code_verifier; Supabase verifies that SHA256(code_verifier) == code_challenge

Why this prevents token theft: Even if an attacker intercepts the code in the URL, they can't use it without the code_verifier, which was never in the URL. The verifier is in sessionStorage — only the original tab can use it.

Section 6 — Common Bugs & Fixes

Bug: Google OAuth redirects back but user isn't logged in

Symptom: User clicks "Continue with Google", authenticates on Google, gets redirected back to the app, but sees the login page again. No session.

Root causes (check in this order):

  1. detectSessionInUrl: true missing: Without this, the client doesn't look for the auth code in the URL on return. The code in the URL expires (it's single-use and short-lived) and the session is lost.
  2. Redirect URL not whitelisted: The URL you passed to redirectTo is not in Supabase's allowed redirect URLs list (Dashboard → Authentication → URL Configuration). Add http://localhost:5173 for dev and your production URL for prod.
  3. Google Cloud Console not configured: The Google OAuth client must also have the Supabase callback URL (https://[project].supabase.co/auth/v1/callback) in its "Authorized redirect URIs".

Bug: App shows login page for a fraction of a second even when user is logged in

Symptom: On every page load, the login page flashes briefly before the app loads. Users with slow connections see this for a noticeable time.

Root cause: The auth state hasn't been resolved yet. If loading is set to false before INITIAL_SESSION fires (e.g., before the Supabase client has checked localStorage), the AuthGate sees session === null and renders the login page.

Fix: Render a loading spinner while loading === true (before INITIAL_SESSION fires). Only then render either the auth page or the app:

function AuthGate({ children }) {
    const { session, loading } = useAuth();
    if (loading) return <LoadingSpinner />;
    if (!session) return <AuthPage />;
    return children;
}

Bug: Manager profile created multiple times for the same user (duplicate rows)

Symptom: The manager_profiles table has multiple rows for the same user_id. This causes FK errors and inconsistent data.

Root cause: Without the profileChecked ref guard, ensureManagerProfile runs on every onAuthStateChange event that has a user — including TOKEN_REFRESHED events that happen every hour. If maybeSingle() and insert() are called in a race condition (two events firing close together), both calls might see no existing row and both insert one.

Fix: The profileChecked ref prevents this. Alternatively, add a UNIQUE constraint on manager_profiles.user_id in the database — even if the application code runs the insert twice, the DB rejects the second one.

Bug: useAuth() crashes with "Cannot read properties of null"

Symptom: A component that calls useAuth() throws at runtime, but only in certain situations (e.g., when rendered in a test or in a specific route context).

Root cause: The component is rendered outside the AuthProvider. useContext(AuthContext) returns null when no provider is found. The explicit guard in useAuth() throws a helpful error — if you removed that guard, you'd get cryptic "cannot destructure null" errors instead.

Fix in production code: Ensure AuthProvider wraps the component tree at the app root. Fix in tests: Wrap the component under test in a mock AuthProvider that provides a fake session:

const mockSession = { user: { id: 'uuid-123', email: 'test@test.com' } };
render(
    <AuthContext.Provider value={{ session: mockSession, user: mockSession.user, loading: false, signOut: vi.fn() }}>
        <ComponentUnderTest />
    </AuthContext.Provider>
);

Section 7 — Exercises

Easy Exercise 1 — Trace the auth state events

Open the browser DevTools console and add a temporary console.log inside the onAuthStateChange callback to log event and whether session is null. Then:

  1. Reload the page while logged in. What events fire?
  2. Log out. What event fires?
  3. Log in with email/password. What events fire?
Show answer
  1. Reload while logged in: INITIAL_SESSION fires once with a valid session (Supabase found it in localStorage).
  2. Log out: SIGNED_OUT fires with session: null.
  3. Log in: SIGNED_IN fires with the new session. Then INITIAL_SESSION may fire again if the page reloads as part of the auth flow.
Medium Exercise 2 — Add a managerId value to the context

Many API calls need the manager's UUID from the manager_profiles table (not the auth user UUID, which is different). Add a managerId value to the AuthContext that fetches the profile UUID when the user signs in, and exposes it via useAuth().

Show solution 
// In AuthContext.jsx
const [managerId, setManagerId] = useState(null);

// Inside onAuthStateChange callback, after ensureManagerProfile:
if (session?.user && !profileChecked.current) {
    profileChecked.current = true;
    ensureManagerProfile(session.user);
    // Fetch the manager's profile ID
    supabase
        .from('manager_profiles')
        .select('id')
        .eq('user_id', session.user.id)
        .maybeSingle()
        .then(({ data }) => { if (data) setManagerId(data.id); });
}
if (!session) { profileChecked.current = false; setManagerId(null); }

// In the Provider value:
value={{ session, user, loading, signOut, managerId }}

Now const { managerId } = useAuth() works anywhere in the tree.

Hard Exercise 3 — Implement a "Remember Me" checkbox

By default, Supabase's session is stored in localStorage (persists across tabs and browser restarts). Add a "Remember me" checkbox to the login form. When unchecked, the session should use sessionStorage instead (cleared when the browser tab closes).

Show solution

Supabase JS v2 controls session storage via the storage option on createClient. This means you'd need to create the client dynamically based on the user's choice — not ideal for a singleton. A simpler approach: always use localStorage, but on sign-in, record the user's preference and call supabase.auth.signOut() on page unload if they didn't check "Remember me":

// In handleEmailAuth, after successful login:
if (!rememberMe) {
    window.addEventListener('beforeunload', () => {
        supabase.auth.signOut();
    }, { once: true });
}

A cleaner but more complex approach: pass a custom storage adapter to createClient that uses sessionStorage when the user hasn't checked "Remember me". This requires creating the Supabase client after the user submits the form — which means breaking the singleton pattern and creating it lazily. For most apps, the simpler approach above is sufficient.

Module 18 — Key Takeaways

  • One Supabase client singleton for the whole app — multiple instances cause state desync.
  • PKCE over implicit: tokens are never in the URL, making them immune to interception via browser history or logs.
  • INITIAL_SESSION is the signal that auth initialization is complete — only set loading: false here to avoid the login-page flash.
  • onAuthStateChange is the single source of truth — never manually set session state; let the event update it.
  • ensureManagerProfile exists because OAuth users bypass the signup form — profile creation must happen outside the form flow.
  • The profileChecked ref prevents duplicate profile inserts from multiple auth events firing close together.
  • detectSessionInUrl: true is required for OAuth to work — the Supabase client needs to look for the auth code in the URL after redirect.
  • Two loading states (loading, googleLoading) for two different async operations prevents one blocking the other's UI.
