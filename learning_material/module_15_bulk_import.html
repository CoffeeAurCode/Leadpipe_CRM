Section 1 — What You Are Building

A manager wants to migrate 200 tenants from an Excel spreadsheet into the system. They shouldn't have to rename all the columns to match the API's expected names first. This module builds a two-step import flow: step 1 analyses the file's columns and uses GPT-4o-mini to produce a column mapping; step 2 uses that mapping to actually import the data.

Two-step flow: STEP 1 — POST /import/analyze ├── Upload file (CSV or XLSX) ├── Parse headers + first 3 rows ├── Check if headers already match required columns │ └── YES → return {needs_mapping: false} (skip AI, go straight to import) └── NO → call GPT-4o-mini with headers + sample data └── returns {needs_mapping: true, mapping: {"Tenant Name": "name", ...}} STEP 2 — POST /import/tenants (or /import/properties) ├── Upload same file again + column_mapping (JSON string from step 1) ├── Parse file → apply mapping (rename columns) └── Row-by-row insert: ├── Look up flat by flat_number ├── Check if flat is already occupied ├── INSERT tenant ├── UPDATE flat (tenant_uuid, occupied=true) └── INSERT rent record (if rent_amount provided) Constants: MAX_ROWS = 1000 (reject files with > 1000 rows) MAX_FILE_BYTES = 5 MB

Section 2 — Concept Deep-Dives

CSV parsing with stdlib — no pandas

Python's standard library includes a fully capable CSV parser. Using it avoids the pandas dependency (a 30MB+ library) for a task that doesn't need data analysis.

import csv, io

def _parse_csv(content: bytes) -> tuple[list[dict], set[str]]:
    text = content.decode("utf-8-sig")           # handles BOM
    reader = csv.DictReader(io.StringIO(text))  # reads header row automatically
    raw_fields = reader.fieldnames or []
    fieldnames = {f.strip().lower() for f in raw_fields}  # normalised set
    rows = [
        {k.strip().lower(): (v or "").strip() for k, v in row.items()}
        for row in reader
    ]
    return rows, fieldnames

csv.DictReader reads the first row as headers and returns subsequent rows as dicts automatically. The keys match the header row. io.StringIO wraps the text string so it looks like a file object — required because DictReader expects a file-like object, not a raw string.

Why utf-8-sig?

When you export a CSV from Microsoft Excel on Windows, it prepends a BOM (byte order mark: \xef\xbb\xbf) to the file. If you decode with plain utf-8, this BOM becomes the first character of the first column header: "﻿property_name" instead of "property_name". The utf-8-sig codec automatically strips the BOM.

This is one of the most common CSV import bugs. Everything looks fine in a text editor (the BOM is invisible), but the DB lookup for property_name silently fails because the actual key is ﻿property_name. The fix is one word: utf-8-sig.

Excel parsing with openpyxl — no pandas

Excel XLSX files are ZIP archives containing XML. openpyxl reads them natively without converting to CSV first.

import openpyxl

def _parse_xlsx(content: bytes) -> tuple[list[dict], set[str]]:
    wb = openpyxl.load_workbook(io.BytesIO(content), data_only=True)
    ws = wb.active                              # first sheet
    rows_iter = ws.iter_rows(values_only=True)  # yield tuples of cell values
    first_row = next(rows_iter, None)          # header row
    if first_row is None:
        return [], set()

    raw_headers = [str(h).strip() if h is not None else "" for h in first_row]
    fieldnames = {h.lower() for h in raw_headers if h}

    rows = []
    for excel_row in rows_iter:
        row_dict = {
            h.strip().lower(): (str(v).strip() if v is not None else "")
            for h, v in zip(raw_headers, excel_row)
            if h.strip()  # skip empty header columns
        }
        if any(row_dict.values()):  # skip completely empty rows
            rows.append(row_dict)
    return rows, fieldnames

data_only=True — reads the cached calculated value of formula cells, not the formula string itself. Without this, cells with =SUM(A1:A10) return the formula text instead of the number.

if v is not None else "" — Excel cells can be None when empty. Converting to string before stripping prevents AttributeError: 'NoneType' object has no attribute 'strip'.

AI column mapping with AsyncOpenAI

A manager's spreadsheet might have columns called "Tenant Full Name", "Mobile Number", "Unit No." instead of the expected "name", "phone", "flat_number". Rather than requiring them to rename everything, GPT-4o-mini maps their column names to the target schema.

response = await client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
    temperature=0,                                # deterministic output
    response_format={"type": "json_object"},      # force valid JSON
)

temperature=0 — zero temperature means the model always picks the highest-probability token. For a deterministic mapping task (same input → same output), this is correct. Non-zero temperature introduces randomness which would make mappings inconsistent across calls.

response_format={"type": "json_object"} — forces the model to output valid JSON. Without this, the model might add markdown code fences (```json ... ```) or a preamble text, causing json.loads() to fail.

Important: When using response_format={"type": "json_object"}, the prompt MUST contain the word "JSON" somewhere. If it doesn't, the OpenAI API returns an error. The prompt in _map_columns_with_ai() ends with: "Return ONLY valid JSON."

The _apply_mapping() function

After the AI returns a mapping like {"Tenant Name": "name", "Mobile": "phone"}, every row needs its column names translated before insertion.

def _apply_mapping(rows: list[dict], mapping: dict) -> list[dict]:
    result = []
    for row in rows:
        new_row = {}
        for orig_key, val in row.items():
            target = mapping.get(orig_key)    # e.g. "Tenant Name" → "name"
            if target:                           # target is None for unmapped columns
                new_row[target] = val
        result.append(new_row)
    return result

# Before: {"Tenant Name": "Alice", "Mobile": "91...", "Extra Col": "ignored"}
# After:  {"name": "Alice", "phone": "91..."}

Columns mapped to None (unmappable) are dropped silently. This is intentional — extra columns in the user's spreadsheet (internal notes, IDs from their old system) don't cause errors.

Importing 200 rows from the same property would normally trigger 200 identical "find this property by name" queries. The property cache prevents this.

The sanitization loop is critical: the AI might hallucinate a target column that doesn't exist (e.g. "tenant_id" which isn't in the schema). The check target in all_targets validates every AI suggestion against the known set of valid target columns — invalid targets become None.

The second loop ensures every input header has an entry in the mapping (even if mapped to None). This gives the frontend a complete view: "here are all your columns and what we think they map to."

except Exception: return {h: None ...} — if the AI call fails entirely, return an all-null mapping. The frontend will see that nothing was mapped and prompt the manager to map columns manually.

Three DB operations per row: INSERT tenant → UPDATE flat → INSERT rent. They're not wrapped in a transaction (Supabase SDK doesn't expose explicit transactions). This means a crash between INSERT and UPDATE leaves a dangling tenant record. For a bulk import tool in an MVP, this is an acceptable risk — failed rows are reported in errors.

The outer per-row try/except means one bad row doesn't abort the entire import. All good rows succeed; bad rows are collected in errors and reported at the end.

Section 4 — Real Bugs & How We Fixed Them

Bug 1: First column always "not found" — the BOM bug

Symptom: Import of a CSV exported from Excel always showed "Missing required columns: property_name" even though the column was clearly there. The AI mapping step also failed to map it.

Root cause: The CSV had a UTF-8 BOM. Decoded with utf-8, the first column header became "﻿property_name" instead of "property_name". The BOM is invisible in most text editors.

How we found it: Added print(repr(fieldnames)) temporarily and saw '﻿property_name' in the output.

Fix: Changed content.decode("utf-8") to content.decode("utf-8-sig"). One word, zero side effects on non-BOM files (the -sig codec is a no-op when no BOM is present).

Bug 2: OpenAI returned invalid JSON (markdown code fence)

Symptom: Column mapping worked in testing but occasionally failed in production with json.JSONDecodeError. Logs showed the raw response was: ```json\n{"name": "name"}\n```.

Root cause: Without response_format={"type": "json_object"}, GPT-4o-mini sometimes wraps JSON in a markdown code fence. json.loads() can't parse fenced output.

Fix: Added response_format={"type": "json_object"} to the API call. Also added the word "JSON" to the prompt (required by OpenAI when using this parameter). The except clause falling back to all-null mapping provides an additional safety net.

Bug 3: Excel cells with formulas returned formula text, not values

Symptom: Some cells imported as "=A2" or "=SUM(B1:B3)" instead of actual values.

Root cause: openpyxl.load_workbook() without data_only=True reads the formula string, not the cached result.

Fix: Added data_only=True to the load_workbook() call. Note: this reads the cached calculated value — if the Excel file was never opened/saved in Excel after adding formulas, the cache may be empty (openpyxl returns None), which is then converted to "" by the if v is not None else "" guard.

Bug 4: AI mapped "Extra Internal ID" to a valid target column incorrectly

Symptom: Column "SrNo" in the manager's spreadsheet was mapped to "flat_number" by the AI because it was a number and the AI guessed it could be a flat number. All tenants imported with serial numbers as their flat number.

Root cause: The AI prompt showed the column name and the first 3 rows of data. "SrNo" values (1, 2, 3) looked plausible as flat numbers to the AI.

Fix (partial): Included sample row data in the prompt so the AI sees actual values (not just names). For "SrNo" with values 1, 2, 3, the AI now sees it's a sequential number — less likely to map to flat_number. The frontend also shows the proposed mapping before import so the manager can review and correct it. This is the correct safeguard — AI suggestions are proposals, not commands.

Section 6 — Key Takeaways

  • Always decode CSV files with utf-8-sig to handle the invisible Excel BOM — this is one of the most common silent import bugs.
  • openpyxl.load_workbook(data_only=True) returns calculated values, not formula strings — always use data_only=True.
  • Two-step flow (analyze → import) lets the user review and correct AI column mapping before any data is written — safer than a single-step import.
  • response_format={"type": "json_object"} forces OpenAI to return valid JSON — required for reliable parsing. Your prompt must also mention "JSON".
  • Sanitize AI output against a known list of valid targets — the AI may hallucinate plausible-sounding column names that don't exist in your schema.
  • Cache property/building lookups in the import loop — without caching, N rows in the same property = N identical DB queries.
  • Per-row try/except with errors list — one bad row must not abort the entire import. Report errors at the end.
  • File parameters in multipart requests must use Form(), not JSON body — FastAPI cannot mix the two in one endpoint.
