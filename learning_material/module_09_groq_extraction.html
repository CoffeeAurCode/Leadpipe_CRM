Module 09 — AI Complaint Extraction (Groq)

Part C — AI & Voice Integration  |  Build Session 3

Module 9 of 26 — 34% through the course

Learner outcome: Can call the Groq LLM API to extract structured data from free-text, validate the output, and handle LLM unreliability with both AI-based and rule-based fallbacks.

Why Two Extractors?

When a tenant finishes a VAPI voice call, the backend receives a raw transcript like:

"Hi, my name is John, I live in unit A-101. The kitchen tap has been leaking for two days and it's getting worse. I'd like someone to come this Thursday around 2pm if possible."

We need to turn this into a structured complaint record:

{
  "flat_number": "A-101",
  "category": "water",
  "priority": "medium",
  "description": "Kitchen tap leaking for two days, getting worse"
}

The codebase uses two approaches:

ApproachFunctionHow it worksWhen to use
AI extractionextract_complaint_from_transcript()Groq LLM reads the transcript and returns JSONVoice transcripts — natural language, messy
Rule-based extractionextract_fields()Regex + keyword listsShorter text inputs, deterministic fallback
Model note: The extractor file uses llama-3.1-8b-instant (fast, cheap, small). For the chatbot in Module 10, we use OpenAI gpt-4o-mini because it handles complex multi-turn tool calling more reliably. The rule never use llama-3.1-70b-versatile (decommissioned) applies to the larger model — the 8b-instant variant is still active.

constants.py — The Single Source of Truth

Before looking at the extractor, understand what it validates against. Every allowed value in the system lives in backend/app/core/constants.py.

from enum import Enum


# ========== COMPLAINT CATEGORIES ==========

ALLOWED_CATEGORIES = [
    "water",
    "electricity",
    "cleaning",
    "noise",
    "maintenance",
    "security",
    "other"
]


# ========== COMPLAINT STATUSES ==========

class ComplaintStatus(str, Enum):
    PENDING = "pending"
    IN_PROGRESS = "in-progress"
    RESOLVED = "resolved"

ALLOWED_STATUSES = [status.value for status in ComplaintStatus]


# ========== PRIORITY (kept for backward compat) ==========
PRIORITY_ENUM = ["low", "medium", "high"]
Design pattern — single source of truth: ALLOWED_CATEGORIES is imported by the extractor, the route validator, the VAPI agent config (as an enum field), and the frontend's status.js. If you ever add a new category (e.g. "pest"), you add it here once and every layer picks it up automatically. Forgetting to update the DB CHECK constraint is the one common mistake.

Why ComplaintStatus(str, Enum)?

Inheriting from both str and Enum means each enum member IS a string. This lets you do:

# Both of these work:
db.table("complaints").insert({"status": ComplaintStatus.PENDING})   # works — is "pending"
db.table("complaints").insert({"status": "pending"})               # works too
ComplaintStatus.PENDING == "pending"   # True — comparison with plain string

validator.py — Completeness Check

After extraction, the voice webhook checks whether all required fields are present before creating a complaint record.

def validate_complaint(data: dict) -> dict:
    required_fields = ["flat_number", "category", "appointment_date"]
    missing_fields = []

    for field in required_fields:
        value = data.get(field)
        if value is None or value == "":
            missing_fields.append(field)

    return {
        "is_complete": len(missing_fields) == 0,
        "missing_fields": missing_fields,
        "data": data      # original data untouched — passed through
    }
Key design choice: The validator does not modify the data. It only checks existence. The caller (voice webhook) decides what to do with missing fields — it sets complaint_status = "incomplete" and does not create the complaint, but still saves the CallLog for audit purposes.

Notice that description and priority are not required. The voice webhook provides a fallback for both:

  • priority → hardcoded to "medium" for all voice complaints
  • description → falls back to the raw transcript if empty

AI Extractor — extract_complaint_from_transcript()

import re
import os
import json
from groq import Groq
from app.core.constants import ALLOWED_CATEGORIES


def extract_complaint_from_transcript(transcript: str) -> dict:
    try:
        client = Groq(api_key=os.getenv("GROQ_API_KEY"))

        system_prompt = """You are a complaint extraction AI.

Your task: Extract structured complaint data from voice call transcripts.

STRICT RULES:
1. Extract ONLY these fields: flat_number, category, priority, description
2. If a field is NOT mentioned or cannot be confidently inferred, return null for that field
3. NEVER fabricate or guess missing information
4. Category must be one of: water, electricity, cleaning, noise, maintenance, security, other
5. Priority must be one of: low, medium, high
6. All category and priority values MUST be lowercase
7. Output valid JSON ONLY - no explanations, no markdown, no code blocks

Field Extraction Guidelines:
- flat_number: Extract apartment/unit number if mentioned (e.g., "A-101", "Flat 204", "12B")
- category: Infer from complaint keywords (leak→water, power cut→electricity, etc.)
- priority: Infer from urgency keywords (urgent→high, whenever→low, etc.)
- description: Extract the core complaint description

Output Format (strict):
{
  "flat_number": "value" or null,
  "category": "value" or null,
  "priority": "value" or null,
  "description": "value" or null
}"""

        response = client.chat.completions.create(
            model="llama-3.1-8b-instant",
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": f"Extract complaint data from this transcript:\n\n{transcript}"}
            ],
            temperature=0,
            max_tokens=500
        )

        result_text = response.choices[0].message.content.strip()
        result = json.loads(result_text)

        # Normalize and validate category
        if result.get("category"):
            result["category"] = result["category"].lower()
            if result["category"] not in ALLOWED_CATEGORIES:
                result["category"] = None    # hallucinated value → discard

        # Normalize and validate priority
        if result.get("priority"):
            result["priority"] = result["priority"].lower()
            if result["priority"] not in ["low", "medium", "high"]:
                result["priority"] = None

        return {
            "flat_number": result.get("flat_number"),
            "category":   result.get("category"),
            "priority":   result.get("priority"),
            "description": result.get("description")
        }

    except Exception as e:
        print(f"AI extraction error: {e}")
        return {           # safe all-None fallback on any error
            "flat_number": None, "category": None,
            "priority": None,   "description": None
        }

System Prompt Engineering for Extraction

Extraction prompts are fundamentally different from chat prompts. Here's the breakdown of every design choice:

ChoiceWhy
temperature=0Extraction must be deterministic. Temperature 0 means the model always picks the highest-probability token — no creativity.
max_tokens=500The output is a small JSON object. Limiting tokens prevents rambling and reduces cost.
"Output valid JSON ONLY — no explanations, no markdown, no code blocks"LLMs love wrapping JSON in ```json ... ```. This instruction suppresses it. Without it, json.loads() will fail.
"If a field is NOT mentioned…return null"Without this, the LLM will hallucinate plausible values. This is the single most important guard.
Enumerated allowed values in the promptThe model knows the exact set of valid strings so it doesn't invent "plumbing" or "electric" instead of "water"/"electricity".
Post-extraction validation against ALLOWED_CATEGORIESBelt-and-suspenders: even if the model ignores the prompt constraint, the code validates and nulls invalid values.

Why Groq (not OpenAI) for extraction?

Voice call ends → transcript available Groq llama-3.1-8b-instant extraction: ✓ ~200ms response time (vs ~800ms OpenAI) ✓ Free tier available (vs paid per-token) ✓ Temperature=0 → deterministic ✓ One-shot task, no tool calling needed OpenAI gpt-4o-mini for chatbot: ✓ Superior multi-turn tool calling ✓ More reliable JSON schema adherence ✓ Better at complex reasoning chains

The rule of thumb: Groq for one-shot extraction, OpenAI for interactive tool calling. Running OpenAI for every voice complaint would be ~4x the cost with no benefit.

Rule-Based Extractor — extract_fields()

This is the deterministic alternative to AI extraction. No LLM call — pure regex and keyword matching.

def extract_fields(text: str) -> dict:
    text_lower = text.lower()
    return {
        "flat_number": _extract_flat_number(text),
        "category":    _extract_category(text_lower),
        "priority":    _extract_priority(text_lower),
        "description": text.strip()   # always the full text
    }

Category Extraction — Keyword Matching

def _extract_category(text_lower: str) -> str | None:
    category_keywords = {
        "water":       ["water", "leak", "leaking", "pipe", "plumbing", "tap", "sink", "flush"],
        "electricity": ["electricity", "power", "light", "bulb", "wiring", "socket", "outage"],
        "cleaning":    ["clean", "garbage", "trash", "dirty", "waste"],
        "noise":       ["noise", "loud", "music", "disturbance", "shouting"],
        "maintenance": ["repair", "broken", "fix", "damage", "crack", "door", "wall"],
        "security":    ["security", "theft", "lock", "gate", "intruder"],
    }

    matched_categories = {}
    for category, keywords in category_keywords.items():
        if category not in ALLOWED_CATEGORIES:    # skip any category not in the master list
            continue
        match_count = sum(1 for kw in keywords if kw in text_lower)
        if match_count > 0:
            matched_categories[category] = match_count

    if matched_categories:
        return max(matched_categories, key=matched_categories.get)  # most keyword hits wins
    return None

The most keyword hits wins strategy handles ambiguous text. "The pipe is broken and leaking" hits both "maintenance" (broken) and "water" (pipe, leaking) — water wins with 2 hits vs 1.

Priority Extraction

def _extract_priority(text_lower: str) -> str | None:
    priority_keywords = {
        "high":   ["urgent", "emergency", "immediately", "asap", "critical", "serious"],
        "medium": ["soon", "important", "quickly", "necessary"],
        "low":    ["whenever", "not urgent", "can wait", "no hurry", "eventually"],
    }

    detected_priorities = []
    for priority, keywords in priority_keywords.items():
        for keyword in keywords:
            if keyword in text_lower:
                detected_priorities.append(priority)
                break           # one keyword match per priority level is enough

    if not detected_priorities:
        return None

    priority_order = {"high": 3, "medium": 2, "low": 1}
    return max(detected_priorities, key=lambda p: priority_order[p])  # highest wins

Flat Number Regex — CRITICAL Priority Order

The flat number extractor is the trickiest part. The code has a long comment block explaining the pattern priority — this is earned wisdom from actual bugs:

def _extract_flat_number(text: str) -> str | None:
    # PRIORITY ORDER: Alphanumeric patterns FIRST, pure digits LAST
    # This prevents "A101" from being incorrectly parsed as "101"
    patterns = [
        # Priority 1: Letter + optional hyphen/space + digits (A-101, A101, A 101)
        r'\b([A-Z]-?\s?\d{1,4}[A-Z]?)\b',

        # Priority 2: Keyword prefix (flat A101, unit B204)
        r'\b(flat|unit)\s+([A-Z0-9-]+)\b',

        # Priority 3: Digits + letter suffix (101A, 204B)
        r'\b(\d{1,4}[A-Z])\b',

        # Priority 4: Letter + space + digits (A 101)
        r'\b([A-Z]\s?\d{1,4})\b',

        # Priority 5: PURE DIGITS ONLY — LAST RESORT
        # Deliberately placed LAST to avoid stripping prefixes
        r'^\s*(\d{2,4})\s*$'
    ]

    for idx, pattern in enumerate(patterns, 1):
        match = re.search(pattern, text, re.IGNORECASE)
        if match:
            if 'flat' in pattern or 'unit' in pattern:
                extracted = match.group(2).strip()   # group(2) skips "flat"/"unit" word
            else:
                extracted = match.group(1).strip()
            return extracted

    return None
Bug that taught this lesson: The original extractor had pure-digit patterns first. For the text "flat A101 has a water issue", the pattern \d{2,4} matched 101 instead of A101. The complaint was logged for flat "101" which didn't exist, causing the webhook to fail silently. The fix was to always try alphanumeric patterns first and only fall back to pure digits as a last resort.

Real Bugs Faced & How We Fixed Them

Bug 1: LLM Returns Markdown-Wrapped JSON

Symptom: json.loads() raises JSONDecodeError on valid-looking extraction results.

Root cause: The LLM returned: 
```json
{"flat_number": "A101", "category": "water", ...}
```
Fix: The prompt now says "Output valid JSON ONLY — no explanations, no markdown, no code blocks". Plus the broad except Exception catches any JSONDecodeError and returns all-None safely.

Bug 2: Hallucinated Category Values

Symptom: Complaints inserted with category = "plumbing" which failed the DB CHECK constraint, causing a 500 error.

Root cause: The LLM returned a semantically correct but non-canonical value.

Fix: Post-extraction validation — after json.loads(), check result["category"] in ALLOWED_CATEGORIES and set to None if not. The voice webhook then uses the fallback transcript.

Bug 3: Using the Wrong Model Name

Symptom: groq.BadRequestError: model 'llama-3.1-70b-versatile' does not exist — this error started appearing in late 2024 when Groq decommissioned the 70b model.

Fix: The extractor uses llama-3.1-8b-instant (small, fast, still active). For other Groq code paths use llama-3.3-70b-versatile (the successor to 70b). Never use llama-3.1-70b-versatile — it no longer exists.

Bug 4: Flat Number "A101" Extracted as "101"

Already documented above in the regex section. Short version: pure-digit pattern must be last in the patterns list, not first.

Bug 5: Exception During Extraction Crashes the Webhook

Symptom: The voice webhook returned 500, causing VAPI to mark the call as failed.

Root cause: Early version of the extractor had no try/except. A network timeout to the Groq API propagated up and crashed the webhook handler.

Fix: Wrap the entire function in try/except Exception and return all-None. The webhook then creates an incomplete call log rather than crashing. The VAPI rule is: always return 200 regardless of what happens internally.

Exercises

Easy   What does the extractor return when the Groq API is unreachable?

It catches the exception and returns {"flat_number": None, "category": None, "priority": None, "description": None}. This means the voice webhook will create an incomplete call log (status = "incomplete") rather than crashing. The transcript is still saved for manual review.

Easy   Why is temperature=0 used for extraction but not for chatbot responses?

Extraction is a mapping task: transcript → fixed JSON schema. There is only one correct answer. Temperature=0 makes the model pick the most likely token at each step — maximally deterministic. The chatbot needs to generate varied, natural-sounding replies; temperature > 0 adds the slight randomness that makes responses feel human rather than robotic.

Hard   The AI extractor uses HTTP calls to Groq's API. In a production system handling 1000 calls/day, what's the risk and how would you mitigate it?
Show solution

Risk 1: Rate limiting — Groq's free tier has per-minute token limits. 1000 calls/day = ~41/hour. Each transcript might be ~300 tokens. At peak, this could hit limits.

Risk 2: Latency — The voice webhook must complete within VAPI's timeout. Adding an external API call adds 200-500ms latency. Under load this can stack up.

Risk 3: Cost at scale — Groq charges per token on paid plans.

Mitigations:

  • Make the Groq call async and move it to a background task — don't block the webhook response on extraction. Save the raw transcript first, extract in background.
  • Cache extraction results by transcript hash (unlikely to see exact duplicates, but possible for short transcripts).
  • The existing rule-based extract_fields() is instant — use it as a pre-filter. Only call Groq if the rule-based extractor returns None for key fields.
  • Use a queue (Celery + Redis) to process transcripts asynchronously at controlled throughput.
