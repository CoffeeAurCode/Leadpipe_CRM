One Line, Two Brains — Routing French Callers to Their Own Ear

Every previous French session improved the one bilingual agent that answers each manager's phone. It listened with Deepgram's multilingual speech engine — a generalist that hears English and French on the same line but is a master of neither. This session gives French callers a dedicated French speech engine. Because a phone's transcriber can't switch language mid-call, we couldn't just "flip to French" — we had to route: the existing agent now opens with a short English language gate ("English or French?"), and on a French choice it hands the call off to a second, French-only assistant (Deepgram nova-3 fr) that searches that manager's real listings. We did it without a squad, without touching the phone numbers, and without changing the English path — then rolled it live to all four per-manager agents with a one-command rollback standing by.

🔴 Advanced ⏱️ ~80 min read / build 📋 Requires: Sessions 08–13 (French STT, fuzzy matching, the register lock, the per-manager deploy pipeline)

📦 Session Overview

This was a routing-and-infrastructure session. Sessions 8–13 all sharpened the single bilingual lease agent. Session 14 splits the French conversation onto its own assistant with its own ear, and builds the plumbing to send French callers there. The work flowed from one question you asked while looking at an exported agent config:

You: i have put voice agent config @French_cere.md — how good is it, and what can I learn to make the french of my lease agent better? ...which surfaced that a dedicated French ear was the real upgrade... You: what about we use a French-only Deepgram model if the caller speaks french and keep the english scenario the same You: apply it to the agent of each manager so we can test against real listings... if this doesn't work, then we will roll back You: for routing, start with a plain English intro, then ask English or French, then route to the respective agent

By the end we had, live on all four manager lines:

  • A dedicated French-only assistant per manager — same leasing brain, but listening with Deepgram nova-3 set to language:"fr" (a monolingual French model) instead of the shared multi engine.
  • An explicit language gate on the entry assistant — it opens in English, asks "English or French? / Anglais ou français?", does no leasing until the caller picks, then hands off to the French assistant only on a French choice. English callers never leave the entry assistant.
  • A handoff with NO squad and NO phone-number change — we discovered (from the Vapi docs) that a handoff tool can target a saved assistant by id directly, which removed the two riskiest parts of the original plan.
  • A provisioning script with a built-in rollback — provision_lease_french_handoff.py, with --dry-run, a fleet guard, and a --rollback that undoes everything.
  • One new DB column + a paper trail — migration 031, plus updates to CODEBASE_CONTEXT.md and a plan doc, so the next session inherits the full picture.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Explain why a phone agent's speech-to-text language can't be switched mid-call, and why that forces routing instead of flipping.
  • Compare a multilingual STT model to a dedicated single-language one, and say when each wins.
  • Describe Vapi squads vs handoff tools, and why a direct assistantId handoff needs neither a squad nor a phone-number change.
  • Design a gated, additive change that adds a French branch while proving the English path is byte-for-byte unchanged.
  • Choose between passive language detection and an explicit language gate (an IVR-style menu).
  • Understand DDL vs DML and why a Supabase client library can't add a column — and how the migration actually gets applied.
  • Treat rollback as a first-class feature and verify a live multi-agent deploy end-to-end.

🌉 Recap Bridge — where we left off

Our product is a CRM (Customer Relationship Management — the web app a property manager uses to track buildings, units, tenants, and leads). It has a voice agent named Max: an AI that answers a phone line, talks to a prospective renter, finds the unit they want, and saves the manager a lead. Max runs on Vapi (a hosted "Voice API" that wires a phone number to three swappable pieces — a transcriber that turns speech into text, a model / LLM that decides what to say, and a voice that speaks the reply). Max's behaviour lives in a long system prompt — the variable _LEASE_SYSTEM_PROMPT_BASE in backend/app/services/vapi_agent_config.py — plus a set of tools that call our backend.

Across Sessions 08–13 we worked the French problem from both ends. On the input side (what Max can hear): Session 08 built fuzzy city matching for garbled French place-names, Session 09 added the banded "did you mean…?" confirmation, Session 12 unified the match gate and gave Max a Montréal clock. On the output side (what Max says): Session 13 locked his French register to the formal vous. Every one of those changes lived on a single bilingual assistant per manager, transcribing with Deepgram nova-3 in language:"multi" mode — one engine listening for both English and French at once.

That shared multi engine is exactly where Session 12's Québec-city garble came from: a generalist model splitting its attention across languages mishears French place-names more than a French specialist would. Session 14 attacks that at the source — give French calls a French-only ear. The catch, which shapes the entire session, is that you can't change a call's transcriber once the call is live. So this session is really about routing: detecting the language and sending the caller to a second assistant built for it.

🧠 Concepts Introduced This Session

Eight ideas. C1 is the physical constraint that dictates the whole design (you can't switch the ear mid-call). C2 is why a dedicated French ear is worth the trouble. C3–C5 are the routing mechanics (squad vs handoff; the gated branch; the language gate). C6–C7 are the deployment realities (raw-HTTP provisioning; why a schema change needs a different tool than data changes). C8 is the discipline that made a live fleet deploy safe (reversibility).

1 · The transcriber's language is locked when the call starts

Plain-English explanation. When a phone call connects, Vapi has to start converting the caller's audio into text immediately — so it loads one speech-to-text configuration, including which language to listen for, before the caller has said a single word. You cannot change that language partway through the call, because to know they're speaking French you'd first have to transcribe them… which requires already having picked a transcriber. It's a chicken-and-egg loop.

Why we need it (for CRM specifically). Our dream was "use the French model if the caller speaks French." That exact sentence is impossible inside one assistant: the "if" can only be evaluated after transcription, and transcription has already committed to a language. This single fact is why we can't just add an instruction to Max's prompt — the fix has to happen at a level above the conversation: which assistant the call is sent to.

How it works (analogy). It's like hiring an interpreter before a guest arrives. You must pick "French interpreter" or "Spanish interpreter" at the door — you can't wait until the guest starts talking, because the interpreter is the very person who'd tell you what language it is. If you guess wrong, you don't re-train that interpreter mid-conversation; you tap a different interpreter on the shoulder and hand the conversation over. That hand-over is the whole idea of this session.

Jargon decoder.

  • STT (Speech-To-Text) — software that converts spoken audio into written words. Also called a "transcriber." Deepgram is the STT provider we use.
  • transcriber config — the JSON block on an assistant that says which STT provider/model/language to use. Fixed at call start.
  • multi mode — Deepgram's setting (language:"multi") that listens for several languages at once, including switching between them in one sentence.
🔑 Key Concept — some choices must be made before you have the information to make them

When a decision depends on data that only exists after the decision is committed, you can't solve it in place — you solve it by routing: make a cheap first guess (or ask), then transfer to a specialist. Recognising "this is a chicken-and-egg constraint" early stops you from designing an impossible in-call switch.

2 · Multilingual vs dedicated speech models

Plain-English explanation. A multilingual STT model is a generalist: it can handle several languages, even mixed in one sentence, but it spreads its "attention" across all of them. A dedicated single-language model is a specialist: told in advance it will only hear French, it can lean entirely on French sounds, spellings, and place-names — so it gets more of them right. The cost of accuracy is flexibility: a French-only model mangles English.

Why we need it (for CRM specifically). Session 12's bug was Max mishearing Québec city names like "Trois-Rivières" off the multi engine. Deepgram's own numbers say their nova-3 model in dedicated French gives "double-digit relative WER reductions" versus the multilingual setting on French audio. For a leasing call where the caller's city decides which listings come back, fewer mis-heard place-names is a direct quality win. The whole point of routing is to put French audio in front of that specialist.

How it works (analogy). A bilingual receptionist who handles English and French walk-ins is convenient, but a born-and-raised Québécois who only takes the French line will catch a mumbled "Saint-Hyacinthe" the generalist fumbles. Same brain power, narrower focus, better French.

Jargon decoder.

  • WER (Word Error Rate) — the standard accuracy metric for transcription: the percentage of words the engine gets wrong. Lower is better; "double-digit relative reduction" means dropping, say, 12% WER to ~10%.
  • nova-3 — Deepgram's current-generation model family. Supports both multi and dedicated single languages like fr.
  • keyterm prompting — feeding the STT engine a list of expected words (e.g. a manager's real street and city names) so it biases toward transcribing them correctly. Works on dedicated nova-3 languages — a future lever (Exercise 🟢).
  • confidenceThreshold — how sure the engine must be before it accepts a transcript; we keep it at 0.4 (the value Session 12 settled on), not the dangerously-low 0.13 we saw in the exported config.

Here is the dedicated French transcriber we added, beside the shared one for contrast:

# The SHARED bilingual ear, used by the ENTRY assistant (unchanged this session):
TRANSCRIBER_CONFIG = {
    "provider": "deepgram",
    "model": "nova-3",
    "language": "multi",        # listens for English AND French at once
    "numerals": True,           # write "two" as "2" for easier tool parsing
    "confidenceThreshold": 0.4, # reject low-confidence guesses
    # ...OpenAI fallback transcriber omitted...
}

# NEW — the dedicated French ear, used ONLY by the French handoff assistant:
FRENCH_TRANSCRIBER_CONFIG = {
    "provider": "deepgram",
    "model": "nova-3",
    "language": "fr",           # monolingual French -> lower WER on French audio
    "numerals": True,
    "confidenceThreshold": 0.4, # same gate as the shared engine
    "fallbackPlan": {           # if Deepgram hiccups, fall back to OpenAI's transcriber
        "transcribers": [
            {"provider": "openai", "model": "gpt-4o-transcribe"}
        ]
    },
}
⚠️ Warning — we verified nova-3 fr exists before trusting it

nova-3 began life English-only and added languages over time, so "does nova-3 even support fr?" was a real question. Getting it wrong means the assistant fails on its first call. We confirmed against Deepgram's docs that nova-3 added dedicated French (with a WER win over nova-2) before writing the config. Verify model/language support; never assume it from a sibling model.

3 · Routing between agents: squads vs handoff tools

Plain-English explanation. Vapi gives you two ways to run more than one assistant on a call. A squad is a pre-declared team of assistants bundled together, with the phone number pointed at the squad; members transfer among themselves. A handoff tool is lighter: a single assistant carries a "transfer this call to that assistant" action it can fire mid-conversation. The decisive discovery this session was that a handoff can target a saved assistant by its id with no squad at all — which means the phone number keeps pointing at the original assistant and nothing about call routing changes for anyone.

Why we need it (for CRM specifically). The first design used a squad and repointed each phone number at it. That touches the most dangerous surface we have: every inbound call, English included, would now enter through new plumbing. When we read the docs and found handoff-by-assistantId needs no squad and no repoint, the blast radius collapsed from "all inbound routing" to "one extra tool on the existing assistant." (That realisation is Bug Story #1.)

How it works (analogy). A squad is re-routing the building's front-door intercom through a new switchboard — everyone who buzzes now goes through it. A direct handoff is the receptionist keeping their same desk and phone, and simply warm-transferring the occasional French caller to a colleague's extension. The front door is untouched.

Jargon decoder.

  • handoff tool — a Vapi tool of type:"handoff" placed in an assistant's tool list; calling it transfers the live call to a destination assistant.
  • squad — a named group of assistants; the phone number is attached to the squad rather than to a single assistant. We did not use one.
  • assistantId vs assistantName — a handoff destination targets a saved assistant by its UUID (assistantId, works anywhere) or, only inside a squad, by assistantName. We used assistantId.
  • contextEngineeringPlan — the setting that controls how much of the conversation so far is carried to the destination assistant. {type:"all"} carries everything, so the French assistant continues the call instead of restarting it.

The handoff tool we attach to the entry assistant:

def _lease_handoff_tool(french_assistant_id: str) -> dict:
    # Gated handoff to the dedicated French assistant. No squad: we target a saved
    # assistantId directly, and carry full context so the French side continues, not restarts.
    return {
        "type": "handoff",                 # Vapi's assistant-to-assistant transfer tool
        "destinations": [
            {
                "type": "assistant",
                "assistantId": french_assistant_id,   # the saved French assistant's UUID
                "description": (                       # the model reads THIS to decide when to fire
                    "Transfer the call to the French-speaking leasing assistant. Use this the "
                    "instant you determine the caller is speaking French. Do NOT use it for "
                    "English callers."
                ),
                "contextEngineeringPlan": {"type": "all"},  # carry the whole conversation across
            }
        ],
    }
🔑 Key Concept — the lightest mechanism that meets the requirement is usually the right one

Squads, repoints, and DB schema for squad ids were all real options — and all heavier than the job needed. A direct assistantId handoff did everything required (transfer + carry context) while leaving the phone numbers and the English path untouched. When two designs both work, prefer the one with the smaller blast radius.

4 · The gated, additive branch (English untouched by construction)

Plain-English explanation. Rather than build a brand-new "router" assistant that every call passes through, we kept each manager's existing assistant as the entry assistant and added French as a single branch off it. The French logic only switches on when (a) we pass a French assistant id into the builder and (b) the caller actually chooses French. With no French id, the function returns byte-for-byte today's config. So the English experience isn't "probably fine" — it's provably unchanged, because the code path that builds it is literally identical.

Why we need it (for CRM specifically). Your hard constraint was "keep the English scenario the same." The cleanest way to guarantee that is to make the new behaviour optional and gated: an extra parameter, french_assistant_id=None, that defaults to off. Every existing caller of build_lease_config keeps the old behaviour for free, and only the new provisioning path opts in.

How it works (analogy). It's a feature flag baked into a function signature. Like adding an optional "gift wrap?" checkbox to a checkout: unchecked, the order flows exactly as before; checked, one extra step runs. You don't fork the whole checkout to add wrapping paper.

Jargon decoder.

  • additive change — a change that only adds a code path; it never alters or removes existing behaviour.
  • blast radius — the set of things a change can possibly affect. We keep it tiny and provable.
  • gated — guarded by a condition so the new path is inert unless explicitly switched on.
def build_lease_config(backend_url: str, manager_id: str,
                       manager_name: str = "our property management team",
                       french_assistant_id: str | None = None) -> dict:  # NEW optional arg, default off
    tools = _alias_apirequest_tool_names(_build_lease_tools(backend_url, manager_id=manager_id))
    context_block = _LEASE_CONTEXT_BLOCK.format(manager_id=manager_id, manager_name=manager_name)
    system_prompt = _LEASE_SYSTEM_PROMPT_BASE + context_block
    if french_assistant_id:                              # the gate: only when a French id is supplied
        system_prompt += _LEASE_FRENCH_ROUTING_BLOCK     #   add the language-gate instructions
        tools = tools + [_lease_handoff_tool(french_assistant_id)]  #   add the handoff tool
    # If french_assistant_id is None, the two lines above never run -> identical to today's config.
    return _lease_assistant_shell(
        name=f"Lease Agent [{manager_id[:8]}]",
        system_prompt=system_prompt, tools=tools, backend_url=backend_url,
    )


def build_lease_config_french(backend_url: str, manager_id: str,
                              manager_name: str = "our property management team") -> dict:
    # The HANDOFF TARGET: same leasing brain + tools, but a French-only ear and a "continue" note.
    tools = _alias_apirequest_tool_names(_build_lease_tools(backend_url, manager_id=manager_id))
    context_block = _LEASE_CONTEXT_BLOCK.format(manager_id=manager_id, manager_name=manager_name)
    system_prompt = _LEASE_SYSTEM_PROMPT_BASE + context_block + _LEASE_FRENCH_CONTINUATION_NOTE
    return _lease_assistant_shell(
        name=f"Lease Agent FR [{manager_id[:8]}]",
        system_prompt=system_prompt, tools=tools, backend_url=backend_url,
        transcriber=FRENCH_TRANSCRIBER_CONFIG,           # the ONLY structural difference: the French ear
    )

To make the French builder possible we also gave the shared assistant "shell" an optional transcriber parameter that defaults to the bilingual one — a one-line, backward-compatible change so the French builder can swap in its own ear without forking the shell.

💡 Tip — prove "unchanged," don't assert it

We later confirmed with a tiny script that build_lease_config_shared(url) with no French id produces a config with no handoff tool and no routing block, while the same call with an id adds exactly one handoff tool. "The English path is unchanged" became a test assertion, not a hope.

5 · Passive detection vs an explicit language gate

Plain-English explanation. There are two ways to learn the caller's language. Passive detection: greet bilingually and infer the language from whatever words come back. An explicit gate: open in English, ask "English or French?", and act on the answer. You chose the gate. It's the same idea as a phone menu ("press 1 for English") but spoken — deterministic, hard to misread, and it makes the routing decision a clean yes/no instead of a guess about ambiguous first words.

Why we need it (for CRM specifically). Passive detection's failure mode is ugly: a French caller who opens with an English place-name ("uh, Montreal?") might be misread as English and never handed off — or worse, an English caller gets wrongly transferred. The explicit gate removes that ambiguity: the caller tells us, and we route on a direct answer. It also gives the French assistant a clean starting point — the caller has only chosen a language, not yet stated their need.

How it works (analogy). Passive detection is a host guessing your language from your accent and sometimes getting it wrong. The gate is the host simply asking "English or French?" — one beat slower, far more reliable.

Jargon decoder.

  • IVR (Interactive Voice Response) — the classic "press 1 for…" phone menu. Our gate is the conversational, spoken equivalent.
  • language gate — the single opening turn whose only job is to establish the call language and route on it.

The routing block we append to the entry assistant (the gate lives here):

[French Routing — STRICT, ENTRY ASSISTANT ONLY]
This line is bilingual, but YOU never conduct the French call — a dedicated French assistant does.
Run your FIRST turn as an explicit language gate:
1. Give a short, plain English introduction (you are Max, the AI leasing assistant for the manager),
   then ask which language they prefer: "Would you like to continue in English, or in French?"
   Append the French of just that question so a French speaker can answer:
   "Préférez-vous continuer en anglais ou en français?"
   (This gate question is the ONE permitted bilingual line — it overrides the bilingual ban in
   [Language Policy] for this single turn. Do NOT start any leasing topic yet.)
2. Wait for their choice before anything else — do NOT ask what they are looking for until they pick.

Route on their answer:
- ENGLISH chosen -> continue the entire call in English, exactly as normal.
- FRENCH chosen (or they simply answer in French / ask for French) -> call the handoff tool
  IMMEDIATELY on that turn. Do NOT answer in French yourself, do NOT announce the transfer.
- Unclear answer -> ask once more "English or French? / Anglais ou français?", then route.

And the note we append to the French assistant so it continues smoothly rather than re-greeting from scratch:

[French Call — Continuation]
The caller just chose to continue in French at the language gate; they have NOT yet said what they
are looking for. Greet them warmly in French with the formal vous, introduce yourself briefly, and
ask what they're looking for — e.g. "Parfait! Je suis Max, votre assistant de location. Qu'est-ce que
vous cherchez comme logement?" The entire call stays in French; never switch to English.
⚠️ Warning — the gate question is the one allowed bilingual line

Session 13 banned mixing languages in one utterance. The gate is the deliberate exception: a French-only caller must be able to understand the question, so we ask it in both languages — but only that one turn. We say so explicitly in the prompt so the model doesn't refuse it as a policy violation.

6 · Provisioning Vapi over raw HTTP (not the SDK)

Plain-English explanation. Vapi ships a Python SDK (a convenience library), but this project deliberately talks to Vapi with plain HTTP requests instead. The reason, discovered in earlier sessions and documented in the codebase: the SDK's strict data types silently drop fields it doesn't recognise — like firstMessageMode and some tool sub-fields — so configs come out subtly wrong. Raw HTTP sends exactly the JSON we built. We followed that same pattern for the new create / patch / delete calls.

Why we need it (for CRM specifically). Our assistant configs use camelCase fields and tool shapes the SDK mangles. Since the existing deploy scripts already use httpx.patch(...) against api.vapi.ai, the new provisioning script matches them: POST /assistant to create the French assistant, PATCH /assistant/{id} to add the handoff to the entry, DELETE /assistant/{id} for rollback. Consistency with the working pattern beats fighting the SDK.

How it works (analogy). The SDK is a "helpful" form that quietly deletes any answer that doesn't fit its boxes. Raw HTTP is mailing the form you actually wrote. When the helper loses your data, you write the letter yourself.

Jargon decoder.

  • SDK (Software Development Kit) — a library that wraps an API in convenient functions. Useful until its assumptions don't match yours.
  • httpx — the Python HTTP client this project uses for direct REST calls.
  • REST verbs — POST creates, PATCH updates, DELETE removes. The Vapi endpoints map cleanly onto these.
  • idempotent — running the same operation twice leaves the same result. Re-running our provisioning patches the existing French assistant rather than making a duplicate.
def _to_vapi_payload(cfg: dict) -> dict:
    # Our config dict uses snake_case keys; Vapi's REST API wants camelCase. Translate, drop Nones.
    payload = {
        "name": cfg.get("name"),
        "firstMessageMode": cfg.get("first_message_mode"),   # the field the SDK silently dropped
        "transcriber": cfg.get("transcriber"),
        "voice": cfg.get("voice"),
        "model": cfg.get("model"),
        # ...more 1:1 mappings...
    }
    return {k: v for k, v in payload.items() if v is not None}

def _create_french_assistant(cfg: dict, dry_run: bool) -> str:
    payload = _to_vapi_payload(cfg)
    if dry_run:                                              # preview mode makes no network call
        print(f"    DRY RUN POST /assistant name={payload['name']}")
        return "<dry-run-french-id>"
    resp = httpx.post(f"{VAPI_API_BASE}/assistant", headers=_headers(), json=payload, timeout=30)
    if resp.status_code not in (200, 201):                  # surface failures loudly, don't swallow
        raise SystemExit(f"create failed HTTP {resp.status_code}: {resp.text[:300]}")
    return resp.json()["id"]                                # the new assistant's UUID, to wire into the entry

7 · DDL vs DML — why a Python client can't add a column

Plain-English explanation. Database operations split into two families. DML (Data Manipulation Language) reads and writes rows — SELECT, INSERT, UPDATE. DDL (Data Definition Language) changes the shape of the database itself — CREATE TABLE, ALTER TABLE to add a column. The Supabase Python client we use talks to PostgREST, a layer that only does DML (rows). It has no way to run an ALTER TABLE. So to add our new column we couldn't script it — it had to go through the Supabase SQL Editor (or a direct Postgres connection, which this environment doesn't have).

Why we need it (for CRM specifically). To remember each manager's French assistant id across redeploys, we needed a new column, vapi_lease_french_assistant_id, on the manager_vapi_config table. That's DDL. The agent literally could not apply it — no DATABASE_URL, no Postgres driver installed, and the Supabase client can't do DDL. So the rollout had a human step: you pasted migration 031 into the Supabase SQL Editor. Knowing which changes you can automate and which need the dashboard prevents a confused "why won't my script add the column?" loop.

How it works (analogy). DML is moving furniture in and out of rooms; DDL is knocking down a wall to add a room. The mover (PostgREST) is licensed to carry furniture, not to do construction. Construction goes to a different crew (the SQL Editor / a direct DB connection).

Jargon decoder.

  • DDL / DML — define the schema vs manipulate the rows.
  • PostgREST — the service that turns a Postgres database into a REST API for rows; what supabase-py speaks. Rows only, no schema changes.
  • migration — a numbered .sql file that records a schema change so it's repeatable and reviewable. Ours is 031_lease_french_assistant_id.sql.
  • ADD COLUMN IF NOT EXISTS — idempotent DDL: safe to run twice, and additive (nullable, default null) so it can't break existing rows.
-- Per-manager dedicated French lease assistant id, for the French-handoff routing.
-- Additive and nullable -- no effect on managers without a French assistant.
ALTER TABLE manager_vapi_config
  ADD COLUMN IF NOT EXISTS vapi_lease_french_assistant_id text;

COMMENT ON COLUMN manager_vapi_config.vapi_lease_french_assistant_id IS
  'VAPI assistant id of the dedicated French-only lease assistant (handoff target). Null = none.';
🔑 Key Concept — know your data layer's powers and limits

A client library exposes a subset of what the database can do. Supabase's client is row-oriented by design. The moment you need to change structure, you've stepped outside its remit and need a different tool — the SQL editor or a direct connection. Recognising that boundary is the difference between "the migration needs a human step" and ten minutes of debugging a 400 error.

8 · Reversibility as a feature (and pilot-gating)

Plain-English explanation. You said "if this doesn't work, we'll roll back." A rollback that's an afterthought is a scramble; a rollback that's designed in is one command. We built --rollback into the provisioning script from the start: it removes the handoff from each entry assistant (rebuilding it with no French id), deletes the French assistants, and clears the DB column — returning everything to exactly today. We also gated the risky fleet rollout behind an explicit --confirm-fleet flag so it can't fire by accident.

Why we need it (for CRM specifically). These are four live phone lines real renters call. "Try it and undo it if it's bad" is only a safe plan if the undo is reliable and instant. Because the change is additive (a tool on an assistant; a nullable column; new standalone assistants), the reverse is mechanical and complete — no data migration to unwind, no phone-number to re-point.

How it works (analogy). Good change management is climbing with a rope already clipped in. You don't wait until you slip to look for an anchor. The --rollback path is the rope, clipped before the first live patch.

# Fleet rollout is REFUSED unless you explicitly confirm — no accidental fire:
$ python provision_lease_french_handoff.py --all --fleet-only
  Refusing --all without --confirm-fleet. ...apply migration 031 first...

# One command undoes the entire session, live:
$ backend/.venv/Scripts/python.exe \
    backend/scripts/provision_lease_french_handoff.py --rollback --all --fleet-only
  # -> removes the handoff from 4 entry assistants, deletes 4 French assistants, clears the column
💡 Tip — build the undo before the do

Writing --rollback before the live push forced us to think through every artifact the rollout creates (an assistant, a tool, a column value) — which is exactly the checklist you need to be confident the forward push is complete. The undo is also the best documentation of what the change actually touched.

🐛 Bug Journal

No crashes shipped to production, but the path there had five honest stumbles — a design that was too big, an API that had moved, a missing dependency, a wall we couldn't drill through from Python, and a fake corruption scare. Each gets the full Symptom → Diagnosis → Root Cause → Fix → Lesson treatment.

🐛 Bug 1 — The first design was twice as risky as the job required

🚨 The Symptom

The initial routing plan used a Vapi squad and repointed every phone number at it, plus new DB columns for squad ids. On paper it worked — but it put new plumbing in front of every inbound call, English included, on four live lines. The plan's own risk table flagged "phone-number → squad repoint" and "untested transfer" as real, not-yet-reversible hazards.

🔍 The Diagnosis

The trigger to re-examine was reading the actual deploy infrastructure: each manager has a single assistant id and a phone number, deployed by a PATCH-only script. The squad design fought that grain. Then we asked the docs a sharper question: "does an assistant-to-assistant handoff require a squad, or can it target a saved assistant by id?" The answer — id works, no squad — dissolved the need for the repoint entirely.

🧠 The Root Cause

Designing before fully reading the deployment surface. "Squad" is the textbook multi-agent answer, so we reached for it before checking whether a lighter mechanism met the requirement. The repoint wasn't required by the goal; it was an artifact of the heavier pattern we picked first.

🔧 The Fix

Switch to a direct assistantId handoff (Concept 3). The phone numbers stay on the entry assistants; no squad object exists; the only live change is one gated tool added to an assistant. The plan doc was rewritten from "squad + repoint" to "handoff, no repoint," and the risk table shrank accordingly.

# BEFORE — heavy: every call re-routed
phone number  ->  SQUAD  ->  [entry assistant, french assistant]   (repoint all 4 numbers)
                                                                   (+ DB columns for squad ids)

# AFTER — light: front door untouched, French is a side-door transfer
phone number  ->  entry assistant  --(handoff on French)-->  french assistant
                  (numbers unchanged; English path identical; one added tool)
🛡️ The Lesson

Read the deployment reality before you promise "non-breaking," and ask whether a lighter primitive meets the requirement before committing to the famous one. The best fix here deleted code and risk rather than adding them.

🐛 Bug 2 — The API in our memory no longer matched the API in the docs

🚨 The Symptom

Looking up assistant-to-assistant transfer, the first doc page described a "handoff tool" with a contextEngineeringPlan — not the transferCall-with-assistantName shape we expected. A second page we tried (/assistants/call-transfers) returned a flat "Page Not Found."

🔍 The Diagnosis

We searched the current Vapi docs and read the live /squads/handoff page. It confirmed a newer model: a type:"handoff" tool, destinations by assistantId or assistantName, and a contextEngineeringPlan with modes like all and lastNMessages. We then verified the exact JSON and the no-squad behaviour before coding.

🧠 The Root Cause

APIs evolve faster than any model's training cut-off. The transfer mechanism had been redesigned since the knowledge we were carrying. Coding from remembered API shapes is a guess dressed up as a fact.

🔧 The Fix

Treat the live documentation as the source of truth. We fetched the current handoff schema and the phone-number update reference (confirming a number can attach to a squadId, which we then chose not to use) and built from those exact shapes.

🛡️ The Lesson

For any third-party API, verify the current shape against today's docs before writing code — especially for fast-moving platforms. A 404 on a remembered URL is a signal the surface moved, not a dead end.

🐛 Bug 3 — ModuleNotFoundError: No module named 'supabase'

🚨 The Symptom

The read-only preview script crashed immediately:

ModuleNotFoundError: No module named 'supabase'

…yet moments earlier the provisioning script's --dry-run had imported the same project modules fine.

🔍 The Diagnosis

The clue was the contrast: the dry-run worked because it only imports modules that depend on the standard library; the preview crashed because it imports supabase. So the difference wasn't the code — it was the interpreter. The base python on the machine doesn't have the project's third-party packages. We searched for a virtual environment and found one: backend/.venv.

$ find . -maxdepth 4 -name "pyvenv.cfg" ./backend/.venv/pyvenv.cfg $ ls backend/.venv/Scripts/python.exe backend/.venv/Scripts/python.exe
🧠 The Root Cause

A virtual environment (venv) is an isolated Python with its own installed packages, separate from the system Python. The project's dependencies — supabase, httpx, etc. — live in backend/.venv, not in the base interpreter we'd been invoking as plain python. Running a project script with the wrong interpreter means its imports aren't there.

🔧 The Fix

Invoke scripts with the venv's interpreter explicitly:

# Wrong: base python, missing the project's installed packages
python backend/scripts/provision_lease_french_handoff.py --all ...

# Right: the venv interpreter that actually has supabase/httpx installed
backend/.venv/Scripts/python.exe backend/scripts/provision_lease_french_handoff.py --all ...
🛡️ The Lesson

Environment parity: a script's behaviour depends on which interpreter runs it. When an import fails for code that obviously uses that package, suspect the environment before the code. On Windows the project interpreter is backend/.venv/Scripts/python.exe; we now use it for every script that touches Supabase.

🐛 Bug 4 — We couldn't add the column from Python at all

🚨 The Symptom

The fleet rollout needs a new column, and the plan was "just have the script add it." But there was no way to run an ALTER TABLE from our tooling — the Supabase client offered no method for it, and a capability check came back empty-handed:

$ backend/.venv/Scripts/python.exe scratch/env_caps.py DATABASE_URL set: False psycopg2: False psycopg: False SUPABASE_URL set: True SUPABASE_SERVICE_KEY set: True
🔍 The Diagnosis

Two independent paths to DDL were both closed. (1) The Supabase Python client talks to PostgREST, which does rows, not schema — no ALTER TABLE. (2) A direct Postgres connection would need a DATABASE_URL and a driver like psycopg; the env has neither. The project's own migration README confirmed the intended path: the Supabase SQL Editor, run by a human.

🧠 The Root Cause

A DDL/DML boundary (Concept 7). The service key authenticates against PostgREST (row API), not raw Postgres. Schema changes are simply outside that key's reach by design — they're an administrative action, not an application one.

🔧 The Fix

Stop trying to automate it. We shipped the change as migration 031_lease_french_assistant_id.sql and handed you the one idempotent statement to paste into the SQL Editor. The script's fleet path also guards on the column: it refuses --all without --confirm-fleet and points at the migration.

🛡️ The Lesson

Know which actions your credentials and libraries can actually perform. A row-API key can't reshape the schema; recognising that immediately turns "why won't this work?" into "this needs the SQL Editor." Design the rollout to expect that human step rather than fight it.

🐛 Bug 5 — The fake mojibake in the terminal

🚨 The Symptom

The dry-run output showed a garbled character where an em-dash should be:

DRY RUN � POST /assistant name=Lease Agent FR [28c43c77] Done. (dry run � nothing changed)

It looked like the accented/French content had been corrupted on write.

🔍 The Diagnosis

We'd already proven, in the local build check, that the config strings contained no mojibake (we grepped for the tell-tale Ã©/Ã sequences and found none). So the bytes on disk were clean. The garble only appeared in the terminal's rendering — meaning it was a display artifact, not data corruption. This was the exact false-alarm pattern Session 13 warned about.

🧠 The Root Cause

The Windows console renders text in a legacy code page (cp1252) by default, which can't draw a UTF-8 em-dash (—) and shows � instead. The string in the file is correct UTF-8; only the terminal's font/codepage can't display it.

🔧 The Fix

None needed — there was no bug in the data. We confirmed the file bytes were clean and moved on, rather than "fixing" a problem that existed only in the console's rendering.

🛡️ The Lesson

Verify the file's bytes, never trust the terminal's glyphs. A garbled console character is a display issue until a byte-level check proves otherwise. Chasing terminal-only mojibake wastes time fixing nothing.

🧯 Troubleshooting / Common Errors

ModuleNotFoundError: No module named 'supabase'

Cause: you ran the script with the base Python, which lacks the project's packages. Fix: use the project venv — backend/.venv/Scripts/python.exe <script> (Bug 3).

The fleet command refuses with "Refusing --all without --confirm-fleet"

Cause: that's the safety guard, on purpose. Fix: confirm you've applied migration 031 and want the live fleet rollout, then re-run with --all --fleet-only --confirm-fleet.

A 400 / "column ... does not exist" on the fleet path

Cause: migration 031 hasn't been applied, so the select on vapi_lease_french_assistant_id fails. Fix: paste 031_lease_french_assistant_id.sql into the Supabase SQL Editor (DDL can't be scripted here — Bug 4), then re-run the read-only preview to confirm column ... PRESENT.

An English caller gets transferred to the French assistant

Cause: the model fired the handoff too eagerly. Fix: tighten the handoff destination description and the [French Routing] block to emphasise "only on an explicit French choice; never for English," then re-run provisioning to patch the entries.

The French assistant re-greets from scratch / re-asks what the caller said

Cause: the handoff isn't carrying context, or the continuation note isn't present. Fix: confirm the handoff destination has contextEngineeringPlan:{type:"all"} and the French prompt includes [French Call — Continuation]; re-verify with the live-content check.

Garbled � or Ã© in the terminal output

Cause: the Windows console's legacy code page can't render a UTF-8 character; the file itself is usually fine. Fix: verify the file's bytes (grep for Ã©); if clean, it's display-only — ignore it (Bug 5).

A routine update_lease_agents.py run stripped the handoff

Cause: the French id wasn't passed when rebuilding the entry. Fix: ensure the per-manager column is populated and the shared VAPI_SHARED_LEASE_FRENCH_ASSISTANT_ID env var is set — the deploy script reads both to preserve the handoff.
