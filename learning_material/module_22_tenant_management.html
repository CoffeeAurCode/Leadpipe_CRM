Module 22 — Tenant Management

Full tenant CRUD with lease badge display, bidirectional flat assignment, and slide-in profile panel. This module covers how the frontend consumes computed fields returned by the API — fields the backend calculates from raw DB data so the frontend only has to display them.

  • Bidirectional assign / unassign tenant
  • Slide-in panel (fixed right, spring animation)
  • Edit / view mode toggle in a panel
  • useCallback + useEffect load pattern
  • document_urls array management
  • Feature-flag gating within a component
  • Tab-based modal (existing vs new tenant)
  • Framer Motion AnimatePresence panel
  • date-fns parseISO / format

const handleSave = async () => {
    const payload = Object.fromEntries(
        Object.entries(form).map(([k, v]) => [k, v === '' ? null : v])
    );
    const updated = await updateTenant(tenant.uuid, payload);
    // Merge joined fields back (not returned by PATCH)
    const merged = {
        ...updated,
        flat_number: tenant.flat_number,
        rent_amount: tenant.rent_amount,
        due_date: tenant.due_date,
        tenant_details_enabled: tenant.tenant_details_enabled,
        tenant_documents_enabled: tenant.tenant_documents_enabled,
    };
    onUpdate(merged);
};
The PATCH endpoint only returns the core tenant row — it doesn't re-JOIN flat or rent data. So we preserve the existing join values from the original tenant object and merge them back. Without this, flat_number would disappear from the panel after saving.
Bug you'll hit: If you remove the merge step, flat_number will show "—" in the table immediately after saving even though the DB didn't change. Always re-merge fields that come from JOINs after a PATCH.

Slide-in panel animation

<motion.div
    className="fixed right-0 top-0 h-full w-full max-w-md bg-card border-l border-border shadow-2xl z-50"
    initial={{ x: '100%' }}
    animate={{ x: 0 }}
    exit={{ x: '100%' }}
    transition={{ type: 'spring', damping: 30, stiffness: 300 }}
>
Spring physics (damping+stiffness) give the panel a natural feel. Pure duration-based transitions feel mechanical on slide effects. x: '100%' means "start 100% of its own width to the right" — completely off-screen.

Bidirectional FK Pattern

Why two pointers?

The DB has: flats.tenant_uuid → tenants AND tenants.flat_uuid → flats. Both FKs exist for query speed — VAPI can look up a tenant's flat number from their phone without a JOIN, and the properties page can show which tenant lives in a flat without a JOIN. The trade-off is that both must be updated atomically when assigning or unassigning.

-- assign-tenant endpoint does both atomically:
UPDATE flats SET tenant_uuid = :tenant_uuid WHERE uuid = :flat_uuid;
UPDATE tenants SET flat_uuid = :flat_uuid WHERE uuid = :tenant_uuid;

The unassign-tenant endpoint clears both to NULL.

Key Patterns to Remember

Three-layer status rule

Lease status flows like this:

DB (lease_start_date, lease_end_date)
  → Backend: TenantResponse.model_validator computes lease_status
       based on remaining days
  → Frontend: displays the string value with a colour badge

The frontend never re-calculates. If lease_status logic changes, it changes in one place — the Pydantic model.

useCallback pattern for data loading

const load = useCallback(async () => { ... }, [dep1, dep2]);
useEffect(() => { load(); }, [load]);

The load function has stable identity when deps haven't changed. This means the effect only re-runs when a filter actually changes — not on every render. Without useCallback, every render would trigger a fresh API call.

Real Bugs Encountered During Build

Bug 1 — PATCH response missing joined fields
Symptom: after saving tenant email, the flat_number column in the table showed "—".
Cause: PATCH /tenants/:uuid returns the raw tenant row. flat_number comes from a JOIN not stored on the tenants table.
Fix: merge the missing joined fields back from the original tenant object in handleSave.
Bug 2 — Stale vacant flat list
Symptom: AddTenantModal showed a flat that was already occupied from an earlier session.
Cause: fetchVacantFlats was called once when the component mounted, not each time the modal opened.
Fix: move fetchVacantFlats into the useEffect that watches isOpen.
Bug 3 — Document re-upload silently ignored
Symptom: uploading the same PDF file twice only uploaded it once.
Cause: the HTML file input doesn't fire onChange if the same file is selected again.
Fix: e.target.value = '' after every upload to reset the input.

Exercise 3 — Make the lease end date column sortable with a toggle

The existing code already wires up toggleSort('lease_end_date') on the Lease End column header. Trace through the data flow: where does the sort happen — frontend or backend?

Answer

Backend. The sort_by and sort_order parameters are passed to fetchTenants(), which sends them to GET /tenants?sort_by=lease_end_date&sort_order=asc. The backend handles the ORDER BY. The frontend never sorts the array itself — this keeps the logic in one place and avoids pagination bugs.

Why This Design

Decision: Consume backend-computed fields instead of computing in React

ApproachProsCons
Display lease_status etc. as delivered (chosen)One implementation (Module 07) serves UI, chatbot, and voice agent; the table sorts/filters via API params so DB and UI always agreeFrontend can't derive variants the API doesn't ship — new displays need a backend change
Compute from raw dates in ReactFrontend-only iterationTimezone drift between browser and backend produces off-by-one-day badges — the exact bug class the computed-field design eliminates

Decision: Merge-after-PATCH vs. refetch-after-save

ApproachProsCons
Merge joined fields back into the PATCH response (chosen)Instant UI update, one network call; the panel and table stay in sync via the parent's callbacksThe merge list (flat_number, rent_amount, …) must be maintained by hand — forget one and it blanks after save
Refetch the tenant (or list) after saveAlways complete and freshSecond round-trip per save; the list flashes; at this app's scale that's the only real cost
Senior takeaway: merge-after-PATCH is a micro-optimization with a maintenance tax. It's the right call here because the joined-field list is short and stable. The moment that list grows past a handful, flip to refetch — correctness beats one saved round-trip.
