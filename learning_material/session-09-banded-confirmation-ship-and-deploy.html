Shipping & Deploying Banded "Did You Mean?" City Confirmation

Session 08 ended with a plan. This session turns that plan into running production code: a phonetic+string matcher that can tell Saint-Lazare from Saint-Lazaire, a tool response that tells the voice agent when to ask "did you mean X or Y?", the prompt that makes Max ask it politely, the tests that prove it, and the deploy that pushed it to five live phone assistants.

The thing we built has a mouthful of a name — "banded fuzzy-band entity confirmation" — but the idea is simple. When a French-accented caller says a city and the speech-to-text mangles it, the agent should:

clear winner → just proceed, no question (AUTO_ACCEPT) two sound-alikes → "did you mean X or Y?" (CONFIRM) nothing close → "here's what we do have…" (NO_MATCH)

🌉 Recap Bridge — where we left off

Our CRM (Customer Relationship Management — the app property managers use to track buildings, units, tenants and leads) has a voice agent named Max: an AI that answers the phone and holds a real spoken conversation with a prospective tenant. Max figures out which unit the caller wants, asks a few qualifying questions, and hands the manager a "lead." If Max fumbles, the lead is lost before a human ever sees it.

In Session 08, a French-speaking partner test-called Max against a real Quebec portfolio and reported two problems: it paused too much, and it didn't understand him. We did the detective work and proved the "didn't understand" half was a speech-to-text (STT) problem: Deepgram (our STT engine) running in language:"multi" mode renders French-accented proper nouns as English-ish garble — "Saint-Lazare" comes out as "Saint-L'Asor." We also wrote a design plan for the fix and built a first, basic accent-tolerant matcher: city_matching.py had normalize_place() (strip accents/hyphens, fold St→Saint) and city_matches() (a plain difflib string-ratio check). That was enough to find a city, but not enough to disambiguate two cities that sound alike.

So at the start of this session, the plan's status line literally read "proposed, not started." The matcher could fuzzy-match one city, but it had no notion of "I matched, but two candidates are about equally likely." That gap is exactly where STT garble causes the agent to silently pick the wrong city. This session closes that gap and ships it.

🧠 Concepts Introduced This Session

Seven ideas carry the whole session. Read these once and the build log and bug journal will feel obvious.

1 · The hybrid max() similarity score

Plain-English explanation. "Similarity" means: how alike are two pieces of text, as a number between 0 (nothing alike) and 1 (identical)? The catch is that there are several different ways to measure "alike," and each one is blind to a different kind of mistake. So instead of trusting one, we run three measures and keep the highest — the logic being "if any reasonable measure thinks these are close, treat them as close."

Why we need it (for CRM specifically). The caller's garbled city has to be matched against the manager's real city names. A purely letter-by-letter comparison catches typos ("Saint Lazole" vs "Saint Lazare") but completely misses sound-alikes spelled differently ("Saint-L'Asor"). A purely sound-based comparison catches those but can over-merge. Taking the max of both means a garble is rescued if it's close either way — which is the only way to reliably recover a mangled French city.

How it works (analogy). Imagine three judges scoring a costume contest: one judge only looks at the spelling on the name tag, one only listens to how the name sounds when spoken, and one is a quick generalist. We don't average them (an average lets one harsh judge sink a good match). We take the most generous score, because our cost of missing a real match is far higher than the cost of a single extra confirmation question.

Jargon decoder.

  • difflib — a library built into Python. Its SequenceMatcher.ratio() measures how much two strings overlap, character by character. Cheap, already there, decent baseline.
  • rapidfuzz — a fast third-party library for fuzzy string matching (matching text that's almost equal). Its ratio() is based on edit distance (how many single-character insert/delete/replace edits turn one string into the other). Returns 0–100, so we divide by 100.
  • phonetic match — comparing how words sound, not how they're spelled (covered in Concept 2).
  • normalize — clean both strings the same way before scoring (lowercase, drop accents/hyphens, fold "St"→"Saint") so cosmetic differences don't count against the match.

Annotated code — the heart of the matcher. Here is the exact hybrid we shipped:

def similarity(spoken: str, candidate: str) -> float:
    # Clean BOTH strings the same way first (lowercase, strip accents/hyphens, St->Saint).
    # Garble carries no accents, so normalizing both sides puts them on equal footing.
    a, b = normalize_place(spoken), normalize_place(candidate)
    if not a or not b:                       # empty after cleaning -> definitely not a match
        return 0.0
    return max(                              # keep the MOST generous of the three measures
        _rapidfuzz_score(a, b),              # edit-distance garble: "Saint Lazole" -> "Saint Lazare"
        _phonetic_ratio(a, b),               # sound-alike/spelled-different: "Saint-L'Asor"
        difflib.SequenceMatcher(None, a, b).ratio(),  # cheap built-in baseline, kept as a floor
    )
📖 Deep Dive — why max, not a weighted average?

Our errors are asymmetric: a false accept (silently proceeding on the wrong city) burns the entire call and captures a junk lead, while a false confirm (asking one extra question) costs a single turn. When the downside of missing a match dwarfs the downside of an extra check, you want the scorer that's most willing to call something a match — that's max(). A weighted average would let one pessimistic scorer veto a real match. We deliberately lean toward "notice the resemblance."

2 · Phonetic encoding with Metaphone (in practice)

Plain-English explanation. A phonetic algorithm turns a word into a short code that represents how it sounds, throwing away spelling details that don't change the sound. Words that sound alike get the same code. "Lazare" and "Lazaire" are spelled differently but sound the same — and both encode to the code LSR. That shared code is what lets us catch a sound-alike that the letter-by-letter scorers would rate as different.

Why we need it (for CRM specifically). This is the single most important detail of the whole feature. The caller's complaint was literally "similar sounding." A spelling-only matcher gives "Saint-L'Asor" vs "Saint-Lazare" a weak ~0.55 — below our match floor — so it would be thrown away and the caller dumped to a full city list. The phonetic leg scores that same pair near 1.0 and rescues it. Without phonetics, the feature would miss exactly the cases it exists for.

How it works (analogy). Think of phonetic encoding as a "soundex fingerprint." Two people with messy handwriting might write a name differently, but if you read both aloud they sound the same — the sound is the fingerprint, not the ink. Metaphone is one recipe for computing that fingerprint.

Jargon decoder.

  • jellyfish — the Python library we use for phonetic encoding. We call jellyfish.metaphone().
  • Metaphone — a phonetic algorithm. It's English-rule based, but it operates on sound, which is the right axis against Deepgram's pseudo-English rendering of French audio.
  • Double Metaphone — a fancier successor that returns two codes (a primary and an alternate) for ambiguous spellings. The plan asked for this — but the installed jellyfish doesn't ship it (see Bug #4). We used single Metaphone, which was plenty here.
  • swappable backend — we put the encoder behind a single variable (_PHONETIC_ENCODER) so a future, more French-aware encoder (e.g. Beider-Morse) can be dropped in without touching the rest of the code.

Annotated code — the phonetic leg. We encode word-by-word and compare the codes, so multi-word names ("saint lazare") work, and near-but-not-identical codes still score partially:

# The encoder lives behind ONE name so it can be swapped for a better one later
# without changing any caller. Defaults to single Metaphone if jellyfish is installed.
_PHONETIC_ENCODER = jellyfish.metaphone if _HAS_JELLYFISH else None

def _phonetic_code(norm: str) -> str:
    if not _PHONETIC_ENCODER or not norm:    # no encoder available -> phonetic leg scores 0
        return ""
    try:
        # Encode each WORD separately, then join the codes. "saint lazare" -> "SNT LSR".
        return " ".join(_PHONETIC_ENCODER(tok) for tok in norm.split() if tok)
    except Exception:
        return ""                            # never let a phonetic hiccup crash a phone call

def _phonetic_ratio(a_norm: str, b_norm: str) -> float:
    ca, cb = _phonetic_code(a_norm), _phonetic_code(b_norm)
    if not ca or not cb:
        return 0.0
    if ca == cb:                             # identical sound codes -> perfect phonetic match
        return 1.0
    # Codes differ but may still overlap (e.g. one word matches) -> graded, not all-or-nothing
    return difflib.SequenceMatcher(None, ca, cb).ratio()

This is the actual proof we ran in the terminal that "Lazare" and "Lazaire" collapse to the same sound code:

$ python -c "import jellyfish; print(jellyfish.metaphone('lazare'), jellyfish.metaphone('lazaire'))" LSR LSR # same code -> these two are phonetically identical

3 · Turning a "confidence band" into a decision function

Plain-English explanation. A score on its own does nothing — you have to decide something with it. We score the caller's word against every real city, sort the scores high-to-low, then sort each call into one of three zones. The cleverness is in the gaps: a high top score with a distant runner-up is a clear winner; a high top score with a close runner-up is genuinely ambiguous.

Why we need it (for CRM specifically). Before this, the agent had only two outcomes: "found a match, proceed" or "no match, read the whole list." There was no "I matched, but two are about equally likely." That missing middle is precisely where silent wrong-routing happened. The three-zone function adds that middle without changing the safety net.

How it works (analogy). Picture a race photo-finish. If one runner is clearly ahead, you call the winner instantly (AUTO_ACCEPT). If two are neck-and-neck across the line, you go to the replay and ask the judges (CONFIRM). If nobody even reached the line, there's no race to call (NO_MATCH). Two numbers decide which case you're in: how far ahead #1 is (the margin), and who's close enough to be "in the photo" (the band).

Jargon decoder.

  • threshold — a cutoff number a score must clear to count.
  • T_HIGH (0.86) — top score must be at least this to be a "clear winner."
  • MARGIN (0.08) — how far #1 must beat #2 to auto-accept. A close #2 means "ambiguous."
  • T_CONFIRM / T_FLOOR (0.66 / 0.55) — the plausible-but-unsure band, and the "nothing close" floor below which we give up.
  • BAND (0.06) — only cities within this distance of the top join the "did you mean?" question. This is the rule that keeps an unrelated city out of the question.
  • N_MAX (3) — never read more than three options aloud.
  • dataclass — a lightweight Python class for bundling named fields together (here, a RankResult holding the decision and the candidate list).

Annotated code — the decision. Note how only two outcomes leave the CONFIRM lane: a clear winner, or nothing close. Everything in between confirms — that's the deliberate lean toward asking in the gray zone:

def rank_candidates(spoken, candidate_values, field_name="city",
                    t_high=T_HIGH, margin=MARGIN, t_confirm=T_CONFIRM,
                    band=BAND, t_floor=T_FLOOR, n_max=N_MAX) -> RankResult:
    spoken_norm = normalize_place(spoken)
    best = {}                                # de-duplicate cities by their normalized form
    for v in candidate_values:
        vn = normalize_place(v)
        if not vn:
            continue
        s = similarity(spoken, v)            # the hybrid score from Concept 1
        if vn not in best or s > best[vn].score:
            best[vn] = Candidate(value=v, score=s)   # keep the original display spelling
    scored = sorted(best.values(), key=lambda c: c.score, reverse=True)  # high -> low

    if not spoken_norm or not scored:
        return RankResult("NO_MATCH", field_name, spoken, None, [], scored)

    top = scored[0]
    second = scored[1] if len(scored) > 1 else None
    gap = top.score - (second.score if second else 0.0)   # how far #1 beats #2

    if top.score < t_floor:                  # nothing even close -> fall back to the city list
        return RankResult("NO_MATCH", field_name, spoken, None, [], scored)

    if top.score >= t_high and (second is None or gap >= margin):  # clear winner
        return RankResult("AUTO_ACCEPT", field_name, spoken, top, [top], scored)

    # Everything else is ambiguous: voice ONLY the cities within `band` of the top, capped.
    band_members = [c for c in scored if (top.score - c.score) <= band][:n_max]
    return RankResult("CONFIRM", field_name, spoken, top, band_members, scored)
⚠️ Warning — the two gaps are not the same thing

MARGIN decides confident vs. ambiguous (how far ahead #1 is). BAND decides who gets invited into the question (who's close to #1). Confusing them is the classic way to build this wrong — you'd either confirm too often or drag unrelated cities into the prompt.

4 · The backend↔model contract (a JSON "disambiguation" block)

Plain-English explanation. The backend (deterministic Python we can unit-test) does the math and decides whether to confirm. The language model (Max's brain, which we can't fully predict) only speaks the decision. The two communicate through a small, fixed JSON shape — a contract. The backend fills it in; the prompt teaches Max how to read it.

Why we need it (for CRM specifically). We could have just handed the model the candidate list and let it decide whether to confirm. But a model is non-deterministic — it might confirm sometimes and not others, and we can't guarantee or test it. By computing the decision in Python, we get something deterministic, unit-testable, and tunable; the model is left with the one job it's good at — phrasing a natural sentence. This mirrors a pattern already in the codebase (find_units already returned an available_cities list the prompt reads).

How it works (analogy). Think of a kitchen ticket. The chef (backend) decides exactly what goes on the plate and writes a precise ticket. The waiter (model) doesn't re-decide the dish — they just present it warmly to the table. A clear ticket means the waiter can't improvise the kitchen's job.

The contract. Here is the exact block find_units now returns when two cities are confusable. Each candidate carries its rent range — that's how the agent will disambiguate by price instead of by name:

{
  "needs_confirmation": true,
  "field": "city",
  "spoken": "Saint-Lazar",
  "candidates": [
    { "value": "Saint-Lazare",  "rent_low": 1400, "rent_high": 1400 },
    { "value": "Saint-Lazaire", "rent_low": 1600, "rent_high": 1700 }
  ]
}

Annotated code — building the block. The backend translates the RankResult into the contract, attaching each city's rent range:

def _build_city_disambiguation(query, listings, available_cities) -> dict:
    rank = rank_candidates(query, available_cities, field_name="city")
    # ONLY surface a confirmation when the decision is genuinely "CONFIRM".
    # A clear winner (AUTO_ACCEPT) or junk (NO_MATCH) -> no extra turn.
    if rank.decision != "CONFIRM" or not rank.candidates:
        return _empty_disambiguation(query)   # {needs_confirmation: False, ...}

    rent_by_city = {}                         # gather every listing's rent, keyed by normalized city
    for r in listings:
        c = (r.get("city") or "").strip()
        if not c:
            continue
        rent_by_city.setdefault(normalize_place(c), []).append(float(r["monthly_rent"]))

    candidates = []
    for cand in rank.candidates:              # only the cities inside the band
        rents = rent_by_city.get(normalize_place(cand.value), [])
        candidates.append({
            "value": cand.value,
            "rent_low":  int(min(rents)) if rents else None,   # cheapest unit in that city
            "rent_high": int(max(rents)) if rents else None,   # priciest unit in that city
        })
    return {"needs_confirmation": True, "field": "city", "spoken": query, "candidates": candidates}
🔑 Key Concept — the homophone trap

If two cities sound alike when Max speaks them, the caller's spoken answer will be garbled the same way — so confirming by name resolves nothing. The fix: the question must be answerable as a number (rent), a yes/no, or an ordinal ("the first or the second?") — never another proper noun. That's why every candidate carries a rent range, and why the prompt forbids re-asking the city name.

5 · Optional dependencies & graceful degradation

Plain-English explanation. Our new libraries (rapidfuzz, jellyfish) make the matcher better, but the code should still run if they happen to be missing — just with a weaker score. We wrap their imports in try/except and set a flag; every place that uses them checks the flag first.

Why we need it (for CRM specifically). Different environments have different packages installed (we hit exactly this — see Bug #1). A leasing route that crashes because an optional scorer is absent would take down phone calls. Far better: fall back to the built-in difflib and keep answering. Tests can run anywhere; production gets the full hybrid.

How it works (analogy). A car with a backup camera is nicer, but if the camera unplugs, the car still drives — you just rely on your mirrors. The camera is "optional"; driving is not.

try:
    from rapidfuzz.fuzz import ratio as _rapidfuzz_ratio
    _HAS_RAPIDFUZZ = True                     # full strength available
except ImportError:
    _HAS_RAPIDFUZZ = False                    # missing -> this leg quietly scores 0

try:
    import jellyfish
    _HAS_JELLYFISH = True
except ImportError:
    _HAS_JELLYFISH = False

def _rapidfuzz_score(a_norm, b_norm):
    if not _HAS_RAPIDFUZZ:
        return 0.0                            # degrade: difflib in similarity() still carries us
    return _rapidfuzz_ratio(a_norm, b_norm) / 100.0   # rapidfuzz returns 0-100; we want 0-1

6 · Field-agnostic design (why Phase 2/3 are "free-ish")

Plain-English explanation. rank_candidates() doesn't care whether the strings it's ranking are cities, building names, or streets. It takes a field_name label purely so the result can say "this was a city decision." The same engine can later disambiguate buildings or streets — you just feed it a different list of values.

Why we need it (for CRM specifically). This is a multi-tenant SaaS: every manager uploads their own properties, so we never know their building or street names in advance. Because the candidate values are pulled live from each manager's database at call time (just like the city list already is), a brand-new manager with names we've never seen is handled automatically. The roadmap's later phases re-use this engine rather than reinventing it.

Phase 1 → caller says a CITY → rank against the manager's cities ✅ shipped this session Phase 2 → caller says a BUILDING → rank against the manager's buildings ⏳ same engine, new list Phase 3 → caller says a STREET → rank against the manager's streets ⏳ same engine, new list
⚠️ Warning — "free-ish," not free

The values supply themselves at runtime, but Phase 2 and 3 are still code you have to write and deploy — they won't appear on their own. Phase 2 needs a cross-field collision rule (a building name can contain a city token, e.g. "carré Saint-Laurent"); Phase 3 needs street-specific normalization (strip civic numbers like "2803", fold Rue/Bd/Av). See What's Next.

7 · The two-stage deploy pipeline

Plain-English explanation. A voice-agent change isn't live until two separate things are updated: (1) the backend code that the agent's tools call over HTTP, and (2) the assistant configuration stored on VAPI — the prompt and the tool definitions that tell the model how to behave. Update only one and you get a mismatch.

Why we need it (for CRM specifically). Our change touched both halves: the backend now returns the disambiguation block, and the prompt now reads it. If we'd deployed only the prompt, Max would look for a block the backend never sends (harmless — it falls back). If we'd deployed only the backend, the block would arrive but Max wouldn't know to act on it. Both must ship.

Jargon decoder.

  • Render — the cloud host running our FastAPI backend. Pushing the backend there is deploy stage 1 (you did this).
  • VAPI ("Voice API") — the hosted platform that wires the phone line to the STT, the model, and the voice. Each manager has their own "assistant" record there.
  • update_lease_agents.py — our script that pushes the latest prompt + tool config to every live assistant via direct HTTP PATCH (the VAPI SDK silently drops some fields, so we use raw HTTP). Deploy stage 2.
  • dry-run — a rehearsal that shows what would change without changing anything. Always do this before a production push.

🛠️ Step-by-Step Build Log

Every action this session, in order, with why each happens now and what would break if skipped.

Step 1 — Read the plan and the code it touches

Before writing a line, we read the design plan plus the five files it names: city_matching.py, leasing.py (the find_units route), vapi_agent_config.py (the prompt + tools), tests/test_city_matching.py, and requirements.txt, plus CODEBASE_CONTEXT.md for the big picture.

Why now: the project's own rule (in CLAUDE.md) is "read CODEBASE_CONTEXT.md before touching any code." Skip it and you re-explore the codebase from scratch and risk breaking an existing contract (like the available_cities safety net we had to leave intact).

Step 2 — Install the new libraries into the backend's virtual environment

A virtual environment (venv) is a project-local folder of Python packages, so this project's dependencies don't collide with other projects on the machine. We installed both libraries into it:

$ backend/.venv/Scripts/python.exe -m pip install "rapidfuzz>=3.0.0" "jellyfish>=1.0.0" Successfully installed jellyfish-1.2.1 rapidfuzz-3.14.5

Then we inspected jellyfish to see what phonetic functions it actually exposes — and learned it has metaphone but not double-metaphone (this became Bug #4):

$ python -c "import jellyfish; print([f for f in dir(jellyfish) if not f.startswith('_')])" ['damerau_levenshtein_distance', 'hamming_distance', 'jaccard_similarity', 'jaro_similarity', 'jaro_winkler_similarity', 'levenshtein_distance', 'match_rating_codex', 'match_rating_comparison', 'metaphone', 'nysiis', 'soundex']

Why now: you can't write code against a library you haven't installed and inspected. Skip it and the import works on your machine but crashes on a fresh checkout — and you'd guess the wrong function name.

Step 3 — Rewrite city_matching.py (the engine)

We kept the existing normalize_place() and city_matches() untouched (other routes depend on them) and added the hybrid similarity(), the swappable phonetic backend, the thresholds, the Candidate/RankResult dataclasses, and rank_candidates() — all shown in Concepts 1–3 and 5.

Why now: this is the foundation; the route and prompt both depend on it. Skip it and there's nothing to call.

Step 4 — Add the disambiguation block to find_units

We added two helpers (_empty_disambiguation, _build_city_disambiguation — Concept 4) and wired the block into all three return paths of the route (the empty-portfolio early return, the main return, and the error/except return) so the field is always present and the agent never reads undefined.

matches = matches[:5]
disambiguation = _build_city_disambiguation(query, listings, available_cities)
return {
    "found": bool(matches),
    "count": len(matches),
    "units": matches,
    "available_cities": available_cities,    # the existing safety net — left untouched
    "disambiguation": disambiguation,        # NEW: the confirm contract
}

Why now: the prompt (next step) reads this block, so it must exist first. Skip a return path and some calls return a response missing the field — a classic source of "works sometimes" bugs.

Step 5 — Teach the agent: tool schema + Step-2 prompt

Two edits in vapi_agent_config.py. First, we declared the new block in the tool's variableExtractionPlan (the schema that tells VAPI which fields to pull out of the JSON response) and expanded the tool description. Second — the important one — we rewrote the agent's Step-2 (Location match) instructions to read the block first, in a strict A→B→C order:

A) disambiguation.needs_confirmation is TRUE → confirm BEFORE going further. Ask ONLY about disambiguation.candidates. Disambiguate by a NUMBER, yes/no, or ordinal — NEVER by re-saying a place name. • rents differ → "one's around [rent_low A] a month, the other's about [rent_low B] — which?" • rents tie → "the first I mentioned, or the second?" • single weak → "just to confirm — did you mean the one around [rent] a month?" B) Otherwise, one or more matches (found is true) → acknowledge, continue to unit size. C) No match (found false, needs_confirmation false) → offer available_cities only.

Why now: the model can't act on a block it hasn't been told about. Skip it and the backend sends the contract but Max ignores it — the feature silently does nothing.

Step 6 — Add the Phase-0 corpus-generation script

We created backend/scripts/generate_stt_garble_corpus.py. It pulls a manager's real city/building names from the database, optionally round-trips each through a French-accent text-to-speech and back through Deepgram to manufacture realistic garble → truth pairs, and writes a labeled corpus to docs/testing/. With no API keys it falls back to a hand-labeled seed set so the file always exists.

Why now: the thresholds in Concept 3 are starting values; this script is the tool to tune them empirically later. Skip it and threshold-tuning has no data to learn from. (It doesn't gate the feature — Phase 1 ships with the defaults.)

Step 7 — Extend and run the tests

We added labeled cases to tests/test_city_matching.py: a portfolio with two near-homophones plus distinct cities, then assertions for each zone — must-AUTO_ACCEPT, must-CONFIRM (with the exact expected band), must-NO_MATCH, and a regression that an unrelated city (Châteauguay) never lands in a Saint-Lazare band.

# Two genuinely near-homophone cities + clearly-distinct ones. Banding must confirm
# Saint-Lazare/Saint-Lazaire TOGETHER while never dragging Chateauguay into the question.
PORTFOLIO = ["Saint-Lazare", "Saint-Lazaire", "Châteauguay", "Montréal", "Longueuil", "Laval"]

# Clear winner -> no extra turn:
_check_rank("Montreal", PORTFOLIO, "AUTO_ACCEPT")
# Confusable pair -> confirm, and ONLY those two are in the band:
_check_rank("Saint-Lazar", PORTFOLIO, "CONFIRM", want_band=["Saint-Lazare", "Saint-Lazaire"])
# Severe garble -> fall through to the city list:
_check_rank("thing on low", PORTFOLIO, "NO_MATCH")

Run with the venv's Python (so the phonetic libraries are present):

Why now: tests lock in the behavior before deploy, so a future change that breaks the band fails loudly. Skip it and you ship on hope.

🐛 Bug Journal

This was a "new code" session more than a "modify old code" session, so there were no logic bugs in the shipped feature — the tests passed first try. But shipping real software means fighting the environment, and we hit seven distinct hitches worth dissecting. Notice the pattern: almost every one is tooling/environment, not algorithm. That's normal, and recognising it keeps you calm.

🐛 Bug #1 — ModuleNotFoundError: No module named 'fastapi'

🚨 The Symptom. We tried to import the leasing route to test the helper directly:

$ .venv/Scripts/python.exe -c "from app.routes.leasing import _build_city_disambiguation" ModuleNotFoundError: No module named 'fastapi'

🔍 The Diagnosis. Odd — this is a FastAPI backend, how is FastAPI missing? We listed what the venv actually contained:

$ .venv/Scripts/python.exe -m pip list | grep -iE "fastapi|supabase|rapidfuzz" jellyfish 1.2.1 RapidFuzz 3.14.5 supabase 2.27.2 # fastapi: not present

🧠 The Root Cause. The backend/.venv on this machine is a partial environment — it has Supabase, Pydantic, and now our two new libs, but not the full web stack. The real backend runs elsewhere (and on Render). Importing app.routes.leasing triggers from fastapi import ... at the top of the file, which fails. The lesson concept: a module's top-level imports run the moment you import it, even if you only want one tiny pure helper from the bottom.

🔧 The Fix. Don't import the whole route. (1) Use py_compile to confirm the file has no syntax errors — it compiles without importing FastAPI. (2) Re-implement the pure helper's logic inline against only city_matching (which the venv does have) to verify behavior:

$ .venv/Scripts/python.exe -m py_compile app/routes/leasing.py && echo "COMPILE OK" COMPILE OK $ # then ran a standalone snippet that imports only city_matching -> printed the exact block CONFIRM: {'needs_confirmation': True, ... 'candidates': [...rent_low 1400...]}

🛡️ The Lesson. When an import explodes, ask "what does importing this drag in?" — not just "what did I ask for." To test pure logic, isolate it from heavy frameworks: py_compile for syntax, a minimal snippet for behavior. Keeping helpers dependent only on lightweight modules (here, city_matching) makes them testable anywhere.

🐛 Bug #2 — cd: backend: No such file or directory

🚨 The Symptom. A command that worked a minute ago suddenly failed:

$ cd backend && .venv/Scripts/python.exe ... /usr/bin/bash: line 8: cd: backend: No such file or directory

🔍 The Diagnosis. We printed the working directory and found we were already inside backend — so cd backend was trying to enter backend/backend, which doesn't exist.

🧠 The Root Cause. The shell tool's working directory persists between calls. An earlier compound command (cd backend && ...) left the shell parked in backend/. The next call's relative paths were then resolved from there — the classic "stateful shell" gotcha.

🔧 The Fix. Stop assuming the starting directory. Either reference paths relative to the actual current directory, or pwd first to orient, or use absolute paths.

$ pwd /c/Users/BIT/Coding/Leadpipe_CRM/backend # aha — already here

🛡️ The Lesson. Persistent shells are convenient but stateful. Prefer absolute paths for anything important, and when a path error appears "out of nowhere," check pwd before anything else.

🐛 Bug #3 — Edit refused: "File has not been read yet"

🚨 The Symptom. Editing CODEBASE_CONTEXT.md failed even though we'd read it earlier:

tool_use_error: File has not been read yet. Read it first before writing to it.

🔍 The Diagnosis & 🧠 Root Cause. CODEBASE_CONTEXT.md is large; the earlier read was truncated (a partial view of the first ~800 lines). The editing tool requires a confirmed, current read of the region you're changing — a partial/older read doesn't count, which is a safety feature to stop you editing stale content.

🔧 The Fix. Re-read just the target region (a handful of lines around the exact text), then edit. Small, precise reads beat re-reading a 1,000-line file.

🛡️ The Lesson. "Read before write" guards exist precisely so you don't clobber a file that changed under you. When blocked, satisfy the guard with a tight, fresh read rather than fighting it.

🐛 Bug #4 — The plan asked for Double Metaphone; the library doesn't have it

🚨 The Symptom. The design plan said, in writing, "Double Metaphone (jellyfish)." But inspecting jellyfish (Step 2) showed only metaphone — no double_metaphone.

🧠 The Root Cause. A documentation/assumption mismatch. Double Metaphone lives in other packages; the installed jellyfish ships single Metaphone. The plan author conflated the family name with the specific function.

🔧 The Fix. Use single jellyfish.metaphone — it's still sound-based (the right axis), and it already collapses our key pair: lazare and lazaire both encode to LSR. Crucially, we kept the encoder swappable (_PHONETIC_ENCODER + a set_phonetic_encoder() setter) so a true Double Metaphone or French Beider-Morse can replace it later with a one-line change.

🛡️ The Lesson. Plans are hypotheses; verify library APIs against reality before committing. And when you must substitute, hide the choice behind a seam (one swappable variable) so the substitution doesn't ripple through your code.

🐛 Bug #5 — A dataclass field named field shadowing dataclasses.field

🚨 The Symptom. No crash — but a footgun spotted on review. Our result class had an attribute literally named field, sitting two lines above a call to field(default_factory=list) imported from the dataclasses module.

@dataclass
class RankResult:
    decision: str
    field: str                               # <-- same name as dataclasses.field!
    spoken: str
    ...
    scored: list = field(default_factory=list)   # relies on `field` STILL meaning the import

🧠 The Root Cause. It happened to work because a bare annotation (field: str with no =) doesn't actually bind the name field in the class body — so the later field(...) still resolved to the import. But that's a subtle rule; one stray assignment and it would silently break. Fragile by construction.

🔧 The Fix. Rename the attribute to field_name (which also reads better next to field_name="city" elsewhere), then re-run the tests to confirm nothing depended on the old name.

$ .venv/Scripts/python.exe ../tests/test_city_matching.py >/dev/null && echo "TESTS PASS" TESTS PASS

🛡️ The Lesson. Don't name a variable the same as a function you're using in the same scope, even when the language lets you get away with it. "Works because of an obscure rule" is a future bug. Clear names > clever names.

🐛 Bug #6 — A stray placeholder glyph in the prompt

🚨 The Symptom. While writing the Step-2 prompt, an editing slip left a stray box character in a sentence: "same/▢missing rent".

🧠 The Root Cause. A typo introduced during a large multi-line edit — the kind of thing that's invisible at a glance but ends up in the model's instructions, where it could confuse phrasing.

🔧 The Fix. A one-line replacement to clean wording: "the same or missing rent". We then re-read the whole edited block to confirm it was clean.

🛡️ The Lesson. Prompts are code too. Proofread edited instruction text the same way you'd review a function — read the final result back, don't trust that the edit landed as intended.

🐛 Bug #7 — UnicodeEncodeError: 'charmap' codec can't encode '→'

🚨 The Symptom. Trying to print the prompt block to verify it, the terminal threw:

UnicodeEncodeError: 'charmap' codec can't encode character '→' ... maps to <undefined>

🧠 The Root Cause. → is the arrow "→". The Windows console defaults to the legacy cp1252 text encoding, which has no arrow character. The file was perfectly fine (it's UTF-8); only printing it to this console failed. A false alarm about the wrong thing.

🔧 The Fix. Don't verify file content by printing through a lossy console. Use the file-reading tool (which handles UTF-8) to inspect the block instead.

🛡️ The Lesson. Separate "is the file wrong?" from "is my terminal mangling the display?" An encoding error on output rarely means the data is bad. On Windows, expect cp1252 console limits and read files with a UTF-8-aware tool.

🧯 Troubleshooting / Common Errors

ModuleNotFoundError: No module named 'rapidfuzz' (or jellyfish)

The phonetic libs aren't installed in the Python you're running. Install into the right environment: backend/.venv/Scripts/python.exe -m pip install rapidfuzz jellyfish. On Render, make sure both are pinned in requirements.txt. The code won't crash without them (it degrades to difflib) — but you lose the phonetic rescue.

ModuleNotFoundError: No module named 'fastapi' when testing a route helper

You're importing a whole route module, which pulls in FastAPI. Test pure helpers in isolation, or use py_compile for a syntax check. See Bug #1.

The agent never asks "did you mean?" even for sound-alikes

Two likely causes. (1) The backend deployed to Render is the old one and isn't returning disambiguation — redeploy. (2) The two cities aren't actually close enough to land in CONFIRM — print rank_candidates(...).scored to see the real scores, and check your thresholds.

The agent asks "did you mean?" on almost every call

Thresholds are too eager. Generate the corpus with generate_stt_garble_corpus.py, look at the decision distribution, and raise T_CONFIRM / widen MARGIN so more calls auto-accept. Track confirm-rate-per-call as your guard metric.

Deploy says [FAIL] HTTP 401 or serverMessages mismatch

401 = a bad/expired PRIVATE_VAPI_API key in .env. A serverMessages mismatch means the pushed config didn't take — re-run; the script verifies each assistant after patching and reports per-agent OK/FAIL.

A path command fails with "No such file or directory" out of nowhere

The shell's working directory persisted from a previous cd. Run pwd to orient, then use a correct relative or absolute path. See Bug #2.
