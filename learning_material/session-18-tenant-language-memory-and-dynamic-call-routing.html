Tenants Remember — Language Memory & Dynamic Call Routing

After Session 17, both languages worked — but every caller, on every call, still had to answer "English or French?" This session turns that one-time question into a stored preference: a tenant's first verified call locks their language, and every future call — inbound and outbound — starts directly with the right assistant, in the right language, with no gate. To build it we add a write-once database column, tag each assistant's verification tool with a language marker, teach the phone number to ask our backend who should pick up (Vapi's assistant-request webhook), and choose per-call greetings with assistantOverrides. Then we deploy it in an order where a single swapped step would take the phone line down — and prove the whole thing works with five tests against production, no phone required.

🔴 Advanced ⏱️ Estimated: 80–95 min Requires: Sessions 01–17 🐛 2 Bug Stories

🧭 B · Session Overview

We built per-tenant language preference routing for the complaint agent, end to end:

  • Migration 032: a preferred_language column on tenants (en / fr / NULL) with a CHECK constraint.
  • Deterministic capture: each assistant's Verify_phone_number tool URL now carries &language=en|fr; the backend records the preference on the tenant's first valid verification — and never overwrites it.
  • A third assistant: "Complaint Agent EN (Alex)" — English-locked, no gate, for returning English tenants.
  • Dynamic inbound routing: the number's static binding is gone; Vapi now POSTs an assistant-request to our new /voice/inbound-router, which returns the caller's assistant.
  • Outbound routing: /voice/call/outbound does the same lookup before dialing.
  • Ordered deploy: migration → env vars → backend → number repoint, plus a provisioning script with a --rollback that restores the old world in one command.
  • Production verification: five API-level tests against the live system, using a seed tenant, then restored to its original state.

The behavior, in one table

Tenant who chose FrenchFrench assistant — "Bonjour, ici Alex de l'équipe de gestion immobilière…"French assistant, same greeting

Why this matters for a CRM

Language preference is customer data, and asking for the same data twice is the cardinal CRM sin — it tells the customer you don't remember them. In Québec it's sharper still: greeting a francophone tenant in English on their tenth call reads as indifference. This feature is the voice-channel version of a CRM remembering a contact's timezone or salutation — small field, outsized respect.

Learning objectives

  • Explain Vapi's three inbound routing modes (static assistant, squad, server-resolved) and when to use each.
  • Capture user preferences deterministically through a tool-URL side channel instead of trusting the LLM to report them.
  • Implement write-once semantics and defend them at the query level.
  • Use assistantOverrides to adapt one saved assistant to different call contexts.
  • Sequence a multi-system deploy (DB → env → code → traffic) so no step depends on a later one.
  • Test a phone feature end-to-end from a terminal, without placing a call.

🧠 D · Concepts Introduced This Session

D1 · The assistant-request webhook — a number that phones home

Plain English: until now, the phone number's config statically named its assistant. Vapi offers a third routing mode: leave assistantId empty and set a server.url on the number. Now, every time someone dials in, Vapi pauses and sends your backend a webhook — {"message": {"type": "assistant-request", "customer": {"number": "+1514…"}}} — asking, literally, "who should take this call?" Your server answers with {"assistantId": "…"} and the call proceeds with that assistant.

Why we need it: per-caller routing cannot be static by definition — the right assistant depends on who is calling, which is only known at ring time. The lookup (phone → tenant → preference) lives in our database, so our backend must be the decision point.

Analogy: a hotel switchboard operator. The old setup was a doorbell wired straight to one receptionist. Now the call reaches an operator (our router) who checks the guest file first: Mme Gagnon → put her through to the French-speaking concierge; unknown caller → the front desk that asks the language question. The caller never sees the lookup; they just hear the right voice.

INBOUND, AFTER THIS SESSION caller dials +14382567782 │ ▼ Vapi looks up the number: assistantId = null, server.url = …/voice/inbound-router │ ▼ POST { message: { type: "assistant-request", customer: { number: "+1514…" }}} our backend: phone → tenants.preferred_language │ ├── "fr" → { assistantId: FR, assistantOverrides: { firstMessage: "Bonjour, ici Alex…" }} ├── "en" → { assistantId: EN } └── NULL/err → { assistantId: ENTRY } ← fail-safe: worst case = the old gate
⚠️ Warning — the router is now on the critical path of every inbound call

Vapi waits only a few seconds (~7.5 s) for the assistant-request answer. If the backend is down or cold-starting (Render can spin down idle services), inbound calls fail entirely. This is the price of dynamic routing: you traded a static config for an availability dependency. Keep the service warm, keep the handler fast (one indexed query), and make it return HTTP 200 with the entry assistant on any internal error — a wrong-language answer beats a dead line.

D2 · Preference capture via URL tagging — don't ask the LLM what it heard

Plain English: how do we know which language the tenant chose? The tempting answer: have the agent report it ("call a save_language tool"). But that trusts an LLM to remember to call a tool — exactly the failure class Session 17 was about. Instead we exploit something structural: each assistant already is a language. The FR assistant only ever conducts French calls. So we stamp the language into each assistant's Verify_phone_number tool URL — …/flats/verify-phone?phone_number={{customer.number}}&language=fr on the FR assistant, &language=en on the entry and EN assistants. When verification succeeds, the backend reads the tag off the URL. No LLM judgment involved anywhere.

Why we need it: the preference decides all future routing — it must be correct. The tag is correct by construction: the only way a language=fr verify can fire is if the caller is already on the French assistant, which only happens if they chose French. It also costs zero latency and zero new tools.

Analogy: pre-printed forms. Instead of asking the clerk to write down which language the meeting was held in (they might forget, or misremember), the French office simply uses forms with "FR" pre-printed in the corner. Whichever form lands in the archive tells you the language — because only that office stocks that form.

def build_complaint_tools(backend_url: str, language: str = "en") -> list:
    # `language` tags the verify call with the assistant's language so the backend
    # can record the tenant's preference on their first verified call.
    # Entry + EN assistants pass "en"; the FR assistant passes "fr".
    return [
        {
            "type": "apiRequest",
            "name": "Verify_phone_number",
            ...
            # {{customer.number}} is filled by VAPI at call time; &language= is baked
            # in when the assistant is provisioned — a per-ASSISTANT constant.
            "url": f"{backend_url}/flats/verify-phone"
                   f"?phone_number={{{{customer.number}}}}&language={language}",
            ...
        },
        ...
    ]
🔑 Key Concept — deterministic side channels beat model self-reporting

Whenever a fact is implied by which code path is running, capture it from the path — a URL parameter, a header, a column default — never from the model's narration of events. The model's job is conversation; the plumbing's job is truth.

D3 · Write-once semantics — first answer wins, forever

Plain English: the spec says the first choice is binding: "in any future call, the English agent will only handle my call." So the column is written only when it is currently NULL. Every later verification — even one tagged with the other language — leaves it untouched. In code that's one guard: if language in ("en","fr") and row.get("preferred_language") is None.

Why we need it: without the guard, the value would be last-write-wins, and the routing would feed back into the data: a French-preference tenant is always routed to the FR assistant, whose verify always sends fr… which sounds stable — until any odd path (an outbound call with an explicit assistant, a shared phone, a manager test) writes the other tag and silently flips the tenant's language. Write-once makes the preference an immutable fact with one clear origin story; changing it becomes a deliberate admin action (set the column back to NULL) rather than a side effect.

Analogy: the language field on a passport application. It's captured once, at issuance, and printed. Border agents (the router) read it on every trip; they don't re-interview you about it. If you genuinely change languages, you file for a new passport — an explicit act, not something that happens because one border guard heard you say "bonjour".

if match:
    current_time_ist = datetime.now(IST).strftime("%Y-%m-%dT%H:%M:%S")

    # First verified call locks the tenant's complaint-agent language (migration 032).
    # Never overwritten afterwards — routing keeps the tenant on their chosen assistant.
    tenant_row = tenant_resp.data[0]
    if language in ("en", "fr") and tenant_row.get("preferred_language") is None:
        try:
            # Service-role client: this endpoint is called by VAPI, no user JWT exists.
            db.table("tenants").update({"preferred_language": language}) \
              .eq("uuid", tenant_row["uuid"]).execute()
        except Exception as pref_err:
            # Preference recording must NEVER break verification — the call comes first.
            print(f"[WARN] verify_phone: failed to store preferred_language: {pref_err}")

D4 · assistantOverrides — one saved assistant, many entrances

Plain English: the FR assistant's saved first message is "Parfait, je continue en français. Quel est votre numéro d'appartement?" — "Perfect, I'll continue in French." That sentence only makes sense mid-conversation, right after a handoff. A returning French tenant whose call starts directly on the FR assistant would hear "Perfect, I'll continue…" as the very first words of the call — answering a question nobody asked. Vapi's fix: both the assistant-request response and the outbound call API accept assistantOverrides, a per-call patch on top of the saved assistant. We override just firstMessage with a proper cold-open: "Bonjour, ici Alex de l'équipe de gestion immobilière. Quel est votre numéro d'appartement?"

Why we need it: the alternative is a fourth assistant (FR-direct vs FR-handoff) — double the French maintenance surface for one differing sentence. Overrides let one saved assistant serve both entrances, with the entrance-specific line supplied by whoever routed the call there.

Analogy: the same actor with two entrance lines. Walking into an ongoing scene: "as I was saying…". Opening the play: "Good evening, ladies and gentlemen." Same costume, same script for the rest — the director (our router) whispers which opening line to use.

response: dict = {"assistantId": assistant_id}
if first_message:
    # Per-call patch: replaces ONLY firstMessage; prompt, tools, voice, transcriber
    # all come from the saved assistant. camelCase because this JSON goes to VAPI.
    response["assistantOverrides"] = {"firstMessage": first_message}
return response  # always HTTP 200 — a routing answer, never an error page

D5 · Migration-tolerant queries — code that survives being deployed "too early"

Plain English: the new backend code SELECTs preferred_language. If that code ever runs against a database where migration 032 hasn't been applied, PostgREST (the REST layer over Postgres that Supabase uses) rejects the whole query — column doesn't exist — and since this SELECT sits inside phone verification, the crash would look like "verification failed" for every caller. So the tenant lookup tries the full column list first and falls back to the old list on any error.

Why we need it: code and schema deploy through different pipelines (git push vs SQL editor), so there is always a window where one is ahead. You either enforce ordering perfectly forever, or write the read side to tolerate both worlds during the window. For a route as critical as verify-phone, tolerance wins.

# preferred_language selected in a migration-tolerant way (migration 032)
def _tenant_lookup(cols: str):
    # One helper, two call sites: primary lookup by flat FK, fallback by tenant_uuid.
    resp = db.table("tenants").select(cols).eq("flat_uuid", flat_uuid).execute()
    if not resp.data and flat.get("tenant_uuid"):
        resp = db.table("tenants").select(cols).eq("uuid", flat["tenant_uuid"]).execute()
    return resp

try:
    # New world: column exists → we also learn the current preference (for the
    # write-once guard) in the same round-trip.
    tenant_resp = _tenant_lookup("uuid, phone, preferred_language")
except Exception:
    # Old world: column missing → verification still works; preference recording
    # silently no-ops until the migration lands. NEVER let bookkeeping kill the call.
    tenant_resp = _tenant_lookup("uuid, phone")
💡 Tip — the "expand, then contract" habit

The general recipe for schema changes with zero downtime: expand (add the column, nullable, no code depends on it) → deploy code that works with and without it → backfill/enable → much later, contract (make it required, drop fallbacks). Our fallback SELECT is the middle step made explicit.

D6 · Deploy ordering — four systems, one safe sequence

Plain English: this feature touches four systems that deploy independently: the database (Supabase), environment variables (Render), backend code (git push → Render), and Vapi config (our scripts). Each step must only depend on steps already done. One ordering is safe; most others break live traffic. The dangerous edge: re-pointing the phone number to /voice/inbound-router before that route exists in production = every inbound call fails — precisely bug 1 from Session 17, self-inflicted this time.

THE SAFE SEQUENCE (each step only leans backwards) 1. DB migration 032 column exists; nothing reads it yet — inert 2. Vapi: patch entry+FR tools, &language= param sent; old backend ignores unknown create EN assistant query params — harmless. EN assistant: unrouted — inert 3. Render env vars read only by code that ships next — inert 4. Deploy backend router live but nothing calls it yet — inert 5. Repoint number (--route-number) ← the ONLY step that moves live traffic 6. Verify + real-call tests Swap 4 and 5 → dead phone line until the deploy finishes. Every step before 5 is invisible to callers. That's the design goal: stack up inert changes, then flip one switch — with a one-command rollback.

Analogy: replacing a bridge. You build the new bridge next to the old one (steps 1–4: nobody drives on it, mistakes cost nothing), and only then move the traffic barriers (step 5). Nobody closes the old bridge first and then starts pouring concrete.

🔑 Key Concept — separate "making it exist" from "sending traffic to it"

Every risky launch gets safer when you split it into inert-preparation steps and exactly one traffic-flip step. The flip should be small, fast, verifiable, and reversible — ours is one PATCH with a scripted --rollback.

🛠️ E · Step-by-Step Build Log

Step 1 — Migration 032: the memory cell

Why now: everything else reads or writes this column; it must exist first (and it's inert until code uses it — the perfect first domino).

-- 032: Per-tenant complaint-agent language preference.
-- Recorded the first time a tenant passes phone verification on a language-specific
-- complaint assistant; once set it is never overwritten by calls.
-- NULL = tenant has never chosen — they get the bilingual language gate.

ALTER TABLE tenants
  ADD COLUMN IF NOT EXISTS preferred_language text          -- nullable on purpose: NULL means "unset"
  CHECK (preferred_language IN ('en', 'fr'));               -- DB-level guard: only two legal values, ever

COMMENT ON COLUMN tenants.preferred_language IS             -- self-documenting schema for the next reader
  'Complaint-agent language chosen on the tenant''s first verified call: en | fr. NULL = not chosen yet.';

What breaks if skipped: nothing crashes immediately (the tolerant SELECT falls back) — but no preference is ever stored, so every caller gets the gate forever and the feature silently doesn't exist. The quiet failure mode is why we verified the column with a live SELECT before testing.

Step 4 — Record the preference in verify_phone

Step 5 — The shared routing brain: _complaint_assistant_for_phone

Why one helper: inbound and outbound must route identically or a tenant would hear French when calling in and the gate when called back. One function, two callers, zero drift.

def _complaint_assistant_for_phone(svc_db: Client, caller_number: str | None):
    """Returns (assistant_id, first_message_override | None) for this caller."""
    entry = (settings.VAPI_COMPLAINT_ASSISTANT_ID, None)   # the universal fallback
    if not caller_number:                                  # anonymous/withheld number →
        return entry                                       # gate, like any stranger
    try:
        pref = None
        # Fast path: exact match on the stored phone (most rows are E.164 already).
        rows = (svc_db.table("tenants")
                .select("phone, preferred_language")
                .eq("phone", caller_number)
                .not_.is_("preferred_language", "null")    # only rows that HAVE a preference
                .limit(1).execute())
        if rows.data:
            pref = rows.data[0]["preferred_language"]
        else:
            # Slow path: stored phones aren't always exact E.164 ("514-555-0102"),
            # so reuse the SAME digits-suffix matcher verify_phone trusts.
            from app.routes.flats import _phones_match
            candidates = (svc_db.table("tenants")
                          .select("phone, preferred_language")
                          .not_.is_("preferred_language", "null").execute())
            for row in candidates.data or []:
                if _phones_match(caller_number, row.get("phone", "")):
                    pref = row["preferred_language"]; break

        if pref == "fr" and settings.VAPI_COMPLAINT_FRENCH_ASSISTANT_ID:
            from app.services.vapi_agent_config import COMPLAINT_FRENCH_DIRECT_FIRST_MESSAGE
            return (settings.VAPI_COMPLAINT_FRENCH_ASSISTANT_ID,
                    COMPLAINT_FRENCH_DIRECT_FIRST_MESSAGE)  # FR + cold-open greeting
        if pref == "en" and settings.VAPI_COMPLAINT_ENGLISH_ASSISTANT_ID:
            return (settings.VAPI_COMPLAINT_ENGLISH_ASSISTANT_ID, None)
    except Exception as e:
        # ANY failure (DB down, column missing, bad data) → log and fall through.
        print(f"[WARN] complaint language routing failed for {caller_number}: {e}")
    return entry   # fail-safe: worst case is the pre-feature behavior, never a dead call

Step 6 — The inbound router endpoint

@router.post("/voice/inbound-router")
async def complaint_inbound_router(request: Request, svc_db: Client = Depends(get_service_db)):
    """VAPI assistant-request handler for the complaint number. Always HTTP 200;
    any failure falls back to the entry assistant so inbound never breaks."""
    try:
        payload = await request.json()
        message = payload.get("message", {})
        if message.get("type") != "assistant-request":   # other event types may arrive;
            return {}                                     # acknowledge and ignore them
        # Caller number location varies slightly by payload shape — check both spots.
        customer = message.get("customer") or message.get("call", {}).get("customer") or {}
        caller_number = customer.get("number")
        assistant_id, first_message = _complaint_assistant_for_phone(svc_db, caller_number)
        response: dict = {"assistantId": assistant_id}
        if first_message:                                 # only FR needs a greeting override
            response["assistantOverrides"] = {"firstMessage": first_message}
        return response
    except Exception as e:
        print(f"[ERROR] inbound-router failed: {type(e).__name__}: {e}")
        return {"assistantId": settings.VAPI_COMPLAINT_ASSISTANT_ID}   # gate beats silence

Why now: must exist in production before the number points at it (concept D6). Note the family resemblance to every VAPI endpoint since Session 08: always 200, fail toward the least-bad behavior.

Step 8 — The provisioning script

backend/scripts/provision_complaint_language_routing.py — same house pattern as Sessions 14–16 (direct HTTP, --dry-run), with the traffic flip isolated behind its own flag:

def route_number(dry_run: bool) -> None:
    # THE traffic flip: clear the static binding AND point server.url at the router.
    # Run ONLY after the backend with /voice/inbound-router is live (deploy ordering!).
    body = {"assistantId": None,
            "server": {"url": f"{BACKEND_URL}/voice/inbound-router"}}
    resp = httpx.patch(f"{VAPI_API_BASE}/phone-number/{number_id}",
                       headers=_headers(), json=body, timeout=30)

def rollback(dry_run: bool) -> None:
    # One command back to the pre-feature world: static entry binding, no server url.
    body = {"assistantId": entry_id, "server": None}
    httpx.patch(f"{VAPI_API_BASE}/phone-number/{number_id}",
                headers=_headers(), json=body, timeout=30)

Step 9 — Deploy in order, wait for the route, flip the switch

Migration run in the Supabase SQL editor and env vars added (steps 1 & 3 of the sequence, done by the project owner); code pushed as commit deef01c0. Then, instead of guessing when Render finished, we polled the new route until it answered — and only then repointed:

# Probe the new endpoint every 20s. A non-assistant-request POST returns {} with
# HTTP 200 once the new code is live — and 404 while the old code still runs.
for i in $(seq 1 30); do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" -X POST \
    "https://tenant-management-mvp.onrender.com/voice/inbound-router" \
    -H "Content-Type: application/json" -d '{"message":{"type":"status-update"}}')
  echo "attempt $i: HTTP $CODE"
  [ "$CODE" = "200" ] && break

done

Step 10 — Prove it on production, without a phone

🐛 F · Bug Journal

A mostly clean build — the two stories below are a discovered latent defect and a caught-before-runtime coding slip. Fewer bugs than Session 17 for a structural reason: we were adding new paths guarded by fallbacks, not rewiring existing behavior.

Bug 1 — Three flats named "102": verification fails for the wrong tenant

🚨 The Symptom

During production testing, we picked tenant Marie-Claude Gagnon (flat "102", phone 514-555-0102) and simulated the FR assistant's verify call. Expected status: "valid". Got:

{"result":"Verification failed: phone number does not match the registered tenant for this flat.","status":"invalid"}
🔍 The Diagnosis
  • Two suspects: the phone matcher (her number is stored as 514-555-0102, not E.164) or the flat lookup. Checked the matcher first — _phones_match is digits-suffix-aware; +15145550102 vs 514-555-0102 matches fine. Not it.
  • Queried the database directly: flats?flat_number=ilike.102 → three rows. Three different flats, in different buildings, all named "102".
  • Read verify_phone: it looks up the flat by number globally and takes flat_resp.data[0] — the first flat 102, whose registered tenant is someone else entirely. Marie-Claude's flat 102 was row three. Mystery solved.
🧠 The Root Cause

Migration 024 made flat numbers unique per building — the right rule for the web app, where every screen has building context. But a phone call has no building context: the voice flow asks only "what's your flat number?" and verify_phone resolves it globally, silently betting that flat numbers are globally unique. They aren't. The class of bug: a uniqueness assumption imported from one context (web UI) into another (voice) where it doesn't hold. It predates this session — our routing tests merely surfaced it.

🔧 The Fix

Deliberately not fixed this session — it's a pre-existing defect in a critical path, out of scope for a routing feature, and any fix (e.g., try every flat with that number and match the caller's phone against each tenant) changes verification semantics and deserves its own tested change. We switched to the tenant actually registered on the first flat 102 for testing, and documented the defect. Honesty note: "not fixed, documented, scoped for later" is a legitimate resolution — pretending otherwise is how bugs get half-fixed at midnight.

🛡️ The Lesson

When a lookup returns a list and the code takes [0], ask: what makes the first row the right row? If the answer is "nothing, we assume there's only one," you've found a bug waiting for data to trigger it. And: testing a new feature on production data is also an audit of old features — budget time for what it digs up.

Bug 2 — The variable that almost wasn't: lang_first_message

🚨 The Symptom

No runtime symptom — this one was caught during the edit, which is exactly the point. The first draft of the outbound change read:

# complaint branch sets lang_first_message; the LEASE branch never does…
first_message = req.first_message or (lang_first_message if req.agent != "lease" else None)
🔍 The Diagnosis + 🧠 Root Cause

The conditional only evaluates lang_first_message when agent != "lease", so Python never raises NameError at runtime — lazy evaluation saves it, today. But the code's correctness now depends on an invisible pact between a branch 30 lines up and the exact short-circuit shape of one expression. The next person who "simplifies" the conditional, or reorders branches, ships a NameError in the lease path. Root cause class: a variable whose definedness depends on control flow — legal, working, and a trap.

🔧 The Fix
# In the LEASE branch, define it explicitly:
lang_first_message = None       # lease calls have no language-preference opener

# …and the expression collapses to something a reviewer parses in one glance:
first_message = req.first_message or lang_first_message
🛡️ The Lesson

Every variable should be obviously defined on every path that can read it — "the interpreter happens not to look" is not a definition. Initialize at branch level, keep expressions dumb. Static analyzers (pylint's possibly-used-before-assignment, mypy) flag exactly this; a linter in CI would have caught the first draft automatically.

Write a query (or a small script against PostgREST) that reports, per manager: how many tenants have preferred_language = 'en', 'fr', and NULL. This is the adoption dashboard for the feature.

Hints

SQL: SELECT manager_id, preferred_language, COUNT(*) FROM tenants GROUP BY 1, 2. Via PostgREST you'll need one request per value or the select=manager_id,preferred_language trick plus client-side counting.

🟡 Stretch — let tenants switch languages politely

Design (prompt + backend) a change_language flow: if a locked-English tenant speaks French for two consecutive turns, the EN assistant offers — once — to switch permanently, and a confirmation updates the column and hands the live call to the FR assistant.

Hints

You need: a handoff tool on the EN assistant (mirror _complaint_handoff_tool), an apiRequest tool that PATCHes the preference (design the endpoint — and decide: does write-once bend here? This is an explicit user action, which is exactly the exception write-once allows), and a prompt rule with a strict once-only bound — remember Session 17's Bug 3.

🔴 Challenge — fix Bug 1 properly

Rework verify_phone for duplicate flat numbers: fetch all flats matching the number, check the caller's phone against each flat's registered tenant, and verify against the (unique) flat whose tenant matches. Define the semantics when the phone matches tenants in two different flats "102", write the code, and list the test cases you'd need before daring to deploy it.

Hints

The loop is easy; the semantics are the work. Zero matches → invalid (unchanged). One match → valid, and note the matched flat_uuid now comes from the tenant side. Two matches (same person rents two flats "102" in different buildings!) → you must either ask a disambiguating question via the agent or pick by most-recent lease — argue your choice. Don't forget the preference-recording line must use the matched tenant row.
