Section 1 — What You Are Building

Modules 02–08 taught the ownership model as it was designed: every flat belongs to a building, every building to a property group, every group to a manager, and RLS policies walk that chain to decide who sees what. This module teaches what happened when reality diverged from that design — and the discipline that grew out of fixing it: evolving RLS policies safely, anchoring ownership on the most stable entity, and shipping schema changes as ordered, tolerant migrations.

The ownership chain (as designed) What broke it ──────────────────────────────── ───────────────────────────── manager_profiles (auth.uid()) "standalone units" — flats └─ properties_list (manager_id) created outside a full └─ buildings (property_id) group→building chain. The └─ flats (building_id) RLS policy walked a chain └─ tenants, complaints that didn't exist for them, so INSERTs were rejected.

Three real production incidents drive this module:

  • Session 7: creating a unit failed with an RLS rejection because the policy assumed a chain some rows don't have. Fixed with an additive policy plus a backfill migration that recovered orphaned rows.
  • Session 11: caller identity was being resolved through the tenant, which moves, churns, and can be missing. Refactored to flat-anchored ownership — resolve through the entity that never moves.
  • Session 18: migration 032_tenant_preferred_language.sql added a column that live code would read before the migration ran everywhere — which forced the discipline of migration-tolerant queries and a four-system deploy order.

Section 2 — Concept Deep-Dives

The ownership chain, and why RLS policies encode assumptions

An RLS policy is a WHERE clause that runs on every query — and every WHERE clause encodes an assumption about the data's shape. The original flats policy said, in effect:

-- "You may touch a flat if you own the building's property group"
USING (
  building_id IN (
    SELECT b.id FROM buildings b
    JOIN properties_list p ON b.property_id = p.uuid
    WHERE p.manager_id = auth.uid()
  )
)

The hidden assumption: every flat's building has a property, and that property has this manager. A flat whose chain is incomplete — a standalone unit — makes the subquery return nothing, and the policy silently denies access. RLS failures never say "your chain is broken"; they say "row violates row-level security policy," which looks identical to an auth bug. That misdirection is why Session 7's diagnosis walked the chain link by link before touching any code.

Additive RLS policies — fix without hiding

PostgreSQL combines multiple permissive policies on the same table with OR. That means you can repair a coverage gap by adding a second policy for the uncovered shape, without touching — or risking — the policy that already protects the covered shape:

-- Existing policy stays untouched (full-chain flats keep working)
-- New policy covers the standalone shape:
CREATE POLICY flats_standalone_owner ON flats
  FOR ALL USING (manager_id = auth.uid());

The alternative — editing the original policy into one bigger OR expression — changes the security surface for every row to fix some rows. Additive policies keep each ownership shape auditable on its own line. The cost: you must remember both exist when reasoning about access (name them descriptively).

Flat-anchored ownership — resolve through the most stable entity

When a voice call comes in, the system must answer: which manager does this caller belong to? The first implementation resolved through the tenant record (phone → tenant → flat → … → manager). Session 11 exposed the weakness: tenants churn, get reassigned, have missing or duplicated phones. Every one of those states broke identity resolution mid-call.

The refactor anchors on the flat: phone → flat (via the tenant link) → building → manager, with the flat as the join point everything else hangs off. Flats are the most stable entity in the domain — they don't move buildings, don't churn, and exist before and after any given tenancy.

🔑 Key concept: when several entities could anchor a lookup, choose the one with the longest lifetime and the fewest state transitions. Tenants are residents of the stable world, not the stable world itself. The same reasoning picks the phone number (not the caller) as identity anchor in Module 12, and the flat (not the complaint) as the complaint's ownership root.
Numbered migrations — the schema's git history

backend/migrations/ holds numbered SQL files (031_lease_french_assistant_id.sql, 032_tenant_preferred_language.sql, …). The number is a promise about order: 032 assumes 031 has run. Each file is:

  • Small — one logical change (a column, a policy, an index), so a failure is diagnosable.
  • Forward-only — there is no automated down-migration here; recovery is a new numbered migration that undoes the change explicitly.
  • Idempotent where cheap — ADD COLUMN IF NOT EXISTS, CREATE POLICY guarded by a drop-if-exists, so re-running by accident is harmless.

Migrations are applied by pasting into the Supabase SQL Editor (no Alembic — Module 02 explains why the SQLAlchemy toolchain is out). The discipline substitutes for the tooling: numbered files in git ARE the migration history.

Migration-tolerant queries — code that survives being deployed "too early"

Session 18 shipped a feature spanning a DB column, backend code, VAPI assistants, and a provisioning script. Four systems cannot update in the same instant, so for some window the new code runs against the old schema. Code that does row["preferred_language"] crashes in that window; code that does row.get("preferred_language") — and treats None as "no preference recorded" — sails through:

# migration-tolerant read: works before AND after 032 runs
lang = (tenant_row.get("preferred_language") or "en")

The same tolerance applies to SELECTs: asking for select("*") survives a new column appearing; asking for an explicit column list that includes a not-yet-existing column fails. Tolerance is a temporary posture — once the migration is confirmed everywhere, the defensive default documents itself as the real default.

Deploy ordering — four systems, one safe sequence

When a change spans DB + backend + external agent config + a switch-flip, there is exactly one order that never serves a broken state:

1. DB migration (adds the column — old code ignores it) 2. Backend deploy (tolerant code — works with or without data) 3. Agent provisioning (new assistants/config that WRITE the column) 4. Flip the switch (routing starts READING the column)

Each step is safe against the world as the previous step left it. Reverse any two adjacent steps and there's a window where something reads a column that doesn't exist, or routes on data nothing writes yet. Write the order down before deploying anything multi-system — Session 18 did, and Step 9 of its build log is literally that list.

Write-once semantics — first answer wins

The tenant's preferred_language is recorded the first time they answer a call in a language, and never overwritten by later calls. Why not update it every call? Because later signals are noisier (a tenant's bilingual roommate picks up once and flips the record), and because a flip-flopping preference makes routing non-deterministic and support tickets undiagnosable. Write-once with an explicit manual override path (settings UI) beats continuous inference for slow-changing facts.

Section 3 — Case Study Walkthrough: the Session-7 RLS Incident

This is the senior-dev debugging sequence, step by step, exactly as it ran. The specific bug matters less than the order of operations — notice how much reading happens before any writing.

Phase 1 — Diagnose (steps 1–5: read, don't guess)

  1. Read the symptom precisely. The error was an RLS rejection on INSERT — not a 401, not a validation error. That single distinction eliminates the auth layer and Pydantic immediately.
  2. Find the code that prints the error. Grep for the error text; identify which route and which service function produced it.
  3. Read both suspects end-to-end — the route (what client, what data) and the service (what table, what columns).
  4. Read the actual RLS policy in the migration SQL, not from memory. The policy's subquery walked group→building→flat.
  5. Confirm the trigger: the failing rows were standalone units whose chain the subquery couldn't complete. Reproduce on one row to prove it.

Phase 2 — Fix twice (steps 6–7: immediate, then durable)

💡 The two-fix pattern: ship Option A (smallest change that unblocks users — here, routing the operation through a path the policy allows) the same hour; then design Option B (the durable schema fix) with the user, because durable fixes change the data model and that's a product decision, not just an engineering one.

Phase 3 — Migrate and recover (steps 8–11)

  1. Write the migration: add the direct-ownership column, create the additive policy, backfill.
  2. Populate the new column for existing rows from the chain where it exists.
  3. Verify code compiles against the new shape (a python -c "import app.main" smoke check catches renamed-column typos before deploy).
  4. Run the migration, then recover the orphans — the rows the old policy had made invisible come back, and the incident's data loss turns out to be data hiding.

Migration 032 — the anatomy of a small, safe migration

-- backend/migrations/032_tenant_preferred_language.sql (shape)
ALTER TABLE tenants
  ADD COLUMN IF NOT EXISTS preferred_language text
  CHECK (preferred_language IN ('en', 'fr'));

Everything this module preaches in five lines: idempotent (IF NOT EXISTS), constrained at the DB (the CHECK means no third value can ever sneak in from any code path), nullable (NULL = "not yet known" is a real state, distinct from either language — the write-once logic depends on it), and numbered after everything it assumes.

🐛 Bug story (Session 18): three flats named "102". Tenant phone-verification matched on flat_number alone — and three different buildings each had a flat "102". Verification matched the wrong tenant in another manager's building. The fix: scope every flat lookup by the ownership anchor (building/manager) — never treat a human-readable label as a unique key. UUIDs are unique; flat numbers are decoration. If you take one rule from this module's bugs, take that one.

Section 7 — Checkpoint ✓

Prove you can read an RLS denial correctly

In the Supabase SQL Editor, run the pg_policies query above for flats and tenants. For each policy, write one sentence: which ownership shape does it cover? Then answer from the policy text alone: could a standalone unit (no property chain) be inserted by its manager?

Success: you can name the exact policy that permits it (or identify that none does). That skill — reading policies as coverage maps — is the entire Session-7 diagnosis compressed into five minutes.

Section 8 — Exercises

Easy Write migration 033

Problem: Product wants a per-tenant emergency_contact_phone. Write 033_tenant_emergency_contact.sql following every convention from Section 2's migration anatomy.

Hints

Idempotent ADD COLUMN; nullable (unknown is a real state); think about whether a CHECK constraint is possible for phone format (hint: E.164 regex via CHECK (col ~ '^\+[0-9]+$') — decide if you want it).

Solution 
-- 033_tenant_emergency_contact.sql
ALTER TABLE tenants
  ADD COLUMN IF NOT EXISTS emergency_contact_phone text
  CHECK (emergency_contact_phone IS NULL OR emergency_contact_phone ~ '^\+[0-9]{7,15}$');

Success: runs twice without error; rejects '9876543210' (no +) but accepts NULL and '+919876543210'. The IS NULL OR matters — without it the CHECK rejects the unknown state too.

Medium Diagnose a policy-coverage gap on paper

Problem: A manager reports that complaints created by the voice agent are invisible in their dashboard, but complaints created in the UI show fine. Voice complaints are inserted with the service client. Using only what this module taught, list the three most likely causes in the order you'd check them.

Solution
  1. The insert didn't set the ownership column (service client bypasses RLS on write, so nothing forced manager_id/flat linkage to be present — the row exists but no read policy matches it). Check the actual rows as service-role first.
  2. The read policy's chain doesn't cover the shape voice inserts create (e.g. complaint anchored to a flat_number string but no flat row — the Session-7 class of bug).
  3. The dashboard query filters on a field voice inserts leave NULL — not RLS at all, which is why you confirm with a service-role read before blaming policies.

The lesson being tested: "invisible rows" splits into row doesn't exist / row exists but no policy matches / row matches but app filters it — and a service-role SELECT distinguishes all three in one query.

Hard Design a deploy plan for building-scoped flat numbers

Problem: To kill the "three flats named 102" class forever, you decide flat lookups must always be building-scoped, and the DB should enforce UNIQUE (building_id, flat_number). Existing data contains cross-building duplicates (fine) and possibly same-building duplicates (must be resolved). Write the numbered-migration + deploy plan, in order, using the four-system sequence.

Solution
  1. Audit first (no migration): SELECT building_id, flat_number, COUNT(*) FROM flats GROUP BY 1,2 HAVING COUNT(*) > 1; — you cannot add a unique constraint over dirty data.
  2. Migration 03X-a: data fix only — rename/merge same-building duplicates (a human decision per row; this migration is generated from the audit, reviewed by the user — Option-B territory).
  3. Backend deploy: make every flat lookup take building/manager scope (tolerant: works with or without the constraint existing).
  4. Migration 03X-b: ALTER TABLE flats ADD CONSTRAINT flats_building_flat_number_key UNIQUE (building_id, flat_number); — safe now because code no longer creates duplicates and data is clean.
  5. Verify: re-run the audit query (zero rows) and attempt a duplicate insert expecting error code 23505 mapped to a friendly 409 (Module 06).

Key insight being tested: constraint-adding migrations are three deploys, not one — clean the data, stop producing dirt, then lock the door. Locking first bricks production.

Section 9 — Glossary

TermDefinition
Additive policyA new permissive RLS policy created alongside existing ones (combined with OR) to cover a previously-uncovered ownership shape
Standalone unitA flat whose ownership chain skips the full group→building hierarchy — the shape the original policies didn't anticipate
Flat-anchored ownershipResolving identity/ownership through the flat (the most stable entity) rather than the tenant
Migration-tolerant queryCode written to work both before and after a schema migration runs (.get() with defaults, select("*"))
Write-once semanticsA field recorded on first observation and never auto-overwritten (e.g. preferred_language)
BackfillA one-off UPDATE populating a new column for rows that predate it
Orphan recoveryRestoring access to rows an over-narrow policy had hidden (they were never gone)
Option A / Option BThe two-fix pattern: immediate unblock now, durable schema fix designed with the user
