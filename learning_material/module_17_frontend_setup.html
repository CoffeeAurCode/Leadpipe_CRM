Section 1 — The Build Pipeline You're Working In

Before writing a single component, you need to understand the tools that compile, serve, and bundle your code. The frontend uses three tools working together: Vite (dev server + bundler), Tailwind CSS (utility-class styling), and React 18 (UI library). Each does a distinct job.

SOURCE CODE (JSX + CSS) │ ▼ ┌─────────────┐ │ Vite │ ← Transforms JSX → JS, processes imports, HMR in dev │ (esbuild) │ └─────────────┘ │ ▼ ┌─────────────┐ │ PostCSS + │ ← Scans source for Tailwind class names, generates CSS │ Tailwind │ └─────────────┘ │ ▼ ┌─────────────┐ │ Browser / │ ← Final bundled JS + CSS served or deployed │ dist/ │ └─────────────┘ Dev mode: `npm run dev` → Vite dev server on :5173 with HMR Prod mode: `npm run build` → Writes optimized output to dist/

The key difference from older tools like Webpack: Vite uses native ES modules in development (no bundle step), so cold start is instant and HMR (Hot Module Replacement — live updates without full reload) patches only the changed module, not the entire app.

Section 2 — package.json Line-by-Line

Every dependency has a reason. Understanding why each package exists makes you able to debug version conflicts, audit bundle size, and explain the stack to a colleague.

{
  "name": "manager-dashboard",
  "private": true,
  "version": "1.0.0",
  "type": "module",
  "engines": { "node": "20.x" },
"type": "module" — tells Node.js to treat .js files as ES Modules (using import/export) instead of CommonJS (require()). Required for Vite to work correctly with native ESM.

"engines": { "node": "20.x" } — documents the expected Node version. CI pipelines and nvm use read this. Node 20 is the current LTS. If a teammate runs Node 16, they'll get a warning rather than a cryptic crash. 
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:ui": "vitest --ui"
  },
"dev" → starts Vite dev server with HMR. "build" → bundles for production into dist/. "preview" → serves the dist/ folder locally to verify the production build before deploying.

"test" → runs Vitest (a Vite-native test runner, drop-in replacement for Jest). "test:watch" → re-runs affected tests on file changes. "test:ui" → opens Vitest's browser UI dashboard.

Section 3 — vite.config.js Line-by-Line

import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'path'

export default defineConfig({
    plugins: [react()],
defineConfig() — TypeScript-aware wrapper that gives you autocomplete for all Vite config options. Not required, but gives IDE hints.

react() — Enables React Fast Refresh: when you edit a component, Vite patches only that component in the browser while preserving React state. Without this plugin, every change would trigger a full page reload and reset all state. 
    resolve: {
        alias: {
            '@': path.resolve(__dirname, './src'),
        },
    },
Path alias @ — maps @ to the src/ directory. Without this, imports would look like ../../lib/utils (fragile — breaks when you move files). With this alias, you always write import { cn } from '@/lib' no matter how deeply nested the importing file is.

path.resolve(__dirname, './src') converts the relative ./src to an absolute path, e.g., /Users/you/project/frontend/src. Absolute paths are what Node module resolution requires. 
    server: {
        port: 5173,
    },
Locks the dev server to port 5173 (Vite's default). Explicit port prevents surprises when another app occupies the default port and Vite silently increments it. The backend runs on :8000. The frontend makes API calls via the VITE_API_URL environment variable (pointing to http://localhost:8000 in dev), so the backend's CORS configuration handles cross-origin requests — no Vite proxy is needed. 
    build: {
        rollupOptions: {
            output: {
                manualChunks: {
                    recharts: ['recharts'],
                    motion: ['framer-motion'],
                    markdown: ['react-markdown'],
                    react: ['react', 'react-dom'],
                },
            },
        },
    },
Manual chunk splitting — tells Rollup (Vite's production bundler) to put specific packages into separate JS files. Why?

Without splitting, everything lands in one massive JS file. Recharts alone is ~400 KB gzipped. The first page load would force the browser to download and parse all 400 KB before showing anything.

With splitting: recharts.js is downloaded once and then cached by the browser independently. When you deploy a new app version, browsers re-download app.js (your changed code) but still use the cached recharts.js (unchanged library). This dramatically reduces the bytes transferred on subsequent deploys.

The chunks are loaded in parallel and only when needed (Vite adds dynamic imports automatically for code that's not on the initial route).

Section 4 — tailwind.config.js Line-by-Line

This project uses a technique called CSS variable-based theming: Tailwind classes like bg-primary don't map to a fixed color — they map to a CSS custom property (--primary) whose value changes when the theme switches. This is the standard shadcn/ui pattern.

darkMode: ['class'],
Tailwind's dark mode strategy. 'class' means Tailwind generates dark-mode variants only when the .dark class is present on the <html> or <body> element. The alternative, 'media', would follow the OS-level dark mode preference — but 'class' lets you toggle dark mode programmatically and persist the preference in localStorage. 
content: [
    "./index.html",
    "./src/**/*.{js,ts,jsx,tsx}",
],
JIT content scanning — Tailwind scans these files at build time and generates CSS only for the class names it finds. This is why production CSS is tiny (~10 KB instead of ~3 MB for the full Tailwind stylesheet).

Common mistake: dynamically constructing class names breaks this. bg-${color}-500 will never be found by the scanner because Tailwind looks for literal strings, not runtime values. Always use full class names: bg-red-500, bg-blue-500. 
theme: {
    extend: {
        colors: {
            border: "hsl(var(--border))",
            background: "hsl(var(--background))",
            foreground: "hsl(var(--foreground))",
            primary: {
                DEFAULT: "hsl(var(--primary))",
                foreground: "hsl(var(--primary-foreground))",
            },
            // ... more tokens ...
        },
    },
},
Each color token is defined as hsl(var(--token-name)). The actual HSL values come from index.css where CSS custom properties are declared for both light and dark themes. This separation means:

• Tailwind generates: .bg-primary { background-color: hsl(var(--primary)); }
• The :root block in index.css declares: --primary: 217 91% 60%; (light theme)
• The .dark :root block declares: --primary: 217 91% 70%; (dark theme)

Switching themes is a single class toggle on <html> — no JavaScript rerendering of components required. 
plugins: [require("tailwindcss-animate")],
Adds animation utility classes like animate-in, fade-in-0, zoom-in-95, slide-in-from-top-2. These are used by modal open/close transitions. The plugin generates the keyframe CSS and the utility classes — you just use them in JSX without writing any custom CSS.

Section 5 — src/main.jsx Line-by-Line

The entry point: the first file the browser executes. Everything flows from here.

import React from 'react';
import ReactDOM from 'react-dom/client';
import App from './App';
import { ThemeProvider } from './context/ThemeContext';
import './i18n';
import './index.css';
import React from 'react' — In React 17+ with the new JSX transform, you no longer need this for JSX files. But importing React explicitly ensures React.StrictMode is available and future-proofs against transform config changes.

'react-dom/client' — React 18's new entry point for the concurrent root API. The old react-dom still exists but uses the legacy mode.

import './i18n' — Side-effect import: initializes the i18next library with language resources. No export needed — just running the module's top-level code configures the global i18n instance used by useTranslation() everywhere.

import './index.css' — Global CSS: defines the CSS custom properties (--primary, --background, etc.) for both themes. Must be imported here so it's part of the bundle from the start. 
ReactDOM.createRoot(document.getElementById('root')).render(
    <React.StrictMode>
        <ThemeProvider>
            <App />
        </ThemeProvider>
    </React.StrictMode>
);
createRoot() vs old ReactDOM.render():
• Old: ReactDOM.render(<App />, document.getElementById('root')) — legacy mode, no concurrent features
• New: ReactDOM.createRoot(...).render() — enables React 18's concurrent mode: automatic batching, useTransition, useDeferredValue, Suspense for data fetching

React.StrictMode — development-only wrapper that:
1. Renders every component twice to detect side effects in the render phase (this is intentional and only happens in dev)
2. Calls useEffect cleanup and re-setup once after mount (double invocation) to detect stale closure bugs
3. Warns about deprecated APIs

Important: if you see console logs appear twice in dev, this is StrictMode. It does NOT happen in production.

ThemeProvider — context provider that manages dark/light mode state. Wrapping at this level makes the theme available to every component in the tree without prop drilling.

Section 6 — Concept Deep-Dives

HMR — Hot Module Replacement explained

HMR is the mechanism that updates your running app when you save a file, without a full page reload. Here's how it works in Vite + React:

1. You edit PropertiesPage.jsx and save. 2. Vite detects the file change via file system watcher. 3. Vite re-compiles only that module (not the whole app). Result: a new JS module chunk is ready in ~5ms. 4. Vite sends a WebSocket message to the browser: "PropertiesPage module has a new version at /path/hash.js" 5. React Fast Refresh (via @vitejs/plugin-react): → Imports the new module → Finds which React components changed → Re-renders only those components → Preserves state in UNCHANGED components Without Fast Refresh: any change would unmount/remount the entire tree, losing all React state (form inputs, open modals, etc.).

The practical effect: you edit a button's color in PropertiesPage.jsx, and the button updates in the browser in under 100ms — while your selected property group, open modal, and everything else stays exactly where it was.

Tailwind JIT (Just-In-Time) compilation

Before JIT (Tailwind v2 and earlier), Tailwind pre-generated CSS for every possible utility class (~3 MB), then used PurgeCSS in production to strip unused ones. Development CSS was enormous and slow to process.

JIT (default since Tailwind v3) flips this: Tailwind watches your source files and generates CSS on-demand as you type class names. The result:

  • Development CSS is tiny — only the classes you've actually used so far
  • Arbitrary values work: top-[23px], bg-[#ff6b6b] — no pre-configuration needed
  • No PurgeCSS step in production — the same JIT scanner runs at build time

JIT gotcha: if you build class names dynamically at runtime (e.g., `text-${size}-500`), JIT won't find them during the build-time scan because it's a static string scanner, not a runtime evaluator. Always use complete class name strings. Conditional classes: isActive ? 'bg-primary' : 'bg-secondary' (both strings visible to the scanner).

Environment variables: VITE_ prefix

Vite has a strict rule: only environment variables prefixed with VITE_ are exposed to client-side code. Variables without this prefix are never bundled into the JS — they stay server-side only.

# .env.local (git-ignored)
VITE_SUPABASE_URL=https://xyz.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
VITE_API_URL=http://localhost:8000
SECRET_INTERNAL_KEY=never_exposed  # NOT prefixed — never reaches the browser

# In code:
const url = import.meta.env.VITE_SUPABASE_URL;  // ✓ works
const secret = import.meta.env.SECRET_INTERNAL_KEY;  // undefined

Note the syntax: import.meta.env (not process.env). Vite inlines these values at build time — the deployed JS contains the literal value, not a reference to an env variable. This is why anon keys (public by design) are safe to expose but never put secret service-role keys in VITE_ variables.

Section 7 — Common Bugs & Fixes

Bug: Tailwind classes not applying after adding a new file location

Symptom: you create src/features/NewPage.jsx and add Tailwind classes, but the CSS isn't generated — the element has no styling.

Root cause: The content glob "./src/**/*.{js,ts,jsx,tsx}" should cover new directories automatically. But if you create a file outside src/, or if Vite's watcher missed the new directory (rare, usually on slow filesystems), the scan misses it.

Fix: Restart npm run dev. The file system watcher re-initializes and picks up new directories. If the glob genuinely doesn't match your new file location, update the content array in tailwind.config.js.

Bug: useEffect runs twice in development, causing double API calls

Symptom: useEffect(() => { fetchData(); }, []) triggers two HTTP requests on mount. Checked the network tab — two identical requests.

Root cause: React 18 StrictMode intentionally mounts → unmounts → remounts components in development to detect side effects. Each mount runs the useEffect.

Fix: This is correct behavior and only happens in dev. In production, the effect runs once. If you must prevent double fetches in dev (e.g., to avoid rate limits on an external API), use a ref flag or an AbortController:

useEffect(() => {
    let cancelled = false;
    fetchData().then(data => {
        if (!cancelled) setData(data);
    });
    return () => { cancelled = true; };
}, []);

Bug: "Cannot find module '@/lib'" after setting up the alias

Symptom: import resolves correctly in Vite but TypeScript shows a red underline and the test runner fails to find the module.

Root cause: The @ alias is configured in vite.config.js, but TypeScript's module resolver and Vitest's resolver are separate systems that don't automatically read Vite config.

Fix: Add the path alias to tsconfig.json (or jsconfig.json) and to vitest.config.js or the test section in vite.config.js:

// jsconfig.json
{
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] }
  }
}

Bug: Dynamic Tailwind classes not appearing in production build

Symptom: const colorClass = `bg-${status}-500` works in dev (because all classes exist) but fails in production (those classes were never found by JIT scan).

Fix: Use a lookup object with full class name strings:

// ✗ BAD — JIT can't scan dynamic construction
const colorClass = `bg-${status}-500`;

// ✓ GOOD — all strings visible to JIT scanner
const STATUS_COLORS = {
    pending: 'bg-amber-500',
    resolved: 'bg-green-500',
    in_progress: 'bg-blue-500',
};
const colorClass = STATUS_COLORS[status];

Section 8 — Exercises

Easy Exercise 1 — Read the build output

Run npm run build in the frontend/ directory. Look at the output — specifically the chunk sizes listed. Answer these questions:

  1. Which chunk is the largest?
  2. What happens if you remove the recharts entry from manualChunks and rebuild?
  3. After any deploy, which chunks do returning users not need to re-download (assuming their browser cached the previous version)?
Show answer
  1. Recharts is typically the largest (400–500 KB gzipped), followed by framer-motion (~80 KB). Without manual chunking, all of this would be in the main index.js bundle.
  2. Without the recharts chunk entry, Rollup bundles Recharts into whichever chunk first imports it (usually the dashboard chunk). That chunk becomes much larger, and every deploy re-downloads it even if only your app code changed.
  3. Chunks whose content hash hasn't changed — recharts.[hash].js, motion.[hash].js, react.[hash].js — are served from browser cache. Only index.[newhash].js (your app code) needs to be downloaded again.
Medium Exercise 2 — Add a new color token

Add a danger color token to tailwind.config.js so you can use bg-danger, text-danger, and border-danger in JSX. The color should be #ef4444 (Tailwind's red-500 equivalent) in light mode and #f87171 (red-400) in dark mode.

Show solution

Step 1: Add to tailwind.config.js:

colors: {
    // ... existing tokens ...
    danger: "hsl(var(--danger))",
},

Step 2: Add to index.css (in the :root block for light and .dark block for dark):

/* index.css */
:root {
    --danger: 0 84% 60%;  /* hsl(0, 84%, 60%) ≈ #ef4444 */
}
.dark {
    --danger: 0 91% 71%;  /* hsl(0, 91%, 71%) ≈ #f87171 */
}

Now bg-danger, text-danger, border-danger all work and automatically respect the theme.

Hard Exercise 3 — Add a Vite dev proxy

Currently, all API calls go to http://localhost:8000 via the VITE_API_URL environment variable. The backend has CORSMiddleware to allow this. But suppose you're deploying to a platform where the backend and frontend share the same domain — you'd want to proxy /api/* requests to the backend without the frontend knowing the backend URL.

Add a server.proxy configuration to vite.config.js that forwards any request starting with /api to http://localhost:8000, stripping the /api prefix.

Show solution 
server: {
    port: 5173,
    proxy: {
        '/api': {
            target: 'http://localhost:8000',
            changeOrigin: true,
            rewrite: (path) => path.replace(/^\/api/, ''),
        },
    },
},

With this config: fetch('/api/flats') → Vite dev server → http://localhost:8000/flats. The browser never sees a cross-origin request, so no CORS headers are needed. In production, your reverse proxy (Nginx, Caddy, etc.) would do the same rewrite.

Note: you'd also need to change API_BASE_URL in apiService.js to '/api' instead of 'http://localhost:8000' to use this approach.

Module 17 — Key Takeaways

  • Vite = dev server with HMR + production bundler. It does NOT run in production — only the dist/ output does.
  • @vitejs/plugin-react enables React Fast Refresh (HMR that preserves component state).
  • Path alias @ maps to src/ — use it everywhere to avoid brittle relative paths like ../../...
  • Manual chunk splitting puts heavy libraries (Recharts, Framer Motion) in separate cached files.
  • Tailwind JIT scans source for literal class strings — never build class names dynamically.
  • CSS variable tokens let one Tailwind class (bg-primary) render differently per theme — configured in index.css, referenced via hsl(var(--primary)).
  • VITE_ prefix is required for env vars to reach the browser. Never put secrets in VITE_ vars — they're bundled into the JS.
  • StrictMode double-invocation in dev is intentional. Production runs effects once.
  • createRoot() opts into React 18 concurrent mode — the foundation for all new React 18 features.
