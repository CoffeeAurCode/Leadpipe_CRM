Section 1 — What You Are Building

A feature flag system that lets managers turn individual features on or off per flat (unit). Some features like SMS notifications cost money — you don't want them on by default for every flat. Others like voice calls require a Twilio setup that not every manager has done. This system gives granular per-unit control, with bulk-apply operations at the building and property level.

Four-file architecture: core/features.py ─── Feature enum + FEATURE_METADATA dict (single source of truth) services/feature_service.py ─── Business logic: get/set at unit/building/property scope dependencies/features.py ─── FastAPI Depends() wrappers (inject FeatureService, gate routes) routes/settings.py ─── HTTP endpoints (GET/PATCH at unit/building/property scope) DB table: property_features unit_id (FK → flats.id) │ feature_key (text) │ enabled (bool) ────────────────────────┼────────────────────┼─────────────── 42 │ sms_reminders │ true 42 │ email_reminders │ false 43 │ sms_reminders │ false ONE ROW PER UNIT PER FEATURE. If no row exists for a feature → use default_enabled from FEATURE_METADATA. No inheritance, no cascading reads — just flat storage + bulk writes.

Section 2 — Concept Deep-Dives

Feature(str, Enum) — why inherit from str

Python enums can inherit from a built-in type. Feature(str, Enum) means each enum member is also a string. This eliminates the need to call .value in most contexts.

class Feature(str, Enum):
    SMS_REMINDERS = "sms_reminders"
    EMAIL_REMINDERS = "email_reminders"

# Without str inheritance:
Feature.SMS_REMINDERS.value  # "sms_reminders"
str(Feature.SMS_REMINDERS)   # "Feature.SMS_REMINDERS" (ugly)

# With str inheritance:
Feature.SMS_REMINDERS        # IS "sms_reminders" (compares equal to the string)
db.eq("feature_key", Feature.SMS_REMINDERS)  # works — no .value needed

The enum values match the exact strings stored in the DB's feature_key column. This means you can pass Feature.SMS_REMINDERS directly to a Supabase .eq() call and it works without conversion.

FEATURE_METADATA — single source of truth for UI

Rather than scattering display names and defaults across the codebase, a single dict holds all the metadata for each feature. The UI reads this to know what to show, and the backend reads it to know what defaults to apply.

FEATURE_METADATA: Dict[Feature, dict] = {
    Feature.SMS_REMINDERS: {
        "category": "Communication",
        "display_name": "SMS Reminders",
        "description": "Automated rent reminders via SMS",
        "default_enabled": False   # off by default — costs money
    },
    Feature.RENT_MANAGEMENT: {
        "category": "Financial",
        "display_name": "Rent Management",
        "description": "Set and manage rent amounts",
        "default_enabled": True    # on by default — everyone needs this
    },
}

Default-on features (like RENT_MANAGEMENT) are enabled for every flat out of the box — no row in property_features is needed. Default-off features (like SMS_REMINDERS) require an explicit opt-in — the manager must toggle them on per flat or per building.

No-inheritance architecture — flat storage + bulk writes

An alternative design would be: store one setting at the property level, let buildings inherit from the property, let units inherit from the building (with per-unit overrides). This is complex to query and maintain.

This project uses a simpler approach: all flags are stored at the unit level. Bulk writes to a building or property resolve all child units and upsert each one individually. Reads are always from the unit level directly.

"Apply SMS_REMINDERS=true to Building 5" operation: set_building_features("5", {"sms_reminders": True}) │ ├── _get_units_for_building("5") → [unit_id=42, unit_id=43, unit_id=44] │ ├── _upsert_unit_features(42, {"sms_reminders": True}) ├── _upsert_unit_features(43, {"sms_reminders": True}) └── _upsert_unit_features(44, {"sms_reminders": True}) Result: 3 rows upserted in property_features. Reading unit 42 later sees sms_reminders=True directly — no "walk up the hierarchy" needed.
Upsert with composite conflict key

The property_features table has a UNIQUE constraint on (unit_id, feature_key). Inserting the same feature twice would normally fail. The solution is an upsert — insert if not exists, update if exists.

self.db.table("property_features") \
    .upsert(
        [{"unit_id": 42, "feature_key": "sms_reminders", "enabled": True}],
        on_conflict="unit_id,feature_key"   # composite key
    ) \
    .execute()

on_conflict="unit_id,feature_key" tells PostgREST: if a row already exists with this (unit_id, feature_key) combination, update the other columns (enabled) instead of raising a duplicate key error. This is the idiomatic way to handle "create or update" operations without a SELECT first.

Majority-vote aggregation for building/property views

When the manager opens settings for a building with 10 units, what should the toggle show? This project uses majority voting: if ≥50% of units have a feature enabled, show the toggle as "on".

# Pseudocode of get_building_features():
unit_ids = _get_units_for_building(building_id)  # [42, 43, 44]
counts = {}  # feature_key → count of units with enabled=True

for uid in unit_ids:
    raw = _get_unit_features_raw(uid)  # {feature_key: bool}
    for key, val in raw.items():
        counts.setdefault(key, 0)
        if val:
            counts[key] += 1

n = len(unit_ids)   # 3
# majority: enabled if count >= n/2
agg_raw = {key: (counts[key] >= n / 2) for key in counts}

This is only used for display (the toggle starting position in the UI). When the manager saves, the new value is applied to all units regardless of what the aggregate was.

FastAPI dependency factory — requires_feature()

A dependency factory is a function that returns a dependency function. This lets you parameterise a dependency — here, the feature key.

def requires_feature(feature: Feature):
    # Returns a new async function each call
    async def check_feature(
        property_uuid: str,
        service: FeatureService = Depends(get_feature_service)
    ):
        is_enabled = await service.is_feature_enabled(property_uuid, feature)
        if not is_enabled:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail={
                    "error": "feature_disabled",
                    "feature": feature.value
                }
            )
    return check_feature

# Usage on a route:
@router.post("/rent", dependencies=[Depends(requires_feature(Feature.RENT_MANAGEMENT))])
async def set_rent(...):
    ...

Each call to requires_feature(Feature.X) creates a new check_feature closure that captures the specific feature enum. FastAPI evaluates the dependency before running the route handler — the route only runs if the feature is enabled.

Why return a function instead of being a function? If requires_feature itself were a dependency, it couldn't accept a feature parameter (FastAPI injects dependencies by type, not by value). The factory pattern lets you pre-bind the feature value.

Section 3 — Line-by-Line Walkthrough

File: backend/app/core/features.py

class Feature(str, Enum):
    RENT_MANAGEMENT = "rent_management"
    RENT_DUE_DATE = "rent_due_date"
    FLAT_DETAILS = "flat_details"
    VOICE_CALLS = "voice_calls"
    SMS_REMINDERS = "sms_reminders"
    EMAIL_REMINDERS = "email_reminders"
    TENANT_DETAILS = "tenant_details"
    TENANT_DOCUMENTS = "tenant_documents"
Eight features across four categories. The string values are exactly what gets stored in the feature_key column of property_features. If you add a new feature, you add it here, add its metadata to FEATURE_METADATA, and the rest of the system (service, routes, UI) picks it up automatically via for feature in Feature: iteration. 
def get_default_state(feature: Feature) -> bool:
    return FEATURE_METADATA.get(feature, {}).get("default_enabled", False)
Double .get() with defaults at both levels. If feature isn't in FEATURE_METADATA (shouldn't happen, but defensive), returns an empty dict. If default_enabled isn't in that dict, returns False (safe default — don't accidentally enable paid features).

File: backend/app/services/feature_service.py

def _get_unit_features_raw(self, unit_id: int) -> Dict[str, bool]:
    result = (
        self.db.table("property_features")
        .select("feature_key, enabled")
        .eq("unit_id", unit_id)
        .execute()
    )
    return {row["feature_key"]: row["enabled"] for row in (result.data or [])}
Returns a dict like {"sms_reminders": True, "email_reminders": False}. Only features that have been explicitly set have entries — features with no row are absent from this dict. The caller (_build_feature_map) handles absent features by falling back to defaults.

result.data or [] — Supabase returns None instead of [] on some error conditions. The or [] ensures the dict comprehension always has something to iterate over. 
def _build_feature_map(self, raw: Dict[str, bool]) -> Dict[str, dict]:
    feature_map = {}
    for feature in Feature:     # iterates all 8 Feature enum members
        metadata = FEATURE_METADATA.get(feature, {})
        key = feature.value
        enabled = raw.get(key)   # None if not set in DB
        if enabled is None:
            enabled = get_default_state(feature)
            source = "default"
        else:
            source = "set"
        feature_map[key] = {
            "enabled": enabled,
            "source": source,       # "default" or "set"
            "category": metadata.get("category", "Other"),
            "display_name": metadata.get("display_name", key),
            "description": metadata.get("description", ""),
        }
    return feature_map
for feature in Feature: — iterating over an enum yields all its members in definition order. This ensures the response always contains all 8 features, even if only some have DB rows.

The source field ("default" vs "set") is surfaced to the frontend. The settings UI can show a subtle indicator like "using default" on features the manager hasn't explicitly configured, which helps them understand what they've actually changed vs what's inherited. 
    async def is_feature_enabled(self, unit_id: int, feature: Feature) -> bool:
        try:
            result = (
                self.db.table("property_features")
                .select("enabled")
                .eq("unit_id", unit_id)
                .eq("feature_key", feature.value)
                .execute()
            )
            if not result.data:
                return get_default_state(feature)
            return result.data[0].get("enabled", False)
        except Exception as e:
            print(f"[FeatureService] Error checking feature {feature.value} for unit {unit_id}: {e}")
            return get_default_state(feature)
This is the fast path used by middleware and guards — only reads a single column for a single feature. Much cheaper than loading the full feature map.

if not result.data: — no row found → feature was never explicitly set → fall back to default. This is the "default-on / default-off" mechanism.

The outer try/except returns the default state on any DB error. This is intentionally permissive: a DB error during a feature check should not block the user from using the feature — failing open is safer than failing closed (blocking all access) for most features.

File: backend/app/routes/settings.py

class FeatureToggleRequest(BaseModel):
    features: Dict[str, bool]

    @validator("features")
    def validate_feature_keys(cls, v):
        valid = {f.value for f in Feature}
        bad = set(v.keys()) - valid
        if bad:
            raise ValueError(f"Invalid feature keys: {', '.join(bad)}")
        return v
The request body is a simple dict: {"sms_reminders": true, "email_reminders": false}. The validator computes the set of valid keys from the enum at request time — so adding a new Feature enum member automatically makes it valid here without touching this file.

set(v.keys()) - valid — set difference: keys in the request that are not in the valid set. If bad is non-empty, the request is rejected with a clear error listing the invalid keys. 
@router.patch("/properties/{property_uuid}/settings")
async def bulk_update_property_settings(
    property_uuid: str,
    request: FeatureToggleRequest,
    user: dict = Depends(require_active_subscription),
    service: FeatureService = Depends(get_feature_service),
):
    units_updated = await service.set_property_features(property_uuid, request.features)
    updated = await service.get_property_features(property_uuid)
    return {
        "scope": "property",
        "property_uuid": property_uuid,
        "units_updated": units_updated,
        "features": updated,
        "message": f"Bulk-applied {len(request.features)} feature(s) to {units_updated} unit(s)",
    }
After writing, the response contains a fresh read of the current state (get_property_features()). This confirms what was actually written and gives the frontend up-to-date data in a single round trip — no need for a separate GET after the PATCH.

units_updated is returned so the manager can see that "3 units were updated" — useful feedback when the property has many units.

Section 4 — Real Bugs & How We Fixed Them

Bug 1: Feature key mismatch — enum vs string

Symptom: is_feature_enabled(unit_id, Feature.SMS_REMINDERS) always returned the default value even when the flag was set in the DB.

Root cause: An early version passed feature (the enum object) directly to .eq("feature_key", feature). The DB stored "sms_reminders" (string) but the query sent Feature.SMS_REMINDERS (Python object). Without str inheritance, this comparison fails silently — no rows match.

Fix: Two options: (1) use feature.value explicitly in every query, or (2) make Feature inherit from str so the enum IS the string. The project chose option 2 — cleaner at the call site.

Bug 2: Upsert failed — composite conflict key format

Symptom: First feature save worked. Second save raised a unique constraint violation instead of updating.

Root cause: The upsert was called with on_conflict="unit_id" (single column). The UNIQUE constraint in the DB is on (unit_id, feature_key) — two columns. PostgREST requires the comma-separated list of ALL columns in the constraint.

Fix: Changed to on_conflict="unit_id,feature_key". Lesson: the on_conflict parameter must match the constraint exactly — both columns, in the same order as the constraint definition.

Bug 3: @validator deprecation warning in Pydantic V2

Symptom: PydanticDeprecatedSince20: Support for class-based `config` is deprecated... and a separate warning about @validator being deprecated.

Root cause: routes/settings.py uses the old @validator decorator from Pydantic V1. The rest of the codebase uses @field_validator / @model_validator (Pydantic V2).

Status: This is a known inconsistency. The validator still works (V2 has a compatibility layer) but produces warnings. The correct fix is to replace it with @field_validator("features") + @classmethod. It's in the backlog.

Bug 4: Building-level toggle applied to wrong units

Symptom: Toggling SMS on for Building A accidentally enabled it on Building B units as well.

Root cause: _get_units_for_building() fetched all flats where building_id = ?. The bug was that building_id was being passed as a string but stored as an integer in the DB — the query matched nothing initially, then fell through to an unfiltered query that returned all flats.

Fix: Ensured building_id is always passed as the correct type (integer for numeric IDs). Added str(b["id"]) conversion in _get_units_for_property() where building IDs come from a mixed-type query result.

Section 5 — Exercises

Exercise 1 Easy — Add a new feature flag

Add a new feature called MAINTENANCE_PHOTOS ("Allow tenants to upload photos with complaints") that is off by default and belongs to the "Tenant Management" category.

Show solution

In core/features.py, add to the enum:

class Feature(str, Enum):
    # ... existing entries ...
    MAINTENANCE_PHOTOS = "maintenance_photos"

Then add to FEATURE_METADATA:

Feature.MAINTENANCE_PHOTOS: {
    "category": "Tenant Management",
    "display_name": "Maintenance Photos",
    "description": "Allow tenants to upload photos with complaints",
    "default_enabled": False
},

That's all. The settings routes, FeatureService, and _build_feature_map() all iterate Feature automatically — no other file changes needed.

Exercise 2 Medium — Add initialize_unit_features() call on flat creation

When a new flat is created via POST /flats, the feature service should automatically set all default feature values for that unit. Find where flats are created and add the call.

Show solution

In routes/flats.py, in the flat creation route, after the flat is inserted:

from app.services.feature_service import FeatureService

# After inserting the flat and getting its ID:
new_flat_id = created_flat["id"]

feature_service = FeatureService(db)
await feature_service.initialize_unit_features(new_flat_id)

The initialize_unit_features() method in feature_service.py already exists — it writes all defaults in one upsert call. Calling it on creation means the DB always has explicit rows for every feature, avoiding the "use default" fallback path on every read.

Exercise 3 Hard — Implement a GET /units/{unit_id}/settings/check?feature=sms_reminders endpoint

Add a lightweight endpoint that returns just {"enabled": true/false} for a single feature on a single unit. This is for mobile clients that don't need the full feature map.

Show solution 
@router.get("/units/{unit_id}/settings/check")
async def check_unit_feature(
    unit_id: int,
    feature: str = Query(...),
    user: dict = Depends(require_active_subscription),
    service: FeatureService = Depends(get_feature_service),
):
    try:
        feature_enum = Feature(feature)   # raises ValueError if invalid
    except ValueError:
        raise HTTPException(400, detail=f"Unknown feature: {feature}")

    enabled = await service.is_feature_enabled(unit_id, feature_enum)
    return {"unit_id": unit_id, "feature": feature, "enabled": enabled}

Feature(feature) converts the query string to the enum — raises ValueError if the string isn't a valid feature key, which we convert to an HTTP 400.

Section 6 — Key Takeaways

  • Feature(str, Enum) makes enum values directly usable as strings — no .value needed in most contexts.
  • FEATURE_METADATA is the single source of truth for display names, categories, and defaults — change it once, the whole system updates.
  • All flags live at the unit level — building/property views are aggregations, not separate rows. Reads are always O(1) per unit.
  • Upsert with composite conflict: on_conflict="unit_id,feature_key" must match the exact DB constraint columns.
  • Default state is returned when no DB row exists — this avoids needing to seed the DB on flat creation (though calling initialize_unit_features() on creation is cleaner).
  • The dependency factory pattern (requires_feature(Feature.X)) lets you gate any route on any feature with one line.
  • Fail open on DB errors during feature checks — a broken DB should not block users from using features that would otherwise be allowed.

Section 7 — Why This Design

Decision: Per-building flags in the DB vs. env vars vs. a flag service

ApproachProsCons
DB rows per building (chosen)Granularity matches the product (a landlord enables SMS for one building, not globally); changes apply instantly without redeploy; the settings UI edits them directlyOne extra query per flag check (mitigated by fetching flags alongside the entity); flags can drift from code if an enum member is removed carelessly
Environment variablesTrivial to implementGlobal only; every change is a redeploy; product staff can't touch them
LaunchDarkly / UnleashTargeting, rollouts, kill switches, audit logMonthly cost and an SDK dependency for what is, here, a boolean column
Senior takeaway: the enum in code (Feature) is the contract; the DB stores only deviations from defaults. Default-ON for features that existed before flagging (nothing breaks for existing users), default-OFF for genuinely new behavior (nobody gets surprised). Getting the default backwards is the classic flag-launch incident.

Section 8 — Checkpoint ✓

Prove a flag flip changes behavior with no restart:

  1. Pick a building and note a flag-gated behavior in the API response (e.g. tenant-details fields present).
  2. In Supabase Table Editor, flip that building's flag row (or insert one with the off value).
  3. Repeat the same GET request with the same token.

Expected: the gated field/behavior disappears from the response immediately — no uvicorn restart, no cache flush. Flip it back and confirm it returns. If a restart was needed, something is caching flag state in module scope; that's a bug worth finding now.
