Cutting Voice-Agent Latency & Tuning the Employment Prompt

A French test-caller's partner said Max "pauses 2–3 seconds before answering." This session is the detective work that confirmed the pause from a real transcript, found why it happens (it's the model, not the silence detector), and shipped three independent speed-ups: a faster LLM, a faster text-to-speech model, and a database query that went from three round-trips down to one. Along the way we changed what Max asks about employment, decided not to build two planned features yet, and wrote a rollback plan so any of it can be undone in one command.

🟡 Intermediate ⏱️ ~70 min read / build 📋 Requires: Sessions 08–09 (French STT, the deploy pipeline)

This was a diagnose-decide-optimise session. It started not with code but with a complaint and a transcript. The exact words that kicked it off:

By the end of the session we had:

  • Confirmed the 2–3 second pause from Transcript3.md using the call's own timestamps, and pinned the cause to LLM time-to-first-token — not the silence detector everybody blames first.
  • Changed the agent's employment question from "what do you do for work?" to "are you employed, and is it full- or part-time?" — and deployed it to five live phone assistants.

🔑 Learning objectives

By the end of this lesson you will be able to:

  • Break a voice-agent's response delay into its stages and reason about which one to attack.
  • Explain time-to-first-token and why a bigger model + bigger prompt is slower on every single turn.
  • Confirm (or refute) a performance complaint from a transcript's timestamps, while respecting their ambiguity.
  • Spot an N+1 query and collapse it with a database nested embed — and validate it before shipping.
  • Recognise shared-config blast radius and scope a change with the spread-override pattern.
  • Make an asymmetric trade-off safely (gate the risky change behind an A/B and a rollback plan).

🧠 Concepts Introduced This Session

Nine ideas carry the whole session. The first four are about finding the latency; the next three are the fixes; the last two are how we shipped them safely.

1 · Anatomy of a voice-agent "turn" (the latency budget)

Plain-English explanation. A "turn" is one back-and-forth: the caller says something, then the agent replies. The gap the caller feels — the silence after they stop talking and before Max starts — is not one delay. It's a relay race of separate stages, each adding a slice of time. To fix "the pause," you have to know which runner in the relay is slow.

Why we need it (for CRM specifically). Our partner said "it pauses 2–3 seconds." If you attack the wrong stage — say, you make the silence-detector trigger faster when the real cost is the model thinking — you spend effort and the caller still waits. Naming the stages is what let us aim at the one that actually mattered.

How it works (analogy). Think of an assembly line. The caller's voice is the raw material; the spoken reply is the finished product. It passes through six stations, and the total wait is the sum of every station's time:

caller stops talking │ ▼ ① ENDPOINTING — "are they actually done, or just pausing?" (~0.1s, we tuned this aggressive) ▼ ② STT FINALIZE — turn the audio into final text (Deepgram) ▼ ③ LLM time-to-first-token — model reads prompt+history, │ decides what to say, emits its FIRST word ← the big one, EVERY turn ▼ ④ TOOL ROUND-TRIP — only on lookup turns: call the backend, │ wait for the database, feed the result back to the model ← extra, lookup turns only ▼ ⑤ LLM SECOND PASS — on tool turns, generate the spoken reply ← extra, lookup turns only ▼ ⑥ TTS first-byte — turn the reply text into the first audio (ElevenLabs) │ ▼ caller hears Max

Jargon decoder.

  • endpointing — the logic that decides the caller has finished speaking (not just taking a breath). Too eager and it cuts people off; too patient and every turn feels laggy.
  • STT (speech-to-text) — converting spoken audio into text. Our engine is Deepgram nova-3.
  • TTS (text-to-speech) — converting the reply text back into spoken audio. Our engine is ElevenLabs.
  • round-trip — a request that leaves our system, does work elsewhere (the backend, the database), and comes back. Each one costs network time.
🔑 Key Concept — find the dominant stage first

The whole session pivots on one realisation: stages ③ and ⑥ are paid on every turn, while ④ and ⑤ are paid only on the lonely lookup turn. So if the caller feels a pause on most replies — including ones with no database lookup — the culprit can't be the database. It has to be the model or the voice. That single deduction is what told us to change the LLM, not the endpointing.

2 · LLM time-to-first-token (why bigger = slower, every turn)

Plain-English explanation. A language model produces its answer one token (roughly, a word-piece) at a time. The delay that matters for "feeling laggy" is time-to-first-token (TTFT) — how long until the first word comes out. Before it can speak word one, the model must read everything you gave it: the system prompt, the conversation so far, and the tool definitions. The more it has to read, and the heavier the model, the longer that first word takes.

Why we need it (for CRM specifically). Max's lease prompt is long — roughly 300 lines of instructions — plus the schemas for three tools, and the whole thing is re-sent on every single turn (the model has no memory between calls; you hand it the full context each time). On a heavy model, reading all that before each reply is exactly the 2–3 second pause the partner felt. Shrinking that delay is the single highest-leverage fix because it's paid on every turn.

How it works (analogy). Imagine a lawyer who must re-read the entire case file from scratch every time you ask a question, before saying a word. A faster reader (a lighter model) gets to "word one" sooner. A shorter file (a smaller prompt) helps too. We chose the faster reader this session.

Jargon decoder.

  • token — a chunk of text the model reads/produces; "Saint-Lazare" might be 3–4 tokens.
  • TTFT (time-to-first-token) — latency until the first output token. The number a human perceives as "responsiveness."
  • prefill — the model reading/encoding all the input tokens before it can generate; longer input = longer prefill.
  • maxTokens — a cap on how long the answer can be. It limits the tail, not the first word, so it barely affects perceived lag (Max's is 300).
  • gpt-4o / gpt-5.2-chat-latest — two OpenAI models; the former is the lighter, lower-latency one we switched to for the lease agent.

Annotated code — the one-line model change. The lease assistant's model lives in a small "shell" config. We changed exactly one field:

"model": {
    "provider": "openai",
    "model": "gpt-4o",          # was "gpt-5.2-chat-latest" — lighter model, lower time-to-first-token
    "messages": [{"role": "system", "content": system_prompt}],  # the ~300-line prompt, re-sent each turn
    "maxTokens": 300,           # caps reply LENGTH (the tail), not the first word — left unchanged
    "temperature": 0.7,         # creativity dial — unchanged
    "tools": tools,             # three tool schemas the model also has to read every turn
},
📖 Deep Dive — why this is the highest-leverage change

Stage ③ (TTFT) appears on every reply, tool or not. If TTFT is ~2s and you shave it to ~0.7s, you save ~1.3s on every single turn of every call. Compare that to optimising the database lookup (stage ④), which only happens once or twice per call. Fixing the per-turn cost beats fixing the per-call cost almost every time. The catch — and the reason this is the scary change — is that a lighter model can be a worse writer (see Concept 7).

3 · Why tool-call turns are the slowest (double pass + a hop)

Plain-English explanation. Most turns are one model pass: read context → speak. But a lookup turn (when Max needs the database) is three things glued together: the model first decides "I should call find_units" (pass one), then we wait for the backend and database (the hop), then the model reads the result and decides what to say (pass two). Two model passes plus a network hop — so the lookup turn is always the longest.

Why we need it (for CRM specifically). The very first thing a caller does is name a city, which triggers find_units. In Transcript3.md that first reply was the slowest gap of the whole call. Knowing the lookup turn is doubly expensive tells us two fixes help here: a faster model (helps both passes) and a faster database lookup (helps the hop, Concept 5).

How it works (analogy). A waiter taking a normal request just answers you. But if you ask "what's the soup today?", the waiter walks to the kitchen, waits, walks back, then tells you. The kitchen trip is the tool hop; the two conversations with you are the two model passes.

The stall phrase is a curtain, not a fix. In Session 09's agent there's a "system-check phrase" — Max says "Un instant, s'il vous plaît" ("one moment please") before a lookup. That exists precisely to fill the lookup-turn silence so it doesn't feel like dead air. But it only covers the lookup turn. On the many non-lookup turns (answering rent, answering an amenities question) there's no phrase by design — so the raw model latency is exposed as bare silence. That's why the partner still heard pauses even though the stall phrase "works."

⚠️ Warning — don't paper over latency you can remove

It's tempting to "fix" perceived pauses by adding more filler phrases. But filler on a non-lookup turn just means Max talks more before answering — it doesn't make him faster, and over-used it sounds robotic (that was the Session-08 over-application bug). Prefer removing the latency (faster model, fewer round-trips) over hiding it.

4 · Reading a transcript forensically (confirm before you fix)

Plain-English explanation. Before changing anything, prove the complaint is real and measure it. A VAPI transcript stamps each turn with a time offset from the start of the call (e.g. (+00:46.23) = 46.23 seconds in). By subtracting consecutive timestamps you can measure the gaps the caller actually experienced.

Why we need it (for CRM specifically). "It feels slow" is a feeling; engineers fix numbers. The timestamps turned a vague complaint into "~3.5–7 seconds between the caller starting and Max replying, on turns with no database lookup" — which both confirmed the pause and pointed straight at the model.

The measured gaps (caller-turn start → Max-turn start, from Transcript3.md):

The gaps include the caller's own speaking time (we only know when each turn starts, not when the caller stopped). Subtract ~1–3 seconds of speech and you land on the partner's "2–3 seconds" of real silence — and crucially, most of those rows have no tool call, which is the proof that the database isn't the main culprit.

⚠️ Warning — respect the ambiguity of timestamps

We don't know exactly when the caller stopped talking, so we can't attribute every millisecond. That's fine — forensics is about the conclusion ("most replies lag 2–4s, lookup or not"), not false precision. State what the data can't tell you; it keeps you honest and stops you over-fitting a fix.

5 · The N+1 query problem & PostgREST nested embeds

Plain-English explanation. When you fetch a list of things and then loop to fetch a related thing for each one, you've made 1 + N database queries — the "N+1 problem." Each query is a separate network round-trip. The fix is to ask the database for everything you need in one query by telling it to include the related rows. In Supabase/PostgREST you do this with a nested embed: name the related table inside your select.

Why we need it (for CRM specifically). Our find_units lookup was doing three sequential queries: first the listings, then the buildings for those listings, then the property groups for those buildings — each waiting on the previous one's IDs. That's three network hops stacked inside stage ④, on the call's slowest (first) turn. Collapsing them to one hop directly shrinks the lookup pause.

How it works (analogy). Instead of phoning the warehouse once for a box, then phoning again for what's in the box, then a third time for the box's shelf label — you send one order that says "the box, its contents, and the shelf label, all together." One call, everything back.

Jargon decoder.

  • PostgREST — the layer Supabase uses to turn database tables into a REST API; it understands "embeds."
  • foreign key (FK) — a column that points at another table's row (here, a flat's building_id points at a buildings row). Embeds only work along declared FKs.
  • to-one — a relationship where each row links to one related row (a flat has one building); PostgREST returns it as a single object (or null), not a list.
  • embed — writing buildings(name, ...) inside a select so the related row comes back nested in the response.

Annotated code — before (3 round-trips). The shape we replaced:

results = q.limit(50).execute()              # query #1: the listings (+ flats, with building_id)
listings = results.data or []

building_ids = list({ r["flats"]["building_id"] for r in listings if ... })
if building_ids:
    b_res = db.table("buildings").select("id, name, property_id").in_("id", building_ids).execute()  # query #2
    for b in (b_res.data or []):
        building_rows[b["id"]] = b
    property_ids = list({ b["property_id"] for b in building_rows.values() if ... })
    if property_ids:
        p_res = db.table("properties_list").select("id, name").in_("id", property_ids).execute()     # query #3
        ...
# 3 sequential round-trips, each waiting on the previous one's IDs

Annotated code — after (1 round-trip). Ask for it all at once, then read the nested objects:

q = (
    db.table("lease_listings")
      .select(
          "uuid, flat_number, title, monthly_rent, available_from, quebec_size, "
          "street_address, city, state, country, "
          # nest buildings INSIDE flats, and properties_list INSIDE buildings -> one query does it all
          "flats!inner(bedrooms, bathrooms, floor_number, buildings(name, properties_list(name)))"
      )
      .eq("is_active", True)
)
results = q.limit(50).execute()              # the ONLY query now

for r in listings:
    flat = r.get("flats") or {}
    building = flat.get("buildings") or {}            # to-one -> a dict, or {} if the flat has no building
    prop_group = building.get("properties_list") or {}
    if not isinstance(prop_group, dict):             # belt-and-suspenders: never let a list crash the call
        prop_group = {}
💡 Tip — embeds only work along declared foreign keys

A nested embed isn't magic; PostgREST can only "walk" a relationship that exists as a real foreign key. We confirmed the chain was navigable because the same embed (one level shallower) was already used elsewhere in the codebase — flats.py does select("*, buildings(name, properties_list(name))"). Reusing a proven pattern is the cheapest way to de-risk a query change.

6 · Shared-config blast radius & the spread-override pattern

Plain-English explanation. When several things reference one shared settings object, editing that object changes all of them at once. The set of things a change can affect is its blast radius. Before editing shared config, you check who uses it — and if you only want to change one user, you make a copy that overrides just the field you need.

Why we need it (for CRM specifically). We wanted a faster text-to-speech model for the lease agent. But the voice settings (VOICE_CONFIG) are shared by three agents — lease, complaint, and tenant. Editing it directly would silently change the complaint and tenant agents' voices too — a change nobody asked for, and one that wouldn't even deploy consistently (our script only pushes lease agents). So we made a lease-only copy.

How it works (analogy). A shared thermostat heats the whole building. If you only want your room warmer, you don't crank the shared dial — you put a small space heater in your room. LEASE_VOICE_CONFIG is that space heater.

Jargon decoder.

  • blast radius — everything a change can affect. Small blast radius = safer change.
  • spread / unpacking — {**base, "key": newvalue} copies every field of base into a new dict, then overrides one key. The original is untouched.

Annotated code — the scoped override. This mirrors a pattern already in the file (COMPLAINT_TRANSCRIBER_CONFIG = {**TRANSCRIBER_CONFIG, ...}):

# Lease agent uses the lower-latency Flash model to cut TTS first-byte on every turn.
# Same voice library / voiceId, so the timbre is unchanged; only the model differs.
LEASE_VOICE_CONFIG = {
    **VOICE_CONFIG,                 # copy EVERY shared setting (voiceId, stability, speed, ...)
    "model": "eleven_flash_v2_5",   # ...then override ONLY the TTS model (was eleven_turbo_v2_5)
}
# VOICE_CONFIG itself is left untouched, so the complaint + tenant agents are unaffected.

Then the lease shell points at the new copy: "voice": LEASE_VOICE_CONFIG (was VOICE_CONFIG). One agent changed; the other two literally cannot be affected.

7 · Asymmetric trade-offs & gating the risky change

Plain-English explanation. Not every change is equally risky. Two of our three fixes (the single query, the Flash voice) are nearly pure wins. The third — the lighter LLM — buys speed but can cost quality: a smaller model may write worse French, skip a qualification step, or call a tool wrong. When the downside of a change is much bigger than its upside in the bad case, the trade-off is asymmetric, and you treat it differently: prove it before trusting it.

Why we need it (for CRM specifically). A 2-second-faster reply is nice. But if the model botches French or drops a qualifying question, you lose the lead — far worse than a slightly slow call. So we recommended A/B testing the model on one manager's agent before all five, and we made it trivially reversible. Speed is worthless if it quietly tanks lead quality.

How it works (analogy). Swapping your tyres for a slicker, faster set helps lap times — but might lose grip in the rain. You don't put them on the whole fleet on a hunch; you test one car in the conditions you actually race in (here: Quebec-French calls), and you keep the old tyres in the garage.

🔑 Key Concept — match your caution to the cost of being wrong

"Safe" and "risky" changes deserve different ceremony. The single query just needed a quick live check. The model swap deserved an A/B plan and a written rollback. Spending equal effort on both would be either reckless (under-testing the model) or wasteful (over-testing the query). Calibrate.

8 · Rollback engineering: config snapshots + an idempotent push

Plain-English explanation. A change you can't undo is a change you should fear. "Rollback engineering" means: before you ship, write down the exact old values and the exact new values, and make sure restoring the old ones is a single, repeatable action. Then a regression is a one-minute fix, not a panic.

Why we need it (for CRM specifically). The user explicitly asked for this: "make note of the previous and this config… so that if we roll back, we can run the script and push." Our deploy script is idempotent — running it just makes the live assistants match the code, no matter how many times you run it. So "rollback" = restore the old value in the code file, then run the same push script. The snapshot document is what makes that restore unambiguous.

How it works (analogy). Before repainting a wall, you write the old paint code on a sticky note. If you hate the new colour, you don't guess — you read the note, buy that exact paint, and roll it back on. The rollback doc is the sticky note; the push script is the roller.

Jargon decoder.

  • idempotent — an operation you can run repeatedly with the same end result. Our push script PATCHes each assistant to match the code; running it twice changes nothing extra.
  • two deploy surfaces — VAPI config (model, voice; pushed by the script) vs backend code (the query; deployed by a git push to Render). They roll back differently — the doc spells out both.

The snapshot we wrote (docs/reference/lease_agent_latency_config_2026-06-23.md) records, for each change, the BEFORE value, the AFTER value, and its specific rollback. Because the model and voice are separate fields, you can roll back just the voice (if French pronunciation regresses) while keeping the faster model — independent levers.

9 · Prompt wording is product behaviour

Plain-English explanation. For an AI agent, the prompt isn't documentation about the product — it is the product's behaviour. Changing one sentence in the prompt changes what real callers are asked on real phone calls. So a prompt edit is a product change and deserves the same care (and the same deploy) as code.

Why we need it (for CRM specifically). The partner wanted Max to stop asking "what do you do for work?" and instead ask whether the caller is employed and, if so, full- or part-time. That's a better question for three reasons: it collects the structured fact the manager actually screens on (employment status), it's less intrusive (no job-title fishing), and it's faster to answer. We changed the one line and added a guard so the model never drifts back to asking the open-ended version.

Annotated change — the employment question.

--- Q4: Employment ---
"Just so the team has the full picture — what do you do for work?"
--- Q4: Employment ---
"Just so the team has the full picture — are you currently employed? And if so, is that full-time or part-time?"
Never ask what the caller does for a living, their job title, or their employer — only whether they are
employed and, if so, whether it is full-time or part-time.

The existing logging branches (full-time / part-time / unemployed) still apply downstream — we only changed the question, not how the answer is recorded.

💡 Tip — pin behaviour with an explicit "never"

Language models drift toward the most natural phrasing they've seen. If you just reword a question, the model may still wander back to the open-ended version. Adding an explicit negative instruction ("never ask job title…") fences the behaviour in. Treat prompts like code with assertions.

🛠️ Step-by-Step Build Log

Every action this session, in order, with why each happens now and what would break if skipped.

Step 1 — Gather the evidence (transcript + prior diagnosis + plan)

We read three things before touching code: Transcript3.md (the new call), the Session-08 pausing/STT diagnosis (to reuse its findings), and PLAN_lease_agent_fuzzy_band_entity_confirmation.md (for the Phase 2/3 question).

Why now: you can't diagnose a pause you haven't measured, and the prior diagnosis already established the architecture. Skip it and you re-derive known facts and risk "fixing" the wrong stage.

Step 2 — Locate the relevant config in the agent file

We searched vapi_agent_config.py for the employment question and the stall-phrase / endpointing settings. This revealed the file has multiple agents in it (Alex the complaint agent around line 27/653; Max the lease agent's prompt in _LEASE_SYSTEM_PROMPT_BASE from ~980) — so we had to target the lease copy specifically.

$ grep -n "what do you do for work\|gpt-5.2\|VOICE_CONFIG\|start_speaking_plan" vapi_agent_config.py 1148: "Just so the team has the full picture — what do you do for work?" 1520: "model": "gpt-5.2-chat-latest", 1536: "start_speaking_plan": {"waitSeconds": 0.1, ... onNumberSeconds: 0.1} # already aggressive

Why now: the endpointing values ruled out stage ① as the cause (it's already 0.1s) — essential for the diagnosis. Skip it and you might "fix" endpointing and achieve nothing.

Step 3 — Diagnose: confirm the pause & name the cause

Using Concept 4's timestamp method we confirmed ~2–4s of real silence on most turns, including non-lookup turns, and tied it to LLM TTFT (Concept 2) on a heavy model with a long prompt — not endpointing. We reported this plus the ranked list of possible fixes.

Why now: the fix list flows from the diagnosis. Skip it and you optimise blind.

Step 4 — Change the employment question (Q4)

One edit to the lease prompt's Q4 (shown in Concept 9), plus the explicit "never ask job title" guard.

Why now: it's an independent, low-risk product change the user asked for; shipping it early gets value live. Skip it and Max keeps asking the intrusive question.

Step 5 — Deploy the prompt change (dry-run, then real)

We pushed only the prompt change first (the latency fixes weren't written yet). Always rehearse with --dry-run.

Why now: the prompt lives on VAPI; the change isn't live until pushed. Skip the dry-run and a bad credential hits production directly.

Step 6 — Answer the Phase 2/3 question (a decision, no code)

We recommended not building Phases 2 (buildings) and 3 (streets) yet. Reasons: they add confirmation turns (more latency — the opposite of the live complaint); Phase 1's thresholds aren't validated yet; data hygiene is a prerequisite; and the plan itself marks Phase 3 optional. Sequence instead: latency → validate Phase 1 → data hygiene → maybe Phase 2.

Why now: deciding not to build is a real deliverable that saves the most time. Skip it and you build low-ROI features that worsen the current complaint.

Step 7 — Present the latency fix menu; take the user's scoping

We listed five possible fixes ranked by impact-to-effort and explained the trade-off of each (Concept 7). The user scoped it: "Render is always warm" (drop #4 keep-alive), "don't do #2" (no prompt trim), "do the rest" (#1 model, #3 query, #5 TTS), and "make note… so we can roll back."

Why now: scoping with the owner avoids wasted work and respects the asymmetric-risk call. Skip it and you might trim the prompt (risking regressions) or chase a non-problem (cold starts that don't exist here).

🐛 Bug Journal — a mostly-clean session

There were no logic bugs in the shipped changes — and that's not luck. Two of the three fixes are exactly the kind that silently break things, and we headed each off before it could. The most valuable lessons this session are the traps we sidestepped, documented in full Bug-Story format below, plus one real (harmless) display artifact.

🐛 Trap #1 (avoided) — the nested embed could have silently broken find_units

🚨 The Symptom (the one we didn't get). Had we shipped the query change untested, the realistic failure is silent: find_units wrapped in a try/except that returns {found: False} on any error. So a bad join wouldn't crash loudly — Max would just stop finding any unit and dump every caller to the "here's what we do have" fallback. A latency fix that quietly kills matching is worse than the latency.

🔍 The Diagnosis (done up front). Two questions had to be true for the embed to work: (1) does the foreign-key chain lease_listings → flats → buildings → properties_list actually exist so PostgREST can walk it? (2) does the deepest relation come back as a single object (to-one) and not a list, since the code calls .get("name") on it? We answered both with evidence: grepped and found flats.py already embeds buildings(name, properties_list(name)); confirmed FK declarations in the migrations; then ran the deeper embed live and printed the Python type of each nested value.

🧠 The Root Cause it would have had. Two classic ORM/REST footguns: an embed only works along a declared FK (an undeclared one returns nothing), and a to-many relation returns a list — calling .get() on a list throws. We weren't sure of either from reading alone, so we measured.

🔧 The Fix (preventive). Validate on real data before deploying (Step 8), and add a defensive guard so even an unexpected shape degrades gracefully:

prop_group = building.get("properties_list") or {}   # to-one -> dict; null -> {}
if not isinstance(prop_group, dict):                  # if it ever comes back a list, don't crash
    prop_group = {}                                   # the loop continues; this listing just lacks a property name

🛡️ The Lesson. When a change touches a live, hard-to-observe path (a phone call), buy certainty cheaply before you ship: reuse a proven pattern, confirm your assumptions against real data, and guard the shapes you're unsure of. "It compiled" is not "it works."

🐛 Trap #2 (avoided) — editing shared VOICE_CONFIG would have changed three agents

🚨 The Symptom (the one we didn't get). Change the TTS model directly in VOICE_CONFIG and the complaint and tenant agents quietly inherit it too — a voice change nobody requested. Worse, our deploy script only pushes lease agents, so the code would say one thing while two live agents still ran the old voice: a config-vs-reality mismatch that's maddening to debug later.

🔍 The Diagnosis (done up front). Before editing, we grepped for every use of VOICE_CONFIG and found three: build_assistant_config (tenant), build_complaint_config (complaint), and _lease_assistant_shell (lease). Three references = blast radius of three.

🧠 The Root Cause it would have had. Shared mutable config: one object, many owners. The "obvious" edit has a blast radius far larger than the intent.

🔧 The Fix (preventive). Make a lease-only copy with the spread-override pattern (Concept 6) and repoint only the lease shell — exactly mirroring the file's existing COMPLAINT_TRANSCRIBER_CONFIG = {**TRANSCRIBER_CONFIG, ...} convention.

🛡️ The Lesson. Before editing a shared constant, grep its usages and count the blast radius. To change one consumer, branch a copy — don't mutate the shared one. Bonus: follow an existing pattern in the file so the next reader recognises it instantly.

🐛 Bug #3 (real, harmless) — the deploy output printed � for an em-dash

🚨 The Symptom. The script's banner came back mangled:

DRY RUN � no changes will be made

🧠 The Root Cause. The script prints an em-dash (—, a non-ASCII character). The Windows console's legacy code page can't represent it, so it shows the replacement glyph �. The script ran perfectly — only the display of one character was lossy. (This is the same class as Session 09's UnicodeEncodeError on →, but milder: here it degrades to a placeholder instead of throwing.)

🔧 The Fix. None needed — it's cosmetic. The verification that matters (5 updated, 0 failed) printed fine. If you want clean output, set the console to UTF-8 or stick to ASCII in script banners.

🛡️ The Lesson. Separate "is the program wrong?" from "is my terminal mangling the display?" A garbled character in output almost never means the work failed. Read the result line, not the decoration.

💡 Why so few bugs?

This was a measure-and-tune session, not a build-new-features session. The changes were small and surgical (one model field, one voice copy, one query rewrite, one prompt line), and we front-loaded the risk checks (live validation, usage grep) instead of discovering failures after deploy. Fewer integration points + verification before shipping = a clean log.

🧯 Troubleshooting / Common Errors

find_units returns matches but building_name/property_name are empty

Either the backend on Render is still the old 3-query version (redeploy), or the embed walked a relation that returned null for that row (a flat with no building — expected; or {} handles it). Re-run the live validation script to see the real shapes.

The agent still asks "what do you do for work?"

The prompt change didn't deploy. Re-run update_lease_agents.py (config changes on VAPI aren't live until pushed), and confirm you edited the lease Q4 (~line 1148), not a different agent's prompt in the same file.

Replies feel more sluggish, not less, after the model swap

Confirm the push actually applied (the script prints each assistant's model? if not, GET the assistant from VAPI to inspect). If gpt-4o is genuinely slower for your traffic, roll back the model field per the rollback doc — that's exactly why we wrote it.

Console shows � or a UnicodeEncodeError when running scripts

A display/encoding issue on Windows, not a failure. The file/work is fine. Read the result line; if you want clean output, switch the console to UTF-8. See Bug #3.

Deploy says [FAIL] HTTP 401

A bad/expired PRIVATE_VAPI_API key in .env. The script verifies each assistant after patching and reports per-agent OK/FAIL — fix the key and re-run (it's idempotent).

The single-query refactor crashes with an AttributeError on .get

A nested relation came back as a list, not a dict (a to-many you didn't expect). The isinstance(..., dict) guard prevents this for properties_list; if it happens elsewhere, add the same guard. See Trap #1.
