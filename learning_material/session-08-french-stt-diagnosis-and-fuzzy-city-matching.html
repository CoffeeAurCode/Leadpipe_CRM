French Voice-Agent Diagnosis & Fuzzy-Band City Matching

A French-speaking partner ran two test calls against our leasing voice agent and reported two things: "it pauses a lot saying one moment" and "it doesn't understand me." This session is the detective work that confirmed both — and the matcher we built so the agent can finally tell Saint-Lazare from Saint-Lazaire without bothering the caller about Châteauguay.

🧠 Concepts Introduced This Session

Seven ideas carry the whole session. Read these once and the build log and bug journal will feel obvious.

1 · Speech-to-Text and language:"multi"

Plain-English explanation. STT (Speech-To-Text, also called ASR — Automatic Speech Recognition) is the part of a voice agent that turns the sound of a person talking into written words. It's the agent's "ears." Everything downstream — the language model, the database lookup — only ever sees the text STT produced. If the ears mishear, the whole brain reasons about the wrong words. Garbage in, garbage out.

Why we need it (for CRM specifically). Our callers are prospective tenants in Quebec. They speak French, English, or both in the same breath. Max literally cannot find a unit if STT writes down the wrong city. A mishear here doesn't just annoy the caller — it loses a paying lead.

How it works (analogy). Imagine a court stenographer who trained mostly on English. Sit a strong-accented Québécois speaker in front of them and ask them to transcribe live, one word at a time, with no chance to rewind. When the speaker says "Saint-Lazare," the stenographer hears sounds that don't map to any English word they know, and writes down the closest English-shaped thing: "Saint-L'Asor." That stenographer is our STT engine.

Jargon decoder.

  • Deepgram — the company/engine doing our STT. nova-3 is the specific model version.
  • language:"multi" — a setting that tells Deepgram "don't lock to one language; auto-detect English and French on the fly." Necessary, because we don't know which language the caller will use — but it's also where accented proper nouns get mangled worst.
  • Transcriber — the STT component of the voice stack, configured separately from the voice and the brain.
  • confidenceThreshold — a number from 0 to 1. If STT is less sure than this about a chunk of audio, it drops it rather than guess. Ours is 0.4.
  • WER (Word Error Rate) — the standard score for STT quality: what fraction of words it got wrong. Lower is better.
  • Code-switching — switching language mid-sentence ("Oui, I'm interested in the trois et demi"). Hard for STT.

Annotated config — our real transcriber. This is the exact block that decides Max's "ears":

# Transcriber — Deepgram nova-3 with an OpenAI fallback.
TRANSCRIBER_CONFIG = {
    "provider": "deepgram",        # which STT company we use
    "model": "nova-3",             # the model version (their multilingual flagship)
    "language": "multi",           # auto-detect EN + FR — needed, but the source of bug #2
    "numerals": True,              # write "two" as "2" — makes prices/sizes easy to parse later
    "confidenceThreshold": 0.4,    # below this confidence, DROP the audio chunk (don't guess)
    "fallbackPlan": {              # if Deepgram fails entirely, switch engines mid-call
        "transcribers": [
            {
                "provider": "openai",
                "model": "gpt-4o-transcribe",   # a different STT engine as a safety net
                # no language lock — OpenAI auto-detects EN/FR too
            }
        ]
    },
}
📖 Deep Dive — why "multi" mangles French names

A monolingual French model carries strong priors about French phonotactics (which sound sequences are legal in French). In multi mode the model is hedging across two languages at once, so a strongly French-accented proper noun — which is rare in its training data and ambiguous between two languages — collapses to whichever spelling scored highest, often an English-shaped one. The result isn't random noise; it's a confident wrong word. That confidence is exactly what makes it dangerous downstream.

2 · The agent's flow — designed vs. observed

Plain-English explanation. A voice agent has a script (the "system prompt" — the long instruction text that tells the AI how to behave) describing the conversation it's supposed to run. But the AI improvises around what the caller actually says. So there are always two flows: the one written in code, and the one that really happened on the call. Diagnosing a voice agent means putting them side by side.

Why we need it (for CRM). If the designed flow and the real flow diverge, you'll fix the wrong thing. We almost "fixed" a search step that, it turned out, never even ran.

Jargon decoder. A tool (or "function call") is something the AI can ask the backend to do mid-conversation — here, find_units (look up units), search_listings (filter inventory), submit_lease_lead (save the lead). The prompt defines them; the model decides when to call them.

The designed flow (from the prompt) is a tidy funnel:

① GREETING → "Hi/Bonjour, I'm Max for [Manager]" → detect language → LOCK ② DISCOVERY → ask city → find_units → size → budget → search_listings → present → caller picks ③ QUALIFICATION → move-in date → landlord aware? → questions → employment → occupants → pets → name ④ HANDOFF → closing line → submit_lease_lead (exactly once, every call)

The observed flow (from the two transcripts) was caller-driven and collapsed — and crucially, only find_units ever ran. search_listings and submit_lease_lead never fired in either call. Why? Because of one fact we discovered by reading the route's code:

# find_units doesn't just say "yes, that city exists." For every match it returns
# the WHOLE listing — rent, address, size, availability — enough to quote the unit.
matches.append({
    "listing_uuid":  r["uuid"],              # the unit's unique id
    "flat_number":   r["flat_number"],
    "building_name": building.get("name") or "",
    "address":       ", ".join(...),         # full street address
    "quebec_size":   r.get("quebec_size") or "",   # e.g. "4½"
    "monthly_rent":  float(r["monthly_rent"]),     # e.g. 1400.0  ← the price, already here!
    "available_from": str(r.get("available_from") or ""),  # move-in date, already here!
})

Because find_units already hands back the rent, address and availability, Max can quote a full unit from that one call. The separate search_listings step in the designed funnel is redundant for a small portfolio — so the model skips it. The designed flow imagined find_units as a cheap "does this city exist?" gate; in reality it is a full search. That mismatch is the lesson: the prompt's funnel didn't match the tool's real behaviour.

3 · System-check "filler" phrases (the "one moment" feature)

Plain-English explanation. When the agent runs a tool, there's a pause while the backend answers. Dead silence on a phone feels broken, so the agent says a short "hang on" phrase to fill the gap — a filler phrase. A prior session made these bilingual (matched to the call language) and rotating (a different phrase each time, never repeating back-to-back).

Why we need it (for CRM). Callers abandon calls that feel dead or robotic. Good filler keeps the call feeling alive. But — as bug #1 shows — too much filler is its own failure.

The exact phrases, straight from the prompt — keep these in mind, you'll recognise every one of them in the transcripts:

The FIRST system check of the call — say this exact phrase:
  English: "Let me check that in my system. One moment please."
  French:  "Laissez-moi vérifier ça dans mon système. Un instant, s'il vous plaît."

EVERY system check after the first — pick ONE at random, never repeat the previous one:
  French:
    - "Un instant, je vérifie ça pour vous."
    - "Laissez-moi regarder ça rapidement."
    - "Juste un moment."
    - "Je vérifie ça tout de suite."

4 · Fuzzy string matching (and where it breaks)

Plain-English explanation. "Fuzzy matching" means deciding whether two pieces of text are close enough to be the same thing, even if they aren't identical. The classic tool is a similarity ratio: a number from 0 (nothing alike) to 1 (identical) based on how many edits turn one string into the other. Python's built-in difflib.SequenceMatcher gives exactly this.

Why we need it (for CRM). A caller never says a city exactly as it's spelled in our database. We need "saint lazare", "St-Lazare", and "saint-lazare" to all match the listing's Saint-Lazare.

How it works (analogy). Think of it as counting keystrokes: how many letters do you insert, delete, or swap to turn "Saint Lazole" into "Saint Lazare"? Few edits → high ratio → probably the same place.

Here is the matcher we already had before this session — the starting point we extended:

import difflib, unicodedata

def normalize_place(s: str) -> str:
    # Strip accents, lowercase, drop hyphens, expand "St"→"Saint" so spellings line up.
    if not s: return ""
    s = unicodedata.normalize("NFKD", s)                       # split accented chars
    s = "".join(c for c in s if not unicodedata.combining(c))  # …and remove the accents
    s = s.lower().replace("-", " ")                            # "Saint-Lazare" → "saint lazare"
    out = []
    for tok in s.split():
        tok = tok.strip(".,'")
        if tok in ("st", "st."):   out.append("saint")        # normalise the abbreviation
        elif tok in ("ste", "ste."): out.append("sainte")
        elif tok: out.append(tok)
    return " ".join(out)

def city_matches(query_norm: str, city_norm: str, threshold: float = 0.82) -> bool:
    if not query_norm or not city_norm: return False
    if query_norm in city_norm or city_norm in query_norm: return True   # substring hit
    # The core fuzzy test: edit-distance ratio must clear 0.82 to count as a match.
    return difflib.SequenceMatcher(None, query_norm, city_norm).ratio() >= 0.82
⚠️ Warning — the trap that defines this whole session

difflib compares letters, not sounds. The real STT garble is the opposite: it sounds like the city but is spelled very differently. "Saint-L'Asor" vs "Saint-Lazare" scores only ~0.55 by letters — below threshold — even though they're near-homophones. A pure string matcher misses exactly the cases we care about. That's why we need the next concept.

5 · Phonetic matching (matching by sound)

Plain-English explanation. A phonetic algorithm reduces a word to a code that represents how it sounds, so that words which sound alike get the same (or similar) code regardless of spelling. Match the codes instead of the letters, and "Saint-L'Asor" can finally meet "Saint-Lazare."

Jargon decoder — the family of algorithms.

  • Soundex — the oldest (1918!), very crude, English-only. Keeps a letter + 3 digits. Too lossy for us.
  • Metaphone / Double Metaphone — smarter English phonetics; Double Metaphone returns two codes to capture alternate pronunciations. Available in the jellyfish Python library.
  • Beider-Morse (BMPM) — built for matching names across languages, with an actual French ruleset. Most accurate for French, but heavier/slower (in the abydos library).
🔑 Key Concept — this is a cross-orthography problem

Here's the subtlety that decided our algorithm choice. Our input is not clean French — it's Deepgram's English-ish spelling of French-accented audio ("Captain mi" for quatre et demi). So we're matching a pseudo-English garble against a canonical French name. A French-only encoder applied to an English-spelled token can actually do worse. The lesson: don't bet on one encoder — score by sound with a sound-based encoder (Double Metaphone), and combine it with edit-distance, taking the best of both.

Our resolved scoring function — the hybrid we shipped:

import difflib
from rapidfuzz import fuzz          # fast, robust edit-distance ratios
import jellyfish                    # Double Metaphone (sound codes)

def _phonetic_match(a: str, b: str) -> float:
    # Encode both words to their sound-codes; 1.0 if a code matches, else 0.0.
    ca, cb = jellyfish.metaphone(a), jellyfish.metaphone(b)
    return 1.0 if ca and ca == cb else 0.0

def similarity(spoken: str, candidate: str) -> float:
    # Run all three scorers and keep the BEST. Each catches a different failure mode:
    a, b = normalize_place(spoken), normalize_place(candidate)
    return max(
        fuzz.ratio(a, b) / 100.0,                     # edit-distance garble ("Saint Lazole")
        _phonetic_match(a, b),                        # sound-alike, spelled-different ("Saint-L'Asor")
        difflib.SequenceMatcher(None, a, b).ratio(),  # the original baseline, kept as a floor
    )

6 · Confidence banding — the three-zone decision

Plain-English explanation. Once we can score how close the caller's word is to each real city, we still have to decide what to do with those scores. Banding splits the decision into three zones:

  1. Auto-accept — one candidate is clearly the best. Just proceed; don't bother the caller.
  2. Confirm — two (or more) candidates are about equally close, i.e. genuinely confusable. Ask the caller to pick between only those.
  3. No-match — nothing is close. Fall back to reading the manager's full city list.

Why we need it (for CRM). This is the partner's exact idea: confirm Saint-Lazare vs Saint-Lazaire (sound alike) but never drag in Châteauguay (sounds nothing alike). Banding is what encodes "genuinely confusable."

The two gaps that matter. A high top score alone isn't enough — what matters is the gap to the runner-up:

  • MARGIN — how far ahead #1 must be over #2 to count as a "clear winner." Big gap → auto-accept. Small gap → ambiguous → confirm.
  • BAND — how close to #1 a candidate must score to join the confirmation question. This is the rule that keeps Châteauguay out: it isn't within BAND of the top, so it's excluded.
# Starting thresholds (tune later against a real corpus — see the build log).
T_HIGH    = 0.86   # "clearly a match" score
MARGIN    = 0.08   # #1 must beat #2 by this much to auto-accept
T_CONFIRM = 0.66   # at/above this but no clear winner → ask the caller
BAND      = 0.06   # candidates within this of the top join the question
T_FLOOR   = 0.55   # below this → nothing is close → no-match
N_MAX     = 3      # never read more than 3 options aloud

def rank_candidates(spoken: str, candidates: list[str]) -> dict:
    # Score the caller's word against every real city the manager has.
    scored = sorted(
        ((c, similarity(spoken, c)) for c in candidates),
        key=lambda cs: cs[1], reverse=True,           # best score first
    )
    if not scored:
        return {"decision": "NO_MATCH", "candidates": []}

    top_city, top = scored[0]
    second = scored[1][1] if len(scored) > 1 else 0.0  # runner-up's score (0 if only one)

    if top >= T_HIGH and (top - second) >= MARGIN:
        # Clear winner: one city well ahead of the rest → proceed silently.
        return {"decision": "AUTO_ACCEPT", "city": top_city}

    if top >= T_CONFIRM:
        # Ambiguous: gather everyone within BAND of the top, capped at N_MAX, and ask.
        near = [c for c, s in scored if s >= top - BAND][:N_MAX]
        return {"decision": "CONFIRM", "candidates": near}

    # Nothing close enough to trust → let the caller hear the real city list.
    return {"decision": "NO_MATCH", "candidates": []}
💡 Tip — why the gap, not just the height

A score of 0.90 sounds great — but if the runner-up is also 0.89, you have two great matches and no idea which the caller meant. The MARGIN check is what turns "high score" into "confident." This is the single most important line in the function.

7 · The fix family — A1, B1, B2 (and why we chose B2)

The broader plan named several complementary fixes. You'll see these labels in the build log and the "What's Next" section, so here's the decoder:

if result["decision"] == "CONFIRM":
    # Attach each confusable city's rent range so the agent can ask "1400 or 1600?"
    disambiguation = {
        "needs_confirmation": True,
        "field": "city",

import pytest
from backend.app.services.city_matching import rank_candidates

CITIES = ["Saint-Lazare", "Chateauguay"]   # the partner's real portfolio

def test_clean_city_auto_accepts():
    # A clean spelling should NOT pester the caller.
    assert rank_candidates("Saint-Lazare", CITIES)["decision"] == "AUTO_ACCEPT"

def test_garbled_but_phonetically_close_recovers():
    # The real STT garble must still resolve to the right city.
    out = rank_candidates("Saint-L'Asor", CITIES)
    assert out["decision"] in ("AUTO_ACCEPT", "CONFIRM")

def test_distinct_cities_never_share_a_band():
    # Regression guard: Chateauguay must NEVER join a Saint-Lazare confirmation.
    out = rank_candidates("Saint-Lazar", CITIES)
    names = out.get("candidates", [])
    assert "Chateauguay" not in names

def test_pure_noise_falls_through_to_no_match():
    assert rank_candidates("thing on low", CITIES)["decision"] == "NO_MATCH"

[find_units] Max: "Laissez-moi vérifier ça dans mon système. Un instant s'il vous plaît. …Château Gué et Saint-Laçore?" [find_units] Max: "Un instant, je vérifie ça pour vous, parfait… 3½ ou 4½?" (no tool ran) Max: "Juste un moment, …quatorze cent par mois…" [find_units] Max: "Je vérifie ça tout de suite, parfait…"

🔍 The diagnosis. We listed each filler against the prompt's phrase list and confirmed they were the exact mandated phrases, rotating correctly. So the feature was working — the problem was frequency. We then counted tool calls: find_units fired three times in one short call (once per garbled-then-corrected city), and one filler even fired on a turn with no tool call at all (the third line above).

🧠 The root cause. A feature shipped that same week mandates a filler before every lookup. Two things compound it: (1) the agent re-calls find_units every time the city is unclear, so each mis-hear earns another filler; (2) the model over-applies the phrase even when it isn't actually looking anything up. It's not a code error — it's a UX consequence of an otherwise-correct feature interacting with a high lookup rate.

🔧 The fix (designed). Two prompt-level changes: only speak a filler on turns where a tool truly runs, and don't re-call find_units for a city the call already resolved (cache it for the turn). Plus — and this is the deeper fix — reduce the number of lookups by getting the city right the first time, which is what Bug #2's fix does.

🛡️ The lesson. A feature can be implemented perfectly and still be a bug at the system level. "Working as specified" and "good experience" are different tests. When you add an action that fires on an event, always ask: how often does that event actually fire?

🐛 Bug #2 — "It doesn't understand me" (STT garble)

🚨 The symptom. The caller's French came back as English gibberish (see the corpus in Step 3): "thing on low", "Captain mi", "Saint-L'Asor". The agent then searched on the garbled token and even spoke it back: "Je ne trouve rien à Saint-LaSort…"

🔍 The diagnosis. We checked the transcriber config and found language:"multi". We cross-referenced a prior session that had already flagged this exact failure mode, and confirmed the garble was at the STT layer, before any of our matching code ran. We ruled out the backend matcher by noting that even a clean "Saint-Lazare" would be fine — the problem is the input never arrives clean.

🧠 The root cause. multi mode hedges across English and French, so strongly French-accented proper nouns collapse to a confident English-shaped spelling. No downstream string matcher can recover a word that's been phonetically rewritten — and lowering the match threshold to catch it would start matching genuinely different nearby cities.

🔧 The fix. Two layers. Long-term: bias the STT itself (A1 keyterm prompting) and/or let the model canonicalize (B1). This session: make the matcher phonetic so mild garble ("Saint-L'Asor") still resolves, and add banded confirmation for the genuinely ambiguous cases. Before/after, the matcher's core test:

# BEFORE — letters only. "Saint-L'Asor" vs "Saint-Lazare" ≈ 0.55 → MISS.
return difflib.SequenceMatcher(None, a, b).ratio() >= 0.82

# AFTER — best of edit-distance AND sound. The phonetic code rescues the near-homophone.
return max(
    fuzz.ratio(a, b) / 100.0,
    _phonetic_match(a, b),                        # ← sound-based; the new escape hatch
    difflib.SequenceMatcher(None, a, b).ratio(),
)

🛡️ The lesson. Know which layer a bug lives in before you touch code. A mishearing is an ears problem; no amount of cleverness in the brain fully fixes it. And when matching human speech, remember that spelling-distance and sound-distance are different metrics — pick the one that matches the failure.

🐛 Bug #3 — The blank company name in the greeting

🚨 The symptom. Transcript 1 opens: "I'm Max, the AI leasing assistant for. Are you looking…" — the manager/business name rendered as nothing, leaving a dangling "for." Transcript 2 rendered it fine ("…for Chantellery").

🔍 The diagnosis. Same prompt, two different outcomes → the bug is intermittent and tied to a missing variable, not the prompt text. A prior session had already noted this exact symptom, so we logged it as a recurring first-message/variable bug rather than re-investigating from scratch.

🧠 The root cause. The greeting interpolates a business-name variable that is sometimes empty at call time (a provisioning/timing gap). With no fallback, an empty value prints literally as "for."

🔧 The fix (designed). Give the greeting a graceful fallback so an empty name never reaches the caller — e.g. drop the "for [name]" clause entirely when the name is blank.

🛡️ The lesson. Any value you splice into user-facing text needs a defined behaviour for "empty." Never assume a variable is populated just because it usually is.

🐛 Bug #4 — The agent's own French was broken

🚨 The symptom. Max said "Tu n'es pas bien compris" (grammatically wrong; it should be "Je n'ai pas bien compris" = "I didn't quite catch that") and switched from the formal vous to the informal tu mid-call. A screening question also came out as a garbled run-on.

🔍 The diagnosis. This text came from the model, not from STT (it's in Max's output, not the caller's). We checked the prompt's language rules: they lock the call to one language but say nothing about keeping a consistent register (vous vs tu).

🧠 The root cause. The prompt under-specifies French register. The model, left to improvise, drifts between formality levels and occasionally produces malformed French — which, ironically, makes the agent look like it doesn't understand.

🔧 The fix (designed). Add an explicit "always use vous; never switch to tu" rule and a corrected stock phrase for "I didn't catch that."

🛡️ The lesson. With language models, anything you don't pin down, the model will improvise — and improvisation in a second language is where polish dies. Specify register, not just language.

🐛 Bug #5 — Double re-prompt into silence

🚨 The symptom. In Transcript 1, Max asked for the city, then asked again 11 seconds later with no caller turn in between — talking into a gap.

🔍 The diagnosis. We looked at the caller's prior turn: it was garbled to a low-confidence token. With confidenceThreshold:0.4, STT dropped it, so the agent received nothing and re-prompted — twice.

🧠 The root cause. The confidence floor that protects against noise also silently deletes hard-to-hear real speech, leaving the agent with a void it fills by repeating itself.

🔧 The fix (designed). Tune endpointing/timeout so a single dropped token doesn't trigger an immediate second prompt — ask once, then wait a beat.

🛡️ The lesson. Every safety threshold has a cost on the other side. A filter that removes bad input also removes some good input; design for what happens when it does.

🐛 Bug #6 (architectural) — a tool that never runs

🚨 The symptom. The designed flow calls search_listings and submit_lease_lead; neither appeared in either transcript. No lead was captured on either call.

🔍 The diagnosis. We read what find_units returns (Concept 2) and saw it already includes rent/address/availability — everything search_listings would add. So the model rationally skips the redundant step. Lead capture didn't happen simply because both calls ended early (one broke on STT garble; one was cut short).

🧠 The root cause. The prompt's mental model of find_units ("a cheap existence check") doesn't match its real behaviour ("a full search"). The funnel was designed around an assumption the code contradicts.

🔧 The fix (noted, not yet shipped). Either make find_units a lean gate and push detail into search_listings, or formally collapse the two steps in the prompt. Documented for a follow-up.

🛡️ The lesson. Read what your functions actually return before you design a flow around them. "Designed flow" and "observed flow" must be reconciled or you'll optimize code paths that never execute.

💡 Note — there were no tooling bugs this session

Our own work (reading files, writing the report, editing the plan) ran clean — this was a diagnosis/design session, so the integration points that usually break weren't touched. Every "bug" above is a diagnosed production behaviour, which is exactly the point: the richest debugging happens on systems you didn't just write.

🧯 Troubleshooting / Common Errors

ModuleNotFoundError: No module named 'rapidfuzz' (or 'jellyfish')

The Phase-1 matcher added two dependencies. Install them into the backend virtual environment (the isolated Python that runs the server): .venv/Scripts/python.exe -m pip install rapidfuzz jellyfish, then add both to requirements.txt so deploys get them too.

The agent confirms the city on every call (too chatty)

Your thresholds are too aggressive — the auto-accept zone is too small. Raise T_HIGH toward 0.90 and/or increase MARGIN so clear winners pass without a question. Confirm-rate per call should be low; if it's high, the band is doing too much.

Two clearly different cities show up in the same confirmation list

BAND is too wide, or the phonetic encoder is collapsing distinct sounds. Lower BAND first. If that doesn't help, your encoder is too lossy for these names — this is the signal to try Beider-Morse French.

A clean French city still isn't matched at all

Check normalize_place first — if accents/hyphens aren't being stripped on both sides, the scores will be artificially low. Then verify the city is actually in the manager's active listings (an empty available_cities means the portfolio, not the matcher, is the problem).

Deepgram still writes English gibberish even after the matcher fix

Expected for severe garble ("thing on low"). Banding only rescues mild garble that stays phonetically near a real city; the rest correctly falls to the available_cities offer. The real fix for severe garble is upstream: A1 keyterm prompting (next session) or switching transcribers.
