Section 1 — Dashboard Architecture

The dashboard is a data-dense view that shows 4 KPI cards and 4 charts, all driven by the same complaints and appointments data, all filterable by time range. The key design challenge: keeping all chart calculations fast while letting the user switch between 7d / 30d / 3m ranges instantly.

BentoDashboard (parent) │ receives: complaints[], appointments[] │ owns: timeRange state ('7d' | '30d' | '3m') │ ├── useMemo: cutoff (derived from timeRange) ├── useMemo: filteredByTime (complaints filtered by cutoff) ├── useMemo: kpis {total, pending, inProgress, appointmentsToday} ├── useMemo: trendsData [{date, complaints}] ├── useMemo: statusData [{name, value}] ├── useMemo: categoriesData [{name, value}] ├── useMemo: appointmentsBarData [{day, count}] │ ├── KPICard × 4 (animated number display) ├── TrendsChart (LineChart — complaints over time) ├── StatusDonut (PieChart with hole — status breakdown) ├── CategoriesPie (PieChart — complaint categories) ├── AppointmentsBar (BarChart — appointments by day of week) ├── DashboardListModal (modal for drill-down on KPI click) └── DailyTasksModal (modal for today's appointments)

All data transformations happen in useMemo hooks at the parent level. The chart components receive pre-formatted arrays and just render them — no data logic in chart components. This separation makes charts reusable and makes the data logic easy to test in isolation.

Section 2 — BentoDashboard.jsx Line-by-Line

Part A — Time range setup and cutoff calculation

const TIME_RANGES = [
    { label: '7d', days: 7 },
    { label: '30d', days: 30 },
    { label: '3m', days: 90 },
];

const DAY_ORDER = ['Mon', 'Tue', 'Wed', 'Thu', 'Fri', 'Sat', 'Sun'];
Module-level constants — defined outside the component so they're not recreated on every render. TIME_RANGES drives both the toggle buttons and the cutoff calculation. DAY_ORDER is used to ensure the appointments bar chart shows days in Mon→Sun order, not whatever order they appear in the data. 
const cutoff = useMemo(() => {
    const days = TIME_RANGES.find(r => r.label === timeRange)?.days ?? 7;
    return subDays(new Date(), days);
}, [timeRange]);
useMemo for the cutoff date: The cutoff is a Date object representing "N days ago." It's memoized because it's used as a dependency by multiple downstream useMemo hooks — if it were computed inline, React wouldn't be able to detect that it's the same value between renders, and all downstream memos would recompute unnecessarily.

subDays(new Date(), days): date-fns utility. new Date() is "now." subDays(now, 7) gives exactly 7 days ago at the current time. The ?.days ?? 7 handles the edge case where timeRange is somehow not in TIME_RANGES — default to 7 days.

Part B — Filtered complaints

const filteredByTime = useMemo(
    () => complaints.filter(c => new Date(c.created_at) >= cutoff),
    [complaints, cutoff]
);
Why useMemo here: This computation runs every time the time range changes. Without useMemo, it would also run on every parent re-render (e.g., every time the modal state changes). For a manager with thousands of complaints, this filter is not free. useMemo ensures the filter only re-runs when complaints or cutoff actually changes.

Dependency array [complaints, cutoff]: This memo re-runs when either the raw data (from API) changes or the time range changes (which changes cutoff). Both are correct invalidation conditions.

Part C — KPI calculations

const kpis = useMemo(() => ({
    total: filteredByTime.length,
    pending: filteredByTime.filter(c => c.status === STATUS.PENDING).length,
    inProgress: filteredByTime.filter(c => c.status === STATUS.IN_PROGRESS).length,
    appointmentsToday: appointments.filter(a => {
        try { return a.appointment_date && isToday(parseISO(a.appointment_date)); }
        catch { return false; }
    }).length,
}), [filteredByTime, appointments]);
Four KPIs in one memo: Computing them together is more efficient than four separate useMemo calls — one function call instead of four, and they share the same dependency array.

STATUS.PENDING — imported from constants/status.js. Using a constant prevents typos (you'd get a linter error if the constant doesn't exist, but not if you misspell 'pedning').

isToday(parseISO(...)) in a try/catch: parseISO throws if the string isn't valid ISO format. For a list of potentially many appointments, one malformed date shouldn't crash the entire KPI calculation. The catch returns false (exclude malformed dates from the count) — a safe fallback.

appointmentsToday uses all appointments, not filteredByTime: Today's appointments should always show today's count regardless of the selected time range. If the time range is "7d" and there are 3 appointments today, you still want to see 3, not filter it by time range.

Part D — Trends data transformation

const trendsData = useMemo(() => {
    const grouped = new Map();
    [...filteredByTime]
        .sort((a, b) => new Date(a.created_at) - new Date(b.created_at))
        .forEach(c => {
            try {
                const d = format(
                    parseISO(c.created_at.endsWith('Z') ? c.created_at : c.created_at + 'Z'),
                    'MMM dd'
                );
                grouped.set(d, (grouped.get(d) || 0) + 1);
            } catch { /* skip malformed dates */ }
        });
    return Array.from(grouped.entries()).map(([date, complaints]) => ({ date, complaints }));
}, [filteredByTime]);
Grouping by day: The LineChart needs one data point per day. Multiple complaints on the same day must be counted together. A Map is used instead of a plain object because Map preserves insertion order — since we sort before iterating, the Map retains chronological order.

[...filteredByTime].sort(...): Spread into a new array before sorting because Array.sort mutates the original array. We never want to mutate filteredByTime (which is a memo-cached array) because that would invalidate other memos that depend on it.

UTC suffix normalization: Same pattern as formatDate in apiService — appending Z ensures JavaScript treats the timestamp as UTC before parsing. Without it, the day grouping would be off by the local timezone.

format(..., 'MMM dd'): Formats as "Jan 15", "Jan 16" etc. These strings become the X-axis labels in the chart. Using the same format for all dates ensures consistent grouping.

Part E — Appointments bar data

const appointmentsBarData = useMemo(() => {
    const counts = Object.fromEntries(DAY_ORDER.map(d => [d, 0]));
    appointments
        .filter(a => {
            try { return a.appointment_date && new Date(a.appointment_date) >= cutoff; }
            catch { return false; }
        })
        .forEach(a => {
            try {
                const day = format(parseISO(a.appointment_date), 'EEE');
                if (day in counts) counts[day]++;
            } catch { /* skip */ }
        });
    return DAY_ORDER.map(day => ({ day, count: counts[day] }));
}, [appointments, cutoff]);
Pre-seeded zero counts: Object.fromEntries(DAY_ORDER.map(d => [d, 0])) creates { Mon: 0, Tue: 0, ..., Sun: 0 }. This ensures all 7 days always appear in the chart, even if there are zero appointments on some days. Without pre-seeding, missing days would create gaps in the bar chart.

format(..., 'EEE'): date-fns format code for abbreviated day name: "Mon", "Tue", etc. The if (day in counts) guard protects against edge cases where format returns an unexpected string.

Final mapping preserves order: The last return DAY_ORDER.map(...) ensures the chart data is always in Mon→Sun order, not whatever order the appointments happened to appear in.

Part F — KPI click handlers and modals

    const openKpiModal = (title, list) => setActiveModal({ title, complaints: list });
    const closeKpiModal = () => setActiveModal(null);

    const todayAppointments = useMemo(() => appointments.filter(a => {
        try { return a.appointment_date && isToday(parseISO(a.appointment_date)); }
        catch { return false; }
    }), [appointments]);
KPI cards are clickable: Clicking "Total Complaints" opens a modal listing all complaints in the time range. Clicking "Pending" opens a modal showing only pending complaints. This drill-down pattern turns KPI metrics into actionable lists without navigating away from the dashboard.

activeModal state: Holds { title, complaints } or null. A single state value handles all four possible modals — whichever KPI was clicked determines what's shown. No need for four separate boolean flags.

todayAppointments memo: Used by DailyTasksModal. Derived from appointments (not filteredByTime) — today's appointments should always be complete regardless of time range.

Section 3 — KPICard.jsx — Animated Number Counter

function AnimatedNumber({ value }) {
    const spring = useSpring(0, { stiffness: 60, damping: 20 });
    const [current, setCurrent] = useState(0);

    useEffect(() => { spring.set(value); }, [spring, value]);
    useMotionValueEvent(spring, 'change', (v) => setCurrent(Math.round(v)));

    return <span>{current}</span>;
}
useSpring: Framer Motion's spring animation hook. Creates a motion value that interpolates from its current value to the target using spring physics. Parameters:
• stiffness: 60 — how fast the spring pulls toward the target (lower = slower, bouncier)
• damping: 20 — how much the spring resists movement (higher = less bouncy, settles faster)

Why use spring physics for numbers? A linear counter from 0 to 47 in 0.5 seconds feels mechanical. A spring starts fast and decelerates (ease-out), which feels natural and satisfying to users.

useMotionValueEvent: Subscribes to changes on the spring motion value. Every time the spring value changes (which is every animation frame, ~60fps), this callback fires with the new value. Math.round(v) converts the floating-point spring value to a displayable integer.

Why not animate CSS directly? CSS counter animations are possible but can't spring (they're easing functions only). Framer Motion's spring physics gives a much more dynamic feel with minimal code. 
export default function KPICard({ label, value, icon: Icon, iconColor = 'text-primary', delay = 0, onClick }) {
    const interactive = typeof onClick === 'function';

    return (
        <motion.div
            initial={{ opacity: 0, y: 20 }}
            animate={{ opacity: 1, y: 0 }}
            transition={{ delay }}
            onClick={onClick}
            whileHover={interactive ? { scale: 1.02 } : undefined}
            className={[
                'bg-card border border-border rounded-xl p-5 transition-all duration-300 group',
                interactive
                    ? 'cursor-pointer hover:border-primary hover:shadow-md'
                    : 'hover:border-primary',
            ].join(' ')}
        >
            <div className="flex items-center justify-between mb-3">
                <span className="text-sm text-muted-foreground">{label}</span>
                <Icon className={`w-5 h-5 ${iconColor}`} />
            </div>
            <p className="text-4xl font-bold text-foreground group-hover:text-primary transition-colors">
                <AnimatedNumber value={value} />
            </p>
        </motion.div>
    );
}
icon: Icon prop pattern: The prop is destructured as icon: Icon — rename icon to Icon during destructuring. This is necessary because React requires component names to start with a capital letter (to distinguish from HTML elements). <icon /> would be treated as an HTML element; <Icon /> is a React component.

interactive boolean: Some KPI cards might not have an onClick handler. The interactive check prevents showing a cursor-pointer and hover animation on non-clickable cards — better UX.

whileHover={interactive ? { scale: 1.02 } : undefined}: Framer Motion's whileHover animates to the given state while the mouse is over the element, reverting on mouse-out. scale: 1.02 makes the card grow 2% — a subtle but satisfying feedback. Passing undefined disables the animation entirely (not the same as passing {}, which would still apply the animation with no changes).

group Tailwind class: Marks this element as a group. Child elements using group-hover:text-primary will activate that style when the parent (the group) is hovered — not when the child itself is hovered. This lets the number change color when anywhere on the card is hovered.

Section 4 — Chart Components

TrendsChart.jsx — LineChart 
import { LineChart, Line, XAxis, YAxis, CartesianGrid, Tooltip, ResponsiveContainer } from 'recharts';

export default function TrendsChart({ data }) {
    const { t } = useTranslation();
    return (
        <div className="bg-card border border-border rounded-xl p-5">
            <h3 className="text-sm font-semibold text-foreground mb-4">{t('charts.complaintsOverTime')}</h3>
            <ResponsiveContainer width="100%" height={200}>
                <LineChart data={data} margin={{ top: 4, right: 8, left: -20, bottom: 0 }}>
                    <CartesianGrid strokeDasharray="3 3" stroke="hsl(var(--chart-grid))" />
                    <XAxis dataKey="date" tick={{ fill: 'hsl(var(--chart-text))', fontSize: 11 }}
                           tickLine={false} axisLine={false} />
                    <YAxis tick={{ fill: 'hsl(var(--chart-text))', fontSize: 11 }}
                           tickLine={false} axisLine={false} allowDecimals={false} />
                    <Tooltip contentStyle={{
                        background: 'hsl(var(--card))',
                        border: '1px solid hsl(var(--border))',
                        borderRadius: '8px',
                        color: 'hsl(var(--foreground))',
                        fontSize: 12,
                    }} cursor={{ stroke: 'hsl(var(--chart-grid))' }} />
                    <Line type="monotone" dataKey="complaints"
                          stroke="hsl(var(--chart-1))" strokeWidth={2}
                          dot={false} activeDot={{ r: 4, fill: 'hsl(var(--chart-1))' }} />
                </LineChart>
            </ResponsiveContainer>
        </div>
    );
}

ResponsiveContainer width="100%": Recharts components have a fixed pixel size by default. ResponsiveContainer measures its parent DOM element and passes the width/height to the chart. This makes the chart responsive — it fills its container and resizes with the browser window.

CSS variable colors: stroke="hsl(var(--chart-1))" — all chart colors use CSS custom properties from index.css. When the user switches dark/light mode, chart colors update automatically without re-rendering the chart component.

margin={{ left: -20 }}: Negative left margin pulls the Y-axis labels closer to the chart edge, saving horizontal space. Without this, Recharts reserves too much space for Y-axis labels and the chart area feels cramped.

dot={false}: By default, Recharts renders a dot at each data point. For dense time-series data (30+ points), these dots clutter the chart. dot={false} removes them. activeDot still shows a dot when hovering (for the tooltip to point to).

StatusDonut.jsx — PieChart with innerRadius 
const COLORS = [
    'hsl(var(--chart-4))', // Pending — amber
    'hsl(var(--chart-2))', // In Progress — blue
    'hsl(var(--chart-3))', // Resolved — green
];

export default function StatusDonut({ data }) {
    const total = data.reduce((s, d) => s + d.value, 0);

    return (
        <div className="bg-card border border-border rounded-xl p-5">
            <h3>...</h3>
            {total === 0 ? (
                <div className="flex items-center justify-center h-[200px] text-sm text-muted-foreground">
                    {t('charts.noData')}
                </div>
            ) : (
                <ResponsiveContainer width="100%" height={200}>
                    <PieChart>
                        <Pie
                            data={data} cx="50%" cy="50%"
                            innerRadius={55} outerRadius={80}
                            paddingAngle={3} dataKey="value" strokeWidth={0}
                        >
                            {data.map((_, i) => (
                                <Cell key={i} fill={COLORS[i % COLORS.length]} />
                            ))}
                        </Pie>
                    </PieChart>
                </ResponsiveContainer>
            )}
        </div>
    );
}

Donut vs pie: innerRadius={55} creates the hole, making it a donut. Donuts are preferred over pies in dashboards because they draw the eye to the proportions (arc lengths) rather than areas, which are harder to compare accurately.

Empty state guard: If total === 0, rendering a PieChart would show an empty circle (or throw an error in some Recharts versions). The empty state shows "No data" text instead — much better UX than a blank chart area.

paddingAngle={3}: Adds a 3-degree gap between pie segments. This makes it easier to distinguish segments visually, especially when one segment is very small.

strokeWidth={0}: Removes the white stroke that Recharts renders between segments by default. On dark mode, the white stroke looks jarring. Removing it gives a cleaner look.

AppointmentsBar.jsx — BarChart 
<Bar dataKey="count" fill="hsl(var(--chart-1))" radius={[4, 4, 0, 0]} />

radius={[4, 4, 0, 0]}: Rounded top corners on bars (top-left, top-right, bottom-right, bottom-left). Rounding only the top corners gives a modern look while keeping bars flush with the X-axis baseline.

barSize={22} on the BarChart: Fixed bar width in pixels. Without this, Recharts sizes bars to fill available space, which makes single-day bars enormous and multi-day bars tiny. A fixed size looks consistent regardless of how many data points there are.

cursor={{ fill: 'hsl(var(--secondary))' }} on the Tooltip: When hovering, Recharts highlights the hovered bar with a background rectangle ("cursor"). Using the --secondary CSS variable makes the hover highlight match the theme.

Section 5 — Common Bugs & Fixes

Bug: Charts don't resize when the browser window changes size

Symptom: The chart renders at the initial size but doesn't shrink or grow when the window is resized.

Root cause: The chart component uses fixed pixel dimensions (width={800} height={300}) instead of ResponsiveContainer.

Fix: Always wrap charts in <ResponsiveContainer width="100%" height={200}>. The container measures its DOM parent and passes the pixel size to the chart. Remove the width prop from the inner chart component — the container provides it.

Bug: Chart colors are black or wrong in production build

Symptom: Charts look correct in development (colors from CSS variables), but after npm run build, chart elements are black or inherit wrong colors.

Root cause: stroke="hsl(var(--chart-1))" is passed as an HTML attribute to an SVG element. SVG doesn't support CSS custom properties in HTML attribute values — var() only works in CSS. This works in development because Vite serves the styles in a way that Chrome handles gracefully, but breaks in optimized builds.

Fix: Read the CSS variable value in JavaScript and pass the resolved color:

const chartColor = getComputedStyle(document.documentElement)
    .getPropertyValue('--chart-1').trim();

// Then pass as a JS value, not CSS:
stroke={`hsl(${chartColor})`}

Or use a useThemeColors hook that reads all chart colors on mount and re-reads them when the theme changes.

Bug: Dashboard re-renders every second and freezes the tab

Symptom: The parent component polls for new data every second (or uses a WebSocket that fires frequently). Every data update causes all charts to recompute and re-render, causing visible lag.

Root cause: The data transforms (trends, categories, etc.) are computed inline in the component body or in non-memoized functions. Every parent re-render recomputes everything from scratch.

Fix: Ensure all data transforms are in useMemo hooks with correct dependency arrays. Only recompute when complaints, appointments, or cutoff actually changes — not on every render. Also reduce polling frequency: every 30 seconds is usually sufficient for a dashboard.

Medium Exercise 2 — Add average resolution time to kpis

Add an avgResolutionDays value to the kpis memo: the average number of days between created_at and resolved_at for complaints with status "resolved" in the time range. Show it as "X.X days" in a new KPI card.

// In kpis useMemo:
const resolvedWithDates = filteredByTime.filter(
    c => c.status === STATUS.RESOLVED && c.resolved_at
);
avgResolutionDays: resolvedWithDates.length === 0 ? 0 :
    resolvedWithDates.reduce((sum, c) => {
        const created = new Date(c.created_at);
        const resolved = new Date(c.resolved_at);
        return sum + (resolved - created) / (1000 * 60 * 60 * 24);
    }, 0) / resolvedWithDates.length,

// Note: AnimatedNumber rounds to integer, so you'll want a different display:
<p className="text-4xl font-bold">{kpis.avgResolutionDays.toFixed(1)}</p>

Module 20 — Key Takeaways

  • All data transforms in useMemo — prevents expensive recalculations on every render. Dependency arrays must be exact.
  • Chart components are "dumb" — they receive pre-formatted arrays and render them. No data logic inside chart components.
  • ResponsiveContainer is required for responsive charts — never use fixed pixel widths on chart components.
  • CSS variable colors in SVG attributes need to be resolved via JavaScript (getComputedStyle), not passed as raw var() strings.
  • Empty state guards before rendering charts with zero data prevent blank or broken chart displays.
  • Framer Motion spring animations for numbers use physics parameters (stiffness, damping) to control feel — not duration/easing.
  • Pre-seeded zero counts for day-of-week data ensure all 7 days always appear in the chart.
  • Staggered animation delays on KPI cards create a cascade entrance effect with minimal code.
  • The group Tailwind class enables child elements to respond to hover events on the parent.
