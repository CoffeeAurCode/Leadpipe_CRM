Build Session 07 · Backend & Database Security

Standalone Units, Row-Level Security & Direct Manager Ownership

How a single line of production logs — 42501: new row violates row-level security policy — unravelled a hidden hole in our database security model, and how we closed it for good.

🔴 Advanced ⏱️ ~70 min read / build 📋 Requires: Module 02 (DB Layer), 03 (Auth/JWT), 06 (Flats), 14 (Feature Flags)

📦 Session Overview

This session was not a "build a new feature" session. It was a diagnosis-and-fix session — the kind that happens constantly in real software work and teaches more than any greenfield feature ever could. A user pasted a slice of production logs from Render (our backend hosting platform) and asked a simple question: "why is this happening?"

The log line that started everything:

2026-06-16T03:44:57Z [FLAT CREATED] UUID: 63d37150-…, Number: 201 2026-06-16T03:44:57Z [FeatureService] Error initializing unit 298: {'message': 'new row violates row-level security policy for table "property_features"', 'code': '42501', …} 2026-06-16T03:44:57Z [FEATURES INITIALIZED] unit_id: 298 2026-06-16T03:44:57Z INFO: "POST /flats HTTP/1.1" 201 Created

By the end of this session we had:

  • Traced a Postgres error code 42501 to a mismatch between two database clients.
  • Discovered that "standalone units" (think a single bungalow with no building above it) had no way to prove who owned them.
  • Shipped an immediate code fix and a durable database migration that adds a direct owner column to every unit.
  • Rewrote four Row-Level Security policies to be safer and more correct.
  • Hand-recovered six orphaned rows of real production data.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Read a Postgres RLS error and reason about which policy rejected which row.
  • Explain the difference between a service-role client and an authenticated client, and when each is safe.
  • Understand why USING and WITH CHECK are different, and what happens when you omit one.
  • Design an additive RLS migration that fixes a hole without hiding existing data.
  • Recover ownership of database rows that were created before the column that tracks ownership existed.

🧠 Concepts Introduced This Session

Eight ideas power everything we did. Read these once and the build log and bug journal will feel obvious.

1 · Row-Level Security (RLS)

Plain-English explanation

Normally, if you can read a database table, you can read every row in it. Row-Level Security (RLS — a Postgres feature that filters rows per user) changes that: the database itself attaches an invisible WHERE clause to every query, so each user only ever sees (or writes) the rows they're allowed to. The rule lives in the database, not in your application code.

Why we need it — for the CRM specifically

Our CRM is multi-tenant (many separate customers share one database). Manager A must never see Manager B's tenants, buildings, or rent records. We could try to enforce that in Python on every single query — but humans forget. RLS makes the database the last line of defence: even if a backend route had a bug and forgot to filter, Postgres would still refuse to hand over another manager's data.

How it works — an analogy

RLS is like a nightclub bouncer who also follows you around inside. It's not enough to get through the door (authentication). For every room you try to enter (every row you touch), the bouncer checks your wristband against the rule for that room. Wrong wristband? You're physically blocked — not because the app asked, but because the building won't let you.

Jargon decoder

  • RLS (Row-Level Security): per-row access rules enforced by Postgres.
  • Policy: a named rule attached to a table that says which rows a user may read/write.
  • Multi-tenant: one system serving many isolated customers ("tenants" in the SaaS sense — not to be confused with the renters our app calls "tenants"!).

Annotated example

-- Turn on RLS for the table. Until a policy is added, the default is DENY ALL.
ALTER TABLE property_features ENABLE ROW LEVEL SECURITY;

-- A policy named "manager_owns_property_features".
-- FOR ALL = applies to SELECT, INSERT, UPDATE and DELETE.
CREATE POLICY "manager_owns_property_features"
ON property_features FOR ALL
USING (                               -- the rule: a row is "visible/usable" only if...
  unit_id IN (                        -- ...its unit_id belongs to a flat that...
    SELECT f.id FROM flats f
    JOIN buildings b ON f.building_id = b.id          -- ...sits in a building...
    JOIN properties_list p ON b.property_id = p.id    -- ...inside a property...
    WHERE p.manager_id = auth.uid()                   -- ...owned by the logged-in manager.
  )
);

2 · auth.uid() and the JWT

Plain-English explanation

auth.uid() is a function you can call inside a Postgres policy that returns "the ID of the user making this request." Supabase fills it in by reading the JWT (JSON Web Token — a tamper-proof ID card) that the request carried. No JWT → auth.uid() is NULL → most policies reject everything.

Why we need it — for the CRM

It is the bridge between "who is logged in" (an app concept) and "which rows are allowed" (a database concept). Every ownership rule in our schema ends in … = auth.uid().

How it works — an analogy

The JWT is your passport; auth.uid() is the border officer reading the passport number aloud so the rest of the system can check it against the guest list. If you show up with no passport, the officer says "NULL" and you're not on anyone's list.

Annotated code — how the JWT gets attached

# This FastAPI "dependency" runs before any protected route.
async def get_authenticated_db(
    credentials: HTTPAuthorizationCredentials = Depends(security),  # pulls the Bearer token from the request header
    db: Client = Depends(get_db),                                  # the shared anon Supabase client
) -> Client:
    # Attach THIS user's JWT to the client. Now every query this client makes
    # runs "as" this manager, so auth.uid() resolves to their ID inside RLS.
    db.postgrest.auth(credentials.credentials)
    return db
⚠️ Warning — this client is shared

Notice get_db() returns a single, module-level client object that is reused across requests, and we mutate its token on every call. That is a latent race condition (two requests fighting over one object) — we flagged it this session but it was not the cause of our bug. Keep it in your peripheral vision.

3 · USING vs WITH CHECK

Plain-English explanation

An RLS policy can have two predicates (conditions):

  • USING — checks rows that already exist. "Can you SELECT/UPDATE/DELETE this row?"
  • WITH CHECK — checks rows you are about to write. "Are you allowed to INSERT/UPDATE a row that looks like this?"

The crucial gotcha: if you write a policy with only USING and no WITH CHECK, Postgres uses the USING expression for inserts too. So an INSERT must satisfy the same condition that controls reads.

Why it mattered this session

Our property_features policy had only a USING. So inserting a feature row required the new row's unit_id to already trace up to the logged-in manager. For a unit with no building, that trace was impossible — and the INSERT was rejected. That is the whole bug in one sentence.

How it works — an analogy

USING is the "who may take a book off the shelf" rule. WITH CHECK is the "what books you're allowed to put on the shelf" rule. If a library only writes down the first rule, it quietly applies the same rule to returns — and a book that doesn't match gets refused at the drop box.

🔑 Key concept

Omitting WITH CHECK isn't "no insert rule" — it's "the read rule, reused for inserts." Many RLS bugs hide in that one fact.

4 · Service-role client vs Authenticated (anon) client

Plain-English explanation

Supabase gives you two API keys:

  • The anon key (anonymous/public): requests made with it obey RLS. This is what logged-in managers use.
  • The service-role key: requests made with it bypass RLS entirely — it is a master key. It must only live on the server, never in a browser.

In our code, db is the RLS-respecting client and svc is the master-key client.

Why we need both — for the CRM

Most manager actions use db so RLS protects them. But some operations legitimately need to bypass RLS: a Stripe webhook (no logged-in user), a phone-call lookup, or — as we'll see — an internal step that runs after we've already verified ownership ourselves.

How it works — an analogy

db is a hotel guest keycard — it opens your room and the gym, nothing else. svc is the housekeeping master key — it opens every door. You hand the master key to trusted staff for specific jobs; you never tape it to the front entrance.

Annotated code

# Anon client — RLS ENFORCED. Per-request JWT is attached later (see get_authenticated_db).
_anon_client: Client = create_client(settings.SUPABASE_URL, settings.SUPABASE_KEY)

# Service-role client — RLS BYPASSED. Built only if the secret key is configured.
_service_client = create_client(settings.SUPABASE_URL, settings.SUPABASE_SERVICE_KEY)

def get_db() -> Client:        # hand routes the RLS-respecting client
    return _anon_client

def get_service_db() -> Client:  # hand webhooks/admin the master-key client
    return _service_client

5 · The building → property → manager ownership chain

Plain-English explanation

Originally, the only way our database knew who owned a unit was by following a chain of foreign keys: a unit points to a building, a building points to a property, a property records its manager. To answer "does this manager own this unit?", Postgres had to JOIN (stitch together) three tables.

How it works — an analogy

It's like proving you own a parking spot by showing: spot → floor → garage → garage's deed-holder. Fine when every spot sits inside a garage. But what about a driveway with no garage above it? The chain has a missing link, and the proof collapses.

⚠️ Warning — INNER JOIN drops the orphans

The chain used JOIN buildings b ON f.building_id = b.id. An inner join only keeps rows that match on both sides. A unit with building_id = NULL matches nothing, so it silently vanishes from the result — and therefore from the set of "rows you own." That silent disappearance is the heart of the bug.

6 · Standalone units (the missing link)

Plain-English explanation

A standalone unit is a rentable place that isn't inside a building — a bungalow, a detached house, a single shop. In our data that means building_id IS NULL. The product genuinely supports these. The frontend even has code for them:

// "standalone units" = attached to a property directly, with no building above them
const standalones = allFlats.filter(f => f.property_id === property.id && !f.building_id);

Here's the twist we discovered: the flats table doesn't actually have a usable property_id column — so that frontend filter was reading a field that doesn't exist (always undefined), and the database had no column at all that tied a standalone unit to its owner. The concept existed in the UI but had no foundation in the schema.

🔑 Key concept — a data-model hole

The feature/security layer assumed "every unit lives in a building." The product assumed "some units stand alone." Those two assumptions silently disagreed. Most nasty bugs are really two correct assumptions that were never introduced to each other.

7 · Additive RLS policies (fix without hiding)

Plain-English explanation

When you change a security rule on live data, the scary failure mode is the opposite of a leak: you hide data people could rightfully see. An additive policy avoids that by widening, never narrowing: it authorizes a row if the old rule passes OR a new rule passes.

Why we need it — for the CRM

We added a brand-new owner column (manager_id) but couldn't backfill it instantly for every row. With an additive policy, building-attached units stay visible via the old chain even before their manager_id is filled in — so nobody loses access mid-migration.

How it works — an analogy

It's like adding a fingerprint scanner next to an existing keypad. Old staff who only know the code still get in; new staff can use their fingerprint. You never rip out the keypad until everyone has enrolled a fingerprint.

8 · Foreign keys & ON DELETE CASCADE

Plain-English explanation

A foreign key (FK) is a column that must point at a real row in another table — the database refuses values that don't exist. ON DELETE CASCADE says "if the parent row is deleted, automatically delete my row too." We made flats.manager_id a foreign key to the auth users table with cascade, so deleting a manager cleans up their units.

How it works — an analogy

A foreign key is a seat reservation that must reference a real ticket. CASCADE means: cancel the flight (delete the parent), and every seat reservation for it is torn up automatically — no orphan stubs left lying around.

🛠️ Step-by-Step Build Log

Every action, in order, with the reasoning for why it happened then.

Step 1 — Read the symptom carefully

We opened Render_logs.md and read the failing line. The two facts that shaped everything:

  • The error is Postgres code 42501 = insufficient privilege, specifically an RLS violation on property_features.
  • The request still returned 201 Created. So the failure was non-fatal and being swallowed.

Why now: you never start fixing before you can state the symptom in one sentence. Ours: "Creating a unit logs an RLS insert failure on property_features but still succeeds."

Step 2 — Find the code that prints the error

We searched the codebase for the log string and the table name.

$ grep -rn "Error initializing unit" backend/ backend/app/services/feature_service.py:270: print(f"[FeatureService] Error initializing unit {unit_id}: {e}")

Why now: the log message is a literal string in the source. Grepping it jumps you straight to the scene of the crime instead of guessing.

Step 3 — Read the two suspects: the route and the service

We read backend/app/routes/flats.py (the POST /flats handler) and feature_service.py. The key discovery — the flat is inserted with one client, the features with another:

# The flat row is inserted with the SERVICE-ROLE client (svc) — RLS bypassed.
flat_response = svc.table("flats").insert(flat_payload).execute()
flat_id = flat["id"]

# ...but features are initialized with the AUTHENTICATED client (db) — RLS enforced.
feature_service = FeatureService(db)            # <-- the mismatch
await feature_service.initialize_unit_features(flat_id)
print(f"[FEATURES INITIALIZED] unit_id: {flat_id}")  # printed even on failure (bug #2)

Step 4 — Read the RLS policy that is rejecting the insert

We opened scripts/02_rls_policies.sql and migration 007. The property_features policy (shown in Concept 1) traced ownership only through building_id, and had no WITH CHECK. Now the mechanism was clear.

Step 5 — Confirm the trigger: standalone units

We checked the flats schema and the frontend. We found the "standalone units" filter and confirmed the flats table has no usable property_id and a manager_id column that was never populated. So building-less units had no ownership path at all.

Step 6 — Ship the immediate fix (Option A)

Make feature initialization use the same client that already created the flat, and stop the log from lying.

# Use svc: ownership was already validated before the flat was created,
# so bypassing RLS here is safe — and it works for standalone units too.
feature_service = FeatureService(svc)           # was FeatureService(db)
await feature_service.initialize_unit_features(flat_id)
print(f"[FEATURES INITIALIZED] unit_id: {flat_id}")
async def initialize_unit_features(self, unit_id: int) -> None:
    defaults = {f.value: get_default_state(f) for f in Feature}
    try:
        self._upsert_unit_features(unit_id, defaults)
    except Exception as e:
        print(f"[FeatureService] Error initializing unit {unit_id}: {e}")
        raise        # <-- re-raise so the success log only prints on real success

Why now, not later: Option A is a one-line, zero-migration change that stops the production error immediately. You always stop the bleeding before performing surgery.

Step 7 — Design the durable fix (Option B) with the user

We presented three directions and the user chose: standalone units are first-class and should connect directly to the manager. That means a new flats.manager_id foreign key, populated on creation, with additive RLS.

Step 8 — Write the migration

We created backend/migrations/029_flats_manager_id_and_rls.sql. It is idempotent (safe to run more than once — every statement guards with IF NOT EXISTS or DROP … IF EXISTS).

Show the full migration 029 (annotated) 
-- 1. Add the owner column, a foreign key to the auth users table, and an index.
ALTER TABLE flats ADD COLUMN IF NOT EXISTS manager_id UUID;

DO $$
BEGIN
  IF NOT EXISTS (                         -- only add the FK if it isn't there yet
    SELECT 1 FROM information_schema.table_constraints
    WHERE constraint_name = 'fk_flats_manager' AND table_name = 'flats'
  ) THEN
    ALTER TABLE flats
      ADD CONSTRAINT fk_flats_manager
      FOREIGN KEY (manager_id) REFERENCES auth.users(id) ON DELETE CASCADE;
  END IF;
END $$;

CREATE INDEX IF NOT EXISTS idx_flats_manager_id ON flats(manager_id);

-- 2. Backfill: building-attached flats can derive their owner from the old chain.
UPDATE flats f
SET manager_id = p.manager_id
FROM buildings b
JOIN properties_list p ON b.property_id = p.id
WHERE f.building_id = b.id
  AND f.manager_id IS NULL;
-- NOTE: standalone flats made before this migration have NO chain to follow,
-- so they stay NULL and must be backfilled by hand (see the orphan script).

-- 3. Rewrite the 4 policies to be ADDITIVE: old building chain OR new manager_id.
DROP POLICY IF EXISTS "manager_owns_property_features" ON property_features;
CREATE POLICY "manager_owns_property_features"
ON property_features FOR ALL
USING (
  unit_id IN (SELECT id FROM flats WHERE manager_id = auth.uid())   -- NEW direct path
  OR unit_id IN (                                                    -- OLD building chain
    SELECT f.id FROM flats f
    JOIN buildings b ON f.building_id = b.id
    JOIN properties_list p ON b.property_id = p.id
    WHERE p.manager_id = auth.uid()
  )
)
WITH CHECK (   -- explicit now, so INSERTs are governed by the SAME rule on purpose
  unit_id IN (SELECT id FROM flats WHERE manager_id = auth.uid())
  OR unit_id IN (
    SELECT f.id FROM flats f
    JOIN buildings b ON f.building_id = b.id
    JOIN properties_list p ON b.property_id = p.id
    WHERE p.manager_id = auth.uid()
  )
);
-- (flats, tenants and rents policies were rewritten the same additive way.)

Why all four tables: a standalone occupied unit also has a tenant and a rent. Those tables used the same building-only chain, so they'd hit the identical wall the moment you added a tenant to a bungalow. Fixing only property_features would have left two more landmines.

🐛 Bug Journal

Four distinct issues. The first is the headline bug; the rest are the smaller traps we hit while fixing and verifying it. These are the most valuable part of the session.

🐛 Bug #1 — 42501: RLS rejects the feature insert

🚨 The symptom

On every unit creation, the logs showed:

[FeatureService] Error initializing unit 298: {'message': 'new row violates row-level security policy for table "property_features"', 'code': '42501', 'hint': None, 'details': None}

…yet POST /flats returned 201 Created. New units silently had no feature rows.

🔍 The diagnosis (the actual trail)
  1. Decoded the error: 42501 + "violates row-level security policy" = an RLS rule blocked a write to property_features.
  2. Grepped the log string → landed in feature_service.py, which caught the exception and only printed it.
  3. Read create_flat and spotted the mismatch: flat inserted via svc (bypasses RLS), features inserted via db (enforces RLS).
  4. Read the policy → it authorizes a unit only through building_id → building → property → manager, with no WITH CHECK (so that read-rule also governs inserts).
  5. Hypothesis: the failing units have building_id = NULL, so the inner joins drop them and the insert check fails.
  6. Red herring considered & rejected: the shared-anon-client race condition. We ruled it out because the failure was deterministic (every create, same single user) and reads in the same logs returned 200 — so auth.uid() was resolving fine.
  7. Confirmed the data-model hole via the frontend's "standalone units" filter and the missing property_id column.
🧠 The root cause

Two correct-but-incompatible designs collided: (1) flat creation was moved to the service-role client to dodge an RLS insert restriction, but (2) feature initialization was left on the RLS-enforced client. For a standalone unit (building_id NULL), the RLS policy literally cannot express its ownership — the only path it knows is through a building that doesn't exist. So Postgres correctly refused the insert. It was never a typo; it was a missing concept in the security model.

🔧 The fix (before → after)

Immediate (code):

- feature_service = FeatureService(db)    # RLS-enforced; rejects building-less units
+ feature_service = FeatureService(svc)   # service-role; ownership already verified above

Durable (database) — give every unit a direct owner and make RLS understand it (migration 029, Step 8). After that, even the RLS-enforced client can write features for a standalone unit, because flats.manager_id = auth.uid() is a path the policy now recognizes.

🛡️ The lesson

When you "fix" an RLS rejection by switching one query to the service-role key, you haven't fixed the rule — you've moved the rejection to the next query that still uses the safe client. Treat a service-role workaround as a flag that says "the policy can't express something true." The real fix is usually to teach the policy that truth (here: a direct owner column). Tools that would have caught this earlier: not swallowing exceptions, and an alert on 42501 in logs.

🐛 Bug #2 — The log that always said "success"

🚨 The symptom

[FEATURES INITIALIZED] unit_id: 298 printed on the very same units where initialization had just failed. The logs were actively lying, which is why nobody noticed the bug for so long.

🔍 Diagnosis & 🧠 root cause

initialize_unit_features caught its own exception, printed it, and returned normally (it didn't re-raise). So control flowed back to create_flat, which unconditionally printed the success line. The "error then success" pair in the logs was the tell.

🔧 The fix

Add raise after logging (Step 6). Now the exception propagates, the success print is skipped, and an outer try/except records a truthful [FEATURE INIT ERROR].

🛡️ The lesson

"Swallowing" an exception (catch, log, continue) is sometimes intentional for non-critical steps — but if you do it, do not print a success message afterward. A log line should never be able to claim victory over a step that threw. When in doubt, re-raise and let the caller decide.

🐛 Bug #3 — The "single-manager shortcut" did nothing

🚨 The symptom

After running migration 029, the user ran a tidy one-liner to assign all orphaned standalone units to "the one manager," then re-checked — and 6 orphans still remained. The UPDATE reported zero rows changed.

🔍 Diagnosis & 🧠 root cause

The shortcut was deliberately guarded:

UPDATE flats
SET manager_id = (SELECT user_id FROM manager_profiles LIMIT 1)
WHERE building_id IS NULL AND manager_id IS NULL
  AND (SELECT COUNT(*) FROM manager_profiles) = 1;   -- only fires if EXACTLY one manager exists

Running SELECT user_id, name FROM manager_profiles; returned multiple rows. The guard COUNT(*) = 1 was false, so the statement was a safe no-op. It wasn't broken — it was correctly refusing to guess among several managers.

🔧 The fix — infer the owner from related data

Since the flats themselves never recorded a creator, we looked at tables that do carry a manager link and still point at these units:

SELECT f.id, f.flat_number, f.occupied,
       (SELECT COUNT(*) FROM complaints c WHERE c.flat_uuid = f.uuid)     AS complaints,
       (SELECT COUNT(*) FROM lease_listings l WHERE l.flat_uuid = f.uuid) AS listings,
       (SELECT c.assigned_manager_id FROM complaints c
          WHERE c.flat_uuid = f.uuid AND c.assigned_manager_id IS NOT NULL
          LIMIT 1)                                                        AS hint_mgr
FROM flats f
WHERE f.building_id IS NULL AND f.manager_id IS NULL
ORDER BY f.created_at;

The result told the whole story: one unit (id 46, flat "355") had 10 complaints all assigned to one manager — a confident owner. The other five were empty, with names like "AEAWE" / "EAWE" / duplicate "201" — obvious throwaway test rows. So: assign the real one, delete the test junk.

🛡️ The lesson

You can't read back a fact the database never stored. When you add an ownership/audit column, the rows that predate it are permanently ambiguous — your best recovery is to triangulate from whatever still references them. The deeper lesson: capture created_by/owner from day one; retrofitting it is archaeology.

🐛 Bug #4 — 42601: running a template literally

🚨 The symptom
ERROR: 42601: syntax error at or near "<" LINE 5: UPDATE flats SET manager_id = '<MANAGER_AUTH_UID>' WHERE id = <flat_id>;
🔍 Diagnosis & 🧠 root cause

42601 is Postgres for "syntax error." The placeholders <MANAGER_AUTH_UID> and <flat_id> were copy-pasted and run as-is. Angle brackets aren't valid SQL — they were fill-in-the-blanks, not code. (And <flat_id> needs a bare integer, while the UUID needs single quotes — two different substitution rules.)

🔧 The fix

Substitute real values before running. Concretely:

UPDATE flats SET manager_id = '24b1b33e-861b-4ed0-acdc-e83f5b5cd27f' WHERE id = 46;

And delete the five empty test units (children first, to respect foreign keys):

DELETE FROM lease_listings   WHERE flat_uuid IN (SELECT uuid FROM flats WHERE id IN (143,145,146,298,299));
DELETE FROM property_features WHERE unit_id IN (143,145,146,298,299);
DELETE FROM flats            WHERE id IN (143,145,146,298,299);
🛡️ The lesson

A convention like <PLACEHOLDER> is human shorthand, not machine input. When you hand someone runnable SQL, prefer forms that need zero editing (like the guarded single-manager UPDATE) and clearly mark anything that still needs substitution. 42601 almost always means "you ran a template, a comment, or pasted two statements as one."

Additive policies (chain OR manager_id) Replace the chain outright with manager_id only Can't backfill instantly; additive guarantees no currently-visible row gets hidden mid-migration Slightly more verbose policies; the old chain lingers until everything is backfilled

🚑 Troubleshooting / Common Errors

42501: new row violates row-level security policy

A write was blocked by RLS. Ask three questions: (1) Which table? (2) Which client made the call — RLS-enforced (db) or service-role (svc)? (3) Does the row satisfy the policy's WITH CHECK (or the USING that stands in for it)? Usually the row references something the policy can't trace back to auth.uid().

42601: syntax error at or near "<" (or near a word)

You ran something that isn't valid SQL — most often a <placeholder>, a commented line run on its own, or two statements pasted as one. Replace placeholders with real values (integers bare, UUIDs/strings in single quotes).

An UPDATE reports "0 rows affected" but you expected changes

The WHERE matched nothing. Check guards like AND (SELECT COUNT(*) … ) = 1 — they can silently make a statement a no-op. Run the SELECT version of your WHERE first to see what it matches.

"Connection terminated due to connection timeout" from the database

On free Supabase tiers the project auto-pauses when idle (status INACTIVE). Open the dashboard / SQL editor to wake it, then retry. This is why, this session, automated queries failed while the user's SQL-editor runs succeeded.

A manager can't see units they created before a policy change

Your new policy is narrowing, not additive. Make sure it reads old_path OR new_path, and that the data the new path needs (manager_id) is backfilled.

23503: foreign key violation when inserting a flat

manager_id must reference a real auth.users(id). If you pass an id that doesn't exist (or the wrong value), the FK rejects it. Confirm you're passing user["sub"] from a validated JWT.
