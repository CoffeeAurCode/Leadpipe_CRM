The current scope is determined by which selection states are non-null. isBulk is true at property or building level — saving there applies changes to ALL units in scope. At unit level, isBulk is false — save affects only that one unit.

Settings load on scope change

useEffect(() => {
    if (!selectedProperty || (selectedProperty.isUnassigned && !selectedUnit)) return;
    (async () => {
        let data;
        if (selectedUnit)     data = await fetchUnitSettings(selectedUnit.id);
        else if (selectedBuilding) data = await fetchBuildingSettings(selectedProperty.id, selectedBuilding.id);

        setPendingChanges({});
    })();
}, [selectedProperty, selectedBuilding, selectedUnit]);
The effect re-runs whenever any of the three selection states changes. When the user drills from a building back to a property, selectedBuilding becomes null, which re-triggers this effect to load property-level settings.

pendingChanges diff pattern

function handleToggle(featureKey, currentValue) {
    setPendingChanges(prev => ({ ...prev, [featureKey]: !currentValue }));
    setHasChanges(true);
}

// In FeaturePanel render:
const currentValue = pendingChanges.hasOwnProperty(feature.key)
    ? pendingChanges[feature.key]
    : feature.enabled;
pendingChanges only stores the DIFF — only toggled keys. When rendering, we check pendingChanges first (user's pending intent), falling back to the server value from settings. This means the UI reflects the user's selections before save without replacing the entire settings object.
Why this matters: If you replaced settings directly, the user couldn't cancel — there'd be no "before" state to restore. With a separate pendingChanges object, Cancel just calls setPendingChanges({}).

Breadcrumb back navigation

function Breadcrumb({ segments, onBack }) {
    return (
        <div className="flex items-center gap-2 text-sm">
            <button onClick={onBack}>
                <ArrowLeft className="w-4 h-4" />
                {segments[0]}
            </button>
            {segments.slice(1).map((seg, i) => (
                <span key={i}><span>/</span> <span>{seg}</span></span>
            ))}
        </div>
    );
}
segments[0] is always the "back" label (what clicking the arrow returns to). Remaining segments are the current path shown as text. The ArrowLeft + text acts as the back button — matching the breadcrumb pattern from macOS Finder and iOS navigation.

Template CRUD in localStorage

const STORAGE_KEY = 'sms_templates';

function loadTemplates() {
    try {
        const raw = localStorage.getItem(STORAGE_KEY);
        return raw ? JSON.parse(raw) : DEFAULT_TEMPLATES;
    } catch {
        return DEFAULT_TEMPLATES;
    }
}

function saveTemplates(templates) {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(templates));
}
Templates are stored in localStorage — no backend endpoint needed. This is intentional: templates are personal preferences, not shared data. The try/catch handles corrupted localStorage (old schema, partial write, etc.).

Variable insertion at cursor position

const textareaRef = useRef(null);

function insertVariable(token) {
    const el = textareaRef.current;
    if (!el) { setMessage(prev => prev + token); return; }
    const start = el.selectionStart ?? message.length;
    const end   = el.selectionEnd   ?? message.length;
    const updated = message.slice(0, start) + token + message.slice(end);
    setMessage(updated);
    // Restore cursor after the inserted token
    requestAnimationFrame(() => {
        el.focus();
        el.setSelectionRange(start + token.length, start + token.length);
    });
}
el.selectionStart/End tracks where the text cursor is in the textarea. We slice the message at the cursor position, insert the token, and re-join. requestAnimationFrame delays the cursor restore until after React has re-rendered the textarea with the new value — without it, setSelectionRange would be overwritten by React's controlled input update.

Set-based selection tracking

const [selectedUuids, setSelectedUuids] = useState(new Set());

function toggleOne(uuid) {
    setSelectedUuids(prev => {
        const next = new Set(prev);
        next.has(uuid) ? next.delete(uuid) : next.add(uuid);
        return next;
    });
}

function toggleAll() {
    if (selectedUuids.size === displayTenants.length) {
        setSelectedUuids(new Set());
    } else {
        setSelectedUuids(new Set(displayTenants.map(t => t.uuid)));
    }
}
Set has O(1) has() and delete() — faster than .includes() on a large array. Always create a new Set (not mutate in place) because React uses reference equality to detect state changes. Mutating prev without cloning would not trigger a re-render.

Live preview with HTML injection

function buildPreview(message) {
    let out = message;
    VARIABLES.forEach(({ token, sample }) => {
        out = out.replaceAll(token, `**${sample}**`);
    });
    out = out.replace(/\*\*(.+?)\*\*/g, '<strong>$1</strong>');
    return out;
}

<span
    dangerouslySetInnerHTML={{ __html: buildPreview(message) }}
/>
dangerouslySetInnerHTML bypasses React's XSS protection. This is safe here because the HTML is generated entirely from user's own message text and our sample strings — never from server data. The "dangerous" in the name is a reminder, not a prohibition.

This handles: clearing localStorage, testing on a new device, and the manager resetting their tour from the Supabase console.

The storage key includes the userId — so different managers on the same browser get separate checklists. The useState lazy initializer (arrow function) only runs once on mount, avoiding a localStorage read on every render.

DB sync on mount

useEffect(() => {
    if (!user) return;
    const fetchStatus = async () => {
        const { data } = await supabase
            .from('manager_profiles')
            .select('tour_completed')
            .eq('user_id', user.id)
            .maybeSingle();

        if (data?.tour_completed) {
            // DB says done — force all items to checked
            const allChecked = {};
            Object.values(SECTION_ITEMS).flat().forEach(id => { allChecked[id] = true; });
            setCheckedState(allChecked);
        } else if (data && !data.tour_completed) {
            // DB says NOT done — clear local if local thinks it's complete
            const localIsAllChecked = ...;
            if (localIsAllChecked) { setCheckedState({}); localStorage.removeItem(...); }
        }
    };
    fetchStatus();
}, [user]);
The second branch (DB says NOT done) handles the "reset for testing" scenario: a developer clears tour_completed in Supabase, but localStorage still has all items checked. Without this branch, the user would see the "All done!" screen even though the DB says otherwise.

Sequential section unlocking

const isSectionUnlocked = useCallback((sectionIndex) => {
    if (sectionIndex === 0) return true;     // first section always unlocked
    for (let i = 0; i < sectionIndex; i++) {
        if (!isSectionComplete(SECTION_ORDER[i])) return false;
    }
    return true;
}, [isSectionComplete]);
Sequential unlock: section N is unlocked only if ALL sections 0 through N-1 are complete. This creates a guided path through the onboarding — the user can't skip ahead. Learner-friendly: it prevents the overwhelm of seeing 8 incomplete sections at once.

Completion sync to backend

useEffect(() => {
    if (!user || !isChecklistComplete || dbTourCompleted || isUpdatingBackend.current) return;

    const saveCompletion = async () => {
        isUpdatingBackend.current = true;
        try {
            await supabase
                .from('manager_profiles')
                .update({ tour_completed: true })
                .eq('user_id', user.id);
            setDbTourCompleted(true);
        } catch {
            isUpdatingBackend.current = false;
        }
    };
    saveCompletion();
}, [user, isChecklistComplete, dbTourCompleted]);
isUpdatingBackend.current is a ref (not state) — it doesn't trigger re-renders when set. It guards against concurrent Supabase writes if this effect fires twice. dbTourCompleted prevents re-saving once we know it's already in the DB.

Key Patterns

pendingChanges vs. direct state mutation

With pendingChanges (SettingsPage approach):

  • Cancel is free — just clear pendingChanges
  • Can show "X unsaved changes" count
  • Can highlight changed items
  • Save sends only the diff

Without it (direct state update):

  • Simpler code
  • Cancel requires a full re-fetch from server
  • Can't distinguish unsaved from saved
  • Save must send the entire feature object

Dual persistence pattern for user preferences

// Write both simultaneously:
localStorage.setItem(key, JSON.stringify(next));   // instant, device-local
await supabase.from('manager_profiles').update({ tour_completed: true }); // authoritative

// Read: DB wins on conflict:
if (data?.tour_completed) { overwrite localStorage with complete state; }

localStorage = fast cache. Supabase = truth. This gives instant UI updates (no spinner waiting for the DB) while keeping data consistent across devices and after localStorage is cleared.

Bugs Encountered

Bug 1 — Feature flag save affects wrong scope
Symptom: toggling "SMS Reminders" at the building level only updated one unit instead of all units in the building.
Cause: the save function was using selectedUnit.id even when no unit was selected because the conditional was checking in the wrong order.
Fix: check selectedUnit first, then selectedBuilding, then fall back to property — matching the drill-down order.
Bug 2 — SMS variable inserted at end of message regardless of cursor
Symptom: clicking "{name}" chip always appended the token to the end, not where the cursor was.
Cause: selectionStart/End were only valid at the moment of click — by the time the state update ran, focus had moved to the chip button, losing the cursor position.
Fix: read selectionStart/End immediately in the click handler before anything else, then pass them into the string manipulation.
Bug 3 — Checklist "complete" screen showed even though DB said tour_completed: false
Symptom: after a Supabase admin reset tour_completed = false, the app still showed the "All set!" screen.
Cause: localStorage had all items checked, and the app used localStorage without consulting the DB first.
Fix: the DB sync useEffect now detects the discrepancy and clears localStorage when DB says not complete.

Exercise 3 — What prevents the onboarding checklist from marking items complete if the DB write fails?

Trace through the sync flow in OnboardingContext. When does the DB write happen, and what happens on failure?

Answer

The DB write in saveCompletion() only runs when ALL items are checked locally (isChecklistComplete). If the Supabase write fails, the catch block resets isUpdatingBackend.current = false and does NOT set dbTourCompleted = true. This means the next re-render that triggers the useEffect will retry the write. The local state remains "complete" — the user sees the celebration screen — but the DB will be retried on the next opportunity.

This is a "write-on-best-effort" pattern. The user experience is prioritised (instant feedback) over strict DB consistency. For this use case (a tour completion flag) this is acceptable — a stale "tour_completed = false" for one session is better than showing the user an error or blocking the celebration screen on a failed DB write.
