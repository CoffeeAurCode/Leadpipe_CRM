The Phantom Vacancy — Filtering on a Column We Never Fetched

A native-French tester called the live lease agent, asked for "un 4 et demi" (a Québec-style two-bedroom) in Saint-Lazare — a unit that absolutely exists in the database — and the agent said there was nothing available. When the tester pushed back ("I can see it in your system"), the agent instantly caved: "Vous avez raison…" and recited the exact unit, floor, date, and rent. Same call, same agent, two opposite answers thirty seconds apart. This session is the hunt for how a search tool can return zero results for inventory that exists, why the agent then contradicted itself, and how one missing word in a database query — a column name absent from a SELECT — silently deleted every listing from every size-filtered search. We fix it with one word, armor it with three regression tests, and verify it against the live production server.

🟡 Intermediate ⏱️ ~60 min read 📋 Requires: Sessions 11–12 (the lease agent's tools); helpful: Session 15 (transcript forensics, the fake mojibake)

📦 Session Overview

This was a diagnose → fix → test → verify-in-production session, start to finish. The user arrived with a transcript file (Transcript3.md) and one instruction:

You: my french partner did another test to the lease agent... this is the transcript... diagnose the issue in this and give to me straight

By the end of the session we had:

  • A confirmed root cause — the /leasing/search-listings endpoint filtered listings by quebec_size (the Québec apartment size, like "4½") but its database query never fetched that column, so the filter compared every listing against None and dropped all of them. Any search that included a size returned zero results, always, for every listing, for every caller.
  • An explanation for the "flip-flop" — the agent's earlier find_units tool call had returned the real unit, so when the caller pushed back, the LLM (Large Language Model — the AI producing the agent's words) abandoned the broken search result and quoted the good data it still had in memory. Two tools disagreed; the agent got caught between them.
  • A one-word fix, times three — quebec_size added to two SELECT strings and to the response formatter, so the search works and the agent can now confirm the size back to callers.
  • Three regression tests — including one that asserts on the query string itself, a technique that catches this class of bug even under mocked databases.
  • Live production verification — after the user committed and deployed, we hit the real Render endpoint and watched the previously-invisible Saint-Lazare 4½ come back in the results.
  • Two false alarms resolved — the transcript's absurd "$14,100/month" rent (a speech-transcription artifact; the real rent is $1,400) and a scary-looking 4Â½ in terminal output (the Windows console rendering artifact we first met in Session 15).

🧠 Concepts Introduced This Session

Seven ideas that stack into the story. C1 is the mechanism of the bug (you only get the columns you ask for). C2 is why nothing crashed (Python's forgiving .get()). C3 is why the agent behaved so strangely (two tools, two answers). C4 explains the architecture that made the bug possible (filtering in Python instead of the database). 1 · Projection — you only get the columns you ask for

Plain-English explanation. When code reads from a database, it almost never says "give me everything about these rows." It names the columns it wants — this is called the projection (the "what to return" half of a query, as opposed to the "which rows" half). Our backend talks to Supabase through a select string: a comma-separated list of column names passed to .select(...). The database returns exactly those columns and nothing else. If a row has forty columns and your select string names twelve, the dictionary you get back in Python has twelve keys. The other twenty-eight don't exist in that dictionary — not as empty values, not as None — they are simply absent.

Why we need it (for CRM specifically). Naming columns is good practice — it keeps payloads small (the voice agent's tool responses must be fast) and makes each endpoint's data needs explicit. But it creates a standing hazard: every time someone adds code that reads a field from a fetched row, they must also check that the select string fetches it. Those two places can be 30 lines apart. In our case they were: the filter at line 530 of leasing.py read quebec_size; the select string at line 498 didn't include it. Nobody connected the two — until a caller in Saint-Lazare did.

How it works (analogy). Ordering room service with a checklist. The kitchen sends up exactly what you ticked — if you didn't tick "cutlery," you get a steak and no knife. The bug was code that ordered a steak without a knife, and then a second piece of code downstream that tried to cut with the knife, found nothing in its hand, and — crucially — didn't complain. It just quietly gave up on dinner.

Jargon decoder.

  • projection — the set of columns a query returns; in SQL (Structured Query Language) it's the part right after the word SELECT.
  • PostgREST — the layer Supabase uses to expose PostgreSQL over HTTP; the select string is its syntax (it even supports joins, like flats!inner(bedrooms, ...), which pulls related columns from the joined flats table).
  • select string — the comma-separated column list our code passes to .select(...); the projection, written as one Python string.

Here is the exact query the search endpoint ran — with the missing word highlighted by its absence. Compare it with find_units' query just 270 lines earlier in the same file, which gets it right:

# search_listings (line ~495) -- the BROKEN one.
q = (
    db.table("lease_listings")           # start a query on the listings table
    .select(
        # The projection: every column this endpoint will ever see.
        "uuid, flat_number, title, monthly_rent, available_from, custom_rules, "
        "square_footage, included_utilities, parking, laundry, "
        # ^^^ quebec_size is NOT in this list. The rows that come back
        #     will not have a "quebec_size" key AT ALL.
        "street_address, city, state, country, "
        "flats!inner(bedrooms, bathrooms, floor_number)"  # joined columns from flats
    )
    .eq("is_active", True)               # which-rows half: only active listings
)

# find_units (line ~221) -- the CORRECT one, same file, same table.
q = (
    db.table("lease_listings")
    .select(
        "uuid, flat_number, title, monthly_rent, available_from, quebec_size, "
        # ^^^ here it IS fetched -- which is why find_units could tell the
        #     caller about the 4-and-a-half while search_listings could not.
        "street_address, city, state, country, "
        "flats!inner(bedrooms, bathrooms, floor_number, buildings(name, properties_list(name)))"
    )
    .eq("is_active", True)
)
🔑 Key Concept — a projection is a contract, and it has two parties

Every field your post-fetch code reads is a promise the select string must keep. When the two are written at different times (the select string existed first; the quebec_size filter was added later), the promise silently breaks. Treat "I added a r.get("column")" and "I added that column to .select()" as one indivisible edit — and, as C5 shows, write a test that fails if anyone ever splits them again.

2 · Silent failures — why .get() never told us

Plain-English explanation. Python dictionaries give you two ways to read a key. row["quebec_size"] crashes with a KeyError if the key is missing. row.get("quebec_size") quietly returns None instead. The filter used .get(), then wrapped it in or "" ("if it's None, treat it as empty text"), then normalized the empty text… which produced an empty string that could never equal "4½". Every row failed the comparison. The function returned a perfectly well-formed, perfectly wrong answer: {"count": 0, "listings": []}. No exception, no log line, no HTTP error. "Completed successfully," said the call transcript — and technically, it had.

Why we need it (for CRM specifically). Our voice-tool endpoints are deliberately forgiving — a hard project rule says VAPI endpoints always return HTTP 200, because a crash mid-call is worse for the caller than an empty result. That's the right trade-off for the caller experience, but it means the usual alarm bells (stack traces, 500 errors, monitoring alerts) are muted by design. In a system built to never crash, a wrong-but-valid answer is the dominant failure mode, and you have to hunt it with tests and transcripts instead of waiting for an exception to find you.

How it works (analogy). A smoke detector with the battery removed so it stops beeping at burnt toast. Quieter kitchen — but now an actual fire is silent too. .get() + or "" + "always return 200" removed every beep between the missing column and the caller being told a real apartment doesn't exist.

Jargon decoder.

  • KeyError — Python's exception for reading a dictionary key that doesn't exist; loud, immediate, and in this one case would have been helpful.
  • falsy coalescing — the x or default idiom: if x is "empty-ish" (None, "", 0), use default. Convenient, and a great way to launder a missing value into a plausible one.
  • silent failure — a defect that produces valid-looking output instead of an error; the hardest class of bug to detect in production.

Here is the exact laundering chain, line by line:

if quebec_size_filter:                     # caller asked for a size, e.g. "4 1/2"
    qs_norm = _normalize_quebec_size(quebec_size_filter)
    # qs_norm is now "4½" -- the caller's side of the comparison is perfect.

    rows = [r for r in rows
            if _normalize_quebec_size(r.get("quebec_size") or "") == qs_norm]
    #                                 ^^^^^^^^^^^^^^^^^^^^^
    # r.get("quebec_size")  ->  None   (the column was never SELECTed, see C1)
    # None or ""            ->  ""     (falsy coalescing hides the None)
    # _normalize_...("")    ->  ""     (normalizing nothing gives nothing)
    # "" == "4½"            ->  False  (for EVERY row, ALWAYS)
    # rows is now []  --  the phantom vacancy is born, silently.
⚠️ Warning — every .get(...) or default is a decision about failure

Sometimes you truly want "missing = empty" (optional columns, genuinely absent data). But when the field is required for the logic to make sense — you cannot meaningfully size-filter a row that has no size — a missing key is a programming error and deserves to be loud. Ask, each time you type .get(): "if this key is missing, is that normal, or is it a bug I'd want to know about?"

3 · The two-tool consistency problem — why the agent flip-flopped

Plain-English explanation. The strangest part of the transcript wasn't the wrong answer — it was the reversal. The agent said "nothing available in 4½ at Saint-Lazare," the caller objected, and the agent immediately produced the exact unit: building, floor, availability date, rent. Where did that come from? From earlier in the same call. When the caller first mentioned Saint-Lazare, the agent ran find_units — the tool whose query does fetch quebec_size (C1) — and it returned the real unit. That result stayed in the conversation context. So the agent held two contradictory "facts": tool A said the unit exists; tool B (broken) said nothing matches. It reported B's answer first. Under social pressure ("I can see it in your system"), it fell back to A's.

Why we need it (for CRM specifically). Two lessons. First, an agent is only as consistent as its tools agree with each other — when two endpoints answer overlapping questions from the same table, a bug in one produces not just a wrong answer but a visible self-contradiction, which is far more trust-destroying to a caller than a plain mistake. Second, the flip-flop is diagnostic gold: the moment you see an agent contradict itself, ask "which tool produced each statement?" — the disagreement points a straight line at the broken one. Here, "no results" came seconds after Search Listings — Completed successfully, and the correct details matched find_units' output field-for-field. That's what let us walk into the code already knowing which function to read.

How it works (analogy). A hotel receptionist with two computer screens. Screen one (reservations) shows room 404 exists. Screen two (the search kiosk, which is broken) shows no rooms match your criteria. The receptionist reads screen two and says "we have nothing." You insist. Flustered, they glance at screen one and say "oh — you're right, room 404, fourth floor." The receptionist isn't dishonest or stupid; their two screens disagree, and they have no way to know which one to trust.

Jargon decoder.

  • conversation context — everything the LLM can see when composing its next line: the system prompt, the dialogue so far, and every previous tool result in the call.
  • sycophancy — an LLM's tendency to agree with a user who pushes back, even against its own prior statement. Usually a flaw; here it accidentally surfaced the truth, because the pushed-to answer came from the working tool.
  • ground truth — the actual state of the database, against which both tool answers can be checked.
one call, two tools, two answers caller: "I'm in Saint-Lazare…" └─> find_units("Saint-Lazare") ──> SELECT … quebec_size … ✓ returns: { flat 76, "4½", floor 4, 2026-06-22, $1400 } ← truth, now in context caller: "…a 4 et demi" └─> search_listings(quebec_size="4½", city="Saint-Lazare") SELECT … (no quebec_size!) … ──> filter drops ALL rows returns: { count: 0 } ← phantom vacancy agent (trusting the latest tool): "je n'ai rien de disponible…" ← wrong caller: "I can see it in your system!" agent (falling back to context): "Vous avez raison… 4½, 4e étage" ← right, for the wrong reason
🔑 Key Concept — "the agent is hallucinating" is a hypothesis, not a diagnosis

It would have been easy to blame the model: it made up a listing when pressured. But every "hallucinated" detail matched the database exactly — building, floor, date. An LLM inventing an apartment doesn't guess the correct availability date. When an agent's "made-up" answer is verifiably true, it almost certainly came from real data somewhere in its context, and the actually-false statement is the one to investigate. Check the tools before you blame the brain.

4 · DB-level filters vs Python post-fetch filters

Plain-English explanation. There are two places to narrow down "which rows": in the database query itself (fast, runs where the data lives — our .lte("monthly_rent", budget) budget cap and .ilike("state", ...) state match) or in Python after fetching (pull a batch of candidate rows, then loop over them with ordinary code). search_listings uses both: numeric filters go to the database; the fuzzy ones — city (accent-tolerant matching), quebec_size (spelling-variant normalization), parking, laundry — run in Python on up to 20 fetched rows.

Why we need it (for CRM specifically). The Python side exists for a real reason: the database can't easily express "'4 1/2', '4.5' and '4½' are the same size" or "'Saint-Lazore' (as the transcriber heard it) means Saint-Lazare." Our _normalize_quebec_size() helper collapses ½, 1/2, and .5 spellings on both sides of the comparison — logic that lives naturally in Python. But note the trap this architecture sets: a Python filter can only see columns the fetch brought back. A DB-level filter on a misspelled or missing column fails loudly (PostgREST returns an error). A Python filter on a missing key fails the C2 way — silently. The flexibility of post-fetch filtering is paid for in fragility, which is exactly why the C5 test exists.

How it works (analogy). The database filter is asking the warehouse to only ship red shirts. The Python filter is having the shipment opened in your office and hand-sorting for "red-ish, including burgundy and brick" — smarter matching, but only possible on shirts that made it into the box. If the warehouse never packed the color tags (didn't SELECT the column), your sorter calls everything not-red and the "red-ish" pile is empty forever.

Jargon decoder.

  • post-fetch filtering — narrowing rows in application code after the database returned them.
  • normalization — converting variant spellings to one canonical form before comparing (here: "4 1/2" → "4½").
  • ilike — PostgreSQL's case-insensitive pattern match, used for the state filter.
def _normalize_quebec_size(s: str) -> str:
    # Canonicalize a Québec size so variant spellings compare equal.
    if not s:                                   # None-safe: empty in, empty out
        return ""
    s = s.strip().lower().replace("Â", "")      # defensive strip of stray mojibake byte
    s = s.replace("1/2", "½").replace(".5", "½") # "4 1/2" and "4.5" both become "4 ½"
    return s.replace(" ", "")                   # drop spaces -> "4½", the stored form

Worth noting: this function was never the problem. The tolerant matching worked perfectly in tests once it had real data to chew on. The lesson of Session 12 (build tolerant matchers) survived; it was starved of input by the layer above it.

5 · Testing the query contract — asserting on the SELECT string itself

Plain-English explanation. Our backend test suite doesn't talk to a real database. It uses mocks — stand-in objects (Python's unittest.mock.MagicMock) that accept any method call and return canned data we configure. When a test says "the listings table contains this row," the mock hands that row back regardless of what the select string said, because a mock doesn't implement projection — it's a prop, not a database. That means the ordinary style of test ("call the endpoint, check the output") could not have caught this bug: give the mock a row that includes quebec_size and the filter works in the test even though production never fetches that column. The fix is to also assert on the call the code made: MagicMock records every call and its arguments, so the test can grab the exact select string the endpoint passed to .select(...) and assert "quebec_size" in select_arg. That's a contract test — it pins the promise between the filter and the projection (C1) so no future edit can quietly split them.

Why we need it (for CRM specifically). This is the honest answer to "why did the bug ship?" — the existing tests for this endpoint checked status codes and response shape, and none mentioned quebec_size at all. Under mocks, even a perfect behavioral test would have lied to us. The three tests we added cover all three layers: the tolerant matching behavior (variant spelling "4 1/2" finds stored "4½"), the exclusion behavior (a "3½" doesn't match a "4½" search), and — the load-bearing one — the query contract itself.

How it works (analogy). A mannequin fitting. Testing clothes on a mannequin (mock) checks the stitching and the shape, but a mannequin never complains that the jacket has no pockets — it doesn't use pockets. If pockets matter, you must inspect the jacket itself ("does it have pockets?") rather than only watching the mannequin wear it. Asserting on the select string is checking the jacket.

Jargon decoder.

  • mock — a configurable stand-in object used in tests; records calls made to it and returns canned responses.
  • MagicMock — Python's auto-permissive mock: any attribute or method you touch springs into existence.
  • call_args — a MagicMock's memory of the most recent call's arguments; .call_args.args[0] is the first positional argument (our select string).
  • contract test — a test asserting on the interaction between two components (what was asked of the database) rather than only the end result.
  • regression test — a test written after a bug is fixed, specifically shaped so that re-introducing the bug makes it fail.
def test_quebec_size_variant_spelling_matches(self, authed_client):
    # Give the mock DB one listing whose stored size is the canonical "4½".
    row = {**_LISTING_ROW, "quebec_size": "4½"}
    tc, _ = authed_client(lease_listings=[row])
    # The caller says it the messy way: "4 1/2". params= handles URL-encoding
    # the space for us (a raw space in a URL string would be invalid).
    resp = tc.get("/leasing/search-listings", params={"quebec_size": "4 1/2"})
    body = resp.json()
    assert body["count"] == 1                       # tolerant match found it
    assert body["listings"][0]["quebec_size"] == "4½"  # and the size is echoed back

def test_quebec_size_mismatch_filters_out(self, authed_client):
    # A three-and-a-half must NOT satisfy a four-and-a-half search.
    row = {**_LISTING_ROW, "quebec_size": "3½"}
    tc, _ = authed_client(lease_listings=[row])
    resp = tc.get("/leasing/search-listings", params={"quebec_size": "4½"})
    assert resp.json()["count"] == 0                # correctly excluded

def test_quebec_size_column_is_fetched(self, authed_client):
    """Regression (Transcript3): the filter compares r['quebec_size'], so the
    select MUST fetch that column -- otherwise every row silently drops and the
    agent reports 'no listings' for sizes that exist."""
    row = {**_LISTING_ROW, "quebec_size": "4½"}
    tc, db = authed_client(lease_listings=[row])     # keep the mock -- we inspect it
    tc.get("/leasing/search-listings", params={"quebec_size": "4½"})
    # The mock recorded every call. Pull the first positional argument that the
    # endpoint passed to .select(...) -- the projection string itself.
    select_arg = db.table("lease_listings").select.call_args.args[0]
    assert "quebec_size" in select_arg               # the contract, pinned forever
📖 Deep Dive — the limits of mocked tests, stated honestly

Mocks trade realism for speed and isolation. Everything a real PostgREST would enforce — projections, joins, type coercion, RLS (Row Level Security) — is absent, so a whole family of "query is wrong" bugs pass mocked tests. The industrial-strength fix is a second tier of tests against a real (local or disposable) database, where .select("nonexistent_column") actually errors. Until then, contract assertions like ours are the cheap, targeted patch: they don't verify the column exists, but they do verify the code asks for every column it uses — which is precisely the mistake that happened.

6 · Dependency drift — when your virtualenv falls behind the code

Plain-English explanation. A virtualenv (virtual environment — a private, per-project folder of installed Python packages, here backend/.venv) is a snapshot: it contains whatever was installed into it, whenever that was. The codebase, meanwhile, keeps moving — a recent commit added a bilingual complaint agent that imports twilio, and requirements.txt (the list of packages the project needs) grew with it. Nobody re-ran pip install into this machine's venv, so when we tried to run the test suite, importing the app crashed at from twilio.rest import Client with ModuleNotFoundError. The code was fine; the environment had drifted behind it.

Why we need it (for CRM specifically). Two practical skills fell out. First, reading pytest exit codes: exit code 1 means "tests ran, some failed," but exit code 4 means "pytest couldn't even start" (usage/collection error) — our first run returned 4, which immediately says don't debug the tests, debug the setup. Second, the fix ritual: identify the project's real interpreter (backend/.venv/Scripts/python.exe — we found it by listing for .venv folders after two wrong guesses about its location), then python -m pip install -r requirements.txt to fast-forward the snapshot to match the code. Packages already present are skipped; only the drift is installed.

How it works (analogy). A shared kitchen with a recipe binder. A teammate adds a new recipe that needs a spice you've never bought (twilio). Next time you cook from the binder, you're missing an ingredient — not because the recipe is wrong, but because your pantry hasn't caught up with the binder. pip install -r requirements.txt is the grocery run that syncs your pantry to the binder.

Jargon decoder.

  • virtualenv / venv — an isolated per-project set of installed Python packages, so projects don't fight over versions.
  • requirements.txt — the project's declared package list; the source of truth the venv should mirror.
  • ModuleNotFoundError — Python's "I can't import that package" error; in a venv-based project, usually means wrong interpreter or drifted venv.
  • pytest exit codes — 0 = all passed, 1 = failures, 2 = interrupted, 3 = internal error, 4 = usage/startup error, 5 = no tests found.

7 · Production smoke testing — and telling artifacts from bugs

Plain-English explanation. After the user committed and deployed, we didn't declare victory from green local tests. We made one real HTTP request to the live Render server — the same request the voice agent's tool makes — and read the answer. This is a smoke test: not a full test suite, just "does the fixed path visibly work where users actually are?" It did: quebec_size=4 1/2 now returned count: 2, and the first result was the very unit from the transcript — 2803 Rue Du Comtois, Saint-Lazare, 4½, 4th floor, available 2026-06-22, $1,400/month.

Why we need it (for CRM specifically). That one response also settled two open worries from the transcript, and taught the discipline of checking ground truth before diagnosing. Worry one: the agent had quoted "14 100 par mois" — $14,100/month, absurd. The live data says the rent is 1400; the agent almost certainly said "quatorze cents" (fourteen hundred, natural Québec French) and the speech-to-text transcriber wrote it down as "14 100." A transcription artifact, not a data or agent bug — no fix needed. Worry two: the JSON in our terminal showed "quebec_size":"4Â½" — the dreaded mojibake. But Session 15's Bug 4 taught us this exact pattern: the Windows console renders UTF-8's two-byte ½ as two cp1252 characters. Proof it's cosmetic: the size filter matched — server-side, the stored bytes normalize cleanly to "4½", which they couldn't do if truly corrupted. The behavior of the system is better evidence than the glyphs in your terminal.

How it works (analogy). After the electrician replaces a breaker, you don't re-read the wiring diagram — you flip the actual light switch in the actual room. And if the bulb's light looks odd through your tinted glasses (the console's rendering), you judge by whether the room is lit, not by the tint.

Jargon decoder.

  • smoke test — a minimal end-to-end check that the deployed system performs the fixed behavior; named after powering on hardware and checking for smoke.
  • Render — the cloud platform hosting our FastAPI backend; deploys automatically from the GitHub branch.
  • Invoke-RestMethod — PowerShell's built-in HTTP client (its curl); fetches a URL and parses JSON into objects.
  • transcription artifact — an error introduced by the speech-to-text layer writing down spoken words, as opposed to an error in the data or the agent's reasoning.

Bug 1 — The phantom vacancy: size-filtered searches always return zero

🚨 The Symptom

A live French test call. The caller asks for a 4½ in Saint-Lazare — a listing that exists and that the same agent described minutes later. The tool log shows Search Listings — Completed successfully, and the agent says:

Lease Agent FR: "…pour le moment, je n'ai rien de disponible en 4 et demi à Saint-Lazare. Est-ce que ce serait correct si je prenais vos informations…"

No error anywhere. No crash. Just a confident, wrong "we have nothing," heading straight into lead-capture — the flow for callers we genuinely can't help.

🔍 The Diagnosis
  1. Read the transcript first and separated the layers. The STT (speech-to-text) garbles ("Sur un 4 minutes") were handled correctly by the agent with clarifying questions — so language understanding was not the failure. The wrong statement came immediately after a "successful" search_listings call. Hypothesis: the tool returned empty.
  2. Used the flip-flop as a compass (C3). The agent's corrected answer contained field-perfect details — floor 4, available 2026-06-22 — that must have come from the earlier find_units result. So the data exists and one tool can see it. The broken one is search_listings specifically.
  3. Grepped for both tool names → backend/app/routes/leasing.py, and read search_listings top to bottom. The filter block at lines 528–530 reads r.get("quebec_size").
  4. Scrolled up 30 lines to the select string. Counted the columns. quebec_size is not there. Scrolled up further to find_units — its select string has it. Diagnosis complete without running a single command: the filter compares every row's None against "4½".
  5. Confirmed the path is hit in production: the Vapi tool definition in vapi_agent_config.py line 1652 templates &quebec_size={{quebec_size}} into the request — so every caller who states a Québec size triggers the dead filter.

Red herring dodged: the obvious first guess — "the agent had trouble understanding 4 and a half" (the user's partner's read) — was checkable and false: the transcript shows the agent asked for clarification and got explicit confirmation before the search fired. The size reached the backend correctly; the backend threw it away.

🧠 The Root Cause

A fetch/filter contract violation (C1 + C2). The quebec_size filter was added to the endpoint (Session 12's Québec-sizing work) without adding the column to that endpoint's select string — while the sibling endpoint find_units, edited in the same era, did get the column. The underlying concept: a Supabase/PostgREST query returns only the named columns, and dict.get() converts the resulting missing key into None without complaint, which or "" then converts into a comparable-but-never-equal empty string. Three permissive layers, each reasonable alone, composed into total silent data loss. And the test suite couldn't catch it because mocked databases don't enforce projections (C5).

🔧 The Fix
  .select(
      "uuid, flat_number, title, monthly_rent, available_from, custom_rules, "
-     "square_footage, included_utilities, parking, laundry, "
+     "square_footage, included_utilities, parking, laundry, quebec_size, "
      "street_address, city, state, country, "
      "flats!inner(bedrooms, bathrooms, floor_number)"
  )

One word. With the column fetched, r.get("quebec_size") returns the stored "4½", both sides normalize identically, and the tolerant matcher from Session 12 finally does the job it was built for. Verified three ways: the new unit tests (33 passed), and the live smoke test flipping from count: 0 to count: 2.

🛡️ The Lesson

"Completed successfully" measures plumbing, not truth. An endpoint that returns a valid shape has succeeded in HTTP terms while failing in business terms. When a system is designed never to error (our always-200 rule for voice tools), you must actively hunt wrong-but-valid answers: compare tools against each other (the flip-flop was the tell), test the query contract, and smoke-test with a request whose correct answer you already know. And whenever you write a post-fetch filter, immediately audit the select string — the pair is one edit, never two.

Bug 2 — The prompt that lied: promised a field the API never sent

🚨 The Symptom

No visible crash — this one was found by reading, during the Bug 1 investigation. The French agent's system prompt tells the model what each search result contains:

vapi_agent_config.py:1781 "…state, bedrooms, bathrooms, quebec_size, monthly_rent, floor_number, available_from, title, parking, laundry."

…but _format_listings, which builds those results, emitted no quebec_size key at all.

🔍 The Diagnosis

While confirming Bug 1's blast radius, we grepped quebec_size across vapi_agent_config.py and cross-referenced each mention against the backend: the tool sends the parameter (line 1652 — real), the tool schema declares it (line 1798 — real), and the prompt describes it in responses (line 1781 — false, until now). Then we read _format_listings (lines 37–65 of leasing.py) and confirmed the key was absent from the output dictionary.

🧠 The Root Cause

A prompt/API contract drift — the same disease as Bug 1, one layer up. The prompt (written when Québec sizing was designed) documents the intended response shape; the formatter implements the actual one; nothing ties them together. For an LLM this is worse than useless: a model told "results include quebec_size" that never sees one may fall back on inference — deducing "4½" from bedrooms: 2 — which is usually right and occasionally, confidently, wrong.

🔧 The Fix
      "bedrooms": flat.get("bedrooms"),
      "bathrooms": flat.get("bathrooms"),
+     "quebec_size": r.get("quebec_size") or "",   # make the prompt's promise true
      "monthly_rent": float(r["monthly_rent"]),

Plus quebec_size added to listings_for_agent's select string, since that endpoint feeds the same formatter. The first new unit test locks this in by asserting the field appears in responses.

🛡️ The Lesson

A system prompt is API documentation that a very literal reader trusts completely. Every field a prompt claims a tool returns must actually be returned — audit prompt-against-formatter whenever either changes. When you fix a data bug, check what the prompt says about that data; drift clusters.

Bug 4 — The $14,100 apartment (false alarm: a transcription artifact)

🚨 The Symptom
Lease Agent FR: "…disponible depuis le 22 juin 2026 à 14 100 par mois."

$14,100/month for a Québec 4½ is off by an order of magnitude. Is the database rent wrong? Did the agent mangle the number?

🔍 The Diagnosis

Deferred until we had ground truth, then read straight off the production smoke test: monthly_rent: 1400.0. The data is correct. So the "14 100" was created somewhere between the agent's text and the transcript. The likely chain: the agent said the rent the natural Québec-French way — "quatorze cents" (fourteen hundred) — and the transcription layer, converting spoken numbers to digits, rendered "quatorze" + "cents" as 14 + 100. The same call shows this transcriber garbling numbers repeatedly ("Sur un 4 minutes", "1 4 et demi"), which raises the prior for a transcription slip over a data slip.

🧠 The Root Cause

Not a bug in our system. Spoken-number formatting is a lossy channel: French hundreds-based counting ("quatorze cents" = 1,400) maps badly onto a digit-by-digit transcription heuristic. The transcript is a witness, not a recording — it can be wrong about what was said.

🔧 The Fix

None shipped — the database is right and the agent (most probably) spoke correctly. The watch-item stands: if a caller ever mishears a rent (not just the transcript), we'd add a prompt rule to speak prices digit-grouped ("mille quatre cents dollars") for unambiguous TTS.

🛡️ The Lesson

Check ground truth before diagnosing. One production query separated "our data is wrong" (a serious bug) from "the transcript wrote the number oddly" (noise). Never file a bug against a value you haven't read from the source of record.

🚨 The Symptom

🔍 The Diagnosis & Root Cause

Session 15's Bug 4, re-run on new data: UTF-8 encodes ½ as two bytes (0xC2 0xBD), and the Windows PowerShell console renders them as two cp1252 characters (Â + ½). This time we didn't even need to check raw bytes — the behavior proved the bytes clean: the size filter matched server-side, and _normalize_quebec_size("4Â½")-style corruption on the server would have needed its (dead, post-lowercase) Â-strip to save it. 🧯 Troubleshooting / Common Errors

My filtered search always returns count: 0 even for data I know exists

This session's signature. Check, in order: (1) is every field the filter reads present in the select string? (2) print one fetched row — does the key exist at all? (3) is the filter comparing normalized-vs-raw (both sides must pass through the same normalizer)? (4) did a DB-level filter (lte/ilike) already empty the candidate set before Python filtering?

pytest exits with code 4 and no test results

Startup failure, not test failure — usually an import error in conftest.py or the app. Read the first traceback line: No module named 'fastapi' means wrong interpreter (use backend/.venv/Scripts/python.exe); a missing newer package (twilio) with core packages present means drifted venv — pip install -r requirements.txt.

ModuleNotFoundError for a package that IS in requirements.txt

requirements.txt is a wish list; the venv is what's actually installed. Being listed ≠ being installed. Sync with python -m pip install -r requirements.txt using the venv's own interpreter (the python -m pip form guarantees pip installs into that Python, not another one on PATH).

My mock-based test passes but production still fails

Mocks don't enforce query correctness — they return your canned rows no matter what the code asked for (C5). If the bug is in what the code asks the database, assert on the recorded call (mock.select.call_args) or add a real-database test tier.

Accented characters look like Â½ or é in my terminal

Almost certainly the Windows console rendering UTF-8 bytes as cp1252 (Bugs 4/5 here; Session 15 Bug 4). Verify with behavior (did a server-side comparison on that value succeed?) or raw bytes (open(path, encoding="utf-8").read()) before "fixing" data that isn't broken.

The agent contradicts itself mid-call

Map each statement to its source tool call in the transcript. Two overlapping tools disagreeing = one of them is broken; the details in the corrected answer usually identify the healthy tool. Then diff the two implementations — ours differed by exactly one word in a select string.

Invoke-RestMethod fails or the URL seems mangled

Spaces are illegal in URLs — encode them as %20 (we sent quebec_size=4%201/2). For a first deploy check, also remember Render free-tier services cold-start: the first request after idling can take tens of seconds; raise -TimeoutSec.
