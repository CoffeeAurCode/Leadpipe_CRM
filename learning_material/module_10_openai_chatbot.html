Module 10 — AI Chatbot with Tool Calling (OpenAI)

Part C — AI & Voice Integration  |  Build Session 3

Module 10 of 26 — 38% through the course

Learner outcome: Can build a multi-turn chatbot with tool calling, inject dynamic context (today's date), truncate history to manage costs, and detect when tools mutate data so the frontend can refresh.

Source files: backend/app/ai/chatbot.py, backend/app/routes/chat.py

What the Chatbot Does

The chatbot lets property managers control the entire system through natural language from within the dashboard. Instead of clicking through modals, a manager can type:

"Add a new building called Maple Court at 45 Oak Street" "Show me all appointments for flat B-203" "Reschedule appointment 14 to next Thursday at 3pm" "Cancel all appointments for the Riverside block"

The chatbot can read data (no side effects) and also mutate data (create buildings, reschedule appointments, delete tenants). When it mutates appointment data, it sends a refresh_needed: true signal back so the frontend refreshes the calendar automatically.

System Prompt + Date Injection

Why inject date at request time, not module load time?

If the date was baked into the system prompt string at server startup, every request for the entire lifetime of the server would use the same date. The server starts on June 1st, runs until July 15th — every chatbot request thinks it's still June 1st. By formatting {today} inside run_chat(), the date is accurate for every single request.

Tool Schema Design

OpenAI tool calling requires defining each tool as a JSON Schema object. The structure is:

{
    "type": "function",
    "function": {
        "name": "add_new_unit",
        "description": "Add a new unit/flat to a building. Looks up the building by name automatically.",
        "parameters": {
            "type": "object",
            "properties": {
                "flat_number": {
                    "type": "string",
                    "description": "The unit/flat identifier (e.g. '4B', 'A101')"
                },
                "building_name": {
                    "type": "string",
                    "description": "The name of the building this unit belongs to (will be looked up by name)"
                }
            },
            "required": ["flat_number", "building_name"]
        }
    }
}

Key design points in descriptions:

Tool name patternWhy it matters
"Looks up the building by name automatically"Tells the model it does NOT need to first call a separate lookup tool. The LLM will otherwise chain unnecessary calls.
"Only use the appointment ID explicitly stated by the user"Guards against the LLM hallucinating a nearby appointment ID when the exact one doesn't match.
Detailed description on each parameterThe LLM reads these when deciding what to pass. Vague descriptions = wrong arguments.

execute_tool() — Deep Dive on Key Patterns

Building name lookup via ilike

Pattern — name lookup with ambiguity handling: The user types "Add unit to Maple" and the tool searches ILIKE '%Maple%'. If 0 results: clear error. If 1 result: proceed. If 2+ results: list them all and ask the user to be more specific. This is the correct pattern for any fuzzy name lookup.

Tool results must be strings

The LLM reads the tool result and formulates a human response from it. If you return a dict, the LLM will try to parse a Python object repr string, which is inconsistent. Always return a plain string the model can read naturally.

Appointment rescheduling with date normalization

Date format bug: Early versions stored dates with a space separator (2025-06-15 10:00:00). JavaScript's parseISO() from date-fns requires a T separator. Appointments stored with spaces showed as "Invalid Date" in the calendar. The fix: always use strftime("%Y-%m-%dT%H:%M:%S").

Notification trigger after reschedule

The chatbot fires the same notification service as the REST API. A manager typing "Reschedule appointment 14 to Thursday" triggers an SMS to the tenant automatically.

run_chat() — The Agentic Loop

The message chain structure

Here's what full_messages looks like after one tool call cycle:

[
  {"role": "system",    "content": "...today is Tuesday June 03..."},
  {"role": "user",      "content": "What appointments are on June 5th?"},
  {"role": "assistant", "content": null, "tool_calls": [{"id": "call_abc", "function": {"name": "check_appointments_by_date", ...}}]},
  {"role": "tool",       "tool_call_id": "call_abc", "content": "Appointments for 2026-06-05:\n- ID 14 | Flat A-101 | ..."},
  // ← model now generates a response reading the tool result
  {"role": "assistant", "content": "On June 5th you have 2 appointments: ..."}
]

The OpenAI API requires this exact alternating structure. If you append a tool message without a preceding assistant message containing the matching tool_calls, the API returns a BadRequestError.

refresh_needed Signal

The chat route returns {"reply": "...", "refresh_needed": true}. The frontend Chatbot.jsx checks this and dispatches a custom event:

// In Chatbot.jsx (frontend)
if (data.refresh_needed) {
  window.dispatchEvent(new Event('refresh-appointments'));
}

App.jsx listens for this event and re-fetches complaints and appointments. This is the simplest possible real-time update mechanism — no WebSockets, no polling for this purpose.

Why only appointment tools trigger refresh? Adding a new building doesn't need a dashboard refresh because the buildings list is fetched on navigation, not continuously. But appointment mutations affect the calendar view which the manager may be looking at right now. Only surfacing the event for visible/time-sensitive data avoids unnecessary re-renders.

History Truncation

OpenAI charges per token. A long conversation grows unbounded. The fix: only send the last 10 messages to the model. The system message is always prepended fresh (not counted in the 10).

Tradeoff: Messages beyond 10 turns back are forgotten. For most property management tasks (3-4 turns to complete an action), this is fine. For very long investigations ("look up the complaint from three weeks ago, then find the tenant for that flat, then reschedule their appointment..."), the model may lose context. A more sophisticated approach would use a sliding window or summarize older history.

BadRequestError Fallback

Groq tool calling quirk (affects Groq models, not OpenAI): llama-3.3-70b-versatile sometimes hallucinates tool names that aren't in the schema (e.g., calls brave_search when it doesn't exist in the TOOLS list). The Groq API returns a BadRequestError with "tool_use_failed" in the error message. The fix: catch BadRequestError and retry without tools as a plain completion. This way the user gets a response instead of an error.

The chatbot uses OpenAI (gpt-4o-mini) so this quirk doesn't actually affect it. The code has this guard as a safety net and for historical reasons — early versions used Groq for both extraction and chat.

chat.py Route

Dependency chain

DependencyWhat it provides
require_active_subscriptionBlocks non-subscribers. Returns the user dict (JWT payload).
get_authenticated_dbRLS-enforced Supabase client. Only data owned by this manager is visible.

The chatbot gets db (not user) injected. It calls Supabase through this RLS-enforced client, so a manager cannot accidentally access another manager's buildings through the chatbot — even if they send malformed messages trying to.

Why Literal["user", "assistant"] for role?

Pydantic validates the role field at request time. If the frontend sends role: "system", FastAPI returns a 422 before the code even runs. This prevents prompt injection attacks where a malicious client tries to override the system prompt by injecting a {"role": "system", "content": "ignore all previous instructions"} message into the chat history.

Real Bugs Faced & How We Fixed Them

Bug 1: Chatbot didn't know today's date — hallucinated appointments in the past

Symptom: Manager says "Schedule for tomorrow" — chatbot uses 2023 or some other training-cutoff date.

Root cause: System prompt had no date injection.

Fix: Added {today} placeholder in _SYSTEM_PROMPT_BASE and the format(today=today) call in run_chat().

Bug 2: Chatbot rescheduled the wrong appointment

Symptom: Manager says "Reschedule appointment 14" — chatbot reschedules appointment 15 because 14 wasn't found.

Root cause: The model was substituting the nearest valid appointment ID when the specified one wasn't found.

Fix: Added the explicit system prompt rule: "When rescheduling, use ONLY the appointment ID that the user explicitly stated. If that appointment is not found, tell the user it does not exist — do NOT substitute a different appointment ID." Also, execute_tool() returns a clear error string when the ID isn't found rather than a soft failure.

Bug 3: Duplicate buildings created

Symptom: After "Add building Maple Court" succeeded, typing it again created a second identical building.

Root cause: No duplicate check in add_new_building.

Fix: Added existing = db.table("buildings").select("id, name").ilike("name", name).execute() before the INSERT. If a match is found, return a message like "A building named 'Maple Court' already exists (ID: abc123). Use this building to add units." This also gives the LLM the existing building's ID in case the user wants to add units to it.

Bug 4: Calendar didn't update after chatbot rescheduled

Symptom: Chatbot said "Appointment rescheduled" but the calendar still showed the old time.

Root cause: The refresh_needed signal existed but was set to False because reschedule_appointment wasn't in _APPOINTMENT_WRITE_TOOLS.

Fix: Added all three mutation tools to _APPOINTMENT_WRITE_TOOLS.

Exercises

Easy   What happens if MAX_TOOL_CALL_TURNS is reached?

The function returns the string "I've reached the maximum number of steps. Please try rephrasing your request." with refresh_needed as whatever it was set to so far. This prevents infinite loops where the model keeps calling tools without converging on a final answer. 5 turns is enough for any legitimate property management task.

Easy   Why does the route use get_authenticated_db and not get_service_db?

The chatbot operates on behalf of a logged-in manager. RLS must be enforced so the chatbot can only see and modify data belonging to that manager. get_service_db bypasses RLS entirely — if used here, any bug in the chatbot's tool execution could expose or modify any manager's data. Use get_service_db only for webhooks that arrive without a JWT (VAPI, Stripe callbacks).

Medium   Add a new tool get_vacant_flats that returns all unoccupied flats.
Show solution

Step 1 — Add to TOOLS list:

{
    "type": "function",
    "function": {
        "name": "get_vacant_flats",
        "description": "List all unoccupied (vacant) flats across all buildings.",
        "parameters": {
            "type": "object",
            "properties": {
                "building_name": {
                    "type": "string",
                    "description": "Optional building name filter"
                }
            },
            "required": []
        }
    }
}

Step 2 — Add to execute_tool():

elif tool_name == "get_vacant_flats":
    building_name = args.get("building_name")
    query = db.table("flats").select("flat_number, building_id, address").eq("occupied", False)
    result = query.execute()
    if not result.data:
        return "No vacant flats found."
    lines = [f"Found {len(result.data)} vacant flat(s):"]
    for f in result.data:
        lines.append(f"- {f.get('flat_number')} | {f.get('address') or 'no address'}")
    return "\n".join(lines)

Note: This tool does not mutate data, so it does NOT go in _APPOINTMENT_WRITE_TOOLS.

Hard   The chatbot sends the full history (up to 10 messages) plus system prompt on every request. How would you reduce the token cost without losing context quality?
Show solution

Option 1: Smarter truncation
Instead of keeping last 10 messages, keep the last 2 user messages + their assistant+tool responses. Tool call turns can be verbose; trimming tool content to just the first 200 characters significantly reduces token count.

Option 2: Summarization
When conversation exceeds 10 turns, call gpt-4o-mini once with just the older turns and ask it to produce a "memory summary" (what was found, what was done). Replace the older turns with this summary as a single assistant message.

summary = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "user", "content": f"Summarize this conversation in under 200 words:\n{old_turns}"}
    ]
)
summary_msg = {"role": "assistant", "content": f"[Earlier context] {summary}"}
full_messages = [system_message, summary_msg] + recent_turns

Option 3: Prompt caching
OpenAI's API supports prompt caching for prompts over 1024 tokens. The system prompt is always the same structure; it's cached and only charged at 50% on repeated requests within the cache window.

Why This Design

Decision: Tool calling vs. alternatives for “chat with your CRM”

ApproachProsCons
Function/tool calling against existing service functions (chosen)Reuses the exact same authenticated data paths as the UI — RLS still applies; model can act (create complaints), not just readTool schemas must be maintained alongside routes; multi-step chains add latency
RAG over exported dataGood for unstructured docsThe data is relational and live — embedding stale snapshots of it is strictly worse than querying it
Text-to-SQLMaximum flexibilityLLM-generated SQL against production with RLS bypass potential — a security review nightmare for an MVP
Senior takeaway: when your data is already behind well-shaped authenticated functions, tool calling is the safest AI integration — the model chooses which function runs, but your code controls what it can touch.

Decision: The refresh_needed signal

When a tool mutates data (creates a complaint, updates a tenant), the chat response carries refresh_needed: true. The frontend then re-fetches affected lists. The alternative — websockets or polling for change detection — is far heavier for one chat widget. A boolean on the response that already exists is the cheapest correct signal.

Decision: Truncating conversation history

gpt-4o-mini is cheap, but context still costs money and latency, and old turns add noise. Keeping the last N messages (plus the system prompt) bounds cost per request. The trade-off: the bot forgets things said 20 turns ago — acceptable for a task-oriented CRM assistant, unacceptable for a companion app. Know which product you're building.

Checkpoint ✓

Open http://localhost:8000/docs, find the /chat POST endpoint, authorize with your Bearer token, and send:

{"message": "How many tenants do I have?"}

Expected: a natural-language answer containing the actual count from YOUR data (cross-check against the tenants table), plus a refresh_needed field that is false for a read-only question.

Then send “Create a complaint for flat 101 about a broken light” — expected: refresh_needed: true and a new row in complaints. Watch the backend logs to see which tools were invoked — that trace is your main debugging surface for the chatbot.
