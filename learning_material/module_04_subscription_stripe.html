Section 1 — What You Are Building

This module adds a payment wall: managers who haven't subscribed via Stripe cannot access any data routes. Two files make this happen: subscription.py provides a FastAPI dependency that checks for an active subscription (raising HTTP 403 if absent), and payments.py implements the Stripe Checkout flow, webhook handler, and subscription status endpoint.

Full authentication + subscription chain on every protected route: Request ──► get_current_user() (Module 03) — validates JWT ──► get_authenticated_db() (Module 03) — injects JWT into DB ──► require_active_subscription() (Module 04) — checks subscriptions table │ ├── subscriptions.status IN ('trialing', 'active') │ ↓ YES │ route handler runs │ └── NOT IN list ↓ HTTP 403 — frontend redirects to pricing page Separate: Stripe Checkout & Webhook lifecycle User → /payments/create-checkout-session → Stripe Checkout URL User pays → Stripe fires webhook → /payments/webhook → updates subscriptions table → user now has access

Section 2 — Concept Deep-Dives

Stripe Checkout — hosted payment page

Stripe Checkout is a Stripe-hosted payment page. Instead of building your own credit card form, you redirect users to a Stripe URL. Stripe handles PCI compliance, 3DS authentication, and card validation. After payment, Stripe redirects the user back to your configured success URL.

Minimal standalone example

import stripe
stripe.api_key = "sk_test_..."

session = stripe.checkout.Session.create(
    mode="subscription",
    customer_email="user@example.com",
    line_items=[{"price": "price_xxx", "quantity": 1}],
    success_url="https://yourapp.com/success?session_id={CHECKOUT_SESSION_ID}",
    cancel_url="https://yourapp.com/pricing?canceled=true",
)

print(session.url)   # redirect user to this URL

The {CHECKOUT_SESSION_ID} placeholder

In the success_url, Stripe replaces the literal string {CHECKOUT_SESSION_ID} with the actual session ID after payment. This lets the success page verify the payment by calling your backend with the session ID.

Line items — why two in this project?

line_items=[
    {# One-time $1 card verification fee
     "price_data": {"currency": "cad", "product_data": {"name": "Card Verification Fee"},
                    "unit_amount": 100},  # $1.00 CAD
     "quantity": 1},
    {# Recurring subscription
     "price": settings.STRIPE_PRICE_ID,
     "quantity": 1},
]

The $1 card verification fee prevents users from signing up with fake cards just to get the 14-day trial. It appears as a separate line item on the Checkout page and is charged immediately even during a trial.

Subscription State Machine

A Stripe subscription moves through a defined set of states. Your subscriptions table mirrors these states and determines whether a manager has access.

User completes Checkout │ ▼ trialing ──────────────────────────────────────────┐ (14 days free) │ payment fails │ ▼ │ trial ends, payment succeeds past_due ▼ │ active ◄──────── invoice.payment_succeeded │ │ │ repeated failures │ user cancels ▼ ▼ canceled / expired canceled

The require_active_subscription dependency allows trialing and active statuses. Any other status (past_due, canceled, expired) triggers a 403, and the frontend redirects the user to the pricing page.

Stripe Webhooks — why they exist

When a user completes Checkout on Stripe's website, Stripe can't call your JavaScript directly (the user's browser is on stripe.com, not your app). Instead, Stripe sends an HTTP POST to a server-side URL you've configured — this is a webhook. Your server receives it, updates the database, and the user gets access on their next request.

Webhook verification

# Stripe signs every webhook payload with STRIPE_WEBHOOK_SECRET
# Always verify this signature before processing

event = stripe.Webhook.construct_event(
    payload=raw_body,      # raw bytes from request.body()
    sig_header=request.headers["stripe-signature"],
    secret=settings.STRIPE_WEBHOOK_SECRET
)
# If signature is invalid → raises stripe.error.SignatureVerificationError
# If valid → event dict with: event["type"], event["data"]["object"]

Never process webhook bodies without verifying the signature. Without verification, any attacker could POST fake events to your webhook URL and grant themselves free subscriptions. The STRIPE_WEBHOOK_SECRET starts with whsec_ and is found in the Stripe dashboard under Webhooks.

Idempotency — handling duplicate events

Stripe guarantees at-least-once delivery — the same event may be delivered multiple times (if your server returns a non-200, Stripe retries). Idempotency means processing the same event twice has the same effect as processing it once.

The pattern used here

def _is_duplicate_event(db: Client, event_id: str, event_type: str) -> bool:
    try:
        # Try to INSERT the event_id (UNIQUE constraint)
        db.table("stripe_events").insert({
            "event_id": event_id,
            "event_type": event_type,
        }).execute()
        return False   # insert succeeded → first time we've seen this event
    except Exception:
        return True    # insert failed (UNIQUE violation) → duplicate

The stripe_events table has a UNIQUE constraint on event_id. The first time an event arrives, the INSERT succeeds and processing continues. If Stripe sends the same event again, the INSERT fails (duplicate key), and the function returns True — skipping processing entirely.

This is the "optimistic" approach — try the operation, catch the conflict. The alternative (SELECT first, INSERT if not found) has a race condition: two concurrent requests could both see "not found" and both proceed to process. INSERT + UNIQUE constraint is atomic and race-safe.

Section 3 — Line-by-Line Walkthrough

File: backend/app/dependencies/subscription.py

async def require_active_subscription(
    user: dict = Depends(get_current_user),
    db: Client = Depends(get_service_db),
) -> dict:
Two dependencies are injected:
  • user from get_current_user — provides the manager's UUID (user["sub"])
  • db from get_service_db — uses the service-role client, bypassing RLS
Why service-role here? The subscriptions table has RLS policies that restrict reads to the owner. But require_active_subscription is checking whether the user has a subscription — if they don't, the anon client with their JWT would also see no rows (correct), but using the service client is more explicit and avoids any edge cases where RLS might block a legitimate subscription check. 
    manager_id = user["sub"]

    result = (
        db.table("subscriptions")
        .select("status, trial_ends_at")
        .eq("manager_id", manager_id)
        .in_("status", ["trialing", "active"])
        .limit(1)
        .execute()
    )
.in_("status", ["trialing", "active"]) — this is the core check. The query only returns rows where the subscription status is "trialing" or "active". Any other status (past_due, canceled) means no rows are returned.

.limit(1) — optimization. Once we know at least one active subscription exists, we don't need more rows. This prevents a full table scan on managers with multiple subscription records (e.g., after a re-subscription). 
    if not result.data:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="No active subscription. Please subscribe to continue.",
        )
    return user
result.data is an empty list ([]) if no subscription row matched. An empty list is falsy in Python, so if not result.data is True when there's no active subscription.

Why HTTP 403 (Forbidden) instead of 402 (Payment Required)? HTTP 402 is technically the "correct" status for payment required, but browser and framework behavior for 402 is inconsistent. 403 is well-supported everywhere and the frontend handles it by redirecting to the pricing page.

return user — returns the user dict so routes that declare _: None = Depends(require_active_subscription) can also use user: dict = Depends(require_active_subscription) to get the user dict without calling get_current_user separately.

File: backend/app/routes/payments.py — Key sections

import stripe
from app.config import settings

stripe.api_key = settings.STRIPE_SECRET_KEY   # set ONCE at module load time

router = APIRouter(prefix="/payments", tags=["Payments"])
Setting stripe.api_key at module level configures the global Stripe SDK key. All subsequent stripe.* calls in this file use this key automatically. This is Stripe's SDK convention — one global key, not per-call.
def _get_or_create_stripe_customer(email: str, manager_id: str) -> str:
    existing = stripe.Customer.list(email=email, limit=1)
    if existing.data:
        return existing.data[0].id

    customer = stripe.Customer.create(
        email=email,
        metadata={"manager_id": manager_id},
    )
    return customer.id
This helper prevents creating duplicate Stripe customers for the same email. When a user subscribes, they become a Stripe Customer — a permanent record in Stripe with their payment methods and billing history.

metadata={"manager_id": manager_id} — Stripe allows attaching arbitrary key-value metadata to any object. Storing the manager's UUID here makes it possible to look up the corresponding database record when Stripe sends webhook events. 
    session = stripe.checkout.Session.create(
        customer=customer_id,
        payment_method_types=["card"],
        mode="subscription",
        line_items=[
            {"price_data": {"currency": "cad", "product_data": {"name": "Card Verification Fee"},
                           "unit_amount": 100}, "quantity": 1},
            {"price": settings.STRIPE_PRICE_ID, "quantity": 1},
        ],
        subscription_data={
            "trial_period_days": 14,
            "metadata": {"manager_id": manager_id},
        },
        metadata={"manager_id": manager_id},
        success_url=f"{settings.LANDING_PAGE_URL}/pricing/success?session_id={{CHECKOUT_SESSION_ID}}",
        cancel_url=f"{settings.LANDING_PAGE_URL}/pricing?canceled=true",
    )
trial_period_days: 14 — the subscription starts in "trialing" status for 14 days. No payment is taken for the subscription during this period (only the $1 verification fee is charged immediately).

metadata is set on BOTH the session and the subscription. The session metadata is available when the success page calls GET /payments/verify-session. The subscription metadata is available in all subsequent webhook events about this subscription.

{{CHECKOUT_SESSION_ID}} — double curly braces are needed because this is an f-string. Single {} would be interpreted as Python string interpolation; {{}} becomes a literal {} in the output, which Stripe then replaces.

The Webhook Handler — key patterns

@router.post("/webhook")
async def stripe_webhook(request: Request, db: Client = Depends(get_service_db)):
    payload = await request.body()
    sig_header = request.headers.get("stripe-signature")

    if not sig_header:
        raise HTTPException(status_code=400, detail="Missing Stripe signature")

    try:
        event = stripe.Webhook.construct_event(
            payload, sig_header, settings.STRIPE_WEBHOOK_SECRET
        )
    except stripe.error.SignatureVerificationError:
        raise HTTPException(status_code=400, detail="Invalid signature")
await request.body() — the raw bytes of the request body. This must be the raw bytes (not parsed JSON) because Stripe's signature verification checks the exact byte sequence, including whitespace. If you parse the body first and re-serialize, the signature won't match.

construct_event() verifies the signature and returns a parsed event object. On failure, it raises SignatureVerificationError — meaning the request didn't come from Stripe (or someone tampered with it). This is the critical security check. 
    if _is_duplicate_event(db, event["id"], event["type"]):
        return {"status": "already_processed"}

    import json as _json
    raw = _json.loads(payload)
    data = raw["data"]["object"]
After the idempotency check, the body is re-parsed as JSON to access the event data. data = raw["data"]["object"] is the Stripe object that changed — a Subscription for customer.subscription.* events, an Invoice for invoice.* events.

import json as _json — imported inside the function with an alias to avoid shadowing any outer json import. Stripe 15.x model objects don't support .get(), so the raw dict (from parsing the payload) is used instead of the SDK's model object. 
    if event_type == "customer.subscription.created":
        manager_id = data.get("metadata", {}).get("manager_id")
        if manager_id:
            sub_data = {"stripe_customer_id": data["customer"],
                        "stripe_subscription_id": data["id"],
                        "plan": "trial", "status": "trialing",
                        "trial_ends_at": _unix_to_iso(data.get("trial_end"))}
            try:
                db.table("subscriptions").insert({"manager_id": manager_id, **sub_data}).execute()
            except Exception:
                db.table("subscriptions").update({**sub_data, "updated_at": "now()"}) \
                    .eq("manager_id", manager_id).execute()
Insert-or-update pattern (upsert): Try to INSERT the subscription row. If a row already exists (e.g., the success page created it first via GET /payments/verify-session), the INSERT raises an exception (duplicate key). The except block then UPDATE the existing row with the real Stripe IDs.

Supabase SDK has a native .upsert() method, but this project uses try/except to be explicit about which fields to set on INSERT vs. which to update on conflict — they're different. 
def _unix_to_iso(ts: int | None) -> str | None:
    if ts is None: return None
    from datetime import datetime, timezone
    return datetime.fromtimestamp(ts, tz=timezone.utc).isoformat()
Stripe stores all timestamps as Unix timestamps (seconds since epoch). The database expects ISO 8601 strings. This helper converts between them. The import datetime is inside the function to keep the module-level imports clean — acceptable for a small helper that's called infrequently.

Section 4 — Why This Design

Decision: Database-backed subscription check vs. JWT claim check

ApproachProsCons
DB check on every request (chosen)Always reflects current subscription state; cancelling works instantlyOne extra DB query per request; slower than JWT-based check
Add "subscribed" claim to JWTZero extra DB queries; works offlineJWT is issued at login; status change doesn't reflect until re-login; cancelled users keep access until token expires (up to 1 hour)

The DB check is chosen because subscription status can change at any moment (Stripe events). A cancelled subscription must take effect immediately, not 1 hour later when the JWT expires.

Decision: 14-day trial + $1 card verification vs. free tier

ApproachProsCons
Trial + $1 card verify (chosen)Filters out non-serious signups; card on file for post-trial billing; reduces fraudSome users won't provide card even for $1; loses some top-of-funnel
Free tier (no card required)Maximum signups; users try before committingMany free users never convert; fraud; resource abuse
Immediate charge (no trial)Maximum revenue per user; serious users onlyLow conversion rate; no chance to experience value first

Section 8 — Exercises

Easy Add trial days remaining to the subscription status endpoint

Problem: Modify GET /payments/subscription-status to also return how many days remain in the trial (if status is "trialing"). Return null for non-trialing subscriptions.

Hints

The subscriptions table has a trial_ends_at column. Fetch it alongside status. Calculate days with (trial_end - datetime.now()).days.

Solution 
from datetime import datetime, timezone

@router.get("/subscription-status")
async def subscription_status(user=Depends(get_current_user), db=Depends(get_service_db)):
    result = (db.table("subscriptions").select("status, trial_ends_at")
              .eq("manager_id", user["sub"]).in_("status", ["trialing", "active"])
              .limit(1).execute())
    if not result.data:
        return {"subscribed": False, "trial_days_remaining": None}
    row = result.data[0]
    days = None
    if row["status"] == "trialing" and row.get("trial_ends_at"):
        trial_end = datetime.fromisoformat(row["trial_ends_at"])
        days = max(0, (trial_end - datetime.now(timezone.utc)).days)
    return {"subscribed": True, "status": row["status"], "trial_days_remaining": days}

Success: trialing users get a number like {"subscribed": true, "status": "trialing", "trial_days_remaining": 12}. Active users get null.

Medium Add a grace period for past_due subscriptions

Problem: Currently, past_due subscriptions are blocked immediately. Modify require_active_subscription to allow a 3-day grace period: if status is past_due and the subscription was last updated less than 3 days ago, still allow access.

Hints

Fetch updated_at alongside status. Check if (datetime.now() - updated_at).days < 3. You'll need to parse the ISO timestamp from Supabase.

Solution 
from datetime import datetime, timezone, timedelta

async def require_active_subscription(user=Depends(get_current_user), db=Depends(get_service_db)):
    result = (db.table("subscriptions").select("status, updated_at")
              .eq("manager_id", user["sub"]).limit(1).execute())
    if not result.data:
        raise HTTPException(status_code=403, detail="No active subscription.")
    row = result.data[0]
    if row["status"] in ("trialing", "active"):
        return user
    if row["status"] == "past_due" and row.get("updated_at"):
        updated = datetime.fromisoformat(row["updated_at"])
        if datetime.now(timezone.utc) - updated < timedelta(days=3):
            return user
    raise HTTPException(status_code=403, detail="No active subscription.")

Success: A past_due subscription updated today still grants access. One updated 4 days ago raises 403.

Create the table in Supabase first.
