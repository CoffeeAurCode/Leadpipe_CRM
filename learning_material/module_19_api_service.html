Section 1 — Why a Central Service Module?

The entire frontend talks to the backend through a single file: apiService.js. This is not an accident — it's a deliberate architectural pattern called the Service Module Pattern.

WITHOUT a service module: ComplaintsPage.jsx: fetch('/complaints', { headers: { Authorization: `Bearer ${token}` } }) PropertiesPage.jsx: fetch('/flats', { headers: { Authorization: `Bearer ${token}` } }) TenantManagement.jsx: fetch('/tenants', { headers: { Authorization: `Bearer ${token}` } }) 30+ components, each managing their own fetch + auth header injection. Change the auth scheme? Touch 30+ files. Backend URL changes? Touch 30+ files. Add retry logic? Touch 30+ files. ───────────────────────────────────────────── WITH a service module (this project): All 30+ components import from apiService.js: import { fetchComplaints } from '../services/apiService'; Change auth scheme? Change authFetch() once. Backend URL changes? Change API_BASE_URL once. Add retry logic? Change authFetch() once. Add request logging? Change authFetch() once.

Section 2 — The authFetch Wrapper (the Heart of the File)

const API_BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:8000';
import { format } from 'date-fns';
import { supabase } from '../lib/supabase';
API_BASE_URL: The base URL for all backend calls. In development, VITE_API_URL is set to http://localhost:8000 in .env.local. In production, it points to the deployed FastAPI server. The || 'http://localhost:8000' fallback means developers can omit the env var locally.

Top-level imports inside a service module: Note that format from date-fns is imported at the module level (for the formatDate helper), and the Supabase singleton is imported to get the current session in authFetch. 
async function authFetch(url, options = {}) {
    const { data: { session } } = await supabase.auth.getSession();

    if (!session) {
        await supabase.auth.signOut();
        window.location.reload();
        throw new Error('No active session');
    }

    const headers = { ...options.headers };
    headers['Authorization'] = `Bearer ${session.access_token}`;

    if (!(options.body instanceof FormData)) {
        headers['Content-Type'] = headers['Content-Type'] || 'application/json';
    }

    const response = await fetch(url, { ...options, headers });

    if (response.status === 401) {
        await supabase.auth.signOut();
        window.location.reload();
        throw new Error('Session expired');
    }

    if (response.status === 403) {
        const landingUrl = import.meta.env.VITE_LANDING_PAGE_URL || 'http://localhost:3000';
        window.location.href = `${landingUrl}/pricing`;
        throw new Error('Subscription required');
    }

    return response;
}
supabase.auth.getSession(): Retrieves the current session from the Supabase client's in-memory cache (not from the backend or network). This is synchronous in effect but async in API — it reads from localStorage/sessionStorage, then returns the session object. The destructuring { data: { session } } handles Supabase's response envelope: { data: { session: ... }, error: ... }.

No session → sign out + reload: If there's no session (user was never logged in, or the session expired and refresh failed), calling signOut() clears any stale auth state, and reload() triggers the onAuthStateChange event with INITIAL_SESSION(null), which causes AuthGate to render the login page. It's a clean reset.

headers['Authorization'] = `Bearer ${session.access_token}`: This is the key line. The FastAPI backend's get_authenticated_db dependency reads this header, extracts the JWT, verifies it with Supabase's JWKS, and injects the user's ID into every DB query via RLS. Without this header, every protected route returns 401.

FormData Content-Type guard: if (!(options.body instanceof FormData)) — when uploading a file with FormData, the browser must set the Content-Type header itself. The header must include the boundary string (a random delimiter separating form fields), e.g., multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW. If you manually set Content-Type: multipart/form-data (without the boundary), the server can't parse the request body. The guard prevents this by letting the browser set the header for FormData requests.

401 vs 403 handling:
  • 401 Unauthorized: token is missing or invalid (expired). Sign out to clear stale state, reload to get a fresh session.
  • 403 Forbidden: token is valid but the user lacks permission — specifically, no active Stripe subscription. Redirect to the pricing page so they can subscribe. The backend's require_active_subscription dependency returns 403 when the subscription table has no active/trialing record.

Section 3 — Function Patterns in the Service Module

Pattern A — Simple GET (fetch a list)

export async function fetchComplaints() {
    try {
        const response = await authFetch(`${API_BASE_URL}/complaints`);
        if (!response.ok) {
            throw new Error(`HTTP error! status: ${response.status}`);
        }
        const data = await response.json();
        return data;
    } catch (error) {
        console.error('Error fetching complaints:', error);
        throw error;
    }
}
Re-throwing the error: The catch block logs the error and then re-throws it. Without re-throwing, the caller (component) would receive undefined (the implicit return of a caught exception) and wouldn't know the fetch failed. Components handle errors by catching the thrown error and showing an error state to the user.

When to NOT re-throw: Some functions (like fetchActiveRent) return null on failure instead of re-throwing, because a missing rent record is a normal state, not an error. The choice between "throw on failure" and "return null on failure" depends on whether the caller can meaningfully handle the absence of data.

Pattern B — GET with query parameters

export async function fetchTenants(params = {}) {
    const query = new URLSearchParams();
    if (params.rent_status) query.set('rent_status', params.rent_status);
    if (params.lease_status) query.set('lease_status', params.lease_status);
    if (params.sort_by) query.set('sort_by', params.sort_by);
    if (params.building_id != null) query.set('building_id', params.building_id);
    const qs = query.toString() ? `?${query}` : '';
    const response = await authFetch(`${API_BASE_URL}/tenants${qs}`);
    if (!response.ok) throw new Error(`HTTP error! status: ${response.status}`);
    return await response.json();
}
URLSearchParams: The browser-native API for building query strings. It handles URL encoding automatically (spaces → %20, special chars escaped). Much safer than manual string concatenation.

Conditional parameter inclusion: Only append a param if it has a value. If params.rent_status is undefined or empty string, it's not appended — the backend receives a clean request without empty-string params that would break server-side validation.

!= null vs !params.building_id: For numeric IDs, use != null (checks for both null and undefined) rather than falsy check (!), because building_id = 0 is falsy but might be a valid ID. Truthy/falsy checks cause subtle bugs with zero values.

Pattern C — POST with JSON body

export async function createBuilding(payload) {
    const response = await authFetch(`${API_BASE_URL}/buildings`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(payload),
    });
    if (!response.ok) {
        const err = await response.json().catch(() => ({}));
        throw new Error(err.detail || `HTTP error! status: ${response.status}`);
    }
    return await response.json();
}
Error detail extraction: When the server returns a 4xx or 5xx status, FastAPI often sends a JSON body with a detail field containing a human-readable error message (from the backend's custom error mapping). The pattern response.json().catch(() => ({})) tries to parse the error body, and if the body isn't valid JSON (server crash, empty body), falls back to an empty object. The err.detail || `HTTP error...` then either shows the backend's message or a generic one.

This is why the user sees "Flat number already exists" instead of "HTTP error! status: 409" — the backend sends { "detail": "Flat number already exists" } and the frontend extracts it.

Pattern D — POST with FormData (file upload)

export async function createProperty(formData) {
    const response = await authFetch(`${API_BASE_URL}/flats`, {
        method: 'POST',
        body: formData,   // FormData — no Content-Type header set
    });

    if (!response.ok) {
        const error = await response.json();
        throw new Error(error.detail || `HTTP error! status: ${response.status}`);
    }

    return await response.json();
}
This function receives a FormData object from the component (pre-populated with flat fields + an image file). Notice there's no headers: { 'Content-Type': ... } — the authFetch wrapper's FormData guard handles this: it detects that body instanceof FormData is true and skips adding Content-Type, letting the browser set the correct multipart boundary automatically.

Pattern E — PATCH with optional detail extraction

export async function updateTenant(tenantUuid, updates) {
    const response = await authFetch(`${API_BASE_URL}/tenants/${tenantUuid}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(updates),
    });
    if (!response.ok) {
        const err = await response.json().catch(() => ({}));
        throw new Error(err.detail || `HTTP error! status: ${response.status}`);
    }
    return await response.json();
}

Pattern F — DELETE returning null for 204

export async function deleteAppointment(id) {
    const response = await authFetch(`${API_BASE_URL}/appointments/${id}`, {
        method: 'DELETE',
    });
    if (!response.ok) {
        const err = await response.json().catch(() => ({}));
        throw new Error(err.detail || `HTTP error! status: ${response.status}`);
    }
    return response.status === 204 ? null : await response.json();
}
204 No Content: Some DELETE endpoints return 204 (no body). Calling response.json() on a 204 response throws a "SyntaxError: Unexpected end of JSON input" because there's no body to parse. The ternary check response.status === 204 ? null : await response.json() handles this safely.

Pattern G — CSV export (download trigger)

export async function exportLeads(params = {}) {
    const qs = new URLSearchParams();
    if (params.listing_uuid) qs.set('listing_uuid', params.listing_uuid);
    const response = await authFetch(`${API_BASE_URL}/leasing/export?${qs}`);
    if (!response.ok) throw new Error(`HTTP error! status: ${response.status}`);
    const blob = await response.blob();
    const url = URL.createObjectURL(blob);
    const a = document.createElement('a');
    a.href = url; a.download = 'leads.csv'; a.click();
    URL.revokeObjectURL(url);
}
Download trigger pattern: The backend returns raw CSV bytes. response.blob() gets the binary data. URL.createObjectURL(blob) creates a temporary in-memory URL. A programmatically created <a> tag with the download attribute triggers the browser's "Save File" dialog when clicked. revokeObjectURL releases the temporary URL's memory immediately after — without this, the blob would stay in memory until the page unloads.

Section 5 — Concept Deep-Dives

Why the service module functions don't need try/catch

Many functions in apiService.js don't have their own try/catch. They just await authFetch() and throw if the response isn't ok. Why is this safe?

Because errors propagate up the call stack automatically. If createBuilding() throws, the component that called await createBuilding() is responsible for catching it. The component typically wraps the call in its own try/catch to show an error message to the user.

The pattern is:

apiService.js functions: - Throw on HTTP errors (let errors bubble up) - Some log to console.error as a side effect - Don't swallow errors (that would hide bugs) Components (consumers): try { await createBuilding(payload); setSuccess(true); } catch (err) { setError(err.message); // Show to user }

The older functions (like fetchComplaints) have a try/catch that re-throws — that's equivalent to not having try/catch, since the error is re-thrown. The newer functions drop this pattern for brevity.

The formatDate helper — IST offset math 
export function formatDate(dateString) {
    if (!dateString) return 'N/A';
    try {
        const utcString = dateString.endsWith('Z') ? dateString : dateString + 'Z';
        const utcDate = new Date(utcString);
        const istDate = new Date(utcDate.getTime() + (5.5 * 60 * 60 * 1000));
        return format(istDate, 'MMM d, yyyy h:mm a');
    } catch (error) {
        return dateString;
    }
}

The backend stores datetimes as IST (India Standard Time, UTC+5:30). But the DB column doesn't have timezone info — it's stored as a plain timestamp string like 2024-01-15T14:30:00. JavaScript's new Date() would interpret this as local timezone (e.g., UTC-5 in Canada), showing the wrong time.

The fix: append Z to tell JavaScript to treat the string as UTC, then manually add the IST offset (+5:30 = +19800 seconds = +19800000ms). This gives the original IST time back. It's manual but explicit and correct.

Section 6 — Common Bugs & Fixes

Bug: File upload fails with "Boundary not found" or "Invalid multipart"

Symptom: Uploading a file works locally but fails in production, or fails intermittently. Server returns 400 Bad Request.

Root cause: Someone added headers: { 'Content-Type': 'multipart/form-data' } to a function that sends FormData. This overrides the browser's auto-generated Content-Type (which includes the required boundary string). The server receives a malformed multipart request it can't parse.

Fix: Never manually set Content-Type when sending FormData. Let the browser set it. The authFetch wrapper's FormData guard enforces this — just don't pass Content-Type in the options:

// ✗ BAD — overrides the boundary
authFetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'multipart/form-data' },  // NO!
    body: formData,
});

// ✓ GOOD — no Content-Type, browser sets it with boundary
authFetch(url, {
    method: 'POST',
    body: formData,
});

Bug: response.json() throws on DELETE 204 response

Symptom: Deleting a resource works (backend confirms deletion) but the frontend throws "SyntaxError: Unexpected end of JSON input" or "SyntaxError: JSON Parse error: Unexpected EOF".

Root cause: The backend returns HTTP 204 (No Content) with an empty body. response.json() tries to parse the empty body as JSON, which fails.

Fix: Check the status code before parsing:

return response.status === 204 ? null : await response.json();

Bug: 401 on every request after the user's token expires

Symptom: After the app has been open for a while (usually 1 hour), all API calls start failing with 401. The user must manually reload to fix it.

Root cause: Supabase access tokens expire after 1 hour. The Supabase client automatically refreshes them using the refresh token — but authFetch calls supabase.auth.getSession() which returns the current session. If the auto-refresh hasn't run yet (or failed), the stale token is sent.

Fix: The Supabase client handles token refresh automatically via onAuthStateChange(TOKEN_REFRESHED). If you're seeing 401s, it may be that the user's session was invalidated (they signed in on another device, or the refresh token was revoked). The authFetch handler signs out and reloads, which is the correct behavior. For more resilient apps, you could add a retry with token refresh before giving up.

Bug: Filter params with value 0 are not sent to the backend

Symptom: Filtering by building_id: 0 (or any numeric zero) doesn't apply the filter. The API is called without the parameter.

Root cause: Early code used if (params.building_id) (truthy check). The value 0 is falsy in JavaScript, so the condition is never true for building_id: 0.

Fix: Use explicit null check: if (params.building_id != null). This passes for any value except null and undefined — including 0, false, and empty string.

Hard Exercise 3 — Add an automatic retry for 503 (server temporarily unavailable)

Network flakiness can cause intermittent 503 errors. Modify authFetch to automatically retry once if the server returns 503, after a 1-second delay. The retry should only happen once (not loop forever).

Show solution 
async function authFetch(url, options = {}, _retry = true) {
    const { data: { session } } = await supabase.auth.getSession();
    // ... session check + header building ...
    const response = await fetch(url, { ...options, headers });

    if (response.status === 503 && _retry) {
        await new Promise(resolve => setTimeout(resolve, 1000));
        return authFetch(url, options, false); // _retry=false prevents infinite loop
    }

    // ... 401/403 handling ...
    return response;
}

The _retry flag is a private parameter (conventionally marked with _ prefix) that controls retry behavior. Callers don't pass it — it defaults to true. The recursive call passes false to prevent a second retry.

Module 19 — Key Takeaways

  • The Service Module Pattern centralizes all HTTP calls — change auth, base URL, or error handling in one place, not 30+ components.
  • authFetch is the core: it gets the session, injects the Bearer token, and handles 401/403 globally.
  • Never set Content-Type when sending FormData — the browser must set it with the multipart boundary. The authFetch FormData guard enforces this.
  • Error detail extraction: response.json().catch(() => ({})) safely handles non-JSON error bodies, then err.detail || fallback shows the backend's message when available.
  • 204 responses have no body — check response.status === 204 before calling response.json().
  • URLSearchParams for query strings — handles encoding automatically. Use != null (not falsy check) for numeric params to avoid zeroes being skipped.
  • 401 = expired/invalid token → sign out and reload. 403 = no subscription → redirect to pricing.

Section 8 — Why This Design

Decision: One hand-rolled authFetch wrapper vs. axios vs. per-component fetch

ApproachProsCons
Central apiService.js over native fetch (chosen)ONE place injects the Bearer token, handles 401/403, parses errors, and names every endpoint — grep apiService.js and you have the app's entire API surface; zero dependenciesFeatures axios gives free (interceptors, upload progress, cancellation) are manual additions
axios + interceptorsBatteries includedA dependency for what ~40 lines of wrapper achieve; interceptor magic is harder to trace than an explicit wrapper
fetch scattered in componentsNo abstraction to learnToken handling copy-pasted N times; one changed header means N edits; this is why it's a hard rule, not a preference
Senior takeaway: the service layer is a chokepoint by design. Auth, error shaping, base URLs, and 401-redirect policy all live at one seam. When you add request IDs or retry logic later, it's one file. The hard rule “no inline fetch in components” is what keeps the chokepoint real.

Decision: Global 401/403 handling

An expired token can surface from any of ~60 call sites. Handling it centrally (sign out + redirect once, in the wrapper) beats sixty try/catch blocks each deciding differently. The subtlety: 401 means “who are you?” (token invalid → sign out), 403 means “you can't do that” (subscription lapsed → paywall, not logout). Conflating them logs paying users out.

Section 9 — Checkpoint ✓

Verify the chokepoint actually chokes:

  1. Header injection: DevTools → Network, click around the app. Expected: every request to :8000 carries Authorization: Bearer eyJ… — no exceptions.
  2. No leaks: grep -rn "fetch(" frontend/src/components/ — expected: zero direct fetch calls (all go through the service).
  3. 401 path: in DevTools → Application, corrupt the access_token inside the sb- localStorage entry, then trigger any API call. Expected: a clean bounce to the auth page — not a white screen or a silent dead UI.
