apiRequest vs function Tools

VAPI supports two types of tools. Understanding the difference is critical:

TypeHow it worksWhen to use
apiRequestVAPI calls your endpoint directly during the call. The agent waits for the HTTP response and uses it in the conversation.Fast lookups: verify phone, check availability, fetch appointments, search listings
function (webhook)VAPI fires a webhook event (tool-calls) to the server_messages URL. The agent does NOT wait — it continues speaking. Your server processes asynchronously.Slow writes: submit_complaint (creates DB records, fires notifications)

The {{{{customer.number}}}} double-brace syntax is VAPI's template variable injection. VAPI replaces {{customer.number}} with the actual caller's phone number at call time. In Python f-strings, curly braces must be doubled to escape them: {{{{ → {{ → VAPI template.

The server_messages Trap

Critical bug that cost hours to debug:

Lease agent config must have server_messages: ["end-of-call-report"] ONLY.

If you add "tool-calls" to this list, VAPI will fire a webhook event every time ANY tool is called. The lease agent calls search_available_listings and find_listing as apiRequest tools during the call. Adding tool-calls to server_messages causes VAPI to also fire a server event for these — and when our webhook receives a tool-calls event, it looks for submit_lease_lead (not found), and returns an unexpected response that VAPI interprets as a tool failure. This silently breaks all lease agent tools.

Complaint agent: Needs ["end-of-call-report", "tool-calls"] because submit_complaint is a function type tool that fires via server events.

Lease agent: ["end-of-call-report"] only. All lease tools are apiRequest type — they don't use the server_messages channel at all.

Twilio Number Pool

The pool is a pre-purchased set of Twilio numbers stored in the twilio_number_pool table. Numbers must be added manually before they can be assigned to managers.

# twilio_number_pool table
id                  UUID PK
phone_number        text UNIQUE   # "+14313415768"
vapi_phone_number_id text UNIQUE  # VAPI's internal ID for this number
status              text          # "available" or "assigned"
assigned_manager_id UUID          # NULL when available
assigned_at         timestamptz

To add a new number to the pool:

python backend/scripts/add_twilio_number_to_vapi.py +14313556789

This script claims the number in Twilio, registers it in VAPI, and inserts a row into twilio_number_pool with status = "available".

Race Condition Guard

Two scenarios can cause the same manager to claim two different numbers:

  1. Manager creates two property groups in rapid succession (both trigger provisioning)
  2. Manager clicks "Retry provisioning" while the first attempt is still running

Application-level guard

Database-level guard (belt and suspenders)

Why both guards? The application-level guard handles the common case efficiently (no DB error, clean code path). The DB-level unique index is the safety net for the rare case where two workers reach the claim step simultaneously before either has written to the pool. Defense in depth.

SDK Bug — Why We Use httpx Directly

VAPI Python SDK bug: client.phone_numbers.update(id=..., assistant_id=...) fails with a validation error about a missing provider field. The SDK's UpdatePhoneNumberDto discriminated union type always serializes the provider field, and VAPI's update endpoint rejects it.

This is a documented workaround — the code comment explicitly says "SDK update endpoint is broken; direct HTTP patch is the only working path." When the VAPI SDK is updated to fix this, the httpx call can be replaced with the SDK call.

BackgroundTask DB Client — Critical Rule

Rule: The background task MUST create its own service DB client. It cannot use the request-scoped DB client.

Why: FastAPI's Depends(get_authenticated_db) creates a DB client scoped to the HTTP request lifecycle. When the request handler returns (sends the HTTP response), the request context is torn down — including the DB client. BackgroundTasks run AFTER the response is sent. If the background task uses the request-scoped client, it will crash with "client already closed" errors.

If it picked up BACKEND_URL=http://localhost:8000 from a developer's .env, all live agents would point their tool calls to the developer's laptop instead of the production server. Real Bugs Faced & How We Fixed Them

Bug 1: Duplicate agents created per manager

Symptom: A manager with 3 property groups had 3 identical VAPI assistants and 3 Twilio numbers claimed from the pool.

Root cause: Early code triggered provisioning on EVERY property group creation, not just the first.

Fix: The route checks how many property groups the manager already has BEFORE adding the background task. If count > 1 (this group makes it the first group or more), don't provision. Also added Guard 1 inside provision_vapi_for_manager(): if status == "active", return immediately.

Bug 2: Race condition — two background tasks claim two different numbers

Symptom: Manager has two numbers assigned (assigned_manager_id = same UUID on two rows). DB unique index violated on the second insert → 500 error.

Root cause: Two background tasks ran simultaneously (server restart during provisioning triggered a retry that overlapped with the original). Both checked the pool, both saw number A as available, both claimed it.

Fix: Application-level reuse check (Guard 2) + DB-level unique index on (assigned_manager_id). The double guard means it's impossible to double-claim at the DB level even if the app-level check is missed.

Bug 3: server_messages with "tool-calls" silently broke all lease agent tools

Already covered in the server_messages section above. Short version: lease agent must use only ["end-of-call-report"]. Adding "tool-calls" causes the eoc-webhook to receive and attempt to handle all tool events, breaking apiRequest tools mid-call.

Bug 4: Background task crashed because the DB client was closed

Symptom: postgrest.exceptions.APIError: Connection closed during provisioning, always starting 50ms after the HTTP response was sent.

Root cause: The background task was passed the request-scoped db client. FastAPI closes it when the response is sent. The task ran milliseconds later on a closed connection.

Fix: Create a fresh svc_db = get_service_db() at the start of provision_vapi_for_manager() instead of accepting the db parameter from the caller.

Exercises

Easy   What is the purpose of "strict": True in the submit_complaint function tool?

OpenAI strict mode enforces that all parameters listed in required must be present when the agent calls the tool. Without strict mode, the model can call the tool with missing parameters (e.g., no appointment_date) and the tool schema doesn't reject it. With strict mode, the model cannot invoke the tool unless all required fields are filled in — preventing incomplete complaint submissions.

Easy   Why does build_lease_config() inject manager_id into the tool URLs?

The lease agent searches listings. Each manager owns multiple property groups. Without a manager_id filter, the search would return listings from ALL managers' properties — a massive data privacy problem. The ?manager_id=<UUID> query parameter is injected at agent-build time so the VAPI tool URL includes the manager's scope. The backend GET /leasing/search route then filters results to only this manager's listings.

Medium   A new manager signs up but the Twilio pool is empty. What happens and what should you do?
Show solution

What happens:

  1. Manager creates first property group
  2. Background task runs provision_vapi_for_manager()
  3. Pool query returns 0 rows
  4. Provisioning upserts manager_vapi_config.vapi_provisioning_status = "failed"
  5. Function returns without error

In the LeasingTab UI, the manager sees a "Provisioning failed" banner with a "Retry" button.

What to do:

# Step 1: Buy a new Twilio number in Twilio console
# Step 2: Add it to VAPI and insert into pool
python backend/scripts/add_twilio_number_to_vapi.py +14315559999

# Step 3: Manager clicks "Retry" in the UI
# OR manually trigger via API:
POST /property-groups/users/me/provision-voice   # with manager's JWT

# This upserts status="pending" and re-runs the background task

The retry endpoint has its own guard: if status == "active" already, it returns early without spawning a new task — preventing accidental re-provisioning for already-active managers.

Hard   You need to roll out a system prompt update to all 50 active per-manager lease agents. How does update_lease_agents.py work, and what could go wrong?
Show solution

How it works:

# update_lease_agents.py (simplified)
BACKEND_URL = "https://tenant-management-mvp.onrender.com"   # hardcoded

rows = svc_db.table("manager_vapi_config").select("manager_id, vapi_lease_assistant_id").eq("vapi_provisioning_status", "active").execute()

for row in rows.data:
    manager_id = row["manager_id"]
    assistant_id = row["vapi_lease_assistant_id"]

    cfg = build_lease_config(BACKEND_URL, manager_id)
    client.assistants.update(id=assistant_id, **cfg)
    print(f"Updated {assistant_id} for manager {manager_id}")

What could go wrong:

  • VAPI API rate limiting: 50 consecutive assistant updates may hit rate limits. Fix: add time.sleep(0.5) between updates.
  • Partial failure: Updates 1-30 succeed, update 31 fails with a network error. Managers 31-50 still have the old prompt. Fix: log which managers were updated and add a dry-run mode to re-run only failed ones.
  • Wrong BACKEND_URL: If you accidentally run this from a dev machine with BACKEND_URL=http://localhost:8000 in your env, all agents will have broken tool URLs. The hardcoded constant prevents this — but double-check before running.
  • Live call disruption: A manager's tenant might be mid-call when their agent is updated. VAPI applies config changes to the NEXT call, not the current one — so this is generally safe.

Why This Design

Decision: One VAPI assistant per manager vs. one shared assistant

ApproachProsCons
Per-manager assistant + dedicated number (chosen)The inbound phone number IS the tenant's identity anchor — no “which landlord?” disambiguation; per-manager prompt customization (building names, policies) baked inN assistants to keep in sync when the base prompt changes; a config migration script becomes mandatory tooling
One shared assistant, route by metadataSingle config to updateCaller must be disambiguated at call time; per-manager customization means giant conditional prompts

Decision: Phone number pool vs. on-demand purchase

ApproachProsCons
Pre-provisioned pool, assign on signup (chosen)Signup is instant — no synchronous dependency on Twilio's purchase API (which can be slow or fail); costs are predictableIdle numbers cost money monthly; pool exhaustion needs monitoring
Buy a number during signupNo idle inventoryCouples your signup success rate to a third-party purchase API — the worst place to fail
Senior takeaway: provisioning is a background workflow with retries, not a request handler. Anything involving third-party resource creation (numbers, assistants) should be async, idempotent (guard against double-provisioning races), and observable via a status field the UI can poll.

Checkpoint ✓

With a JWT (Module 05) for an account that has completed provisioning:

curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/flats/users/me/vapi-config

Expected: JSON with the manager's assistant/phone state (assistant id, phone number, status). For a fresh account, trigger it:

curl -X POST -H "Authorization: Bearer $TOKEN" http://localhost:8000/flats/users/me/provision-voice

then poll the config endpoint until the status lands in a terminal state. Cross-check in the VAPI dashboard that exactly ONE assistant exists for this manager — fire the provision call twice in a row and confirm the race guard prevents a duplicate.
