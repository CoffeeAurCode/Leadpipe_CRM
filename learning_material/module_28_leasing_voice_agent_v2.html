Module 28 — Leasing Voice Agent v2: Language, Matching & Routing

Section 1 — What You Are Building

Module 16 built the leasing API; Module 12 provisioned voice agents. What shipped after that was v1 — and v1 met real callers. Real callers speak French, mispronounce city names, interrupt, hang up mid-question, and call from numbers the system has never seen. This module is the distillation of ten build sessions of hardening v1 into v2: an agent that hears imperfectly but matches confidently, speaks the caller's language without drifting, never leaves dead air, knows what time it is in Montréal, and routes every caller to the right agent automatically.

Inbound call │ ▼ /leasing/voice/inbound-router ── reads tenant preferred_language (Module 27) │ │ en ▼ fr ▼ EN assistant FR assistant ── register-locked prompts, French templates │ ▼ tool calls (find-units, search-listings…) /leasing endpoints ── fuzzy + phonetic city matching, banded confirmation, │ Montréal clock stamped on every response ▼ lead capture (3 redundant layers) → lease_leads pipeline → manager UI

Every subsystem above exists because a specific production call failed in a specific way. The walkthrough (Section 3) is that story in build order — it's the closest thing this course has to watching a senior engineer work over ten sessions.

Section 2 — Concept Deep-Dives

1 · The STT error model — your input is a guess, not a transcript

Speech-to-text output is a hypothesis. For short, proper-noun answers ("Montréal", "Longueuil") spoken over a phone line — possibly with a French accent into an English-configured transcriber — the hypothesis is frequently wrong in systematic ways: syllables merge, accents shift vowels, and the STT substitutes phonetically-similar English words. Session 8's diagnosis built a garble corpus (backend/scripts/generate_stt_garble_corpus.py): a list of real and synthesized mis-hearings per city, which then became the regression test bed for every matcher change.

🔑 Key concept: you cannot fix STT errors upstream (you don't own the transcriber's model). You fix them downstream, by making your matching tolerant — and you measure that tolerance against a corpus, not against vibes.
2 · Fuzzy vs. phonetic matching — two different kinds of "close"

Fuzzy (edit-distance) matching — RapidFuzz's ratio family — measures how many character edits separate two strings. Great for typos; weak for mis-hearings, because "Munreal" is phonetically near Montréal but several edits away.

Phonetic matching — Metaphone-style encoding — collapses words to how they sound. "Montreal" and "Munreal" encode to the same key. Weak for typos of the visual kind; strong for exactly the STT failure mode.

The production matcher (app/services/city_matching.py) is a hybrid: normalize (strip accents, lowercase), try exact, then phonetic, then fuzzy, and produce a score, not a boolean. The score feeds the band logic below. Both extra libraries are optional dependencies with graceful degradation — if the phonetic lib is missing, the matcher falls back to fuzzy-only rather than crashing the route (Session 9's "fail-open initialization" principle).

3 · Confidence banding — three zones, and the gate/ranker law

A score alone is useless until you decide what to do at each level. The banded decision function has three zones:

BandScoreBehavior
AcceptHighProceed silently — confirming "did you say Montréal?" on an obvious match wastes the caller's time
ConfirmMiddleReturn a disambiguation block — a JSON contract the agent's prompt knows how to speak: "Did you mean Montréal?"
RejectLowAsk again from scratch; guessing here creates confidently-wrong searches
🐛 Bug story (Session 12): the silent drop. The matcher ranked candidates with the hybrid scorer, but a separate validity gate upstream still used plain fuzzy matching. A city the ranker would have matched fine was discarded by the stricter gate before ranking ever ran — the agent said "no listings" for a city with listings, and nothing logged an error. The law that came out of it: a gate must never be stricter than its ranker. If two components score the same input, they must share one scoring function — the fix literally unified them into one code path.
4 · The latency budget — anatomy of a voice-agent turn

Every turn a caller experiences is a pipeline: STT finalizes → LLM time-to-first-token → (maybe: tool call → your backend → second LLM pass) → TTS starts speaking. Session 10 budgeted it:

  • Model size is a per-turn tax — a bigger model adds TTFT to every single exchange, not just hard ones.
  • Tool turns are the slowest — the model generates the call, waits on your HTTP endpoint, then generates again. Your backend's latency sits in the middle of a live conversation, which is why the N+1 query in a tool endpoint (fixed with a PostgREST nested embed) was a caller-audible bug.
  • Dead air is the failure mode — humans tolerate ~1s of silence before "hello?". Two tools exist for bridging: request-start filler messages (deterministic phrases VAPI speaks the moment a tool call starts — "let me check that for you") and prompt-level acknowledgment habits. Fillers are configuration, not model behavior, so they never fail to fire.
🐛 Bug story (Session 17): the promise that never ran. The prompt told the agent to say a filler phrase and then call the tool. The model said the phrase… and considered its turn complete. No tool call, permanent silence — the caller and agent each waiting for the other. Fix: prompt must command the tool call in the same turn ("say X while calling the tool" → use request-start messages instead of asking the model to sequence it). A voice conversation has a turn-taking floor: whoever holds it must either speak or yield — a skipped tool call holds it forever.
5 · Language discipline — locks, register, and handing the model the line

Bilingual calling surfaced a family of failures with one root: the model treats language as a suggestion unless you make it structural.

  • Register drift (Session 13): mid-call, French slid from formal vous to informal tu and grammar degraded. LLMs drift when asked to generate French continuously. The fix: hand the model the line — put exact French sentence templates in the prompt for the fixed questions, so the model recites rather than translates. Recitation can't drift.
  • The static-string leak (Session 11): a hardcoded English filler string played during French calls, because a static config value can't respect a per-call language lock. Anything spoken must either be per-language configured or generated under the lock — never a shared constant.
  • The handoff gate (Session 14): when the complaint agent hands off to a French flow, the language decision must be made once, explicitly, at the gate — and everything downstream (prompt, first message, fillers) derives from it. Distributed language decisions disagree with each other.
6 · Handoff mechanics — who speaks first, and why silence happened

Session 15's incident: after handoff to the French assistant, ~6 seconds of silence. Three findings that generalize:

  • firstMessage modes matter. VAPI assistants can speak a fixed first message, generate one, or wait for the user. A generated first message after handoff means cold-start LLM latency before anyone speaks — into a call that just went quiet. The fix was a static first message: instant, deterministic, correct-register French.
  • Context leakage: carrying the full prior conversation into the new assistant made it "continue" instead of greeting — sometimes concluding it had nothing to say. Scope what crosses the handoff.
  • Non-determinism means one good test call proves nothing. Call one worked, call two didn't — temperature guarantees variance. Test conversational changes multiple times before declaring victory.
7 · Language models have no clock — inject time as data

A caller asks "can I view it tomorrow at 3?" — and the model has no idea what "tomorrow" is. It will confidently guess. Session 12's fix: the backend stamps Montréal-local current datetime (via zoneinfo/tzdata — DST-correct) onto every relevant tool response, and a variableExtractionPlan exposes it to the model as a variable it can reference. Generalization: anything the model must be right about (time, prices, availability) must arrive as data in-context — never from its priors.

8 · Dynamic call routing — memory + a router endpoint

Session 18 closed the loop: instead of every caller getting the English agent and opting into French per call, the system remembers. The pieces:

  • The memory cell: tenants.preferred_language (migration 032, Module 27), write-once.
  • Preference capture via URL tagging: the French assistant's verify-tool URL carries a lang=fr tag, so the backend knows the answered language from which endpoint variant was called — a deterministic signal — rather than asking the LLM to report what language it heard (an unreliable one).
  • The routing brain: /leasing/voice/inbound-router looks up the caller's number → tenant → preferred language, and returns which assistant takes the call. Outbound calls consult the same function — one brain, two directions.
  • Migration-tolerant + ordered deploy: the whole feature shipped in the four-step order from Module 27, and every read of the new column was tolerant, so no step could break live calls.

Section 3 — The Build, Session by Session

Read this as a build order — if you were recreating v2 from scratch, this is the sequence, and each step's lesson is what you'd carry forward. (Each session has a full standalone lesson file — sessions.html indexes them — this is the connective tissue.)

Session 8 — Diagnose before designing

Complaints: the agent paused awkwardly ("one moment…") and mis-heard cities. Built the evidence base first: transcript forensics, a garble corpus, a designed-vs-observed flow comparison. Only then designed the fix family and chose banded confirmation (B2) over always-confirm (A1) and reject-only (B1). Lesson: the diagnosis document is a deliverable — it's what makes the design defensible.

Session 9 — Ship the hybrid matcher

Implemented normalize→exact→phonetic→fuzzy with score bands, the JSON disambiguation contract, tool schema + prompt updates, corpus tests, pinned deps, and a dry-run-then-deploy pipeline. Made the new libraries optional with graceful fallback. Lesson: a matcher is a contract between backend and prompt — ship both sides together.

Session 10 — Buy back latency

Latency budget analysis; fixed an N+1 with a nested embed; tightened prompts (a reworded question is a product change); gated the risky model swap behind evidence; wrote a rollback snapshot before touching shared config. Lesson: in shared-config systems, know your blast radius and pre-write your rollback.

Session 11 — Leads must survive anything

Missing leads investigation. Fixed tolerant matching for size fields, then built defense in depth for lead capture: three independent layers (during-call tool write, end-of-call webhook extraction, direct capture endpoint) so no single mechanism owns critical data. Also: killed a function-name collision hypothesis with evidence, retracted a wrong "corruption" theory after byte-level verification. Lesson: for revenue-critical data, redundancy beats elegance; and hypotheses get falsified, not assumed.

Session 12 — Unify the gate, teach it the time

The silent-drop fix (gate = ranker, one scoring path) and the Montréal clock injection with variableExtractionPlan. Lesson: duplicate scoring logic will eventually disagree — and the disagreement will be silent.

Sessions 13–15 — French that stays French

Register lock via handed lines (13); the handoff language gate — decide once, derive everything (14); the dead-air fix — static first message, scoped context, and re-testing under non-determinism (15). All three were prompt/config-only deploys — no backend release needed, which is its own architectural win (see Section 4). Lesson: language behavior is engineered, not requested.

Session 18 — Close the loop with memory

Preference memory + dynamic routing, shipped across four systems in strict order. Lesson: when a feature spans systems, the deploy plan is part of the design.

Section 4 — Why This Design

Decision: Banded confirmation (B2) vs. the alternatives

OptionBehaviorWhy / why not
A1 — always confirmRepeat every city backSafe but maddening — doubles turn count on the happy path; callers hang up on robots that confirm the obvious
B1 — hard thresholdMatch or re-ask, never confirmWastes the middle band — cases where one clarifying question would have saved the call
B2 — three bands (chosen)Accept / confirm / reject by scoreSpends caller patience exactly where uncertainty lives; the confirm band is also your telemetry for tuning thresholds later

Decision: Separate EN/FR assistants + router vs. one bilingual assistant

ApproachProsCons
Per-language assistants, routed by stored preference (chosen)Each assistant's prompt, first message, fillers, and templates are single-language — the entire drift/leak bug family becomes structurally impossible; transcriber can be tuned per languageN×languages assistants to provision and keep in sync — the provisioning scripts (Module 12's discipline) carry the weight
One bilingual assistantOne configEvery string is a potential wrong-language leak; register control twice as hard; the transcriber must guess the language per utterance

Decision: Deterministic mechanisms over model behavior, wherever stakes are high

ConcernDeterministic mechanism (chosen)Rejected model-dependent alternative
Filler speech during tool callsrequest-start messages (config)“Remember to say something before calling tools” (prompt)
Which language the caller answered inURL tag on the tool endpointAsking the model to report the language it heard
First words after handoffStatic firstMessageGenerated greeting (cold-start latency + variance)
Lead data reaching the DBThree redundant capture layersTrusting the one in-call tool invocation
Current date/timeBackend-stamped Montréal clockThe model's guess
🔑 The meta-pattern of the entire module: every hardening step moved something from "the model usually does this" to "the system always does this." Prompts are for judgment; configuration and code are for guarantees. When a failure repeats, ask which side of that line the mechanism is on — and move it.

Section 7 — Checkpoint ✓

Prove the three bands with three inputs

Hit /leasing/find-units (or run the matcher in a Python shell) with: (1) Montreal — exact/accept; (2) a corpus garble like Munreal — accept or confirm with the right candidate; (3) garbage like Xyzzyville — reject, no guessed city.

Success: three inputs, three different behaviors, zero errors — and you can say which band each landed in and why. If you can also point to the single function where gate and ranker share their score, you've absorbed the module's hardest-won lesson.

Section 8 — Exercises

Easy Extend the garble corpus

Problem: Add three plausible STT mis-hearings for "Longueuil" (say them aloud with an anglophone accent — that's the generator) to the corpus test data, assert the expected match, and run the suite.

Solution sketch

Candidates like "long gay", "lawn gale", "longay". Add to the corpus entries in tests/test_city_matching.py (follow the existing structure), run pytest. If one lands in reject, that's a finding, not a failure — decide whether the matcher should stretch (phonetic key tweak) or the band is correctly refusing. Document whichever you conclude — that judgment call is the exercise.

Medium Threshold tuning with a confusion mindset

Problem: Product wants fewer "did you mean…?" confirmations. You could widen the accept band. Using the corpus, describe how you'd measure what that change trades away before shipping it.

Solution

Run every corpus entry through the scorer and bucket by band at the current and proposed thresholds. The entries that move from confirm to accept split into: correctly-matched (pure win) and wrongly-matched (now a silent wrong search — the worst outcome, worse than a confirmation). Count both. Ship only if the wrong-accept count is zero on the corpus, and add the moved entries as regression pins. The general form: never tune a threshold without a labeled set on both sides of it — the corpus (Session 8's artifact) is exactly that set. Note the asymmetry: an unnecessary confirmation costs 3 seconds; a wrong accept costs the whole call's trust.

Hard Add Spanish without re-fighting the war

Problem: Spanish support is requested. Using this module's patterns, write the design (no code): what gets created, what gets extended, and which five deterministic mechanisms from Section 4 must exist in Spanish form before the first test call.

Solution
  1. Create: an ES assistant (per-language, not bilingual) with ES-tuned transcriber; static ES firstMessage; ES request-start fillers; handed-line ES templates for the fixed questions (usted register — decide once, at the gate).
  2. Extend: migration widens the preferred_language CHECK to ('en','fr','es') (Module 27 conventions — and note the deploy order: migration → tolerant backend → assistant → router flip); the verify-tool URL tagging gains lang=es; the router's language map gains a branch.
  3. Unchanged by design: city matching (language-independent phonetics may need corpus entries from Spanish-accented garbles — new corpus rows, same machinery), the clock injection, the three lead layers, gate=ranker.
  4. Test plan: corpus additions first, then multiple live calls (non-determinism rule from Session 15), then the write-once preference check: an ES answer must not overwrite an existing FR record.

What's being tested: recognizing that Sessions 8–18 built machinery, not French support — a third language is configuration plus corpus, and if any step requires new architecture, that's a smell you missed a pattern.
