Section 1 — What You Are Building

This module covers the top two layers of the data hierarchy: Property Groups (a collection of buildings, e.g. "Sunrise Apartments") and Buildings (a physical structure inside a group, e.g. "Block A"). Together they form the container that all flats, tenants, and complaints live inside.

Hierarchy ───────── PropertyGroup (properties_list table) └── Building (buildings table) ←── Module 05 └── Flat (flats table) ←── Module 06 └── Tenant (tenants table) ←── Module 07 Route prefixes (no /api prefix — project rule) ─────────────────────────────────────────────── GET /property-groups → list all groups (with building counts) POST /property-groups → create group + trigger VAPI provisioning GET /property-groups/{id}/buildings → list buildings inside one group DELETE /property-groups/{id} → cascade-delete entire group GET /buildings → list all buildings (with unit counts) GET /buildings/{id}/units → list flats inside one building POST /buildings → create building PATCH /buildings/{id} → update building DELETE /buildings/{id} → cascade-delete building + its flats/tenants

Both route files share the same structural pattern: Pydantic schemas at the top, helper functions in the middle, endpoint handlers at the bottom. This layout is consistent across the entire backend.

Section 2 — Concept Deep-Dives

The N+1 Query Problem and the 2-Query Fix

Imagine you want to show 10 property groups, each with a building count. The naive approach:

python# BAD — N+1: 1 query for groups + 1 query PER group = 11 queries total
for group in groups:
    count = db.table("buildings").select("id").eq("property_id", group["id"]).execute()
    group["building_count"] = len(count.data)

With 100 groups this becomes 101 queries. The database is hit once per row — this is the N+1 problem.

The fix used in this codebase: fetch everything in 2 flat queries, then merge in Python:

python# GOOD — exactly 2 queries regardless of how many groups exist
groups_resp = db.table("properties_list").select("*").execute()
buildings_resp = db.table("buildings").select("property_id").execute()

# Build a count map in Python (O(n) loop, not O(n) DB round-trips)
count_map = {}
for b in buildings_resp.data:
    pid = b.get("property_id")
    count_map[pid] = count_map.get(pid, 0) + 1

# Attach count to each group dict
for g in groups_resp.data:
    g["building_count"] = count_map.get(str(g["id"]), 0)

Key insight: database round-trips are expensive (network latency). In-memory Python loops are cheap (nanoseconds). Always batch into the fewest queries possible, then merge.

PostgREST JOIN syntax — select("*, related_table(col1, col2)")

Supabase's PostgREST API supports relationship traversal inside a single select() call. When two tables have a foreign key between them, you can fetch related rows in one query:

python# Fetch buildings with property_type name and icon in one query
resp = db.table("buildings").select("*, property_types(name, icon_type)").execute()

# Each row has a nested dict:
# { "id": "...", "name": "Block A", ...,
#   "property_types": {"name": "Residential", "icon_type": "house"} }

# Extract nested data safely (may be None if FK is null)
for b in resp.data:
    pt = b.get("property_types") or {}
    name = pt.get("name")  # "Residential"

This is PostgREST's version of a SQL LEFT JOIN. The nested table name must match the actual table name referenced by the FK in your schema.

Gotcha: If a row has property_type_id = NULL, the nested value is None, not an empty dict. Always use b.get("property_types") or {} — never assume it's present.

Cascade Delete — Manual vs Database-Level

PostgreSQL can cascade deletes automatically via ON DELETE CASCADE on FK constraints. This codebase does not rely on that — it does cascades manually in Python, in a strict order. Why?

  • Manual cascades are explicit — you can see exactly what gets deleted
  • You can add business logic (e.g., notify tenants before deleting)
  • RLS policies sometimes block automatic cascades
  • You can bail out early if something is in a protected state

The correct deletion order for a property group (child before parent, no orphaned FKs):

DELETE ORDER (must go from leaf → root) ─────────────────────────────────────── 1. tenants (FK → flats.uuid) 2. rents (FK → flats.uuid) 3. flats (FK → buildings.id) 4. buildings (FK → properties_list.id) 5. properties_list (root — no parent)

If you try to delete a building before its flats, PostgreSQL raises a foreign key violation error. Always delete children before parents.

FastAPI BackgroundTasks

Some work should happen after the HTTP response is sent — e.g., provisioning a VAPI phone number (which takes 2-5 seconds). You don't want to make the user wait. BackgroundTasks solves this:

pythonfrom fastapi import BackgroundTasks

@router.post("")
async def create_property_group(
    request: PropertyGroupCreate,
    background_tasks: BackgroundTasks,  # injected by FastAPI
    ...
):
    # 1. Do the main work synchronously (user waits for this)
    response = db.table("properties_list").insert(payload).execute()

    # 2. Schedule background work (user does NOT wait for this)
    background_tasks.add_task(provision_vapi_for_manager, user["sub"], svc_db)

    # 3. Return immediately — provisioning runs after response is sent
    return response.data[0]

Critical: The background task runs in the same process but after the response is sent. This means the request's DB client may already be closed. Always pass a service-role DB client to background tasks — never use the request-scoped authenticated client.

Pydantic V2 model_dump(exclude_none=True)

When building a dict to insert into the database, you only want fields the user actually provided — not None values that would overwrite existing data with nulls.

pythonclass PropertyGroupCreate(BaseModel):
    name: str
    description: Optional[str] = None
    address: Optional[str] = None

# If user sends: {"name": "Sunrise"} (no description, no address)
create = PropertyGroupCreate(name="Sunrise")

# WITHOUT exclude_none — inserts nulls for description and address
create.model_dump()
# → {"name": "Sunrise", "description": None, "address": None}

# WITH exclude_none — only sends what was provided
create.model_dump(exclude_none=True)
# → {"name": "Sunrise"}

For PATCH (partial updates), use model_dump(exclude_unset=True) instead — that excludes fields the caller didn't mention at all, even if they have a default value.

UUID serialization — why str(v) if isinstance(v, UUID)

Pydantic parses UUID-typed fields into Python's uuid.UUID objects. But Supabase's Python client expects plain strings for UUID columns, not UUID objects.

python# Pattern used in buildings.py for every PATCH/POST payload
payload = {
    k: str(v) if isinstance(v, UUID) else v
    for k, v in request.model_dump(exclude_none=True).items()
}

# Without this: Supabase client receives UUID('abc-123-...') object → TypeError
# With this:    Supabase client receives "abc-123-..." string → works

An alternative is to use model_dump(mode='json') in Pydantic V2, which serializes UUIDs and dates to strings automatically. Both patterns exist in this codebase depending on the context.

DELETE /{property_id} — cascade delete

python@router.delete("/{property_id}", status_code=status.HTTP_204_NO_CONTENT)
async def delete_property_group(property_id: str, ...):
    # Step 1: verify it exists (raises 404 if not)
    prop_resp = db.table("properties_list").select("id").eq("id", property_id).execute()
    if not prop_resp.data:
        raise HTTPException(status_code=404, detail="...")

    # Step 2: get all building IDs in this group
    buildings_resp = db.table("buildings").select("id").eq("property_id", property_id).execute()
    building_ids = [b["id"] for b in buildings_resp.data]

    if building_ids:
        # Step 3: get all flat UUIDs + tenant UUIDs inside those buildings
        flats_resp = (
            db.table("flats")
            .select("id, uuid, tenant_uuid")
            .in_("building_id", building_ids)
            .execute()
        )
        flat_uuids = [f["uuid"] for f in flats_resp.data if f.get("uuid")]
        tenant_uuids = [f["tenant_uuid"] for f in flats_resp.data if f.get("tenant_uuid")]

        # Step 4: delete leaves first, then parents (never delete parent before child)
        if tenant_uuids:
            db.table("tenants").delete().in_("uuid", tenant_uuids).execute()
        if flat_uuids:
            db.table("rents").delete().in_("flat_uuid", flat_uuids).execute()
        db.table("flats").delete().in_("building_id", building_ids).execute()
        db.table("buildings").delete().eq("property_id", property_id).execute()

    # Step 5: now safe to delete the root
    db.table("properties_list").delete().eq("id", property_id).execute()
    return None  # 204 No Content

.in_("building_id", building_ids) is the Supabase SDK's equivalent of SQL WHERE building_id IN (...). It accepts a Python list. This deletes all matching flats in a single query rather than one delete per flat.

Section 4 — buildings.py Line by Line

The _enrich_buildings helper

pythondef _enrich_buildings(buildings: list, all_flats: list) -> list:
    """Merges unit count data from all_flats into buildings list."""
    unit_counts: dict[str, int] = {}
    occupied_counts: dict[str, int] = {}

    for flat in all_flats:
        bid = flat.get("building_id")
        if bid:
            unit_counts[bid] = unit_counts.get(bid, 0) + 1
            if flat.get("tenant_uuid"):   # tenant_uuid is set = occupied
                occupied_counts[bid] = occupied_counts.get(bid, 0) + 1

    result = []
    for b in buildings:
        pt = b.get("property_types") or {}
        bid = str(b["id"])
        result.append({
            "id": b["id"],
            "name": b["name"],
            ...
            "property_type_name": pt.get("name"),
            "unit_count": unit_counts.get(bid, 0),
            "occupied_count": occupied_counts.get(bid, 0),
        })
    return result

This helper is extracted because the same merge logic is used by both GET /buildings and GET /property-groups/{id}/buildings. Extracting it prevents duplication. In Python, a function starting with _ signals it is a module-private helper — not part of the public API, only used within this file.

Section 5 — Real Bugs We Hit

Bug: Duplicate VAPI provisioning on every group creation

Symptom: Manager creates 3 property groups → 3 VAPI assistants are provisioned → 3 phone numbers are charged → phone calls only work on one of them.

Root cause: The original code called provision_vapi_for_manager inside every POST /property-groups — there was no check for an existing provisioning record.

Fix: Added a guard that checks manager_vapi_config first. Only provision if no row exists for this manager:

pythonexisting_config = (
    svc_db.table("manager_vapi_config")
    .select("id")
    .eq("manager_id", user["sub"])
    .limit(1)
    .execute()
)
if not existing_config.data:  # only on FIRST property group
    background_tasks.add_task(provision_vapi_for_manager, ...)
Bug: Background task fails because authenticated DB client is closed

Symptom: VAPI provisioning silently fails. No error in the response (the request succeeded), but no phone number is ever assigned.

Root cause: The background task was using the request-scoped db client (authenticated, user-JWT). FastAPI closes this client after the response is sent. The background task runs after the response — the client is gone.

Fix: Background tasks must use a separately-created service-role client that is not tied to the request lifecycle:

python# WRONG — svc_db here is the request-scoped client, already closed
background_tasks.add_task(provision_vapi_for_manager, user["sub"], db)

# CORRECT — create a fresh service-role client before scheduling
from app.db.session import get_service_db
svc_db = get_service_db()  # fresh, independent of the request
background_tasks.add_task(provision_vapi_for_manager, user["sub"], svc_db)
Bug: CASCADE delete order violation — FK constraint error

Symptom: DELETE /property-groups/{id} returns 500 with a PostgreSQL foreign key violation error.

Root cause: The original code deleted buildings before deleting the flats inside them. Since flats have a FK to buildings (flats.building_id → buildings.id), the database rejected the building deletion.

Fix: Strict deletion order — always delete child rows before parent rows:

python# WRONG order
db.table("buildings").delete().execute()  # flats still reference buildings → FK error
db.table("flats").delete().execute()

# CORRECT order
db.table("tenants").delete().in_("uuid", tenant_uuids).execute()
db.table("rents").delete().in_("flat_uuid", flat_uuids).execute()
db.table("flats").delete().in_("building_id", building_ids).execute()
db.table("buildings").delete().eq("property_id", property_id).execute()
db.table("properties_list").delete().eq("id", property_id).execute()

Exercise 3 Hard

The cascade delete for a property group currently fails silently if one of the intermediate deletes raises an error — subsequent deletes still run even though the data is in a broken state. Refactor delete_property_group to wrap the entire cascade in a try/except that raises a clear 500 error if any intermediate step fails, and add a log message for each step so you can see exactly which step failed.

Full worked solution 
python@router.delete("/{property_id}", status_code=status.HTTP_204_NO_CONTENT)
async def delete_property_group(property_id: str, user=Depends(require_active_subscription), db=Depends(get_authenticated_db)):
    prop_resp = db.table("properties_list").select("id").eq("id", property_id).execute()
    if not prop_resp.data:
        raise HTTPException(status_code=404, detail=f"Property group {property_id} not found")

    buildings_resp = db.table("buildings").select("id").eq("property_id", property_id).execute()
    building_ids = [b["id"] for b in buildings_resp.data]

    try:
        if building_ids:
            flats_resp = db.table("flats").select("id, uuid, tenant_uuid").in_("building_id", building_ids).execute()
            flat_uuids = [f["uuid"] for f in flats_resp.data if f.get("uuid")]
            tenant_uuids = [f["tenant_uuid"] for f in flats_resp.data if f.get("tenant_uuid")]

            if tenant_uuids:
                print(f"[DELETE] Removing {len(tenant_uuids)} tenants")
                db.table("tenants").delete().in_("uuid", tenant_uuids).execute()

            if flat_uuids:
                print(f"[DELETE] Removing rents for {len(flat_uuids)} flats")
                db.table("rents").delete().in_("flat_uuid", flat_uuids).execute()

            print(f"[DELETE] Removing flats in buildings {building_ids}")
            db.table("flats").delete().in_("building_id", building_ids).execute()

            print(f"[DELETE] Removing buildings for property {property_id}")
            db.table("buildings").delete().eq("property_id", property_id).execute()

        print(f"[DELETE] Removing property group {property_id}")
        db.table("properties_list").delete().eq("id", property_id).execute()
        return None

    except HTTPException:
        raise
    except Exception as e:
        print(f"[ERROR] Cascade delete failed at property {property_id}: {type(e).__name__}: {e}")
        raise HTTPException(
            status_code=500,
