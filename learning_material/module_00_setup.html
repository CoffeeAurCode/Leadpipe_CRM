Section 1 — What You Are Building

This module prepares your development machine to run the Tenant Management MVP backend. You will create an isolated Python environment, install every dependency from requirements.txt, populate a .env file with credentials, create a Supabase project, and run the backend server for the first time.

The backend is a FastAPI application (Python) that talks to a Supabase database (PostgreSQL). Before any code can run, three things must exist: the Python runtime, the dependency packages, and the external service credentials. This module sets up all three.

Section 2 — Concept Deep-Dives

Python Virtual Environments (venv)

A virtual environment is an isolated copy of the Python interpreter plus a private package store. Without one, every project on your machine shares the same packages — installing a new version for one project silently breaks another.

Minimal standalone example

# Create an isolated environment in a folder called "venv"
python -m venv venv

# Activate it (Windows PowerShell)
.\venv\Scripts\Activate.ps1

# Activate it (macOS / Linux bash)
source venv/bin/activate

# Your prompt now shows (venv) — pip installs go into venv/
pip install requests       # only in this environment

# Deactivate when done
deactivate

How this project uses it

The project's requirements.txt lists every dependency at a pinned version. After creating a venv and running pip install -r requirements.txt, you get an exact replica of the production environment.

What breaks without it

If you run pip install -r requirements.txt without a venv, packages install into your system Python. A future project installing a different version of pydantic will silently break this one.

Try it yourself

Create a new folder, make a venv inside it, activate it, and confirm Python is isolated:

mkdir test_venv && cd test_venv
python -m venv venv
.\venv\Scripts\Activate.ps1   # Windows
python -c "import sys; print(sys.executable)"
# Should show a path INSIDE the venv folder, not system Python

Success: the printed path contains venv and does not point to your system Python installation.

Environment Variables and .env Files

An environment variable is a named value the operating system makes available to any process. Applications use them for secrets (API keys, passwords) so that credentials never appear in source code that might be committed to git.

Minimal standalone example

# .env file (never commit this)
DATABASE_URL=postgresql://user:pass@localhost/mydb
SECRET_KEY=super-secret-value

# read_env.py
from dotenv import load_dotenv
import os

load_dotenv()   # reads .env into environment

db_url = os.getenv("DATABASE_URL")
print(db_url)   # postgresql://user:pass@localhost/mydb

How this project uses it

config.py calls load_dotenv() at module load time and reads every credential via os.getenv(). The .env.example file is committed to git as a template — it shows every variable that must exist but uses placeholder values.

Never commit .env to git. The .gitignore should always contain .env. If you accidentally commit a real secret, rotate the key immediately — git history is public.

Try it yourself

Create a test.env file with MY_NAME=Alice, then read it:

pip install python-dotenv
python -c "from dotenv import load_dotenv; import os; load_dotenv('test.env'); print(os.getenv('MY_NAME'))"

Success: prints Alice.

Supabase — PostgreSQL as a Service

Supabase is a hosted PostgreSQL database that also provides: authentication (Auth), file storage (Storage), and a REST/GraphQL API auto-generated from your schema (PostgREST). You interact with it using the supabase-py SDK, which wraps HTTP calls to the PostgREST API.

Key concepts

  • Project URL — https://<project-ref>.supabase.co — the base URL for all SDK calls.
  • Anon key — public key. Safe to expose to browsers. Respects Row Level Security (RLS).
  • Service-role key — private key. Bypasses RLS. Never expose to the frontend.
  • JWT Secret — used to verify Supabase-issued JWTs in your backend.

Minimal standalone example

from supabase import create_client

client = create_client(
    "https://abc123.supabase.co",
    "your-anon-key"
)

# Fetch all rows from "complaints"
result = client.table("complaints").select("*").execute()
print(result.data)   # list of dicts
Try it yourself

After creating your Supabase project (step 3 below), open the Supabase dashboard → SQL Editor and run:

SELECT current_timestamp;

Success: the query returns the current UTC timestamp. Your database is live.

Section 3 — Reading the Source Files

File: backend/.env.example

This file is a template committed to git. It shows every environment variable the app needs, with placeholder values. Developers copy it to .env and fill in real credentials.

# Supabase
SUPABASE_URL=https://xxx.supabase.co         # Your project URL from Supabase dashboard
SUPABASE_KEY=your-anon-key                   # Safe to use in authenticated routes
SUPABASE_SERVICE_KEY=your-service-role-key   # NEVER expose; bypasses all security
SUPABASE_JWT_SECRET=your-jwt-secret          # Dashboard > Settings > API > JWT Secret

# Stripe
STRIPE_SECRET_KEY=sk_test_xxx                # sk_test_ prefix = test mode (safe)
STRIPE_WEBHOOK_SECRET=whsec_xxx              # From Stripe dashboard > Webhooks
STRIPE_PRICE_ID=price_xxx                    # The subscription plan price ID

# URLs
FRONTEND_URL=http://localhost:5173           # Where React dev server runs
BACKEND_URL=https://your-deploy.onrender.com # Production backend URL
ALLOWED_ORIGINS=http://localhost:3000,http://localhost:5173

# AI / Voice
OPEN_AI_API=your-openai-api-key             # For the chatbot
GROQ_API_KEY=your-groq-api-key              # For complaint extraction
PRIVATE_VAPI_API=your-vapi-api-key          # Server-side VAPI key

Why separate the VAPI assistant IDs per role? The complaint agent is global (one assistant for all managers). The lease agent is per-manager (provisioned on first use). Separate env vars prevent the complaint endpoint from accidentally using a lease agent ID.

File: backend/requirements.txt

All 80 lines are exact version pins. Notice the important distinction: some packages use == (exact pin) while others use >= (minimum version). The >= packages (stripe, twilio, openai) are vendor SDKs where the API changes infrequently, so a minimum version is fine. Core framework packages (fastapi, pydantic, supabase) are pinned exactly because minor versions can break things subtly.

SQLAlchemy appears in requirements.txt (SQLAlchemy==2.0.46) because it was used in the original prototype. The current codebase uses the Supabase SDK instead. The models.py file still exists for historical reference but is never imported by live routes.

File: backend/schema.sql

This is the initial schema from when the project used a local SQLite/PostgreSQL database. The live Supabase schema has evolved significantly beyond this file — new tables like properties_list, buildings, manager_profiles, subscriptions, and lease_leads don't appear here. Treat this file as a historical artifact, not the current schema definition.

Key things to notice about the schema structure:

  • SERIAL PRIMARY KEY — auto-incrementing integer ID (legacy; new tables use UUID)
  • VARCHAR(20) NOT NULL UNIQUE on flat_number — the DB enforces uniqueness, not just the app
  • CONSTRAINT ... CHECK — the DB rejects invalid values even if the app forgets to validate
  • ON DELETE CASCADE on foreign keys — deleting a tenant auto-deletes their complaints

Section 4 — Why This Design

Decision: Supabase vs. self-managed PostgreSQL

ApproachProsCons
Supabase (chosen)Free tier, auth built-in, RLS, Storage, PostgREST API, realtime subscriptions, dashboard UIVendor lock-in; SDK API changes between versions; can't run locally without Docker
Self-managed PostgreSQL + SQLAlchemyFull control; runs 100% locally; no external service neededMust implement auth, RLS, storage, API yourself; more setup; harder in serverless
Firebase / MongoDBServerless-native; easy horizontal scalingNoSQL loses relational integrity; no SQL joins; pricing unpredictable at scale

When you'd choose differently: Use self-managed PostgreSQL + SQLAlchemy if your team is strong in SQL and you need complex migrations, stored procedures, or full offline development. Use Supabase if you want to ship fast with auth + storage included.

Decision: Python 3.13+ with FastAPI over older stacks

ApproachProsCons
FastAPI (chosen)Automatic OpenAPI/Swagger docs; async-native; Pydantic validation built in; fastest Python frameworkYounger ecosystem than Django; fewer batteries included
Django REST FrameworkMature; ORM included; admin panel; huge communitySynchronous by default; more boilerplate; heavier for microservices
Node.js / ExpressSame language as React frontend; massive npm ecosystemDynamic typing; no built-in validation; team must know JS on backend too

Section 6 — Running & Testing

Step-by-step setup

1. Clone the project and create a virtual environment

git clone https://github.com/your-org/Tenant_management_MVP.git
cd Tenant_management_MVP/backend

python -m venv venv

# Windows PowerShell
.\venv\Scripts\Activate.ps1

source venv/bin/activate

pip install -r requirements.txt

3. Create your Supabase project

  1. Go to supabase.com → New Project
  2. Choose a region close to you
  3. Copy: Project URL, anon key, service-role key, JWT secret (Dashboard → Settings → API)

cp .env.example .env

INFO:     Application startup complete.

Section 8 — Exercises

Easy Add a new environment variable and read it

Problem: Add a variable COMPANY_NAME=Acme Properties to your .env file and print it when the server starts.

Edit config.py to add COMPANY_NAME: str = os.getenv("COMPANY_NAME", "Unknown") to the Settings class. Then in main.py, add a startup event that prints it.

Hints

FastAPI startup events use the @app.on_event("startup") decorator (or the newer lifespan context manager). The settings singleton is imported from app.config.

Solution

In config.py:

COMPANY_NAME: str = os.getenv("COMPANY_NAME", "Unknown")

In main.py:

@app.on_event("startup")
async def startup():
    print(f"Starting: {config.COMPANY_NAME}")

You know you got it right when the server prints Starting: Acme Properties on startup.

Medium Check for missing required variables at startup

Problem: The current session.py raises an error when the Supabase client is first created. But STRIPE_SECRET_KEY, OPEN_AI_API, and GROQ_API_KEY are only validated when those routes are first called. Add a startup check that lists all missing required env vars and exits with a clear error message.

Hints

Add a @app.on_event("startup") function in main.py. Import settings from app.config. Check which attributes are empty strings and collect them into a list. Use sys.exit(1) if any are missing.

Solution 
import sys

REQUIRED_VARS = [
    ("STRIPE_SECRET_KEY", config.STRIPE_SECRET_KEY),
    ("OPEN_AI_API", config.OPEN_AI_API),
    ("GROQ_API_KEY", config.GROQ_API_KEY),
]

@app.on_event("startup")
async def check_config():
    missing = [name for name, val in REQUIRED_VARS if not val]
    if missing:
        print(f"ERROR: Missing env vars: {', '.join(missing)}")
        sys.exit(1)

You know you got it right when removing OPEN_AI_API from .env and restarting causes the server to exit with a clear error listing the missing variable.

Hard Build a /health endpoint that checks all external services

Problem: Create a GET /health endpoint that checks whether Supabase, Stripe, and the OpenAI API are reachable, and returns a JSON summary like {"supabase": "ok", "stripe": "ok", "openai": "ok"}. Each check should time out after 3 seconds and return "error" if it fails.

Hints

Use asyncio.gather() with return_exceptions=True to run all three checks in parallel. For Supabase, try a simple .select("id").limit(1) on any table. For Stripe, call stripe.Balance.retrieve(). Wrap each in a try/except that returns "ok" or "error".

Solution 
import asyncio
import stripe
from openai import AsyncOpenAI

@app.get("/health")
async def health_check():
    async def check_supabase():
        try:
            get_service_db().table("manager_profiles").select("user_id").limit(1).execute()
            return "ok"
        except: return "error"

    async def check_stripe():
        try:
            await asyncio.to_thread(stripe.Balance.retrieve)
            return "ok"
        except: return "error"

    results = await asyncio.gather(
        check_supabase(), check_stripe(), return_exceptions=True
    )
    return {"supabase": results[0], "stripe": results[1]}

You know you got it right when GET /health returns {"supabase": "ok", "stripe": "ok"} in under 3 seconds, and returns "error" for any service with wrong credentials.
