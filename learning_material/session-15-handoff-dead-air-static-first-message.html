The Six-Second Silence — When a Handoff Forgot to Pass the Mic

Last session we taught the lease agent to hand French callers off to a dedicated French assistant. It worked — on the first test call. On the second call, the French assistant picked up, said "Parfait, je vous mets en relation avec mon collègue francophone tout de suite," ("I'll connect you to my French colleague right away") … and then went silent for six seconds. Nobody spoke. The whole session is the hunt for why a single line of generated speech could freeze a call — and why it broke on call two but not call one. The answer is a tour through how Vapi opens a handed-off call, how an LLM can leak the framing of a conversation into its first words, and why a coin-flip of temperature made the bug intermittent. The fix is four small edits and a one-command redeploy.

🔴 Advanced ⏱️ ~70 min read / build 📋 Requires: Session 14 (the French handoff & language gate); helpful: Sessions 10–11 (latency, dead air)

📦 Session Overview

This was a diagnosis-and-hotfix session. There was no new feature — we made a feature that already shipped actually feel right. A native-French partner did two test calls against the live agent built in Session 14. Call one was smooth. Call two had a jarring gap. The user brought us the transcript and one question:

You: my french partner did a test call, it worked in the first call, but in the second call... "Parfait, je vous mets en relation avec mon collègue francophone tout de suite," ... there was silence for 6 seconds... why was that

By the end of the session we had, live on all four manager lines:

  • A precise root cause for the silence — not a guess. We traced it to the French assistant's opening line being generated by the model instead of being a fixed script, which let it announce a transfer that never happens and then wait for nobody.
  • A deterministic French opener — the French assistant now always says one fixed sentence that ends in a question, so the caller is always invited to speak. No more dead air, no more generation lag.
  • A hardened prompt — the continuation note now explicitly forbids the assistant from ever announcing a transfer or mentioning a "colleague."
  • A plumbing fix — the field that carries that fixed opener (firstMessage) was never actually being sent to Vapi by our deploy scripts; we added it to both.
  • A verified live deploy — re-provisioned all four French assistants and confirmed by reading the live config straight back from Vapi's API.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Explain Vapi's three firstMessage modes and when a model-generated opener is a liability rather than a convenience.
  • Describe what happens — and how long it takes — when a call is handed off to a fresh assistant (the "cold start").
  • Recognise context leakage: how carrying an entire conversation into a second assistant can bias what it says first.
  • Diagnose dead air as a turn-taking failure — nobody holding the "conversational floor" — and fix it by always ending a turn with a question.
  • Explain why LLM temperature made the bug intermittent ("worked the first call, not the second"), and why determinism is the cure.
  • Read a call transcript forensically — timestamps, speaker labels, and a trailing comma — to reconstruct what the software did.
  • Scope a new field to a subset of agents safely using None-filtering, leaving the English path byte-for-byte unchanged.

🌉 Recap Bridge — where we left off

Our product is a CRM (Customer Relationship Management — the web app a property manager uses to track buildings, units, tenants, and leads). It runs an AI voice agent called Max that answers a phone line, talks to a prospective renter, finds the unit they want, and saves a lead. Max lives on Vapi (a hosted "Voice API" that wires a phone number to three swappable pieces — a transcriber that turns speech into text, a model / LLM that decides what to say, and a voice that speaks the reply).

Session 14 solved a hard constraint: a phone call's transcriber language is locked the instant the call connects, so you cannot "switch to French" mid-call. The fix was routing. Each manager's existing bilingual assistant became an entry assistant that opens with a spoken language gate ("English or French? / Anglais ou français?"). On a French choice it fires a Vapi handoff tool that transfers the live call to a second, French-only assistant (Deepgram nova-3 set to language:"fr"). The handoff carries the whole conversation across (contextEngineeringPlan:{type:"all"}) so the French assistant continues the call rather than restarting it. We shipped it live to all four per-manager agents with a one-command rollback standing by.

That is exactly where this session begins: the handoff fires correctly — the call really does move to the French assistant. The problem is the very first thing the French assistant says once it takes over. Session 14 even flagged this as the thing to watch: its open question #1 was "Exact French-assistant first-message behavior on handoff (continue vs. re-greet) — settle from the pilot transcript." This session is us settling it, the hard way — from a transcript with a six-second hole in it.

🧠 Concepts Introduced This Session

Seven ideas, and they stack into the bug. C1 is the knob we got wrong (who writes the first line). C2 and C3 explain the two halves of the gap (the cold-start lag, then the wrong words). C4 explains why the wrong words freeze the call. C5 explains why it only happened sometimes. C6 is the skill that let us see all of it (reading the transcript). C7 is the small, safe way we shipped the fix.

1 · Who speaks first: the three firstMessage modes

Plain-English explanation. Every Vapi assistant has a setting that decides how it opens a call — its firstMessageMode. There are three choices. assistant-speaks-first means it speaks a fixed, pre-written sentence you supply in a firstMessage field. assistant-speaks-first-with-model-generated-message means it speaks first, but the LLM writes the opening line on the fly each call. assistant-waits-for-user means it stays quiet until the caller talks. Our French assistant was on the middle one — the model improvised its opener — and that improvisation is the whole bug.

Why we need it (for CRM specifically). For the entry assistant, a model-generated opener is genuinely nice: it can weave in the manager's name ("I'm Max, the AI leasing assistant for Sean Siri") and ask the language-gate question in a natural way, fresh each call. But the French assistant has exactly one job on its first turn — greet and ask what the caller wants. There is nothing to improvise. Letting the model write that line buys us no flexibility and, as we'll see, hands it a loaded gun.

How it works (analogy). Think of a stage actor. assistant-speaks-first is reading a scripted line off the page — same every night. The model-generated mode is improv: the actor invents the opening line based on whatever just happened in the scene. Improv is great for a lead who needs to react — and a disaster for a stagehand whose only line is "Right this way, what are you looking for?" Give the stagehand the script.

Jargon decoder.

  • firstMessageMode — the Vapi assistant setting choosing how the assistant opens: fixed line, generated line, or silence.
  • firstMessage — the fixed text spoken when the mode is assistant-speaks-first. (Ignored by the generated mode — which is why nobody had set it.)
  • LLM (Large Language Model) — the AI "brain" (here OpenAI gpt-5.2-chat-latest) that produces the assistant's words.

Here is the shared "shell" every lease assistant is built from. Notice the mode — and notice what's missing:

def _lease_assistant_shell(name, system_prompt, tools, backend_url=BACKEND_URL,
                           transcriber=None):
    return {
        "name": name,
        # The model improvises the opening line every call. Good for the entry
        # assistant's bilingual greeting -- but the French assistant inherits it too.
        "first_message_mode": "assistant-speaks-first-with-model-generated-message",
        # NOTE: there is NO "first_message" key here at all. Nothing to fall back to.
        "voicemail_message": "...",
        "transcriber": transcriber or TRANSCRIBER_CONFIG,
        # ...voice, model (gpt-5.2-chat-latest, temperature 0.7), tools, server...
    }
🔑 Key Concept — a "convenience" default is a decision in disguise

The French assistant didn't choose a generated opener — it inherited one from the shared shell because nobody overrode it. Shared defaults are great for consistency, but every assistant that reuses a shell silently adopts its choices. When a new assistant has different needs (here: a scripted opener), you must consciously override, not assume the default fits.

2 · The handoff cold-start (why ~2.3 seconds passed before it spoke)

Plain-English explanation. A handoff isn't a single brain changing topic — it's a second, separate assistant taking over a live call. That second assistant has its own transcriber, its own model session, and its own voice connection, and none of them exist yet at the moment of handoff. They have to be spun up: open a fresh Deepgram nova-3 fr websocket, start a model session, connect the text-to-speech voice. Then, because our mode was "generate the opener," the model also had to read the entire carried-over conversation and write a sentence before a single word could be spoken. All of that is the ~2.3-second gap between "handoff completed" and the French assistant's first audio.

Why we need it (for CRM specifically). Understanding this gap tells you which delay you can remove and which you can't. The websocket/voice spin-up is structural — it comes with handing off. But the "read the whole transcript and compose a line" delay is optional: it only exists because we asked the model to generate the opener. Switch to a fixed line and that part of the latency vanishes. So this concept is half the motivation for the fix.

How it works (analogy). A warm transfer in a call centre: when Agent A passes you to Agent B, B has to pull up your file, put on their headset, and read what's happened before they can greet you. If B also insists on composing a bespoke greeting from your whole history before speaking, you wait even longer. A B who just says their standard "Hi, you're through to the French desk — what are you after?" greets you instantly.

Jargon decoder.

  • cold start — the one-time setup cost of a resource that wasn't running yet (here, the destination assistant's whole audio pipeline).
  • websocket — a persistent two-way network connection; Deepgram streams audio over one. Opening it takes a beat.
  • TTFT (Time To First Token) — how long the model takes to produce the first word of its reply. Generating an opener from a long transcript raises it.

Reading the timestamps straight from the transcript shows the two delays clearly:

11:13:00 (+19.36) Handoff To 8900a5c4-… Completed successfully 11:13:03 (+21.71) Lease Agent FR: "Parfait, je vous mets en relation…" <- ~2.3s cold start + generation 11:13:03 → ~11:13:09 ······ six seconds of silence ······ <- the real bug (see C4)
💡 Tip — separate the two gaps

There were two delays, and conflating them sends you down the wrong rabbit hole. The ~2.3s before the French line is cold-start + generation (partly unavoidable). The ~6s after the line is the dead air we actually have to fix. The user's question was about the second one — but understanding the first kept us honest about what the fix could and couldn't speed up.

3 · Context leakage — when carrying the conversation backfires

Plain-English explanation. To make the French assistant continue the call smoothly, the handoff carries the entire conversation so far into it (contextEngineeringPlan:{type:"all"}). That's usually what you want — it knows the caller already chose French. But it has a side effect: when the model then composes its opening line, it can see that a routing/transfer just happened, and it pattern-matches to that framing. Instead of greeting as the destination, it role-plays the router again — "I'll connect you to my French colleague" — as if it were still the entry agent passing the call onward. The framing of the prior turns leaked into its first words.

Why we need it (for CRM specifically). This is the subtle one, and it's exactly why a model-generated opener was dangerous here specifically. The carried context is full of language-gate / hand-off cues. A model improvising on top of that context is being nudged toward "announce a transfer." The continuation note we wrote in Session 14 told it to greet-and-ask — but a soft instruction competes with a strong contextual pattern, and at temperature 0.7 (see C5) the context sometimes wins.

How it works (analogy). You ask a new hire to introduce themselves to a customer, and hand them the full email thread first. Half the thread is the previous rep saying "let me loop in a French speaker." The new hire skims it and opens with "Hi, I'll get you over to our French speaker" — echoing the thread's vibe instead of realising they are the French speaker. The context they were given to help them shaped what they said, wrongly.

Jargon decoder.

  • contextEngineeringPlan — the Vapi setting controlling how much prior conversation is carried to a handoff destination. {type:"all"} = carry everything.
  • context leakage — when information meant as background ends up steering the output in an unintended way.
  • system prompt — the standing instructions for an assistant; ours appends a [French Call — Continuation] note telling the FR assistant how to behave.
⚠️ Warning — a soft prompt does not reliably beat a strong context cue

"I told it in the prompt not to do that" is not a guarantee. An LLM weighs everything in its window — your instruction and the conversation it can see. When the surrounding context strongly suggests one behaviour, a single polite instruction may lose. The robust fix removes the model's discretion entirely (a fixed line); the hardened prompt is a belt-and-suspenders backup.

4 · The conversational floor — why a wrong line caused silence

Plain-English explanation. In any conversation, exactly one party "has the floor" — it's their turn to talk — and a turn usually ends in a way that hands the floor to the other side, most clearly by asking a question. When the French assistant said "I'll connect you to my colleague right away," it did two damaging things: it implied someone else is about to speak, and it ended on a trailing comma with no question. So the assistant fell silent, expecting the (non-existent) colleague to come on. The caller fell silent too, politely waiting to be connected. Neither side held the floor. That stalemate is the six seconds of dead air.

Why we need it (for CRM specifically). This reframes the fix. The cure for dead air isn't "make the model talk more" — it's "make sure every turn that needs a reply ends by inviting one." A greeting that ends in "…what are you looking for?" structurally cannot cause this stall: the caller is explicitly cued to speak. Session 11 fought dead air around tool calls; this is the same disease in a new spot — the handoff seam.

How it works (analogy). A walkie-talkie. You end your turn with "over" so the other person knows to talk. The bad line was like releasing the button after "I'll get my colleague…" without saying "over" — both people sit there holding their radios, waiting for the other. The good line ends with a clear "over" (the question).

Jargon decoder.

  • turn-taking — the implicit protocol of who talks when in a conversation.
  • conversational floor — the right/expectation to be the one speaking at a given moment.
  • dead air — broadcast/telephony term for unwanted silence when someone should be talking.
  • endpointing — the engine's judgement of "the user has stopped talking, it's our turn." Irrelevant here because the caller, cued to wait, never started — there was nothing to endpoint.

Look at the offending line. The diagnosis is in the punctuation and the missing question mark:

Lease Agent FR: "Parfait, je vous mets en relation avec mon collègue francophone tout de suite," └─ implies a 3rd party is coming + trailing comma, no question = floor dropped on the floor
🔑 Key Concept — design every agent turn to end by handing back the floor

The most reliable anti-dead-air rule for a voice agent: if a turn expects a response, it must end on a question. This is a conversation-design invariant, not a model tuning trick. Our fixed opener bakes it in — it literally ends with "…?" — so the failure mode is structurally impossible, not merely discouraged.

5 · Non-determinism & temperature — why call one worked, call two didn't

Plain-English explanation. An LLM doesn't return the same answer every time. A setting called temperature controls how much randomness it injects when picking each next word. At temperature 0.7 (our value) the model deliberately varies — so the same situation can yield a correct greet-and-ask on one call and a wrong transfer-announcement on the next. That is precisely the user's report: "it worked in the first call, but in the second call…". The bug wasn't random gremlins; it was a non-deterministic opener rolling the dice and losing the second time.

Why we need it (for CRM specifically). "Works sometimes" is the signature of a non-determinism bug, and it's the strongest clue that the culprit is generated content rather than fixed code. It also dictates the fix: you cannot reliably patch a dice roll by re-rolling with slightly better instructions; you make the value deterministic. A fixed firstMessage removes the dice from the one turn that can't afford them.

How it works (analogy). Temperature is how loosely a jazz musician improvises. High temperature = wild, surprising solos; low = plays it straight. Improvisation is wonderful for a solo, terrible for the safety announcement before take-off — that one you read verbatim, every flight. The French opener is a safety announcement.

Jargon decoder.

  • temperature — a 0–1+ knob on LLM sampling; higher = more random/creative, lower = more predictable. Ours is 0.7.
  • deterministic vs non-deterministic — same input → always same output, vs same input → possibly different outputs.
  • intermittent bug — one that doesn't reproduce every time; the hardest kind, and a fingerprint of randomness or timing.
📖 Deep Dive — "it's flaky" is diagnostic information, not noise

When a stakeholder says "it happened once but not again," resist the urge to call it unreproducible and move on. Intermittency narrows the search dramatically: it points at sources of variation — randomness (LLM sampling), timing (races, cold starts), or environment differences. Here, "worked then didn't" with identical config pointed straight at the one non-deterministic element in the path: the model writing the opener. Lowering temperature would reduce the odds; removing generation eliminates them. Prefer eliminating a class of failure over making it rarer.

6 · Reading a transcript forensically

Plain-English explanation. A Vapi call transcript isn't just a chat log — it's a timestamped event record, and you can reconstruct what the software did from it. Three details cracked this case: (1) the speaker label flipped from "Lease Agent" to "Lease Agent FR" right after the "Handoff … Completed successfully" event, proving the handoff really fired and the French line came from the destination assistant; (2) the timestamps separated cold-start lag from dead air; (3) the trailing comma on the French line hinted the utterance was a dangling announcement, not a complete, floor-handing turn.

Why we need it (for CRM specifically). Voice bugs are ephemeral — you can't set a breakpoint in a phone call. The transcript (plus call logs) is your crime scene. Learning to read the labels and the clock is how you separate "the handoff is broken" (it wasn't) from "the destination's first line is wrong" (it was). That distinction saved us from re-engineering the routing we'd just shipped.

How it works (analogy). A flight recorder. You don't watch the crash happen; you read the timestamped instrument trace afterwards and rebuild the sequence. The label flip is the cockpit handover; the clock is the timeline; the dangling comma is the last reading before the silence.

Jargon decoder.

  • speaker label / diarization — the transcript's attribution of each line to a party; here it even names which assistant spoke ("Lease Agent" vs "Lease Agent FR").
  • handoff event — the explicit "Handoff To <id> — Completed successfully" marker the transcript logs at the transfer.
  • relative timestamp — the (+MM:SS.ss) offset from call start; subtract two to measure a gap.

7 · Scoping a field with None-filtering (English untouched, again)

Plain-English explanation. We needed to start sending a new field, firstMessage, to Vapi — but only for the French assistants, never for the English entry assistants. The trick: the function that builds the API payload already drops any key whose value is None. So we set first_message only inside the French builders; the English builders never set it, it comes out as None, and the filter removes it before the request is sent. One mapper line serves both — French gets the field, English provably doesn't.

Why we need it (for CRM specifically). Same constraint as Session 14: do not touch the English path. If we'd put first_message in the shared shell, every assistant (English included) would suddenly get a fixed French opener — catastrophic. None-filtering lets one shared payload mapper carry an optional field that's present for some agents and absent for others, with the absence being a provable fact, not a hope.

How it works (analogy). A customs form with an optional "items to declare" box. If you have nothing, you leave it blank and the officer ignores it — same form, same process, no extra handling. The French agents declare a first message; the English agents leave the box blank.

Jargon decoder.

  • None — Python's "no value." Our payload builder treats a None value as "don't send this field."
  • dict comprehension — the one-liner {k: v for k, v in d.items() if v is not None} that rebuilds a dict keeping only non-None entries.
  • payload mapper — the function (_to_vapi_payload) that converts our internal snake_case config into Vapi's camelCase JSON.

We started with the artifact, not the code. The user pasted the second call's transcript. We read it as a timeline (see Concept 6) and pinned down the exact failing moment: the French assistant's first line, then six seconds of nothing.

Why now: you cannot fix what you haven't located in time. If skipped: you guess, and a voice bug has a dozen plausible-but-wrong causes (network, TTS, endpointing, the handoff itself).

Step 2 — Locate the French handoff code

We searched the repo for the French/handoff machinery and read the three files that matter: the provisioning script, the routing plan, and the config builders.

Step 4 — Edit ①: add a fixed opener + harden the continuation note

We added a constant for the deterministic French opener and rewrote the continuation note to forbid transfer talk and demand a question.

# A fixed opener for the FRENCH assistant. Deterministic (no model dice), and it
# ENDS ON A QUESTION so the caller is always cued to speak -> no dead air.
_LEASE_FRENCH_FIRST_MESSAGE = "Parfait, je continue en français. Qu'est-ce que vous cherchez comme logement?"


# Appended to the FRENCH assistant's system prompt. Now it forbids the failure mode.
_LEASE_FRENCH_CONTINUATION_NOTE = """

[French Call — Continuation]
You ARE the French-speaking leasing assistant — the caller has already been routed to you. NEVER say
you will transfer, connect, or hand them to anyone, and never mention a "collègue" — there is no one
else; you handle the whole call. The caller just chose French at the language gate and has NOT yet
said what they are looking for. Your opening line greets them and asks what they're looking for, and
every turn that needs a reply must end with a question so the caller knows to speak. Use the formal
vous. The entire call stays in French; never switch to English.
"""

Why now: the constant and note are referenced by Edit ② next. If skipped: the builder edit would reference an undefined name.

Step 5 — Edit ②: override the mode in both French builders

The builders call the shared shell (which sets the generated mode), then override the two keys. Same change in the per-manager and shared French builders.

def build_lease_config_french(backend_url, manager_id,
                              manager_name="our property management team"):
    tools = _alias_apirequest_tool_names(_build_lease_tools(backend_url, manager_id=manager_id))
    context_block = _LEASE_CONTEXT_BLOCK.format(manager_id=manager_id, manager_name=manager_name)
    system_prompt = _LEASE_SYSTEM_PROMPT_BASE + context_block + _LEASE_FRENCH_CONTINUATION_NOTE
    cfg = _lease_assistant_shell(                       # shell still returns the generated mode...
        name=f"Lease Agent FR [{manager_id[:8]}]",
        system_prompt=system_prompt, tools=tools, backend_url=backend_url,
        transcriber=FRENCH_TRANSCRIBER_CONFIG,
    )
    cfg["first_message_mode"] = "assistant-speaks-first"   # ...override: speak a FIXED line
    cfg["first_message"] = _LEASE_FRENCH_FIRST_MESSAGE     # ...the line itself (deterministic)
    return cfg

Why now: this is the core behaviour change. If skipped: nothing else matters — the opener stays generated.

Step 6 — Edit ③: actually send firstMessage to Vapi

Then the quiet bombshell (Bug 2): the deploy scripts' payload mappers sent firstMessageMode but never firstMessage. So even a correct config wouldn't reach Vapi. We added one line to both mappers.

    payload = {
        "name": cfg.get("name"),
        "firstMessageMode": cfg.get("first_message_mode"),
        "firstMessage": cfg.get("first_message"),     # ADDED — without this, the fixed line never ships
        "voicemailMessage": cfg.get("voicemail_message"),
        # ...rest unchanged...
    }
    # None-filter: English agents set no first_message -> key dropped -> English path untouched.
    return {k: v for k, v in payload.items() if v is not None}

Why now: the fix is inert until the field is transmitted. If skipped: "I changed the config but the call still misbehaves" — the worst kind of silent no-op.

🐛 Bug Journal

Four bugs, in descending order of nastiness: the one we were hired to fix, the silent no-op hiding behind it, the rotten test baseline, and a fake bug that wasn't a bug.

Bug 1 — The six-second silence after handoff

🚨 The Symptom

On the second French test call (the first was fine), right after the handoff completed, the French assistant said one line and then nothing happened for six seconds:

Lease Agent: Hi there. I am Max, the AI leasing assistant for Sean Siri. Would you like to continue in English or in French? Préférez-vous… User: Uh, we're in Wisconsin. Lease Agent: English or French? / anglais ou français? User: Oui français. Handoff To 8900a5c4-… — Completed successfully Lease Agent FR: Parfait, je vous mets en relation avec mon collègue francophone tout de suite, ······ [ 6 seconds of silence ] ······
🔍 The Diagnosis

The exact steps we took:

  1. Confirmed the handoff fired. The speaker label flips to "Lease Agent FR" right after "Handoff … Completed successfully" — so routing works; the bad line comes from the destination assistant, not the entry one. This ruled out "the handoff is broken."
  2. Measured the two gaps. Handoff at +19.36s, French line at +21.71s (~2.3s), then ~6s silence. Two different problems: a cold-start delay (partly unavoidable) and the dead air (the real target). We focused on the dead air.
  3. Read the line itself. "Je vous mets en relation avec mon collègue francophone" = "I'll connect you to my French colleague." But the French assistant is that colleague. It was role-playing the router. And it ended on a comma — no question — so it handed the floor to no one.
  4. Found the mechanism in code. The French assistant inherited first_message_mode = assistant-speaks-first-with-model-generated-message from the shell, and the handoff carries the whole transcript (contextEngineeringPlan:{type:"all"}). So the model improvised an opener off a context full of "transfer" cues — and improvised a transfer announcement.
  5. Explained the intermittency. Generation runs at temperature 0.7. Non-deterministic → correct greeting on call one, wrong announcement on call two. The "worked then didn't" report was the diagnosis confirming itself.

Red herring considered & rejected: "maybe the new nova-3 fr transcriber didn't hear the caller." Rejected because the caller, told someone was coming, never spoke — so there was nothing to transcribe. The silence was a turn-taking stall, not a missed transcription.

🧠 The Root Cause

A model-generated first message on the handoff destination, composing its opener from a carried context saturated with routing/transfer framing (context leakage), at a non-zero temperature that made it intermittent. The improvised line announced a transfer that doesn't exist and ended without a question, so neither party held the conversational floor → six seconds of dead air. The class of bug: letting an LLM improvise a turn that has exactly one correct, fixed form.

🔧 The Fix

Make the opener deterministic, and forbid the failure mode in the prompt.

    # build_lease_config_french(): returns the shell as-is
    return _lease_assistant_shell(
        name=f"Lease Agent FR [{manager_id[:8]}]",
        system_prompt=system_prompt, tools=tools, backend_url=backend_url,
        transcriber=FRENCH_TRANSCRIBER_CONFIG,
    )
    # mode = ...with-model-generated-message  (inherited)  -> model improvises the first line
    cfg = _lease_assistant_shell(
        name=f"Lease Agent FR [{manager_id[:8]}]",
        system_prompt=system_prompt, tools=tools, backend_url=backend_url,
        transcriber=FRENCH_TRANSCRIBER_CONFIG,
    )
    cfg["first_message_mode"] = "assistant-speaks-first"   # no improvisation on this turn
    cfg["first_message"] = _LEASE_FRENCH_FIRST_MESSAGE     # "...Qu'est-ce que vous cherchez ?" (ends on a question)
    return cfg

Plus the hardened note (Step 4) that bans "je vous mets en relation" / "collègue" outright, as a backup against any residual generation.

🛡️ The Lesson

Three transferable principles. (1) If a conversational turn has exactly one correct form, don't let the model write it — script it. Reserve generation for turns that genuinely need to adapt. (2) "Works sometimes" = look for non-determinism (LLM sampling, timing) and remove it, don't just discourage it. (3) Carrying context into a handoff helps continuity but can steer the first output — when you carry context, pin down the opening turn.

Bug 2 — The fixed line that would never have shipped

🚨 The Symptom

Latent, not yet observed — we caught it while writing the fix. Setting first_message in the config would have had zero effect on the live agent, even after deploy.

🔍 The Diagnosis

We read both deploy scripts' _to_vapi_payload mappers and noticed they translated first_message_mode → firstMessageMode but had no line for firstMessage at all. The mapper is an explicit allow-list; any key not listed is silently never sent. So our new fixed opener would sit in the config dict and quietly get dropped before the HTTP request.

🧠 The Root Cause

An allow-list payload mapper only forwards fields it explicitly names. firstMessage was never needed before (nothing set it), so it was never added. New config field + un-updated mapper = silent no-op. This is the dual of Session 14's lesson about the Vapi SDK dropping fields — here it's our own mapper doing the dropping.

🔧 The Fix

Add "firstMessage": cfg.get("first_message") to both mappers (Step 6). The existing None-filter keeps it scoped to French agents automatically.

🛡️ The Lesson

When you add a config field, trace it all the way to the wire. An allow-list serializer is a common silent-drop point. The cheap guard is exactly what we did in Step 7: assert the field is present in the built payload before deploying, so a forgotten mapper line fails loudly on your laptop, not silently in production.

Bug 3 — Ten unit tests already red on arrival

🚨 The Symptom

Our very first pytest run, before any edit, showed 10 failed, 21 passed.

🔍 The Diagnosis

We read the failing assertions. They expected tools named load_listings / find_listing and a top-level first_message key — all from an older lease-agent design that was since replaced by find_units / search_listings (and the entry assistant's generated greeting, with no first_message). The tests were never updated when the design changed, so they fail against current code.

🧠 The Root Cause

Test rot. Production code evolved; the tests didn't follow. They now assert a contract that no longer exists, so they're noise, not signal.

🔧 The Fix

Deliberately scoped out for this hotfix. Rewriting ten stale assertions is its own task and unrelated to the silence bug; bundling it would muddy the change and its review. We instead baselined (Step 3) and confirmed our edits added zero new failures (Step 9). Fixing the suite is filed as Exercise 🔴.

🛡️ The Lesson

A red test suite that everyone ignores is worse than none — it hides real regressions in the noise. When you find pre-existing failures mid-task, baseline and diff rather than getting derailed, but file the cleanup so the rot doesn't compound. Tests are a contract; when the contract changes, the tests are part of the change.

Bug 4 — The fake mojibake (a bug that wasn't)

🚨 The Symptom

Our verification printout showed the opener as "Parfait, je continue en fran�ais…" — a replacement character where the ç should be. Looks like classic encoding corruption.

🔍 The Diagnosis

We'd seen this ghost before, so we didn't trust the eyes — we checked the bytes. Opening the source file as UTF-8 and testing "français" in line returned True. The string in memory was perfect; only the display was wrong.

🧠 The Root Cause

The Windows console (code page 1252) can't render the UTF-8 bytes for ç, so it draws a �. The file, the Python string, and what we sent to Vapi were all correct UTF-8. It's a rendering artifact at the terminal, not data corruption — confirmed again live, where Vapi returned the ç intact.

🔧 The Fix

None — there was nothing to fix. The "fix" is the method: verify the underlying bytes before believing a terminal's depiction of them.

🛡️ The Lesson

Distinguish data from its presentation. A garbled glyph in a console is a claim, not proof. Test the bytes ("français" in s, a hex dump, a length check) before re-encoding anything — otherwise you "fix" a healthy file and introduce the very corruption you imagined.

🧯 Troubleshooting / Common Errors

The FR assistant still announces a transfer / mentions a "collègue"

The PATCH didn't reach that assistant, or you patched the wrong one. GET the assistant by id and check firstMessageMode is assistant-speaks-first and firstMessage is the fixed line. Re-run the provisioner; confirm the id in the dry-run matches the handoff target in the transcript.

Config looks right locally but the live call is unchanged

Classic Bug 2: the field isn't being transmitted. Confirm "firstMessage": cfg.get("first_message") exists in the deploy script's _to_vapi_payload, and that a built payload actually contains the key (Step 7). Also confirm you ran the script with the backend venv python, not base python.

ModuleNotFoundError: No module named 'supabase'

You ran the script with the wrong interpreter. The fleet path imports supabase, which only exists in the backend virtualenv. Use backend/.venv/Scripts/python.exe …, not a bare python.

The provisioner refuses to run with --all

The fleet rollout is guarded: it requires --confirm-fleet (acknowledging the DB column exists and the pilot was validated). Add it. To preview safely first, append --dry-run.

HTTP 401 from api.vapi.ai

Missing/!wrong API key. The script reads PRIVATE_VAPI_API from backend/.env. Confirm it's set and current.

Accented French shows as fran�ais in my terminal

Almost certainly Bug 4 — a Windows console rendering artifact, not corruption. Verify the bytes: "français" in open(path, encoding="utf-8").read(). If that's True, your data is fine; ignore the console glyph.
