Section 1 — What You Are Building

The leasing module serves two very different audiences from a single route file. VAPI voice agents need unauthenticated search endpoints to answer caller questions ("what 2-bedroom units do you have under $3000?"). Managers need authenticated CRUD endpoints to manage listings and track leads through a qualification pipeline. One file, two audiences, carefully separated.

leasing.py route map: VAPI TOOL ENDPOINTS (no auth, service DB, always return 200): GET /leasing/find-listing?query=... → exact/fuzzy flat search GET /leasing/search?bedrooms=2&budget_max=3000 → filter by criteria MANAGER CRUD (auth required, subscription gate): GET /leasing/listings → list manager's listings POST /leasing/listings → create listing PATCH /leasing/listings/{uuid} → update listing DELETE /leasing/listings/{uuid} → delete listing GET /leasing/leads → list leads (with filters) PATCH /leasing/leads/{uuid} → update lead status/notes DELETE /leasing/leads/{uuid} → delete lead GET /leasing/metrics?days=30 → call volume + qualification stats GET /leasing/export → CSV download of leads Lead qualification state machine: (VAPI creates lead) new → qualified / not_qualified / unmatched ↓ (manager moves) contacted → toured → converted → lost

Section 2 — Concept Deep-Dives

Dual-audience route design — VAPI vs manager

The biggest architectural decision in this file: should VAPI endpoints live in a separate file from manager endpoints? The answer was no — they share the same /leasing prefix and the same DB tables. Keeping them together makes it easier to see the full picture of what the leasing system does.

The key difference is authentication:

AspectVAPI endpointsManager endpoints
AuthNone — voice agents can't hold tokensrequire_active_subscription
DB clientget_service_db (service role)get_authenticated_db or get_service_db
Error handlingAlways return 200 with found: falseStandard HTTP errors (400, 404, 500)
Who calls itVAPI voice agent toolReact frontend

VAPI endpoints have no authentication — they're publicly accessible. This is acceptable because they return only publicly-listable data (available listings). They cannot create or modify anything. Never put mutation operations on VAPI-style endpoints.

The VAPI empty-string parameter problem

VAPI's voice agent extracts parameters from conversation. If a caller says "I need a 2-bedroom apartment" but doesn't mention budget, VAPI sends budget_max="" (empty string) — not budget_max=null or omitting the parameter entirely.

This breaks normal Python int() and float():

int("")    # ValueError: invalid literal for int() with base 10: ''
float("")  # ValueError: could not convert string to float: ''
int("0")   # works, but 0 means "no filter" in this context

The solution: _parse_int() and _parse_float()

def _parse_int(v):
    try:
        n = int(v)
        return n if n > 0 else None   # 0 means "unspecified" → None
    except (TypeError, ValueError):
        return None                     # "" or None → None

_parse_int("")    # None
_parse_int("2")   # 2
_parse_int("0")   # None (VAPI sends "0" for unspecified)
_parse_int(None)  # None

These helpers turn VAPI's quirky empty-string / zero encoding into proper Python None, which then cleanly maps to "skip this filter".

Three-path search strategy in find_listing

A caller might say "find the apartment on Maple Street" or "find unit A-101" or "find the south wing". The search tries three increasingly broad strategies in sequence, returning early as soon as something matches.

find_listing(query="maple"): Path 1: .ilike("flat_number", "%maple%") → fast — DB-level filter — most specific → if results: return immediately Path 2: .ilike("title", "%maple%") → DB-level filter on listing title → if results: return immediately Path 3: load all active listings (up to 20), filter in Python → checks: flat.address, building.name, building.address, listing.title → catches: "3rd floor, South Block, Maple Tower" → most flexible but does more work

Path 1 and 2 push the filter to the DB (efficient). Path 3 is a Python-side filter applied after fetching all rows — it handles multi-field address matching that PostgREST's .ilike() can't express in a single call. The 20-row limit on Path 3 prevents excessive memory use.

JSONB custom_rules — nested Pydantic → dict

Each listing can have custom tenant rules (max occupants, pets policy, etc.) stored as JSONB in Postgres. In Python, this is modeled as a nested CustomRules Pydantic model. But Supabase's SDK doesn't accept Pydantic objects — it needs plain dicts.

class CustomRules(BaseModel):
    max_occupants: Optional[int] = None
    income_required: Optional[bool] = False
    pets_allowed: Optional[str] = "no"
    vegetarian_only: Optional[bool] = False
    lease_term_months: Optional[int] = 11
    custom_question: Optional[str] = ""

# In the route, before DB insert:
payload = body.model_dump(exclude_none=True)
if "custom_rules" in payload and hasattr(payload["custom_rules"], "model_dump"):
    payload["custom_rules"] = payload["custom_rules"].model_dump()

body.model_dump() converts the top-level model to a dict, but custom_rules remains a CustomRules Pydantic object inside the dict (model_dump is shallow for nested models unless you use mode="json"). The hasattr(..., "model_dump") check detects this and calls .model_dump() on the nested object to convert it to a plain dict that Supabase accepts.

Decimal type and JSON serialization

monthly_rent uses Pydantic's Decimal type for precision (avoids floating point errors common with float). But Decimal objects are not JSON-serializable and Supabase's REST client rejects them.

from decimal import Decimal

# After model_dump(), fix Decimal values:
payload = {k: float(v) if isinstance(v, Decimal) else v for k, v in payload.items()}

# This converts: {"monthly_rent": Decimal("2500.00")} → {"monthly_rent": 2500.0}

The dict comprehension converts all Decimal values to float in one pass. The loss of arbitrary precision is acceptable here — rent values like 2500.00 are represented exactly as float64.

exclude_none vs exclude_unset in Pydantic

This distinction is critical when building CRUD APIs. Getting it wrong silently overwrites data.

MethodExcludesUse case
model_dump(exclude_none=True)Fields where value IS NoneCREATE — include all fields the user provided, skip ones they left as None
model_dump(exclude_unset=True)Fields the user did NOT send in the requestPATCH — only update fields explicitly sent; leave others untouched in the DB
# PATCH request body: {"title": "New Title"} (only title is being changed)

# With exclude_none=True:
# monthly_rent defaults to None in the model → excluded ✓
# But if monthly_rent was EXPLICITLY sent as null → also excluded ✗

# With exclude_unset=True:
# Only {"title": "New Title"} is in the payload
# monthly_rent was not sent → excluded ✓ (DB keeps its current value)
# If someone sends null explicitly → {"monthly_rent": null} is included ✓

The CREATE endpoint uses exclude_none=True. The PATCH endpoint uses exclude_unset=True. Mixing these up is a subtle bug: using exclude_none on a PATCH would correctly send only non-null fields, but would also drop explicitly-nulled fields. Using exclude_unset on a CREATE would work but might include fields you didn't want if the model has non-None defaults.

PostgreSQL array contains operator — cs.{uuid}

A lead can be interested in multiple listings, stored as a UUID array in interested_listing_ids. To query "give me leads interested in listing X", you need the PostgreSQL @> (contains) operator.

# Supabase PostgREST syntax for array contains:
q = q.or_(
    f"listing_uuid.eq.{listing_uuid},interested_listing_ids.cs.{{{listing_uuid}}}"
)
# Breakdown:
#   listing_uuid.eq.{uuid}          → exact match on the primary listing FK
#   interested_listing_ids.cs.{uuid} → array CONTAINS the uuid
#   cs = contains, {{uuid}} = literal {uuid} in PostgREST query string

The triple braces {{{listing_uuid}}} in the f-string: the outer {{ and }} escape to literal { and } in the f-string, and the inner {listing_uuid} is the variable expansion. Result: interested_listing_ids.cs.{actual-uuid-value} — the curly braces are PostgREST's array literal syntax.

CSV export with StreamingResponse

The leads export generates a CSV in memory and streams it as a file download — no temp file needed.

import io, csv
from fastapi.responses import StreamingResponse

output = io.StringIO()           # in-memory string buffer
writer = csv.writer(output)
writer.writerow(["Name", "Phone", ...])  # header row
for lead in leads:
    writer.writerow([lead.get("caller_name", ""), ...])

output.seek(0)   # reset cursor to start before reading
return StreamingResponse(
    iter([output.getvalue()]),
    media_type="text/csv",
    headers={"Content-Disposition": "attachment; filename=leads.csv"}
)

io.StringIO() — an in-memory file-like object that accepts strings. csv.writer writes to it just like a real file. output.seek(0) resets the cursor to the beginning (after writing, the cursor is at the end — reading from there gives an empty string). Content-Disposition: attachment tells the browser to download the response as a file rather than displaying it inline.

class ListingCreate(BaseModel):

monthly_rent: Decimal — required field (no default). The Decimal type from Python's decimal module stores exact decimal numbers, unlike float which can have precision errors (e.g. 0.1 + 0.2 = 0.30000000000000004). For currency values, Decimal is the correct type.

Field(default_factory=list) — creates a new empty list for each model instance. Using default=[] would share the same list object across all instances (a classic Python mutable default bug). default_factory is always the correct way to default mutable types in Pydantic.

Field(default_factory=CustomRules) — same pattern: creates a fresh CustomRules() instance (with all fields at their defaults) for each new listing that doesn't specify custom rules.

File: backend/app/routes/leasing.py — VAPI endpoints

@router.get("/search")
async def search_available_listings(
    bedrooms: Optional[str] = Query(None),  # str not int — VAPI sends ""
    budget_max: Optional[str] = Query(None),
    address: Optional[str] = Query(None),
    property_group_id: Optional[str] = Query(None),
    manager_id: Optional[str] = Query(None),
    db: Client = Depends(get_service_db),
):
All VAPI-facing parameters are declared as Optional[str] even though logically they're numeric. This is the VAPI empty-string workaround: FastAPI would reject bedrooms="" if declared as Optional[int] (can't parse "" as int). Declaring as string lets the value through, and _parse_int() handles the normalization.

No user or subscription dependency — this endpoint is deliberately unauthenticated. VAPI agents don't carry user tokens. 
    try:
        bedrooms_filter = _parse_int(bedrooms)
        budget_filter = _parse_float(budget_max)

        q = db.table("lease_listings").select("..., flats!inner(...)").eq("is_active", True)
        if budget_filter is not None:
            q = q.lte("monthly_rent", budget_filter)
        results = q.limit(20).execute()

        for listing in results.data:
            flat = listing.get("flats") or {}
            if bedrooms_filter is not None and flat.get("bedrooms") != bedrooms_filter:
                continue

    except Exception as e:
        print(f"[ERROR] search_available_listings: {e}")
        return {"count": 0, "listings": []}
budget_filter is applied at the DB level (.lte("monthly_rent", budget_filter)) — this reduces the amount of data fetched from the DB before Python filtering.

bedrooms_filter is applied in Python after fetching — because bedrooms lives on the flats table (joined via flats!inner(...)). PostgREST can filter on joined table columns, but the syntax is complex. Python-side filtering is simpler here.

The outer try/except returning {"count": 0, "listings": []} ensures VAPI always gets a valid response, never a 500. The VAPI agent can then say "I couldn't find any available units" rather than crashing the call.

Manager CRUD — creating a listing

@router.post("/listings", response_model=ListingResponse, status_code=201)
async def create_listing(
    body: ListingCreate,
    user: dict = Depends(require_active_subscription),
    db: Client = Depends(get_authenticated_db),     # RLS client for ownership check
    svc_db: Client = Depends(get_service_db),        # service client for INSERT
):
Two DB clients injected: an authenticated (RLS-enforced) client for the ownership check, and a service-role client for the actual INSERT. Why?

The ownership check uses db (authenticated): db.table("flats").select(...).eq("uuid", flat_uuid). RLS ensures this only returns flats belonging to the logged-in manager. If the manager passes a UUID they don't own, the query returns no rows → 404 error.

The INSERT uses svc_db (service role): lease_listings had no RLS INSERT policy at the time this was written. The service client bypasses RLS and can always insert. This is a pragmatic workaround documented in the code comment. 
    flat_resp = db.table("flats").select("flat_number, building_id").eq("uuid", str(body.flat_uuid)).limit(1).execute()
    if not flat_resp.data:
        raise HTTPException(status_code=404, detail="Flat not found")

    flat = flat_resp.data[0]
    building_resp = db.table("buildings").select("property_id").eq("id", flat["building_id"]).execute()
    property_group_id = str(building_resp.data[0]["property_id"])
The route traverses the hierarchy upward: flat → building → property_group. This populates property_group_id on the listing automatically — the manager doesn't need to pass it. The manager just says "create a listing for flat X" and the system fills in which property group it belongs to.

str(body.flat_uuid) — Pydantic's UUID type stores the value as a Python uuid.UUID object. Supabase's SDK needs it as a string for the query. This is a subtle type mismatch that Python doesn't warn about — it just passes the UUID object and the query returns no results.

Updating a lead — status restriction

_MANAGER_EDITABLE_STATUSES = {"contacted", "toured", "converted", "lost"}

if "qualification_status" in payload and payload["qualification_status"] not in _MANAGER_EDITABLE_STATUSES:
    raise HTTPException(
        status_code=400,
        detail="Managers can only set status to: contacted, toured, converted, lost",
    )
Leads are created by VAPI with status qualified / not_qualified / unmatched. Managers can move a lead through the pipeline (contacted → toured → converted / lost) but should not be able to set qualified or not_qualified — those are set by the AI agent's qualification logic during the call.

This enforces the state machine boundary: the AI owns the qualification decision; humans own the follow-up workflow. Without this check, a manager could accidentally mark a lead as "qualified" when it was actually disqualified by the AI.

Section 4 — Real Bugs & How We Fixed Them

Bug 1: VAPI search crashed with ValueError: invalid literal for int()

Symptom: Voice calls where the caller didn't specify a bedroom count caused the search to crash. VAPI logs showed the call was killed with an error.

Root cause: The original code declared bedrooms: Optional[int] and did int(bedrooms). VAPI sends bedrooms="" when unspecified. FastAPI accepted "" as a string but int("") raised ValueError.

Fix: Changed parameter type to Optional[str] and added _parse_int() helper. The entire endpoint is wrapped in try/except returning {"count": 0} as a final safety net.

Bug 2: Decimal type caused json.JSONDecodeError on DB insert

Symptom: POST /leasing/listings always failed with a serialization error. The error was not from FastAPI's JSON response — it was from the Supabase Python client trying to serialize the payload.

Root cause: body.model_dump() preserves the Decimal type for monthly_rent. Supabase's SDK uses json.dumps() internally which doesn't know how to serialize Decimal objects.

Fix: Added the dict comprehension {k: float(v) if isinstance(v, Decimal) else v ...} after model_dump(). The same fix was needed in the PATCH endpoint.

Bug 3: Listing created but owned by no manager — RLS filter missed

Symptom: After switching the INSERT to use the service client (svc_db), some listings appeared in other managers' list views.

Root cause: When using the service-role client for INSERT, manager_id must be set explicitly in the payload. The original code forgot to add it after switching clients. The service client bypasses RLS, so the row was inserted without a manager_id.

Fix: Added payload["manager_id"] = user.get("sub") explicitly before the INSERT. The GET /leasing/listings endpoint filters by .eq("manager_id", user["sub"]) so the listing was invisible to all managers including the one who created it.

Bug 4: PATCH listing silently overwrote all optional fields with None

Symptom: Updating only a listing's title also cleared its available_from date and description.

Root cause: The original PATCH used body.model_dump(exclude_none=True). ListingUpdate has Optional fields that default to None — the manager only sent {"title": "new"}, but the other fields were None. With exclude_none=True, they were excluded from the payload correctly. But the bug was that available_from had type Optional[date] — when it was not sent, Pydantic defaulted it to None, and exclude_none=True would correctly exclude it. So why was it being overwritten?

The actual bug: the test was wrong — the PATCH was being used where a PUT was needed. Once investigated, the real issue was a frontend bug sending all fields every time. The lesson: use exclude_unset=True (not exclude_none) for PATCH endpoints to be safe.

Exercise 2 Medium — Add a GET /leasing/leads/{uuid} detail endpoint

The current API only has list and update for leads — no way to fetch a single lead by UUID. Add a GET endpoint that returns a single lead, raising 404 if not found or not owned by the requesting manager.

Show solution 
@router.get("/leads/{lead_uuid}", response_model=LeadResponse)
async def get_lead(
    lead_uuid: str,
    user: dict = Depends(require_active_subscription),
    db: Client = Depends(get_service_db),
):
    resp = (
        db.table("lease_leads")
        .select("*")
        .eq("uuid", lead_uuid)
        .eq("manager_id", user["sub"])  # ownership check
        .limit(1)
        .execute()
    )
    if not resp.data:
        raise HTTPException(status_code=404, detail="Lead not found")
    return resp.data[0]

Important: place this route BEFORE /leads list route in the file if they share a prefix — FastAPI matches routes in order and /leads could shadow /leads/{uuid} if defined first.

Exercise 3 Hard — Add lead auto-assignment when a listing is deleted

When a manager deletes a listing, any leads with listing_uuid set to that listing should have their listing_uuid set to null and their notes updated with "Listing was deleted". Implement this in the delete endpoint.

Show solution 
@router.delete("/listings/{listing_uuid}", status_code=204)
async def delete_listing(
    listing_uuid: str,
    user: dict = Depends(require_active_subscription),
    db: Client = Depends(get_service_db),
):
    # Nullify listing_uuid on associated leads before deleting
    db.table("lease_leads").update({
        "listing_uuid": None,
        "notes": "Listing was deleted",
    }).eq("listing_uuid", listing_uuid).eq("manager_id", user["sub"]).execute()

    # Then delete the listing
    db.table("lease_listings").delete().eq("uuid", listing_uuid).eq("manager_id", user["sub"]).execute()
    return None

The update fires before the delete — if the listing has a FK constraint to leads, the delete would fail if done first. Update first, delete second is the safe order. You should also add the manager_id filter to the lead update to prevent accidentally clearing another manager's leads.

Section 6 — Key Takeaways

  • Dual-audience routes — VAPI (no auth, service DB, always 200) and manager (auth, RLS, standard errors) can coexist in one file; the key is clear separation at the dependency level.
  • VAPI sends "" for unspecified numeric params — always use Optional[str] and _parse_int()/_parse_float() for VAPI-facing numeric query params.
  • Three-path search (exact → title → address/building fuzzy) gives progressively broader coverage while keeping common cases fast.
  • Decimal → float conversion is required before inserting into Supabase — {k: float(v) if isinstance(v, Decimal) else v ...}.
  • model_dump(exclude_unset=True) for PATCH (only update what was sent); model_dump(exclude_none=True) for CREATE (include all non-null provided values).
  • JSONB nested model needs .model_dump() called explicitly on the nested object before DB insert — model_dump() on the parent is shallow.
  • PostgreSQL array contains in PostgREST: interested_listing_ids.cs.{uuid} — the curly braces are PostgREST's array literal, not f-string syntax.
  • CSV export: io.StringIO() + csv.writer + StreamingResponse — no temp file, no disk I/O.
  • State machine enforcement: VAPI owns qualification statuses; managers own the post-qualification pipeline. Enforce boundaries in the PATCH validator.
