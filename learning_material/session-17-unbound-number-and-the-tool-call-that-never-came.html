Dead Line, Dead Air — The Unbound Number and the Tool Call That Never Came

Our French test partner dialed the complaint agent and got… nothing. The call connected, then died. When we fixed that, he called again — this time the French assistant answered, took his flat number, said "Laissez-moi vérifier ça dans mon système" ("Let me check that in my system")… and went silent until the call timed out. Two totally different failures, one afternoon. This session is a masterclass in production call forensics: we read Vapi's phone-number bindings, its call ledger, and finally its per-call flight-recorder logs to prove — token by token — that the LLM (Large Language Model — the AI that generates the agent's words) announced a database check and then never performed it. The first fix was one API call. The second was two sentences of prompt engineering. Neither touched a line of backend code.

🔴 Advanced ⏱️ Estimated: 70–85 min Requires: Sessions 01–15 (esp. 14 & 15) 🐛 4 Bug Stories

🧭 B · Session Overview

This was a pure diagnosis-and-hotfix session — no new features, but two production incidents on the complaint agent, both reported the same way: "my French partner can't use it." What we actually did:

  • Diagnosed and fixed inbound call failure — the complaint phone number in Vapi had assistantId: null, so inbound calls had no agent to connect to. Outbound kept working, which was the key clue.
  • Proved the French assistant never emitted tool calls — using Vapi's per-call log file (artifact.logUrl) we saw the exact LLM response: 21 tokens of filler speech, zero tool calls.
  • Fixed it with prompt engineering — rewrote the [System-Check Phrases] block so the "checking" phrase and the tool call must go out in the same turn, and bounded the flat-number "letter prefix" rule that had trapped the caller in a question loop.
  • Cleared a false alarm — apparent character corruption (mojibake) in the stored Vapi configs turned out to be our own terminal's fault, not real data damage. Again.

Why this matters for a CRM

The complaint line is the product for tenants. A number that rings and dies, or an agent that goes silent mid-verification, doesn't look like "a bug" to a tenant — it looks like the property manager doesn't answer the phone. Worse, both failures were invisible from the English side: every English test call passed. Without a French tester and the forensic tools in this session, these would have shipped to every francophone tenant in Québec.

Learning objectives

By the end of this session you will be able to:

  • Explain why inbound and outbound calls take different routing paths in Vapi, and why one can work while the other is completely broken.
  • Read a Vapi call list and use endedReason values as a diagnostic triage tool.
  • Download and read a per-call log file to see exactly what tools were handed to the LLM and exactly what it responded.
  • Explain the turn-taking rule that turns a missing tool call into permanent silence.
  • Spot the prompt-wording trap ("say X before the tool runs") that caused it — and the same-turn rule that fixes it.
  • Verify raw bytes before declaring an encoding bug.

🧠 D · Concepts Introduced This Session

D1 · Inbound vs outbound: two different routing paths

Plain English: When your server starts a call (outbound), it tells Vapi in the API request which assistant to use: "call this number, using this assistant, from this caller ID." But when a stranger dials your number (inbound), nobody is there to say which assistant should pick up — Vapi has to figure it out from the phone number's own configuration. Every Vapi phone number has an optional assistantId field: "when someone calls me, connect them to this assistant."

Why we need it: Our complaint line does both directions. The website's "Call me" button triggers POST /voice/call/outbound, which passes VAPI_COMPLAINT_ASSISTANT_ID explicitly. Tenants also dial the number directly. If the number's assistantId is empty, only the second path breaks — which is exactly the confusing symptom we saw.

Analogy: outbound is you walking out of the office with a specific employee and knocking on a customer's door — you chose who's doing the talking. Inbound is the customer walking into your lobby: if no receptionist has been assigned to the front desk, the customer stands in an empty lobby and eventually leaves. The building is fine. The staff are fine. The desk is just unstaffed.

OUTBOUND (works even with an unbound number) backend ──POST /call──> Vapi: { assistantId: 9e50…, phoneNumberId: c3b8…, customer: +1514… } assistant chosen per-call ✓ INBOUND (depends entirely on the number's own config) caller ──dials +14382567782──> Twilio ──webhook──> Vapi ──looks up──> phone-number c3b8… assistantId: null ✗ nobody assigned squadId: null server: null → call answered, then dropped
🔑 Key Concept — "Outbound works" proves almost nothing about inbound

Because the two directions resolve the assistant differently, each must be tested separately. A number can place perfect outbound calls for weeks while being completely deaf to inbound. Whenever a phone feature "half works," ask first: which direction, and where does that direction get its assistant from?

D2 · endedReason — triage before you read a single transcript

Plain English: every finished Vapi call carries an endedReason string — Vapi's one-line verdict on why the call stopped. Learning to read these is like a paramedic reading vital signs: you triage dozens of calls in seconds before opening any of them.

Why we need it: we listed 25 recent calls and two rows told the whole story of bug 1 — an inbound call with an empty assistant column and the reason call.in-progress.twilio-completed-call (Twilio finished a call that Vapi never staffed). The rest of the diagnosis was just confirming it.

endedReasonWhat it meansHealthy?
customer-ended-callThe human hung up — the normal end of most calls.USUALLY
assistant-said-end-call-phraseThe agent said its goodbye phrase and closed the call itself.YES
customer-did-not-answerOutbound ring, nobody picked up.NEUTRAL
silence-timed-outNeither side spoke for the timeout window (30 s here). Somebody was waiting for somebody.RED FLAG
call.in-progress.twilio-completed-callTwilio delivered the call but it ended without Vapi running an assistant — classic "nobody assigned to the number".RED FLAG
💡 Tip — pair endedReason with the assistant column

An inbound call with a blank assistantId is physically impossible if the number is bound — Vapi stamps every routed call with the assistant that took it. Blank assistant + twilio-completed-call = the routing itself failed, before any AI was involved.

D3 · The per-call flight recorder: artifact.logUrl

Plain English: transcripts show what was said. But Vapi also keeps a much deeper record per call: a compressed JSONL (JSON Lines — one JSON object per line) log file, linked from the call's artifact.logUrl field. It contains every internal event: every STT (Speech-To-Text) fragment, every LLM request with the full list of tools handed to the model, every response with the exact text and token counts, every timeout.

Why we need it: our hypothesis war was: "the French assistant doesn't have the tools" (the user's theory) vs "it has them but doesn't use them." The transcript can't settle that. The flight recorder can — the assistant.model.requestAttemptStarted events list the tools in the request, and assistant.model.responseSucceeded shows the completion. That's how we proved: 6 tools sent, 21 tokens of filler returned, zero tool calls.

Analogy: a plane crash investigation. The transcript is witness testimony ("the agent said it would check"). The flight recorder is the instrument log — it shows the pilot had a working engine lever (the tools were in the request) and simply never pulled it (no tool_calls in the response). Testimony suggests; instruments prove.

# 1) Fetch the call object; artifact.logUrl points at a gzipped JSONL file on Vapi's CDN
curl -s -H "Authorization: Bearer $VAPI_KEY" https://api.vapi.ai/call/<CALL_ID> \
  | python -c "import json,sys; print(json.load(sys.stdin)['artifact']['logUrl'])"

# 2) Download and decompress it (gunzip: decompress a .gz — gzip-compressed — file)
curl -s "<the logUrl printed above>" -o call_logs.jsonl.gz
gunzip call_logs.jsonl.gz            # produces call_logs.jsonl — one event per line

# 3) Each line is one event; the interesting ones for tool debugging:
#    assistant.model.requestAttemptStarted  → contains request.tools (what the LLM was GIVEN)
#    assistant.model.responseSucceeded      → contains completionText (what the LLM RETURNED)
#    assistant.model.toolCallsReceived      → present ONLY if the LLM actually called a tool
#    call.silenceTimeout                    → the 30s guillotine

D4 · Turn-taking: why one missing tool call becomes permanent silence

Plain English: a voice agent is not a chat window where the model can send a second message whenever it likes. Vapi runs a strict turn loop: the model gets invoked when (a) the user finishes speaking, or (b) a tool returns a result. Those are the only two triggers. If a model ends its turn with pure speech — no tool call — and the human politely waits (because the agent just said "one moment please"!), then neither trigger ever fires. The agent cannot spontaneously wake up. Thirty seconds later the silence timeout kills the call.

Why we need it: this explains the exact shape of Transcript 1: agent says "Laissez-moi vérifier ça dans mon système. Un instant, s'il vous plaît" — a sentence that explicitly asks the caller not to speak — then dead air, then silence-timed-out. The politer the caller, the deader the call. It's a deadlock: each side is waiting for the other, and the agent physically has no way to move first.

Analogy: a walkie-talkie conversation. Saying "let me check, stand by — over" and releasing the transmit button is fine if you actually go check. But our agent said "stand by — over," put the radio down, and forgot the errand. The other side dutifully stands by forever. Nothing in the radio protocol lets the first speaker be reminded.

THE DEADLOCK, RECONSTRUCTED FROM THE FLIGHT RECORDER 44.1s caller: "Le 26." ← user speech triggers a model turn 44.1s LLM request sent (6 tools included) ✓ tools were available 45.3s LLM response: "Laissez-moi vérifier ça dans mon système. Un instant, s'il vous plaît." completionTokens: 21 tool_calls: NONE ✗ speech only — turn over 47.1s TTS speaks the sentence. Caller obediently waits. … (no user speech → no trigger; no tool result → no trigger) … 79s call.silenceTimeout (timeoutSeconds: 30) → call ends: silence-timed-out
🔑 Key Concept — an announced action is not an action

LLMs are trained on human dialogue, where "let me check that" is usually followed by the speaker checking. But in tool-calling systems, speech and action are separate channels in the same response. A model can fill the speech channel convincingly while leaving the action channel empty — and everything downstream treats the sentence as if it were the deed. Every agent system you ever build needs a defense against this gap.

D5 · Same-turn tool calling — the two-word prompt trap

Plain English: our prompt told the agent: say a short checking phrase "OUT LOUD before the tool runs." To a human that means "narrate, then do it — right away." But "before" describes a sequence, and an LLM that thinks in turns can satisfy a sequence across two turns: this turn I say the phrase; the tool comes "after" (i.e., some future turn that never arrives). The fix is to demand simultaneity, not sequence: the phrase and the tool call must ship in the same response.

Why we need it: the same prompt ran fine in English for weeks — the model happened to bundle speech + tool call together (or skipped the phrase and just called the tool). In the French assistant's post-handoff context, the model latched onto the literal reading. Crucially, our own prompt already used the correct pattern elsewhere: the submit_complaint section says "never say it's logged unless you actually emitted the tool call in that same turn" — and that tool never once failed to fire. The evidence for the fix was already in the file.

Analogy: a relay race. "Say the phrase before you run" invites the runner to make a speech and then sit down — the race hasn't started, technically nothing was violated. "Say the phrase as you take the baton" fuses the two into a single act. Same words spoken; completely different guarantee.

--- BEFORE (sequence — the trap) -------------------------------------------
Any time you look something up — Verify_phone_number, check_availability, … —
say a short "checking" phrase OUT LOUD before the tool runs.
Never run a tool silently, and never let the wait turn into dead air.

--- AFTER (simultaneity — the fix) -----------------------------------------
Any time you look something up — Verify_phone_number, check_availability, … —
say a short "checking" phrase AS you fire the tool: the phrase and the tool
call go out together, in the SAME turn, in one single response. The phrase is
never a turn of its own.
- NEVER end a turn having announced a check without emitting the tool call in
  that same turn. Saying "let me check" (in any language) without the tool
  call is a hard failure — nothing runs, the line goes silent, and the call
  dies. If you spoke a checking phrase, the tool call MUST be attached to
  that very response.
- Never run a tool silently either — the phrase covers the wait so there is
  no dead air.
⚠️ Warning — prompts are load-bearing infrastructure

This bug's "code change" is prose. Treat prompt wording with the same rigor as function signatures: version it, review it, and when an agent misbehaves, read the prompt as the model would — literally, turn by turn — before assuming the model is broken. Two words ("before" → "as") were the entire difference between a working agent and a dead line.

D6 · False mojibake — verify the bytes before blaming the data

Plain English: while diffing the two assistants' stored configs, the output showed l'Ã©quipe — the classic mojibake (garbled text produced by decoding bytes with the wrong character table) signature of UTF-8's é read as two Latin-1 characters Ã©. Panic instinct: "our provisioning script corrupted the French text in Vapi!" Reality: our own inspection tool caused it. On Windows, Python's open() without an encoding= argument defaults to the legacy code page cp1252 — so a perfectly healthy UTF-8 file we had just downloaded was decoded wrong by us, locally, at read time.

Why we need it: this is the second time this series has hit a fake encoding bug (Session 15's was a console pipe artifact). The rule that saves you both times: before declaring data corruption, verify the raw bytes at the source — or at minimum, re-read with an explicit encoding="utf-8". One argument, zero drama. The partner's own transcript showing correct accents ("Préférez-vous…") was the cross-check that broke the panic.

# WRONG on Windows: encoding defaults to the machine's legacy code page (cp1252),
# so UTF-8 bytes C3 A9 ("é") decode as TWO characters: Ã (C3) + © (A9) → fake mojibake
data = json.load(open("assistant.json"))

# RIGHT: say what the bytes are. The file IS UTF-8 — read it as UTF-8.
data = json.load(open("assistant.json", encoding="utf-8"))

🐛 F · Bug Journal

Bug 1 — The unbound number: inbound calls to a receptionist who was never hired

🚨 The Symptom

The French partner dials the complaint line +1 438 256 7782. The call "connects" (it rings, it picks up) and then ends without any agent speaking. Meanwhile the website's outbound "call me" flow works perfectly for the same agent. No error appears anywhere on our side — the backend never even hears about the call.

🔍 The Diagnosis
  • Asymmetric symptom → asked where does each direction get its assistant? Outbound: from our API request body. Inbound: from the phone number's stored config. So read the phone number: GET /phone-number/<id> → assistantId: null, no squad, no fallback, no server.
  • Listed all numbers in the account for context — the entry complaint assistant was actually bound to a completely different number (+19734904520, "complaint manager") that nobody publishes. Several other pool numbers were also unbound (fine — they're inventory).
  • Confirmed with the call ledger: the partner's inbound attempt showed an empty assistant column and endedReason: call.in-progress.twilio-completed-call.
  • Red herring dodged: the French-handoff provisioning had shipped the day before, so it was the natural suspect — but that script only PATCHes assistants, never phone numbers. The docs also revealed the complaint line had changed numbers at some point (docs said +14382314283, env said +14382567782) — the newer number simply never got a binding.
🧠 The Root Cause

Vapi resolves inbound and outbound assistants through independent mechanisms. Outbound passes assistantId per call, so it works with a completely unconfigured number. Inbound needs the number itself to name an assistant (or a server to ask). When the complaint line moved to a new number, someone imported the number and updated the env vars — but nobody bound the assistant, and nothing failed until the first real inbound call. The class of bug: a resource with per-direction configuration, where only one direction was ever tested.

🔧 The Fix

One PATCH (Step 3 above): {"assistantId": "9e507761-…"} on the number. Verified by re-reading the number and by the partner's next call actually reaching Alex.

🛡️ The Lesson

When a channel "half works," enumerate the paths, not the components. The assistant, prompt, backend, and Twilio were all shared between the working and broken flows — only the routing lookup differed. Test matrices for phone systems must always contain both directions as separate rows. (Foreshadowing: in the next session we deliberately un-bind this number again — for a good reason — which is why the fix here also taught us the failure signature to watch for.)

Bug 2 — The promise that never ran: filler speech instead of a tool call

🚨 The Symptom

French call, post-handoff. Caller gives flat "26". Agent: "Laissez-moi vérifier ça dans mon système. Un instant, s'il vous plaît." Then nothing, forever. Call ends silence-timed-out after 30 s. English calls on the same day: verification tool fires within 2 seconds of the flat number, every time.

🔍 The Diagnosis
  • Hypothesis A (user's): FR assistant lacks tools. Diffed live configs → tools byte-identical. Falsified.
  • Hypothesis B: tools attached but not sent to the model at request time. Downloaded the call's artifact.logUrl JSONL → requestAttemptStarted shows all 6 tools in the request. Falsified.
  • Hypothesis C: model called a tool but the call was lost. Searched the log for toolCallsReceived → exactly one in the whole call (the handoff, on the entry assistant). The FR turn's responseSucceeded shows completionTokens: 21 and pure text. Confirmed: the model produced speech only.
  • Then read the prompt as the model would: the filler sentence it spoke is a scripted phrase from the prompt, and the instruction says to say it "before the tool runs" — a sequential framing the model satisfied by stopping after step one.
  • Cross-check that sealed it: the lease agent (same model!) never has this problem — its prompt says "say the phrase AS you fire it." And our own submit_complaint section already used same-turn wording and never failed. Same model, three wordings, only the sequential one dies.
🧠 The Root Cause

A prompt encoded a sequence ("speak, then tool") where the system needs simultaneity ("speak+tool in one response"). GPT-5.2 in the English context happened to bundle them anyway; in the French post-handoff context it followed the letter of the instruction, ended its turn after the filler, and the turn-taking loop (concept D4) guaranteed no second chance. The class of bug: an instruction that is unambiguous to humans but has two valid machine readings, where one reading deadlocks. It's a race-condition cousin: latent, context-dependent, and invisible in the tests you happened to run.

🔧 The Fix

Rewrote [System-Check Phrases] (before/after in concept D5): the phrase must ride on the tool-call response, plus an explicit hard-failure clause — "ending a turn having announced a check without emitting the tool call is a hard failure." Redeployed both complaint assistants via the provisioning script; verified the new wording live.

🛡️ The Lesson

Three lessons in one bug. (1) Falsify hypotheses with recorded evidence, cheapest first — config diff, then request log, then response log; each step killed a theory in minutes. (2) "Works in language A" says little about language B — same prompt, same model, different behavior; bilingual features need bilingual tests. (3) When two prompts drive the same model and only one misbehaves, diff the prompts, not the model — your working prompt is a control group you already own.

Bug 3 — The letter-prefix interrogation loop

🚨 The Symptom

Transcript 2: caller says flat "26". The FR agent asks for "the complete flat number with the letter at the beginning" — then asks again, and again, four phrasings in a row, talking over the caller's protests ("il n'y a pas de lettre — c'est 2, 2…"). Caller hangs up. The verification tool is never reached.

🔍 The Diagnosis

Searched the shared prompt for "letter": the tool-data rules say flat numbers like "s 2 0 1" must be concatenated to "S201" — "Never drop the letter." Written to prevent losing a spoken prefix, it contains no bound and no exit: nothing tells the model that digits-only is a valid answer. Add the French transcriber fragmenting the caller's replies into partial turns ("Oui," / "il n'y a pas de, il n'y pas de" / "C'est 2, 2") and the model never received one clean "no letter, it's 26" utterance to satisfy itself with — so it re-asked forever.

🧠 The Root Cause

An unbounded validation rule. "Never drop the letter" is a constraint with no terminating condition — the LLM equivalent of a while loop with no exit. Any rule you give an agent about user input needs (a) what counts as satisfied, (b) how many times it may re-ask, and (c) what to do when the user says the constraint doesn't apply.

🔧 The Fix

Added the bound (Step 7, Edit 2): digits-only is explicitly valid; the letter question may be asked at most once; "no letter" or repeated digits = accepted, proceed to verification, never re-ask.

🛡️ The Lesson

Prompts are programs. Review every "always/never" rule for a missing exit condition, exactly as you'd review a loop for a missing break. If a rule can collide with a legitimate user answer ("there is no letter"), the rule must say who wins.

The downloaded JSON file was valid UTF-8; the inspection script had opened it with bare open(path), and Windows Python defaults that to cp1252 — the mojibake was created at read time, on our machine. Lesson: instrument error is a hypothesis you must rule out first — especially for encoding, where the display chain (file → decode → terminal → font) has four places to lie to you. This is now the second fake mojibake in this series; the pattern is officially a house speciality.
