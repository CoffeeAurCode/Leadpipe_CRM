Section 1 — What You Are Building

This module wires up two external notification channels — Twilio for SMS and SendGrid for email — and combines them in a single orchestration service. Whenever an appointment is created, rescheduled, or cancelled, the system fires personalised messages automatically. Crucially, notification failures are never allowed to crash the main request — they are always caught, logged, and silently swallowed.

Three-file architecture: integrations/twilio_client.py ─── TwilioClient class + singleton getter integrations/email_client.py ─── EmailClient class + singleton getter services/notifications.py ─── Orchestration layer (calls both clients) Call flow when an appointment is created: appointments route └── BackgroundTasks.add_task(notify_manager_appointment_scheduled, appt) └── notifications.py ├── fetch complaint details from DB ├── fetch feature flags (SMS enabled? Email enabled?) ├── build SMS text + HTML email body ├── if sms_enabled → get_twilio_client().send_sms(...) └── if email_enabled → get_email_client().send_email(...) Tenant SMS (notify_tenant_appointment): appointments route (create / reschedule / cancel / attend / reactivate) └── BackgroundTasks.add_task(notify_tenant_appointment, flat_uuid, event, ...) └── DB lookup: tenants WHERE flat_uuid = ? └── get_twilio_client().send_sms(to=tenant.phone, message=...)

Section 2 — Concept Deep-Dives

Twilio Python SDK — how it works

Twilio is a cloud communications platform. To send an SMS, you POST to Twilio's REST API with your account credentials. The Python SDK is just a thin wrapper around those HTTP calls.

Minimal standalone example

from twilio.rest import Client

client = Client("AC...", "auth_token...")
msg = client.messages.create(
    body="Hello from Python!",
    from_="+1415XXXXXXX",   # your Twilio number
    to="+919998064026"       # recipient — must be E.164 format
)
print(msg.sid)  # SMxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

E.164 phone format

Twilio requires phone numbers in E.164 format: +[country code][number] with no spaces or dashes. +919998064026 = India (+91) + 10-digit number. If you pass 9998064026 without the +91, Twilio raises an error. The project stores phones in E.164 in the database, so no conversion is needed at send time.

What messages.create() returns

A MessageInstance object. The most useful fields are .sid (message ID, starts with SM), .status (queued / sent / delivered / failed), and .error_code (non-null on failure). The project logs the SID for traceability.

Twilio numbers and trial accounts: On a Twilio trial account, you can only send to verified numbers. You must verify each recipient's phone manually in the Twilio console. Unverified numbers get a silent error or a 403 from Twilio. Production accounts have no this restriction.

SendGrid Python SDK — how it works

SendGrid is an email delivery service. The Python SDK wraps their HTTP API. Unlike Twilio, which uses account SID + auth token, SendGrid uses a single API key.

Minimal standalone example

from sendgrid import SendGridAPIClient
from sendgrid.helpers.mail import Mail, Email, To, Content

client = SendGridAPIClient("SG.xxx...")
message = Mail(
    from_email=Email("no-reply@yourdomain.com"),
    to_emails=To("manager@example.com"),
    subject="New Appointment",
    html_content=Content("text/html", "<h1>Hello</h1>")
)
response = client.send(message)
print(response.status_code)  # 202 = accepted (not 200!)

Why 202, not 200?

SendGrid returns HTTP 202 (Accepted) to mean "we received your request and will deliver it". The email isn't delivered yet — SendGrid queues it. This is why the project checks response.status_code in [200, 201, 202] rather than just == 200. If you checked only for 200 you'd log every email as failed even when it succeeded.

Sender verification

SendGrid requires the from_email address to be verified (either as a single sender or via domain authentication). If you use an unverified sender, SendGrid returns 403. This is a common setup mistake — you must verify the sender in the SendGrid dashboard before the first email will go through.

Singleton pattern for API clients

Both TwilioClient and EmailClient use the singleton pattern: a module-level variable is created once and reused on every subsequent call. This avoids re-reading environment variables and re-initializing the SDK on every request.

# Module-level variable — None until first call
_twilio_client = None

def get_twilio_client() -> TwilioClient:
    global _twilio_client
    if _twilio_client is None:
        _twilio_client = TwilioClient()
    return _twilio_client

The first call initializes the client. Every subsequent call returns the same object. In FastAPI, with uvicorn running as a single process, module-level state persists across requests — the client is initialized once at startup and shared.

Why not FastAPI's lifespan? You could initialize clients in a startup event and store them in app.state. The singleton approach is simpler for a small app — both approaches are valid. The tradeoff is that the singleton is less testable (harder to swap in a mock) but requires zero framework plumbing.

Non-blocking notifications — errors logged, never raised

Notification failures must never crash the main request. If Twilio is down, the appointment should still be created. This is achieved in two ways:

1. Background tasks (FastAPI BackgroundTasks)

# In the appointments route:
async def create_appointment(
    ...,
    background_tasks: BackgroundTasks,
):
    # ... create appointment in DB ...
    background_tasks.add_task(
        notify_manager_appointment_scheduled,
        appointment=created_appt
    )
    return created_appt  # returns immediately; notification runs after

BackgroundTasks.add_task() schedules the function to run after the HTTP response is sent. The client gets their 201 response without waiting for Twilio/SendGrid to respond.

2. Try/except catch-all inside every notification function

def notify_tenant_appointment(...):
    try:
        # ... all notification logic ...
    except Exception as e:
        logger.error(f"notify_tenant_appointment failed: {type(e).__name__} - {str(e)}")
        # no re-raise — caller never sees this exception

Even if the background task itself crashes (unhandled exception), it won't affect other requests. The exception is absorbed inside the try/except and written to the log.

Feature-flag-gated notifications

Notifications are not unconditionally sent. Each flat has per-feature flags (sms_reminders, email_reminders) stored in the property_features table. The manager notification function checks these flags before sending.

if sms_enabled:
    twilio_client.send_sms(to=manager_phone, message=sms_message)
else:
    logger.info(f"SMS notification skipped for flat {flat_number} (feature disabled)")

if email_enabled:
    email_client.send_email(subject=email_subject, html_content=email_html)
else:
    logger.info(f"Email notification skipped for flat {flat_number} (feature disabled)")

This is important because both SMS and email cost money per message. The default for both features is False — so new flats get no notifications until the manager explicitly enables them in Settings.

Section 3 — Line-by-Line Walkthrough

File: backend/app/integrations/twilio_client.py

import os
from twilio.rest import Client
from typing import Optional
import logging

logger = logging.getLogger(__name__)
logging.getLogger(__name__) creates a logger named after the module (e.g. app.integrations.twilio_client). This makes it easy to filter logs by module in production. __name__ resolves to the fully-qualified module path at import time. 
class TwilioClient:
    def __init__(self):
        self.account_sid = os.getenv("TWILIO_ACCOUNT_SID")
        self.auth_token = os.getenv("TWILIO_AUTH_TOKEN")
        self.phone_number = os.getenv("TWILIO_PHONE_NUMBER")

        if not all([self.account_sid, self.auth_token, self.phone_number]):
            logger.warning("Twilio credentials not fully configured...")
            self.client = None
        else:
            self.client = Client(self.account_sid, self.auth_token)
all([...]) returns True only if every item in the list is truthy. If any env var is missing (returns None which is falsy), the whole check is False and self.client = None.

Setting self.client = None when credentials are missing is a graceful degradation pattern: the object is created successfully, but SMS calls will be silently skipped. The alternative (raising an exception in __init__) would crash the server on startup if Twilio isn't configured — unacceptable for a feature that may be disabled in some deployments. 
    def send_sms(self, to: str, message: str) -> Optional[str]:
        if not self.client:
            logger.error("Twilio client not initialized. Check environment variables.")
            return None

        try:
            message_obj = self.client.messages.create(
                body=message,
                from_=self.phone_number,
                to=to
            )
            logger.info(f"SMS sent successfully. SID: {message_obj.sid}, To: {to}")
            return message_obj.sid
        except Exception as e:
            logger.error(f"Failed to send SMS to {to}: {type(e).__name__} - {str(e)}")
            return None
Return type is Optional[str] — either a message SID string on success, or None on failure. The caller checks the return value to determine if the SMS went through.

from_=self.phone_number — the underscore suffix is because from is a reserved Python keyword. The Twilio SDK parameter is actually named from_ in the Python wrapper.

type(e).__name__ — logs the exception class name (e.g. TwilioRestException) alongside the message, which is much more useful for debugging than just the message string.

File: backend/app/integrations/email_client.py

def send_email(self, subject: str, html_content: str,
               to_email: Optional[str] = None) -> bool:
    # Always read fresh from env so .env changes take effect without restart
    recipient = to_email or os.getenv("MANAGER_EMAIL") or self.manager_email
    from_email = os.getenv("SENDGRID_FROM_EMAIL") or self.from_email
os.getenv("MANAGER_EMAIL") is read fresh on every call (not cached in __init__). This means you can update the env var in a running process and the next email will use the new value — useful during debugging without restarting the server.

The or chain: try to_email param first → fall back to fresh env read → fall back to value cached at init time. 
    try:
        message = Mail(
            from_email=Email(from_email),
            to_emails=To(recipient),
            subject=subject,
            html_content=Content("text/html", html_content)
        )
        response = self.client.send(message)
        return response.status_code in [200, 201, 202]
    except Exception as e:
        logger.error(f"Failed to send email to {recipient}: {type(e).__name__} - {str(e)}")
        return False
response.status_code in [200, 201, 202] — SendGrid almost always returns 202. Checking for all three prevents false negatives. Return type is bool — simpler than returning a status object since the caller only cares whether it succeeded.

File: backend/app/services/notifications.py — notify_tenant_appointment()

def notify_tenant_appointment(
    flat_uuid: str,
    event: str,   # "created" | "rescheduled" | "cancelled" | "attended" | "reactivated"
    flat_number: str,
    db: Client,
    new_date: Optional[str] = None,
) -> None:
This function sends a personalised SMS directly to the tenant. It receives the db client as a parameter — it does NOT create its own client. The caller (the appointments route) passes its already-open DB connection so the function can look up the tenant's phone number without credentials.

event is a plain string (not an enum) — five event types are handled: created, rescheduled, cancelled, attended, reactivated. Unknown events trigger a warning log and early return. 
    try:
        tenant_resp = (
            db.table("tenants")
            .select("name, phone")
            .eq("flat_uuid", flat_uuid)
            .maybe_single()
            .execute()
        )
        if not tenant_resp.data:
            logger.warning(f"notify_tenant_appointment: no tenant for flat_uuid={flat_uuid}")
            return
.maybe_single() — a Supabase SDK modifier that returns a single object or None (as opposed to .single() which raises an error if 0 or 2+ rows are returned). Used here because a flat might be unoccupied — in that case tenant_resp.data is None and we early-return with a warning. 
        formatted_date = new_date or ""
        if new_date:
            try:
                dt = datetime.fromisoformat(new_date.replace("T", " ").replace("Z", ""))
                formatted_date = dt.strftime("%d %b %Y at %I:%M %p")
            except Exception:
                formatted_date = new_date
The date coming from the DB is in YYYY-MM-DDTHH:MM:SS format. datetime.fromisoformat() in Python 3.10 doesn't accept the T separator without a timezone — the .replace("T", " ") converts it to a format fromisoformat accepts. .replace("Z", "") strips the UTC timezone indicator if present.

The inner try/except catches any parse failure and falls back to the raw string. This is defensive: a notification with an ugly date is better than a failed notification. 
        if event == "created":
            message = (f"Hi {tenant_name}, a new maintenance appointment has been "
                       f"scheduled for flat {flat_number}.")
        elif event == "rescheduled":
            message = (f"Hi {tenant_name}, your maintenance appointment for flat "
                       f"{flat_number} has been rescheduled to {formatted_date}.")
        # ... cancelled / attended / reactivated ...
        else:
            logger.warning(f"notify_tenant_appointment: unknown event '{event}'")
            return

        get_twilio_client().send_sms(to=phone, message=message)
Each event type produces a different personalised message. The else branch with return is a safety guard — if someone adds a new event type in the appointments route but forgets to add it here, the function exits gracefully with a warning log rather than sending a garbled message.

get_twilio_client().send_sms(...) — calling the singleton getter inline. No need to store the client in a variable first.

File: notifications.py — notify_manager_appointment_scheduled()

def notify_manager_appointment_scheduled(appointment: Dict[str, Any]) -> None:
    try:
        from supabase import create_client
        supabase_url = os.getenv("SUPABASE_URL")
        supabase_key = os.getenv("SUPABASE_KEY")
        db = create_client(supabase_url, supabase_key)
This function runs as a BackgroundTask — it is called after the HTTP response is returned. At that point, the route's injected db dependency may have been torn down. This is why the function creates its own Supabase client from environment variables rather than accepting a db parameter.

This is the exact same problem as in the VAPI provisioning module (Module 12) — background tasks must not depend on request-scoped resources. The solution is identical: create a fresh service-role client inside the task. 
        try:
            loop = asyncio.get_event_loop()
            if loop.is_running():
                import nest_asyncio
                nest_asyncio.apply()
        except RuntimeError:
            loop = asyncio.new_event_loop()
            asyncio.set_event_loop(loop)

        sms_enabled, email_enabled = loop.run_until_complete(get_flags())
FeatureService.is_feature_enabled() is an async method. But this notification function is synchronous (def, not async def). To call an async function from sync code, you need an event loop.

The problem: FastAPI runs on uvicorn which already has a running event loop. You can't call asyncio.run() from inside a running loop — it raises RuntimeError: This event loop is already running. The fix is nest_asyncio.apply(), which patches asyncio to allow nested run_until_complete() calls.

The try/except RuntimeError handles the case where there's no current event loop (rare in production, possible in tests or standalone scripts), in which case a fresh loop is created.

Section 4 — Real Bugs & How We Fixed Them

Bug 1: All emails showed "Failed" even though they were delivered

Symptom: Logs showed Failed to send email: status_code=202. The emails actually arrived in the inbox.

Root cause: The original code checked response.status_code == 200. SendGrid always returns 202 for successful sends.

Fix: Changed the check to response.status_code in [200, 201, 202]. Lesson: always check the vendor's API docs for what status code they actually return — don't assume 200.

Bug 2: RuntimeError: This event loop is already running in BackgroundTask

Symptom: The notification background task crashed with RuntimeError on the loop.run_until_complete(get_flags()) line. No notification was sent.

Root cause: FastAPI's event loop is already running. asyncio.run() and a bare run_until_complete() on the existing loop both raise this error.

Fix: Added nest_asyncio.apply() before run_until_complete(). This patches the event loop to permit nested calls. Add nest_asyncio to requirements.txt.

Bug 3: SMS to tenant silently failed — no error, no delivery

Symptom: Logs showed SMS sent successfully. SID: SM... but the tenant never received the message. Twilio dashboard showed status "undelivered".

Root cause: The tenant's phone number was stored without the country code (e.g. 9998064026 instead of +919998064026). Twilio requires E.164 format.

Fix: Added a phone number validation note to the tenant creation form. The DB stores phones as entered — you should validate and normalize to E.164 at input time (on the frontend or in the Pydantic schema).

Bug 4: Notifications fired even when both SMS and email were disabled

Symptom: On a flat with no features enabled, the notification code still ran all the DB queries (complaint lookup, feature flag check) before deciding to do nothing.

Root cause: The feature flag check happened after all the DB queries. If both are disabled, all that work was wasted.

Fix: This is an efficiency issue, not a correctness bug. In a high-volume system you'd check features first and early-return if both are disabled. In this MVP, the current order is acceptable — the wasted DB queries are fast and rare.

Exercise 2 Medium — Add CC support to email

Modify EmailClient.send_email() to accept an optional cc_email: Optional[str] = None parameter and include it in the SendGrid message if provided.

Show solution 
from sendgrid.helpers.mail import Mail, Email, To, Content, Cc

def send_email(self, subject: str, html_content: str,
               to_email: Optional[str] = None,
               cc_email: Optional[str] = None) -> bool:
    # ... existing recipient/from_email setup ...
    message = Mail(
        from_email=Email(from_email),
        to_emails=To(recipient),
        subject=subject,
        html_content=Content("text/html", html_content)
    )
    if cc_email:
        message.cc = [Cc(cc_email)]
    response = self.client.send(message)
    return response.status_code in [200, 201, 202]

Cc is imported from sendgrid.helpers.mail. The .cc attribute accepts a list of Cc objects.

Exercise 3 Hard — Make notification failures visible in the API response

Currently, notification failures are invisible to the caller — they're only in logs. Design and implement a way for the appointment creation endpoint to include notification status in the response body (e.g. "notifications": {"sms": "sent", "email": "skipped"}) without breaking the non-blocking pattern.

Show solution (one approach)

One approach: change notify_manager_appointment_scheduled to return a dict, and store the result in the DB (e.g. an appointment_notifications table). The frontend polls separately. This avoids breaking the non-blocking pattern because the appointment creation response is still returned immediately.

A simpler approach (if you accept a slight coupling): run the notification synchronously (not as a background task) but still catch all exceptions. Return the status in the response:

# In the route handler (synchronous notification):
notif_result = {"sms": "skipped", "email": "skipped"}
if sms_enabled:
    sid = get_twilio_client().send_sms(to=phone, message=msg)
    notif_result["sms"] = "sent" if sid else "failed"
if email_enabled:
    ok = get_email_client().send_email(subject=subj, html_content=html)
    notif_result["email"] = "sent" if ok else "failed"

return {"appointment": created_appt, "notifications": notif_result}

The tradeoff: the HTTP response now waits for Twilio/SendGrid (adds ~200-500ms latency). Acceptable for an admin tool, problematic for a high-traffic API.

Section 6 — Key Takeaways

  • Both Twilio and SendGrid use API key credentials read from env vars — never hardcode these.
  • The singleton pattern (_client = None → get_client()) avoids re-initializing expensive objects on every request.
  • Notification functions must always catch all exceptions — a failed SMS must never crash the request that triggered it.
  • Use FastAPI BackgroundTasks to run notifications after the HTTP response is sent — the user gets an instant response and the notification is fire-and-forget.
  • BackgroundTasks must create their own DB client — the route's injected client is request-scoped and may be torn down before the background task runs.
  • SendGrid returns 202, not 200 for successful sends — check status_code in [200, 201, 202].
  • Feature flags gate spending — SMS and email are off by default because each message costs money.
  • nest_asyncio is needed when calling async code from a sync function running inside an already-running event loop (common in background tasks).
