Why Max Looped & Alex Lied: VAPI Tool Routing and Flat-Anchored Ownership

Two voice agents broke in two completely different ways, and both were invisible until we read the right logs. Max (the leasing agent) got stuck in a loop, kept saying a bilingual "one moment" line, and never saved a lead — every lead came out as "Unknown." Alex (the complaint agent) cheerfully told a caller "your complaint has been logged" and then logged nothing. We trace both to their roots — one is a tool-name collision, the other is a prompt that lets the model narrate instead of act — fix them, push to the live phone agents, and finish with a clean data-model refactor that makes complaints work for building-less standalone units.

🟡 Intermediate ⏱️ ~85 min read / build 📋 Requires: Sessions 09–10 (the VAPI deploy pipeline, lease-agent internals)

📦 Session Overview

This was a pure diagnose-and-repair session — three distinct failures, three root causes, three fixes, all shipped to the live phone agents. No new feature; just making the two agents we already have actually do their one job: record the thing the caller called about.

It opened with a single observation from a real test call:

You: i did a test call in english ... the agent kept searching unit and kept saying that polite message in both the language, it didn't log the lead and on the front end i see unknown leads ... first diagnose the issue and suggest the fix ...after the lease fix shipped... You: the lease agent works but the complaint agent is not working, it didn't file the complaint ...then a design idea... You: rather than connect a number, tenant or a complaint to a property group id, make it connect to the flat id ... won't that be better for standalone units?

By the end of the session we had:

  • Found that all three of Max's tools shared one internal name (api_request_tool), so the model could only ever reach the first one — and fixed it with a tiny helper that gives each tool a unique name.
  • Removed a static bilingual "one moment" string that couldn't respect the call's language lock, letting the model speak the filler itself in the caller's language.
  • Rewrote the deploy script for the shared agents from the VAPI SDK to a raw HTTP PATCH, because the SDK silently dropped fields.
  • Caught Alex narrating success without calling the tool — proven from the live VAPI call object — and hardened the prompt so the model must actually emit submit_complaint.
  • Refactored owner resolution to anchor on the flat (flats.manager_id) instead of walking up to the property group — fixing complaints for standalone units and deleting a vestigial required field in the process.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Explain how an LLM chooses and calls a tool, and why two tools sharing a name collapse into one.
  • Tell apart VAPI's apiRequest and function tool types and know how each is routed to your backend.
  • Diagnose a voice bug from server logs and from the provider's live call object — not guesswork.
  • Recognise when a bug is config vs prompt, and harden a prompt so the model acts instead of narrates.
  • Choose the right data anchor for a lookup so building-less edge cases don't silently break.
  • Push assistant config to production with a dry-run + verify loop, and know which changes need a backend redeploy too.

🌉 Recap Bridge — where we left off

Our product is a CRM (Customer Relationship Management — the app a property manager uses to track buildings, units, tenants, complaints, and rental leads). Two of its features are voice agents: AI personalities that answer the phone. Max handles leasing calls (a prospective tenant asks about available units; Max qualifies them and saves a lead). Alex handles existing-tenant calls (someone reports a broken AC; Alex files a complaint and books a manager callback).

Both run on VAPI (a hosted "Voice API" that connects the phone line to a speech-to-text engine, a language model, and a text-to-speech voice). When an agent needs data — "what units are in Laval?", "file this complaint" — it calls a tool, which is just an HTTP request to our FastAPI backend. That backend runs on Render (a cloud host) and stores everything in Supabase (hosted PostgreSQL). A recurring theme from Sessions 09–10: a voice-agent change has two deploy surfaces — the backend code (deployed by a git push to Render) and the assistant configuration (pushed to VAPI by a Python script). A change isn't live until both are updated.

In Session 10 we made Max faster and changed the question he asks about employment. That work was fine. But this session a fresh English test call exposed something older and deeper: Max would find a unit, ask his qualifying questions, then — at the very end — get stuck, repeating a "let me check my system" line and never saving the lead. And when we later tested Alex, he confidently announced a complaint was filed that was never written to the database. Same symptom shape ("the agent says it worked but nothing is saved"), two unrelated causes. That is what we untangle here.

🧠 Concepts Introduced This Session

Eight ideas carry the session. The first five are about how tools are defined, named, routed, and triggered; the sixth is the debugging method; the last two are the data-model and prompt principles that made the fixes durable.

1 · How an LLM actually calls a tool

Plain-English explanation. A language model can't "do" anything on its own — it only produces text. To let it take actions (look up units, file a complaint), we give it a list of tools. Each tool has a name, a description ("use this to file a complaint"), and a parameter schema (what arguments it takes). When the model decides it needs a tool, it doesn't run code — it emits a special message that says "call the tool named X with these arguments." Something outside the model (here, VAPI) reads that message, actually performs the action, and hands the result back.

Why we need it (for CRM specifically). Every useful thing Max and Alex do is a tool call: find_units, search_listings, submit_lease_lead, Verify_phone_number, check_availability, submit_complaint. If the model picks the wrong tool, or can't reach the right one, or never emits the call, the caller gets a smooth-sounding conversation that accomplishes nothing. Both of this session's headline bugs live exactly here.

How it works (analogy). Think of the model as a manager who can't leave their desk. In front of them is a panel of labelled buttons (the tools). To get something done, the manager calls out a button's label and the values to use — "press FILE-COMPLAINT with flat 1804, category electricity." An assistant standing outside the room (VAPI) hears the label, presses the real button, and reports back what happened. The manager never touches the machinery; they only name buttons.

Jargon decoder.

  • LLM (Large Language Model) — the AI that generates text; here OpenAI's gpt-5.2-chat-latest drives both agents.
  • tool / function call — the structured "please run X with these args" message the model emits instead of plain speech.
  • tool schema — the JSON description of a tool: its name, what it's for, and its parameters. This is all the model knows about a tool.
  • arguments — the values the model fills in for the tool's parameters (e.g. flat_number: "1804").
🔑 Key Concept — the name is the address

When the model wants a tool, it refers to it by name. The name is how the model points at one button and not another. Hold onto this: if two buttons share a label, calling that label is ambiguous — and that ambiguity is Bug 1.

2 · The function-name uniqueness rule

Plain-English explanation. Every tool you give a model must have a unique name. If two tools share a name, the platform (VAPI, and underneath it OpenAI) can't tell them apart — they collapse into one. In practice only the first tool with that name survives; the others become unreachable. The model literally cannot call a tool it can't see by a distinct name.

Why we need it (for CRM specifically). Max has three tools, and through a copy-paste habit all three carried the same internal function name, api_request_tool. So when Max wanted to save the lead (submit_lease_lead), the call resolved to the first tool with that name — find_units — which just searches and returns nothing useful for saving. Max, never seeing it work, tried again and again: the loop, the repeated "one moment," and zero leads saved.

How it works (analogy). Imagine a TV remote where the VOLUME, CHANNEL, and POWER buttons are all engraved "BUTTON." You press "BUTTON" meaning POWER, but the remote can only act on the first thing called BUTTON — volume. No matter what you intend, you keep changing the volume. The buttons exist; the labels are useless because they're not unique.

Jargon decoder.

  • top-level name — VAPI's human-facing tool name (e.g. find_units). These were unique.
  • function.name — the nested name passed down to the LLM as the callable identifier. These were all api_request_tool — the bug.
  • dedupe / collapse — when a system encounters duplicate keys and keeps only one.

Annotated code — the one-helper fix. Instead of editing 13 duplicated strings by hand, we wrote a helper that copies each tool's already-unique top-level name down into its function.name:

# VAPI/OpenAI dedupe tools by function name. apiRequest tools historically all
# used "api_request_tool", so every tool after the first was unreachable. Alias
# each apiRequest tool's function.name to its (already unique) top-level name.
def _alias_apirequest_tool_names(tools: list) -> list:
    for t in tools:                       # walk every tool in this agent's list
        top_name = t.get("name")          # the unique label, e.g. "submit_lease_lead"
        fn = t.get("function")            # the nested {"name": ..., "description": ...}
        if top_name and isinstance(fn, dict):  # function tools have NO top-level name -> skipped
            fn["name"] = top_name         # copy the unique name down so the model sees it
    return tools                          # same list, mutated in place, returned for chaining

Then we wrapped each builder's output once, so the fix is automatic for every agent:

# build_lease_config(...):
tools = _alias_apirequest_tool_names(_build_lease_tools(backend_url, manager_id=manager_id))
# build_complaint_config(...):
tools = _alias_apirequest_tool_names(build_complaint_tools(backend_url))
💡 Tip — fix the cause, not the 13 symptoms

We could have hand-edited every "name": "api_request_tool" to a unique string. But there were 13 of them across three agents — easy to miss one, and the bug would silently return whenever someone copy-pasted a new tool. A single helper applied at one choke-point makes the property structural: every tool list that passes through it is guaranteed unique. Prefer one durable guarantee over many fragile edits.

3 · Two kinds of VAPI tool: apiRequest vs function

Plain-English explanation. VAPI lets you define a tool in two styles. An apiRequest tool bakes the HTTP call right into the tool definition: VAPI itself makes the request to a URL you specify and reads the response. A function tool instead forwards the call to a server URL you own as a webhook, and your code decides what to do. The key difference for debugging: an apiRequest tool is routed by its URL, while a function tool is identified by its name in the webhook payload.

Why we need it (for CRM specifically). Max's tools (find_units, search_listings, submit_lease_lead) are all apiRequest — each has its own URL on our backend, so renaming their function.name in Bug 1 was perfectly safe: the backend never matches on that name, it just receives an HTTP call at a URL. Alex's submit_complaint, by contrast, is a function tool that posts to /voice/webhook, where our handler matches on the literal name "submit_complaint". Knowing which style each tool uses told us exactly what we could change without breaking the wiring.

How it works (analogy). An apiRequest tool is like direct dial: the phone number is printed on the button, so pressing it always reaches the right desk regardless of what the button is labelled. A function tool is like calling the front desk and asking for a person by name — the receptionist (your webhook) routes by the name you say, so the name has to match.

Jargon decoder.

  • webhook — a URL on your server that an external system calls when an event happens (here, "the model invoked this tool").
  • apiRequest tool — VAPI makes the HTTP call for you; routed by the URL embedded in the tool.
  • function tool — VAPI forwards the call to your server URL; your code matches by the tool's name.
  • {{customer.number}} — a VAPI template variable; VAPI substitutes the caller's real phone number into the URL at call time.

Annotated code — the two shapes side by side.

{
  "type": "apiRequest",                 # VAPI makes this HTTP call itself
  "name": "submit_lease_lead",          # unique top-level label
  "function": {"name": "submit_lease_lead",   # (after our fix) the identifier the LLM sees
               "description": "Capture the prospective tenant as a lead."},
  "url": f"{backend_url}/voice/lease-lead-direct?call_id={{{{call.id}}}}&phone={{{{customer.number}}}}",
  "method": "POST",                     # the backend reads the JSON body; it never checks the tool name
}
{
  "type": "function",                   # VAPI forwards this to OUR server URL
  "async": True,                        # fire-and-continue; the model doesn't wait for the result
  "function": {"name": "submit_complaint",    # our /voice/webhook matches on THIS literal string
               "strict": True,
               "parameters": { ... }},
  "server": {"url": f"{backend_url}/voice/webhook", "timeoutSeconds": 20},
}
📖 Deep Dive — the request-start "filler" message

Each apiRequest tool can carry a messages list with a request-start entry — a line VAPI speaks the instant the tool fires, so the caller doesn't hear dead air while the lookup runs. Max's find_units had a hard-coded bilingual string here. That's Concept 4, and it's why callers heard the same "one moment" in two languages on a loop: every retry of the mis-routed tool replayed that fixed string.

4 · A static string can't respect a per-call language lock

Plain-English explanation. Max is bilingual: he detects whether the caller speaks English or French on their first words and then locks to that language for the whole call. A static filler string — text fixed at config time — can't know which language this particular call is in. So a string like "Let me check that in my system. Un instant, je vérifie ça." speaks both languages on every call, violating the lock.

Why we need it (for CRM specifically). The caller reported Max "kept saying that polite message in both the language." Two things were stacked: the tool loop (Bug 1) made the line repeat many times, and the line itself was bilingual by construction. Fixing the loop stops the repetition; removing the static string stops the bilingual bleed. The right pattern — already used by Alex — is to let the model speak the filler, because the model knows the locked language.

How it works (analogy). A pre-printed "Back in 5 minutes" sign always says the same thing regardless of who walks up. If half your visitors speak French, you don't print a bilingual sign that everyone has to read twice — you have a person say "one moment" in the visitor's own language. The model is that person.

Annotated change — hand the filler back to the model.

# VAPI speaks this verbatim the instant the tool fires — but it's bilingual AND static,
# so it ignores the per-call language lock and repeats on every (looping) retry.
"messages": [{
    "type": "request-start",
    "content": "Let me check that in my system, one moment. Un instant, je vérifie ça.",
    "blocking": False,
}],
# No static content — a static string can't respect the per-call language lock.
# The model speaks a short checking phrase in the locked language (see [System-Check Phrases]).
"messages": [],

And the lease prompt was switched from "the system speaks it automatically" to instructing the model to say a short, single-language phrase itself:

[System-Check Phrases - Locked Language Only]
The instant you trigger a lookup (find_units or search_listings), say a SHORT, natural
"one moment" phrase OUT LOUD so there is never dead air. Speak it ONLY in the caller's
locked language - never the other language, never both, never an appended translation.
Do NOT say a checking phrase for submit_lease_lead - that is the lead capture, not a lookup.
⚠️ Warning — config can't know runtime state

Anything you bake into a config file is decided before the call exists. If a behaviour depends on something only known during the call (which language, which caller, which unit), it belongs to the runtime actor — the model — not to a static field. Hard-coding runtime-dependent text is a recurring trap.

5 · SDK convenience vs raw HTTP control (and PATCH merge semantics)

Plain-English explanation. To update a VAPI assistant you can either use VAPI's Python SDK (a convenience library with typed methods) or send a raw HTTP PATCH request yourself. The SDK is friendlier but it only knows about the fields its types model — anything it doesn't recognise it silently drops. A raw PATCH sends exactly the JSON you give it. Because PATCH means "update only these fields," it's a partial merge: fields you omit are left untouched on the server.

Why we need it (for CRM specifically). The script that updates our shared agents (update_shared_agents.py) used the SDK, and our own notes warned it "silently drops firstMessageMode and apiRequest tool subfields." We were about to push critical tool changes to Alex — if the SDK mangled the tool definitions or the first-message behaviour, we could break a working complaint flow while trying to fix it. So we rewrote the script to use a raw HTTP PATCH, exactly like the lease-agent script already did, and verified the response echoed back the fields we expected.

How it works (analogy). The SDK is a helpful courier who only accepts parcels that fit their standard boxes — hand them an odd-shaped item and they quietly leave it behind without telling you. Raw HTTP is addressing the envelope yourself: more work, but everything you put in actually ships.

Jargon decoder.

  • SDK (Software Development Kit) — a library that wraps an API in your language's idioms.
  • HTTP verbs — PATCH = partial update (merge); PUT = full replace; POST = create. We want PATCH so untouched fields survive.
  • snake_case vs camelCase — our config uses first_message_mode; VAPI's REST API wants firstMessageMode. The script maps between them.
  • idempotent — running the push repeatedly yields the same end state; safe to re-run.

Annotated code — the key-mapping PATCH.

# snake_case (our config) -> camelCase (VAPI REST). Only keys present are sent;
# PATCH merge leaves everything else on the assistant intact.
_KEY_MAP = {
    "name": "name", "first_message": "firstMessage", "first_message_mode": "firstMessageMode",
    "model": "model", "server": "server", "server_messages": "serverMessages",
    "analysis_plan": "analysisPlan", "transcriber": "transcriber", "voice": "voice",
    # ...plus end-call, background, speaking-plan keys...
}
def _to_vapi_payload(cfg: dict) -> dict:
    payload = {}
    for snake, camel in _KEY_MAP.items():
        v = cfg.get(snake)
        if v is not None:                 # omit missing keys -> PATCH won't blank them
            payload[camel] = v
    return payload

resp = httpx.patch(f"{VAPI_API_BASE}/assistant/{assistant_id}",
                   headers=headers, json=_to_vapi_payload(cfg), timeout=30)
💡 Tip — verify the echo, don't trust the 200

A 200 OK only means the request was accepted, not that your field stuck. After the PATCH we re-read the response body and asserted serverMessages, firstMessageMode, and the tools names matched what we sent. With the SDK, those were exactly the fields that vanished — so checking the echo is what catches a silent drop.

6 · Prompt strength is tool-call reliability (act, don't narrate)

Plain-English explanation. An LLM is fundamentally a text predictor. If your prompt describes a flow as a story — "say the checking phrase, then call the tool, then say it's done" — the model may produce the whole story as speech, including "it's done," without ever emitting the actual tool call. To make a tool call reliable you must make it impossible to skip: pull it out of the narration, and add explicit, repeated, hard rules that calling the tool is the only way to succeed.

Why we need it (for CRM specifically). Alex said "your complaint has been logged" but never called submit_complaint — so nothing was saved. Comparing the two agents revealed why: Max's prompt hammers "submit_lease_lead is the ONLY way to record the lead; a call without it has FAILED," and it excludes that tool from the "say a checking phrase first" list. Alex's prompt mentioned submit_complaint once, buried in a numbered list, and told him to "say a phrase before" it — so he narrated the phrase and the success line as one smooth turn and skipped the call.

How it works (analogy). A new cashier reads a script: "greet, scan items, take payment, say thank you." If they're nervous they might recite the whole script — including "thank you for your payment" — while forgetting to actually run the card. You fix it by separating the action from the patter ("do not say thank-you until the terminal shows APPROVED") and by drilling that the sale isn't real until the card clears.

Annotated change — three prompt edits, zero code/config change.

# BEFORE: submit_complaint was in the "say a checking phrase before this tool" list.
# AFTER:  it is removed from that list, with an explicit note:
(submit_complaint is NOT a lookup - do not pre-narrate it. You CALL it, then speak the
confirmation. See [CALLBACK SCHEDULING FLOW] and [Complaint Submission - NO EXCEPTIONS].)
4. NOW actually CALL the submit_complaint tool with flat_number, category, description, and
   appointment_date. This is a real tool invocation, not something you describe - you MUST
   emit the submit_complaint call here.
5. ONLY after you have fired submit_complaint, say: "Your complaint has been logged..."
   Never say this sentence unless you have actually called submit_complaint in this turn.
[Complaint Submission - NO EXCEPTIONS]
submit_complaint is the ONLY way to file a complaint - check_availability only checks a slot;
it does NOT record anything. A call where the caller reported an issue but you never called
submit_complaint has FAILED, even if you told them it was logged.
🔑 Key Concept — the prompt is the product's behaviour

For an AI agent there is no separate "code path" for the conversation — the prompt is the behaviour. A weakly-worded instruction isn't a documentation problem; it's a bug. Treat prompt wording with the same rigour as code: separate side-effects from narration, and assert the invariant ("never claim success without the call") in plain, emphatic language.

7 · Forensic debugging: server logs + the provider's live call object

Plain-English explanation. When a voice agent misbehaves you have two independent sources of truth. First, your server logs — every HTTP request the agent made to your backend (which tools fired, with what arguments, what came back). Second, the provider's call object — VAPI stores a complete record of each call you can fetch by its API, including the exact list of messages and tool calls the model produced. Cross-checking the two tells you precisely where the chain broke.

Why we need it (for CRM specifically). Both bugs looked fine in the transcript — the agent spoke as though everything worked. The truth was only in the logs. For Max, the Render logs showed many GET /leasing/find-units calls, zero /leasing/search-listings, and zero /voice/lease-lead-direct — proof that only one of three tools ever ran. For Alex, we fetched the live VAPI call and saw the model's message list contained Verify_phone_number and check_availability but no submit_complaint — proof the model never even tried to file it.

How it works (analogy). A delivery says "delivered" but the box isn't on your porch. The courier's app log (your server logs) shows which stops they actually made; the building's security camera (the provider's call object) shows what physically happened at your door. One might lie or be incomplete; together they pin the truth.

The smoking-gun logs for Max — note the empty query=, which is a mis-routed lead-save landing on the search tool:

GET /leasing/find-units?manager_id=28c43c77...&query=Montreal%20Avenue%20Libre 200 OK GET /leasing/find-units?manager_id=28c43c77...&query= 200 OK <- empty query = a submit attempt mis-routed GET /leasing/find-units?manager_id=28c43c77...&query=48%20Avenue%20Libre 200 OK # NOTE: zero GET /leasing/search-listings and zero POST /voice/lease-lead-direct [LEASE EOC] Lead saved (structured=False) ... name=Unknown status=unmatched <- the "Unknown" lead

The smoking gun for Alex — fetched from VAPI's GET /call for that call id:

$ python - <<'PY' # fetch the live call and list its tool calls role=tool_calls toolCalls=['Verify_phone_number'] role=tool_call_result result={... "status": "valid", "property_group_id": "17232efd..." } role=tool_calls toolCalls=['check_availability'] role=tool_call_result result={"status": "available"} # NO 'submit_complaint' anywhere - the model had all the data and still never called it
💡 Tip — absence is evidence

The most powerful clue in both bugs was something that wasn't there: no search-listings request, no submit_complaint tool call. When an agent claims success, don't just read what it said — grep the logs for the request that should have happened. A missing line is a louder signal than an error line.

8 · Anchor resolution on the most stable entity (flat-centric ownership)

Plain-English explanation. To save a record (a complaint, a lead) you need to know who owns it — which manager it belongs to — so the right person sees it. You can derive that ownership by walking a chain of relationships, or by reading it directly off the closest stable thing. The principle: anchor on the entity that always exists and always carries the answer, rather than a longer chain that can break at any link.

Why we need it (for CRM specifically). Our data hierarchy is PropertyGroup → Building → Flat → Tenant. The complaint webhook used to find the manager by walking flat → building → property group → manager_id. But some units are standalone (a bungalow, a house) with no building — so that chain hits a missing link and returns nothing, and the complaint gets saved with manager_id = NULL, invisible to the manager. The fix: every flat carries its own manager_id column (added in an earlier migration), so we read it directly off the flat. The flat is the entity the caller actually identified by its number, it always exists, and it always has an owner.

How it works (analogy). To find who's responsible for a hotel room, you could look up the room → the floor → the wing → the wing's manager. But if a cottage has no "floor" or "wing," that lookup fails. Far simpler: every room key already has the manager's name printed on it. Read the key.

Jargon decoder.

  • standalone unit — a flat with building_id = NULL (a bungalow/house with no parent building).
  • resolution chain — deriving a value by hopping across related tables.
  • migration — a versioned change to the database structure (here, the one that added flats.manager_id and backfilled it).
  • vestigial field — a parameter that's still required but no longer used by anything; dead weight that adds friction.

The discovery that made the fix safe. Before trusting flats.manager_id, we checked the live database — was the column actually populated, including for standalone units?

$ python - <<'PY' # count flats and NULL owners flats total=90 flats with NULL manager_id : 0 standalone (no building) : 11 standalone w/ NULL manager : 0 # every standalone unit already has an owner

📖 Deep Dive — why the vestigial field was worth deleting

submit_complaint required property_group_id, the prompt had a whole section about fetching and passing it, and… the webhook never read it. Keeping a required field that does nothing isn't harmless: it's one more value the model must produce to make a valid call, which (per Concept 6) is exactly the kind of friction that makes a flaky tool flakier. Removing it both simplified the model's job and deleted a misleading section of the prompt. Dead parameters are technical debt with a behavioural cost.

🐛 Bug Journal

Three bugs, three completely different root causes. This is the heart of the session — read each as a detective story.

🐛 Bug 1 — Max loops on find_units, never saves a lead

🚨 The Symptom

On an English test call, Max found a unit and qualified the caller, then near the end repeated "Let me check that in my system, one moment. Un instant, je vérifie ça." several times, never confirmed the lead, and the dashboard showed the lead as "Unknown." The caller even asked "have you noted my lead?" and Max claimed yes — but nothing useful was saved.

🔍 The Diagnosis

We read the Render logs line by line and found a telling pattern:

  • Many GET /leasing/find-units requests — including one with an empty query=.
  • Zero GET /leasing/search-listings.
  • Zero POST /voice/lease-lead-direct (the lead-save endpoint).
  • A final [LEASE EOC] Lead saved (structured=False) ... name=Unknown.

So out of three tools, only find_units ever ran. The empty-query= call was the clue: that's a lead-save attempt (which has no query field) landing on find_units (whose only param is query, defaulting to empty). We then opened the tool definitions and saw all three carried function.name = "api_request_tool", and a VAPI community note confirmed: duplicate function names mean only the first tool is callable. The "Unknown" lead was a separate safety-net (an end-of-call extractor) firing because the real save never happened.

🧠 The Root Cause

A tool-name collision. The model addresses tools by function.name; all three lease tools shared one name, so VAPI/OpenAI deduped them and only the first (find_units) was reachable. When Max wanted submit_lease_lead, the call resolved to find_units, returned search results instead of a save confirmation, and Max — never seeing success — retried, producing the loop and the repeated bilingual filler (that filler being find_units' static request-start message).

🔧 The Fix

Give every tool a unique function.name via the helper from Concept 2, and remove the static bilingual filler (Concept 4). Before/after, distilled:

"function": {"name": "api_request_tool", "description": "Find available units..."}    # find_units
"function": {"name": "api_request_tool", "description": "Preference-based search..."}   # search_listings
"function": {"name": "api_request_tool", "description": "Capture the lead..."}          # submit_lease_lead
# _alias_apirequest_tool_names() copies each tool's top-level name into function.name:
"function": {"name": "find_units", ...}
"function": {"name": "search_listings", ...}
"function": {"name": "submit_lease_lead", ...}   # now reachable -> leads actually save

Verified on the live assistant: tools=['find_units', 'search_listings', 'submit_lease_lead'], each with a matching unique function.name. The next real call saved a qualified lead with the caller's real name.

🛡️ The Lesson

When an agent repeats itself or only ever hits one endpoint, suspect that the other tools are unreachable, not that the model is "confused." The fastest tell is in the logs: which tools fired, and which never did. And whenever you template multiple tools from one prototype, make uniqueness a structural guarantee (a helper, a test), because copy-paste will reintroduce duplicates.

🐛 Bug 2 — Alex says "complaint logged" but files nothing

🚨 The Symptom

A complaint test call (broken AC, flat 1804). Alex verified the caller, checked availability, confirmed a callback time, and said: "Your complaint has been logged, and a callback is scheduled." But no complaint and no appointment appeared on the dashboard, and the Render logs had no POST /voice/webhook at all.

🔍 The Diagnosis

We first suspected config: maybe submit_complaint was mis-wired, or required a field the model couldn't supply. So we fetched the live tool config — it was correct (type function, server URL /voice/webhook, required fields present). We checked whether verify-phone returned the property_group_id the tool then required — it did (17232efd...) — and whether flat 1804 was a standalone unit — it wasn't. With config and data ruled out, we fetched the live VAPI call object and read the model's message list: it contained Verify_phone_number and check_availability tool calls and their results, but no submit_complaint tool call whatsoever. The "errors" we grepped turned out to be the literal text "[Error Handling]" in the prompt — a red herring.

🧠 The Root Cause

Prompt weakness let the model narrate instead of act. The model had everything it needed and still chose to speak "complaint logged" without emitting the tool call. Comparing prompts revealed why: Max's lead-save is hammered as mandatory and excluded from the "say a phrase first" list, while Alex's submit_complaint was mentioned once in a numbered list and included among tools to pre-narrate. So Alex produced the checking phrase and the success line as one fluent turn — and skipped the call. It was never a config or data bug.

🔧 The Fix

Three prompt edits (full text in Concept 6): (1) remove submit_complaint from the checking-phrase list, (2) make step 4/5 an explicit "you MUST emit the call; never say 'logged' without calling it," and (3) add a [Complaint Submission - NO EXCEPTIONS] block. Zero code or tool-config change. Pushed via the rewritten HTTP-PATCH script and verified the new section was live on the assistant.

🛡️ The Lesson

When an agent claims success but nothing persists and there's no request at all on your server, the model never called the tool — so look at the prompt, not the plumbing. The provider's call object is the ground truth for "did the model emit the call." And design prompts so side-effects are separated from narration: never let the success sentence live in the same breath as the action it's supposed to follow.

🐛 Bug 3 — The latent NULL owner for standalone units

🚨 The Symptom

This one was latent — surfaced by the user's question, not a crash: "won't anchoring on the flat be better for standalone units?" The hidden failure: a complaint from a building-less unit would resolve manager_id = NULL through the old chain, so it would save but be invisible to the manager (filtered out by row-level security).

🔍 The Diagnosis

We traced the webhook's owner resolution: phone → tenant → flat → building → property group → manager_id. For a standalone unit, flat.building_id is NULL, so the chain dead-ends and manager_id stays None. We confirmed against the live DB that 11 of 90 flats are standalone — and crucially that every flat (standalone included) already has a populated flats.manager_id column. We also noticed the property_group_id the tool required was never actually read by the webhook.

🧠 The Root Cause

The resolution was anchored on the wrong entity — a multi-hop chain through buildings, which doesn't exist for standalone units (and whose properties_list.manager_id could itself be NULL). The robust anchor is the flat itself, which always exists and carries its owner directly.

🔧 The Fix

Read flats.manager_id directly (Concept 8): 2 hops instead of 4, works for every unit type, and no fragile NULLs. We also deleted the vestigial property_group_id from submit_complaint and its prompt section. (The backend half ships on the next Render deploy; the tool-config half is already live.)

🛡️ The Lesson

Every relationship hop is a place a query can return nothing. When several records all need the same fact (here, the owner), put that fact on the closest stable entity and read it directly. And listen to "won't X be simpler?" questions — they often surface a latent edge-case bug before a real user hits it.

🧯 Troubleshooting / Common Errors

The agent repeats the same "one moment" line and never finishes

Cause: a tool the model wants is unreachable (often a name collision), so it retries the only tool it can reach, replaying that tool's request-start message. Fix: confirm every tool's function.name is unique (run the alias helper); check the logs for which endpoints actually fired.

The agent says it saved something, but nothing is in the database

Cause A (no request at all): the model never emitted the tool call — a prompt-strength problem. Fetch the VAPI call object and confirm the tool is absent from the message list; then harden the prompt. Cause B (request failed): the call fired but the handler errored — look for the POST and its non-200 / error log.

A record saves but the manager can't see it

Cause: manager_id resolved to NULL, so row-level security hides it. Fix: resolve the owner from flats.manager_id directly rather than a chain that can dead-end on standalone units.

VAPI push returns 200 but the field didn't change

Cause: the SDK dropped an unrecognised field, or you sent the wrong case (first_message_mode instead of firstMessageMode). Fix: use the raw HTTP PATCH with the snake→camel map and re-read the response body to confirm the field stuck.

A backend code change "didn't work" after deploying the agent

Cause: you pushed the VAPI config but not the backend. The voice.py/route changes live on Render and need a git push to redeploy. Fix: remember the two deploy surfaces — push config and redeploy the backend.

🔭 What's Next

With both agents reliably recording what callers ask for, the natural next step is defence in depth: give the complaint agent the same end-of-call safety net the lease agent has, so a complaint can be reconstructed from the transcript even if a future prompt regression makes the model skip the tool. After that, we'll want a small automated test that asserts tool-name uniqueness and required-field shape for every agent at build time — turning today's manual verification into a guarantee. And once the standalone-unit owner fix is live on Render, a quick standalone-unit test call (pointing a test tenant's phone at a building-less flat) closes the loop on Bug 3.
