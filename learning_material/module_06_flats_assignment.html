Section 1 — What You Are Building

This module covers the flats layer — the individual units inside buildings. A flat is the entity that ties together a physical location (building_id), a resident (tenant_uuid), and a complaint history. The trickiest part is the bidirectional foreign key: both flats.tenant_uuid and tenants.flat_uuid point at each other, and you must keep them in sync.

Bidirectional FK (the "married couple" pattern) ──────────────────────────────────────────────── flats table tenants table ────────────────── ────────────────────── uuid PK uuid PK flat_number UNIQUE name building_id FK→buildings phone UNIQUE tenant_uuid FK→tenants.uuid flat_uuid FK→flats.uuid occupied bool When you ASSIGN a tenant to a flat, you must update BOTH: UPDATE flats SET tenant_uuid = 'tenant-uuid', occupied = true WHERE uuid = 'flat-uuid' UPDATE tenants SET flat_uuid = 'flat-uuid' WHERE uuid = 'tenant-uuid' When you UNASSIGN: UPDATE tenants SET flat_uuid = NULL WHERE uuid = 'tenant-uuid' UPDATE flats SET tenant_uuid = NULL, occupied = false WHERE uuid = 'flat-uuid'

This module also covers two VAPI integration endpoints (/verify-phone and /identify-caller) that must always return HTTP 200, and the _clean_db_error helper that translates PostgreSQL error codes into human-readable messages.

Section 2 — Concept Deep-Dives

Bidirectional FK — Why Two Pointers?

In a strict normalized schema, you would have only one FK: either flats.tenant_uuid OR tenants.flat_uuid, not both. Having both creates data redundancy — two columns storing the same relationship.

This codebase uses both intentionally for two different access patterns:

  • Starting from a flat: flat.tenant_uuid — "who lives here?" — one lookup, no join
  • Starting from a tenant: tenant.flat_uuid — "where does this person live?" — one lookup, no join

The cost: any write that changes the relationship must update both rows atomically. If you update one but not the other (e.g. server crash mid-operation), the data is corrupted. This is why assign and unassign always do two updates in sequence.

Supabase limitation: PostgREST does not support multi-table transactions in a single HTTP call. The two updates are separate API calls with no rollback. If the second update fails, the first is already committed. In practice this is acceptable for an MVP but would need a Postgres function (RPC) for production-grade atomicity.

Input Normalization — .strip().upper()

Flat numbers are typed by humans. Humans are inconsistent. A flat registered as "A-101" might be queried as "a-101", " A-101 ", or "a101". Without normalization, these all fail to match.

python# All these should match the stored flat "A-101"
# Without normalization: only exact match works
# With normalization: all work

flat_number_normalized = flat_number.strip().upper()
# " a-101 " → "A-101" ✓
# "a-101"   → "A-101" ✓
# "A-101"   → "A-101" ✓

# Also used in queries with ilike (case-insensitive LIKE)
db.table("flats").select("*").ilike("flat_number", normalized_flat).execute()

ilike is PostgreSQL's case-insensitive string match. Combined with .strip().upper() on the input, every flat lookup is whitespace-tolerant and case-insensitive. This pattern appears in every route that accepts a flat number from outside.

PostgreSQL Error Codes and _clean_db_error

When a database constraint is violated, PostgreSQL raises an exception with a numeric error code. Without handling, these leak raw error messages like "duplicate key value violates unique constraint 'flats_flat_number_key'" to the API caller. This is confusing and exposes schema details.

The _clean_db_error helper maps the three most common codes to human-readable messages:

Error CodePostgreSQL meaningHuman message
42501INSUFFICIENT PRIVILEGE (RLS policy denied)"Permission denied: you are not authorized..."
23505UNIQUE VIOLATION (duplicate record)"This record already exists."
23503FOREIGN KEY VIOLATION (referenced row missing)"A required related record does not exist."
 
pythondef _clean_db_error(e: Exception) -> str:
    code = str(getattr(e, 'code', ''))
    if '42501' in code or '42501' in str(e):
        return "Permission denied: you are not authorized..."
    if '23505' in code or '23505' in str(e):
        return "This record already exists."
    if '23503' in code or '23503' in str(e):
        return "A required related record does not exist."
    # Fall back to the raw message from the exception if it's a string
    msg = getattr(e, 'message', None)
    if msg and isinstance(msg, str):
        return msg
    return "A database error occurred. Please try again."

The code checks both e.code (Supabase client attribute) and str(e) (the exception string) for the error code string. This is necessary because different versions of the Supabase Python client surface the code in different ways.

Service-Role Client for Flat INSERT — Why?

The POST /flats endpoint uses the service-role client to insert the flat, even though it also uses the authenticated client for queries. Why?

Supabase RLS INSERT policies can be restrictive. The flats table might have a policy that prevents inserting rows via the anon key if the user doesn't have explicit write permission. The service-role key bypasses all RLS policies, guaranteeing the insert works regardless of policy configuration.

python@router.post("")
async def create_flat(
    ...
    db: Client = Depends(get_authenticated_db),   # for reads (RLS-filtered)
    svc: Client = Depends(get_service_db),         # for writes (bypasses RLS)
):
    # Reads use RLS-enforced client — only sees this manager's data
    existing = db.table("flats").select("*").eq("flat_number", normalized).execute()

    # Insert uses service-role client — guaranteed to work
    flat_response = svc.table("flats").insert(flat_payload).execute()

Security note: Using service-role for writes is safe here because the route is still protected by require_active_subscription — unauthenticated users can't reach this endpoint. The service-role bypass is only to satisfy the INSERT policy, not to skip authentication.

Route Ordering — VAPI endpoint MUST come before /{flat_number}

FastAPI matches routes in the order they are registered. Consider these two routes:

python# If registered in this order:
@router.get("/{flat_number}")    # dynamic — matches ANY string
@router.post("/verify-phone")  # literal — matches only "verify-phone"

# Request: POST /flats/verify-phone
# FastAPI would try to match /{flat_number} first → flat_number="verify-phone"
# The verify-phone handler is NEVER reached!

The fix in flats.py: VAPI endpoints (/verify-phone, /identify-caller) are defined at the top of the file, before any dynamic path routes like /{flat_number}. FastAPI matches routes top-to-bottom.

Rule: Always register specific literal paths before dynamic /{param} paths. This pattern comes up in both flats.py and appointments.py.

Phone Normalization — Country Code Problem

VAPI passes the caller's phone number in E.164 format: +919998064026. But the tenant's phone might be stored as 9998064026 (without country code). A simple equality check would fail.

pythonimport re

def _digits_only(phone: str) -> str:
    """Strip everything except digits."""
    return re.sub(r"\D", "", phone)


def _phones_match(a: str, b: str) -> bool:
    """
    Compare two phone numbers flexibly.
    Normalises both to digits only, then checks whether
    either is a SUFFIX of the other.

    +919998064026  vs  9998064026  → digits: 919998064026 vs 9998064026
                                   → 919998064026.endswith("9998064026") → True ✓
    """
    da, db_ = _digits_only(a), _digits_only(b)
    if not da or not db_:
        return False
    return da.endswith(db_) or db_.endswith(da)

The suffix check handles both directions: VAPI number has country code but DB doesn't, or DB has country code but VAPI doesn't. It also handles cases where both have or both lack the country code.

Section 3 — VAPI Endpoints

POST /flats/verify-phone

This is called by VAPI as an API Request tool when a caller says their flat number. VAPI sends the flat number in the request body and the caller's phone in the query string.

python@router.post("/verify-phone", response_model=FlatVerifyPhoneResponse)
async def verify_phone(
    request: FlatVerifyPhoneRequest,
    phone_number: Optional[str] = Query(None),  # from VAPI: {{customer.number}}
    db: Client = Depends(get_service_db),        # service-role: no JWT from VAPI
):
    # CRITICAL: never raise, always return FlatVerifyPhoneResponse
    try:
        if not request.flat_number:
            return FlatVerifyPhoneResponse(
                result="Verification failed: no flat number provided.",
                status="invalid"
            )

        normalized_flat = request.flat_number.strip().upper()

        # 1. Lookup flat (include building_id for property_group resolution)
        flat_resp = (
            db.table("flats")
            .select("uuid, tenant_uuid, building_id")
            .ilike("flat_number", normalized_flat)
            .execute()
        )
        if not flat_resp.data:
            return FlatVerifyPhoneResponse(
                result="Verification failed: flat not found.", status="invalid"
            )

        flat = flat_resp.data[0]
        flat_uuid = flat["uuid"]

        # 2. Find tenant — primary: flat_uuid FK; fallback: flat.tenant_uuid
        tenant_resp = (
            db.table("tenants").select("phone").eq("flat_uuid", flat_uuid).execute()
        )
        if not tenant_resp.data and flat.get("tenant_uuid"):
            tenant_resp = (
                db.table("tenants").select("phone").eq("uuid", flat["tenant_uuid"]).execute()
            )

        if not tenant_resp.data:
            return FlatVerifyPhoneResponse(
                result="Verification result: vacant.", status="vacant"
            )

        # 3. Compare phones using flexible suffix-match
        tenant_phone = tenant_resp.data[0].get("phone", "")
        match = _phones_match(phone_number, tenant_phone)

        if match:
            current_time_ist = datetime.now(IST).strftime("%Y-%m-%dT%H:%M:%S")

            # Resolve property_group_id: flat → building → property_group
            property_group_id = None
            if flat.get("building_id"):
                bldg_resp = (
                    db.table("buildings")
                    .select("property_id")
                    .eq("id", flat["building_id"])
                    .limit(1)
                    .execute()
                )
                if bldg_resp.data:
                    property_group_id = str(bldg_resp.data[0]["property_id"])

            return FlatVerifyPhoneResponse(
                result=f"Verification result: valid. Current IST time: {current_time_ist}.",
                status="valid",
                datetime=current_time_ist,
                property_group_id=property_group_id,
            )

        return FlatVerifyPhoneResponse(
            result="Verification failed: phone does not match.",
            status="invalid"
        )

    except Exception as e:
        print(f"[ERROR] verify_phone failed: {type(e).__name__}: {e}")
        # Never raise — return a safe error response
        return FlatVerifyPhoneResponse(
            result="Verification failed due to an internal error.", status="invalid"
        )

Three statuses are possible: "valid" (phone matches registered tenant), "invalid" (flat not found, phone mismatch, or error), and "vacant" (flat exists but has no tenant). VAPI reads the status field to decide what to say to the caller.

The two-step tenant lookup (first by flat_uuid, fallback to flat.tenant_uuid) exists because data created in different sessions may have only one of the two FK directions set. The fallback guards against historical data inconsistency.

Section 4 — Flat CRUD Line by Line

POST /flats — multi-step create with image upload

Creating a flat is the most complex operation in this file. It has 6 numbered steps:

python@router.post("", response_model=FlatResponse, status_code=201)
async def create_flat(
    flat_number: str = Form(...),           # Form fields (not JSON body)
    address: Optional[str] = Form(None),   # because request may include a file
    ...
    image: Optional[UploadFile] = File(None),
    db: Client = Depends(get_authenticated_db),
    svc: Client = Depends(get_service_db),
):
    image_url = None
    uploaded_filename = None  # track for cleanup on failure

    # STEP 1: Upload image to Supabase Storage if provided
    if image:
        contents = await image.read()
        file_ext = image.filename.split('.')[-1]
        uploaded_filename = f"{uuid4()}.{file_ext}"
        svc.storage.from_("Property Pics").upload(
            uploaded_filename, contents, {"content-type": image.content_type}
        )
        image_url = svc.storage.from_("Property Pics").get_public_url(uploaded_filename)

    # STEP 2: Validate and normalize
    flat_number_normalized = flat_number.strip().upper()

    # STEP 3: Check for duplicates BEFORE any DB writes
    existing_flat = db.table("flats").select("*").eq("flat_number", flat_number_normalized).execute()
    if existing_flat.data:
        # Clean up uploaded image before raising error
        if uploaded_filename:
            svc.storage.from_("Property Pics").remove([uploaded_filename])
        raise HTTPException(400, detail=f"Flat {flat_number_normalized} already exists")

    # STEP 4: Create the flat (uses service-role to bypass INSERT policy)
    flat_payload = {
        "flat_number": flat_number_normalized,
        "image_url": image_url,
        "building_id": building_id,
        "tenant_uuid": None,
        "occupied": False,
        ...
    }
    flat_response = svc.table("flats").insert(flat_payload).execute()
    flat = flat_response.data[0]
    flat_uuid = flat["uuid"]

    # STEP 4.5: Initialize feature flags (non-blocking — errors are logged only)
    try:
        feature_service = FeatureService(db)
        await feature_service.initialize_unit_features(flat["id"])
    except Exception as f_err:
        print(f"[FEATURE INIT ERROR] {f_err}")

    # STEP 5: Create and link tenant if provided
    tenant_info = None
    if tenant_name and tenant_phone:
        tenant_payload = {"name": tenant_name.strip(), "phone": tenant_phone.strip(), "flat_uuid": flat_uuid}
        tenant_response = db.table("tenants").insert(tenant_payload).execute()
        if tenant_response.data:
            tenant_info = tenant_response.data[0]
            # Bidirectional link: update flat to point at new tenant
            db.table("flats").update({
                "tenant_uuid": tenant_info["uuid"], "occupied": True
            }).eq("uuid", flat_uuid).execute()

    # STEP 6: Return flat with nested tenant details
    return {**flat, "tenant": tenant_info}

The duplicate check (Step 3) happens before any DB writes. This ensures that if the flat already exists, we clean up the uploaded image and return a 400 error without leaving orphaned data in storage.

The outer try/except at the bottom of the function calls svc.storage.from_("Property Pics").remove([uploaded_filename]) if an unexpected error happens at any step — this prevents orphaned images accumulating in storage.

PATCH /{flat_uuid}/assign-tenant

python@router.patch("/{flat_uuid}/assign-tenant")
async def assign_tenant(flat_uuid: str, body: AssignTenantRequest, ...):
    # Guard 1: flat must exist
    flat_resp = db.table("flats").select("uuid, tenant_uuid").eq("uuid", flat_uuid).execute()
    if not flat_resp.data:
        raise HTTPException(status_code=404, detail="Flat not found")

    # Guard 2: flat must be vacant
    if flat_resp.data[0].get("tenant_uuid"):
        raise HTTPException(status_code=400, detail="Flat is already occupied")

    # Bidirectional update: both sides of the FK
    db.table("flats").update({
        "tenant_uuid": body.tenant_uuid, "occupied": True
    }).eq("uuid", flat_uuid).execute()

    db.table("tenants").update({
        "flat_uuid": flat_uuid
    }).eq("uuid", body.tenant_uuid).execute()

    return {"success": True}

PATCH /{flat_uuid}/unassign-tenant

python@router.patch("/{flat_uuid}/unassign-tenant")
async def unassign_tenant(flat_uuid: str, ...):
    flat_resp = db.table("flats").select("uuid, tenant_uuid").eq("uuid", flat_uuid).execute()
    if not flat_resp.data:
        raise HTTPException(status_code=404, detail="Flat not found")

    tenant_uuid = flat_resp.data[0].get("tenant_uuid")
    if tenant_uuid:
        # Clear tenant side first
        db.table("tenants").update({"flat_uuid": None}).eq("uuid", tenant_uuid).execute()

    # Then clear flat side
    db.table("flats").update({
        "tenant_uuid": None, "occupied": False
    }).eq("uuid", flat_uuid).execute()

    return {"success": True}

Section 6 — Real Bugs We Hit

Bug: VAPI couldn't reach /verify-phone — 404 at the wrong endpoint

Symptom: VAPI tool calls to POST /flats/verify-phone returned 404 or matched the wrong route. The flat lookup was returning results for a flat literally named "verify-phone".

Root cause: @router.get("/{flat_number}") was registered before @router.post("/verify-phone"). FastAPI matched flat_number="verify-phone" instead of the literal route.

Fix: Move all literal-path VAPI endpoints to the top of the router file, before any /{param} routes. Added a comment block explaining this constraint.

Bug: Phone verification failed for Indian numbers (country code prefix)

Symptom: Tenants calling their own number were told "phone does not match". DB had 9998064026, VAPI sent +919998064026.

Root cause: Original code used tenant_phone == phone_number (exact match). Failed for every caller with a country code prefix.

Fix: Replaced with _phones_match() using digit-only suffix comparison. Also handles edge cases: empty strings, None values, and numbers stored with or without country code.

Bug: Orphaned image in Supabase Storage after duplicate flat error

Symptom: Manager uploads a photo while creating flat "A-101", but A-101 already exists. API returns 400. The image file was already uploaded — it now sits in storage with no reference and accumulates over time.

Root cause: Image upload (Step 1) happened before the duplicate check (Step 3).

Fix: Added cleanup before every raise in the duplicate check and in the outer catch block. Track the uploaded filename in uploaded_filename so cleanup knows what to remove.

pythonif existing_flat.data:

            pass  # storage cleanup failure is non-fatal

Exercise 3 Hard

Currently, PATCH /{flat_uuid}/assign-tenant does NOT check whether the tenant being assigned already lives in a different flat. If tenant X is in flat A, and you assign them to flat B, flat A's tenant_uuid is left pointing at a tenant who no longer lives there. Fix this by checking if the tenant is already assigned elsewhere, and if so, first clearing the old flat before doing the new assignment.

Full worked solution 
python@router.patch("/{flat_uuid}/assign-tenant")
async def assign_tenant(flat_uuid: str, body: AssignTenantRequest, user=Depends(require_active_subscription), db=Depends(get_authenticated_db)):
    # Guard 1: target flat must exist and be vacant
    flat_resp = db.table("flats").select("uuid, tenant_uuid").eq("uuid", flat_uuid).execute()
    if not flat_resp.data:
        raise HTTPException(status_code=404, detail="Flat not found")
    if flat_resp.data[0].get("tenant_uuid"):
        raise HTTPException(status_code=400, detail="Flat is already occupied")

    # Guard 2: check if this tenant is already in another flat
    tenant_resp = db.table("tenants").select("uuid, flat_uuid").eq("uuid", body.tenant_uuid).execute()
    if not tenant_resp.data:
        raise HTTPException(status_code=404, detail="Tenant not found")

    existing_flat_uuid = tenant_resp.data[0].get("flat_uuid")
    if existing_flat_uuid and existing_flat_uuid != flat_uuid:
        # Clear the old flat first
        db.table("flats").update({
            "tenant_uuid": None, "occupied": False
        }).eq("uuid", existing_flat_uuid).execute()

    # Now do the bidirectional assignment
    db.table("flats").update({
        "tenant_uuid": body.tenant_uuid, "occupied": True
    }).eq("uuid", flat_uuid).execute()

    db.table("tenants").update({
        "flat_uuid": flat_uuid
    }).eq("uuid", body.tenant_uuid).execute()

    return {"success": True, "moved_from": existing_flat_uuid}

Section 8 — Why This Design

Decision: Bidirectional FK (flats.tenant_uuid ⇄ tenants.flat_uuid) vs. single FK

ApproachProsCons
Both sides store the link (chosen)Either table can be queried alone with no JOIN — the flats list shows tenant names and the tenants list shows flat numbers in one SELECT eachTwo writes per assign/unassign; the two columns can drift if one write fails — assignment must update both or neither
Single FK on tenants.flat_uuidOne source of truth; can never disagree with itself“Who lives in flat 101?” always needs a JOIN or reverse lookup; PostgREST nested selects get deeper
Join table (occupancies)Models history (move-in/move-out dates)Overkill for an MVP where a flat has at most one current tenant
Senior takeaway: denormalization is a loan — you get read speed now and pay with write discipline forever. Every place that assigns or unassigns MUST go through the one endpoint that updates both sides. Never update flats.tenant_uuid from anywhere else.

Decision: Mapping PostgreSQL error codes to HTTP responses

ApproachProsCons
Catch APIError, map 23505→409, 23503→400 (chosen)The frontend gets actionable messages (“flat number already exists”) instead of a blank 500Mapping table must be maintained as constraints are added
Let errors bubble as 500Zero codeUsers see “something went wrong”; support burden lands on you
