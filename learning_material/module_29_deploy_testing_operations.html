Section 1 — What You Are Building

Modules 00–28 built the product. This module is about everything that keeps it alive: how changes reach production safely, how you know they work, and how you find out why they don't. None of it is optional knowledge — every session from 9 onward spent as much time on these skills as on feature code, which is an accurate picture of senior work.

The three operational surfaces of this system 1. BACKEND CODE git push → Render auto-deploy (env vars in dashboard) 2. AGENT CONFIG backend/scripts/*.py → VAPI API (dry-run, then push) 3. DATABASE numbered SQL in Supabase SQL Editor (Module 27) Different speeds, different blast radii, different rollbacks. Knowing WHICH surface a change lives on is the first deploy decision.

Section 2 — Concept Deep-Dives

1 · The two-stage deploy: dry-run, then push

Every agent-config deploy script in backend/scripts/ (e.g. update_lease_agents.py, update_shared_agents.py) supports a dry run: build the would-be config, diff it against what's live, print, change nothing. The real push runs only after a human reads the diff. This mattered every single session because the scripts fan out to five assistants at once — a bad push is five broken phone lines.

python backend/scripts/update_lease_agents.py --dry-run   # show the diff
python backend/scripts/update_lease_agents.py             # apply it
python backend/scripts/vapi_inspect.py                    # read back what's ACTUALLY live
🔑 Key concept: a deploy isn't done when the script exits — it's done when you read the live state back and it matches intent (Session 15 verified the live config by fetching it after provisioning). Push, then read back, every time. Config systems drift; read-back is how you catch it.
2 · Snapshots and idempotent rollback

Before Session 10 touched shared latency config, it wrote a rollback snapshot document: the exact current values of everything about to change, plus an idempotent push script that restores them. Rollback engineering happens before the risky change, while the system still works — not during the incident, from memory, at 2am. "Idempotent" matters: a restore you can run twice safely is a restore you can run while panicking.

3 · Prompt-only changes are their own deploy class

Sessions 13–15 shipped behavior changes (French register, handoff fixes) without any backend release — they were prompt/config pushes only. Recognizing which surface a change needs is leverage: prompt-only fixes skip the Render deploy queue entirely, and conversely, a fix that spans both surfaces needs ordering (backend first if the prompt references new tool behavior). The question to ask of every voice-agent change: "which of the three surfaces does this touch, and in what order?"

4 · The test pyramid, as it actually exists in this repo
LayerWhereWhat it catchesSpeed
Unitbackend/tests/unit/, tests/test_city_matching.py (corpus)Matcher regressions, auth logic, chatbot tool schemasSeconds
Integrationbackend/tests/integration/ (per-route: tenants, leasing, voice…)Route + schema + DB contract breaksMinutes

E2Ee2e/ (Playwright + MANUAL_TESTING.md)Full browser flows: auth → CRUD → UI stateSlow; run before releases
Live callA phone, multiple times (non-determinism!)Everything no automation can hear: register, dead air, toneHuman minutes — the scarcest kind

The pyramid's operational rule: test at the layer that failed. Session 16's bug was a query bug → it got a query-contract test, not an e2e test. Session 15's bug was conversational → it got repeated live calls, not a unit test. Writing the test at the wrong layer gives you green checkmarks and the same bug next month.

5 · Query-contract tests — asserting on the SELECT itself

Session 16's phantom-vacancy bug (full case study below) was fixed by adding a column name to a .select(...) projection. The regression test doesn't spin up a database — it asserts on the query string the code builds: does the projection include the column the downstream filter needs? That's testing the contract between query and consumer. It's fast, needs no fixtures, and fails the instant someone "cleans up" the projection again. When a bug is "the code asked for the wrong thing," pin the asking, not just the outcome.

6 · Environment parity — the stale virtualenv wall

Also Session 16: the new tests wouldn't run locally because the dev virtualenv had drifted behind requirements.txt — the code under test imported a library the venv predated. Two rules fall out: (1) when tests fail with ImportError, suspect the environment before the code; (2) after every pull that touches requirements.txt, re-run pip install -r requirements.txt. Pinned versions (Session 9 pinned the new matcher deps) are what make "works on my machine" reproducible at all.

7 · Forensic debugging — the discipline the sessions keep reusing

Across sessions 11–17, the same investigation shape repeats. Learn it as a checklist:

  1. Layer isolation (Session 11): reproduce at the lowest layer you can reach directly. "Agent says no Montréal listings" → curl the backend endpoint first. If the backend is right, the bug is above it; you just eliminated half the system in one command.
  2. The flight recorder (Session 17): the provider keeps a per-call object — tools attached, messages exchanged, what the model actually did. Read it via vapi_inspect.py / the VAPI API before theorizing. Session 17's "missing tools" hypothesis died in one look: the tools were attached; the model just never called one.
  3. Falsify, don't confirm: Session 11 formed a function-name-collision hypothesis and then killed it with evidence before acting. The measure of a debugging session is hypotheses destroyed per hour.
  4. Verify bytes before blaming data (Sessions 11, 13, 16, 17): the recurring "11½ → 11Â½ corruption" was, three separate times, a Windows console rendering artifact (cp1252 vs UTF-8), not corrupt data. Check with python -c "print(open(f,'rb').read()[i:j])" — raw bytes end mojibake debates in seconds. A false bug costs as much as a real one until it's retracted.
  5. Distinguish artifacts from bugs (Session 16): the "$14,100 apartment" was an STT transcription artifact, not a data bug. Production forensics must sort observations into defect / artifact / expected — and only defects get fixes.
8 · Backend deployment — Render + environment variables

The backend deploys to Render: push to the deploy branch → build → restart. Configuration is entirely environment variables (docs/reference/RENDER_ENV_VARS.md is the canonical list — Supabase keys, Stripe, Twilio, SendGrid, VAPI, OpenAI, Groq). The operational habits:

  • A new env var is a deploy dependency: set it in Render's dashboard before deploying code that reads it — config.py's fail-fast startup (Module 01) will otherwise crash-loop the service.
  • Update RENDER_ENV_VARS.md in the same PR that introduces the variable — the doc is only useful while it's true.
  • After deploy, smoke: hit / and one authenticated endpoint (smoke_test_leasing.ps1 automates the leasing surface). Session 16 smoke-tested production after the fix deploy and found the two false alarms above — that's the smoke test doing its job: telling you what production actually looks like.
9 · The paper trail — living docs as part of the definition of done

Every session ends the same way: update CODEBASE_CONTEXT.md (the always-current map), append decision records to the relevant plan doc in docs/development_plans/, and record diagnoses in docs/diagnoses/. This isn't bureaucracy — Session 10's rollback doc and Session 8's diagnosis were load-bearing artifacts that later sessions built on. The rule from CLAUDE.md: docs update in the same session as the change, never "later."

Section 3 — Case Study: the Phantom Vacancy (Session 16, end to end)

One bug, worked from complaint to closed — every concept above appears in order.

  1. The complaint: callers asking for a size-filtered search ("a 3½ in Montréal") always heard "nothing available" — while unfiltered searches for the same city returned listings. The agent flip-flopped between its two search tools.
  2. Read the transcript like a detective: pin down which tool returned empty and with which parameters. The defect list: size-filtered = always zero; unfiltered = fine.
  3. Find the suspect code: the size filter ran in Python, after the fetch — on rows whose .select(...) projection didn't include the size column. Every row's size read as missing; every row failed the filter; result: permanently empty. No error anywhere, because asking PostgREST for a subset of columns is perfectly legal.
  4. The fix: one word, three places — add the column to three projections. The diff is trivially small; the finding is not. (This is the general shape of projection bugs: silent, legal, and downstream.)
  5. Regression tests at the right layer: query-contract tests asserting the projections include what the filters consume (test_listings_for_agent_v2.py).
  6. Hit the environment wall: stale venv, ImportError, pip install -r requirements.txt, tests green.
  7. Update the living docs, deploy to Render, then smoke-test production — where the two false alarms ($14,100 rent, "4Â½") were investigated and correctly classified as artifacts, not bugs.
🐛 The companion bug (Session 17), compressed: a partner's inbound test calls hit a dead line — the phone number was never bound to the entry assistant (provisioning created everything but the binding). Diagnosis path: check what the number points at (one API read) → confirm via the call ledger → bind → retest. Then the follow-up transcripts exposed the same-turn tool-call trap (Module 28, concept 4). Lesson: inbound and outbound are different routing paths — verify each end-to-end separately.

Section 4 — Why This Design

Decision: Dry-run-first deploy scripts vs. direct pushes

ApproachProsCons
Dry-run diff + human read + push + read-back (chosen)Five-assistant fan-out means one mistake is five outages; the diff catches it at zero cost; read-back catches partial failuresSlower; requires the script to be able to fetch and diff live state (worth building once)
Push directlyFastYou learn about mistakes from callers

Decision: Smoke-test production vs. trusting staging

ApproachProsCons
Scripted smoke against prod after every deploy (chosen)There is no staging VAPI + staging phone number + staging caller — the integration surface only fully exists in prod; smoke scripts make checking it cheap and repeatableSmoke calls touch real data — scripts must be read-only or clearly tagged
Full staging environmentSafe rehearsalDoubling every third-party integration (numbers, assistants, webhooks) for an MVP is cost without matching risk reduction — revisit at scale

Decision: Where a regression test lives

Bug classRight testWrong (but tempting) test
Query builds the wrong requestContract test on the built queryE2E that happens to traverse it (slow, and green if data masks it)
Matcher mis-scores inputCorpus unit testLive call (non-deterministic, unrepeatable)
Conversational behaviorRepeated live callsUnit test of the prompt string (proves nothing about behavior)
Route/schema contractIntegration test per routeManual curl you'll forget next month

Section 7 — Checkpoint ✓

One green ladder, one read diff

Run the unit tests and the city-matching corpus (both should pass in under a minute), then run update_lease_agents.py --dry-run and read the diff it prints without applying it.

Success: green tests, and you can explain each line of the dry-run diff — either "no drift" or you can name which session/change produced each difference. Being able to read a config diff against live is the checkpoint; pushing is just pressing enter.

Section 8 — Exercises

Easy Write a query-contract test

Problem: Pick any route that fetches rows and then filters/reads a field in Python. Write a test asserting the .select(...) projection contains every column the Python code consumes.

Solution sketch

Import the module, locate the select string (constant or built), and assert membership: assert "quebec_size" in LISTING_SELECT. If the projection is inline, extract it to a module-level constant first — that refactor is half the exercise's value: contracts you can test are contracts you can see. Model it on backend/tests/integration/test_listings_for_agent_v2.py.

Medium Rollback drill

Problem: You're about to change the lease agents' temperature and two prompt sections. Write the rollback snapshot first, Session-10 style: what do you record, where does it live, and what makes the restore idempotent?

Solution

Record: per-assistant current values of every field you'll touch (fetched from the live API, not from your repo — the repo is intent, the API is truth), timestamped, in docs/reference/ with a dated, searchable name (e.g. lease_agent_latency_config_2026-07-04.md — note the existing 2026-06-23 one as your template). Restore script: PATCH exactly those fields to exactly those values — PATCHing absolute values is naturally idempotent (running twice sets the same state twice), unlike "undo my diff" logic. Test the restore path once before making the risky change: an unrehearsed rollback is a hypothesis, not a safety net.

Hard Triage a mixed observation list

Problem: A production smoke test after a deploy surfaces: (a) a listing priced at $14,100/mo; (b) "4Â½" rendering in your terminal; (c) a size-filtered search returning zero rows; (d) one French call where the agent greeted in English. For each: defect, artifact, or needs-more-evidence? Name the single cheapest next action for each.

Solution
  • (a) Needs evidence → likely artifact: check the DB row. If the DB says $1,410 and only the transcript says $14,100, it's an STT artifact (Session 16's exact case). Cheapest action: one SELECT.
  • (b) Artifact: Windows console cp1252 rendering of UTF-8. Cheapest action: print raw bytes; if they're C2 BD (½), the data is fine. Do NOT "fix" the data — that's how false mojibake becomes real corruption.
  • (c) Defect until proven otherwise: the phantom-vacancy signature. Cheapest action: curl the endpoint with and without the filter; if filtered ≠ subset of unfiltered, open the projection.
  • (d) Needs evidence — non-determinism rule: one call proves nothing (Session 15). Cheapest action: read that call's flight-recorder object (was routing's language decision wrong — a defect in the router — or did the right assistant generate the wrong greeting — a prompt/firstMessage defect?), then place it before re-calling.

What's being tested: triage discipline — the instinct to buy maximum information with minimum action, and to never fix an artifact.
