When the Map Forgets a City & the Agent Forgets the Date

Three real phone transcripts landed on the desk. Two callers — both in Saint-Lazare, Québec — hung up after Max told them, in mangled French, that there was nothing in their town. A third was told a unit "isn't available that quickly" for a move-in that the unit actually could meet. This session is two surgical fixes wearing one theme — give the machine the truth it was missing. Fix #1: stop the unit-search from silently dropping a city it was secretly confident about. Fix #2: hand the agent a real clock set to Montréal time, because a language model has no idea what day it is. Along the way: a phantom "phonetic score of zero," a crash over a missing time-zone database, and a self-inflicted test bug — all documented.

🔴 Advanced ⏱️ ~85 min read / build 📋 Requires: Sessions 08–11 (French STT, fuzzy city matching, banded confirmation, deploy pipeline)

📦 Session Overview

This was a diagnose-from-transcripts session. No new feature — instead, three recorded calls exposed two independent defects in the lease agent (Max), and we fixed the two highest-leverage ones. The thread that started it:

You: do #1 and #2 (send time and date according to montreal, canada). keep rest of the issue context and if it arises again then we will see. ...after the code + verification... You: run update_lease_agents.py to deploy.

By the end we had:

  • Read three call transcripts as evidence and turned a vague "the agent is bad in French" into a ranked list of five discrete defects, each tied to a file and line.
  • Fixed #1 — the silent-drop. The unit lookup (find_units) judged a caller's city with a weaker string comparison than the one it used to ask "did you mean…?". So a city the system was internally confident about could be dropped from the results and never offered for confirmation — the caller heard "nothing found" for a town the manager actually serves. We unified the two so the gate can never be weaker than the ranker again.
  • Fixed #2 — the missing clock. Max never learns today's date (he never calls the tenant-verification tool that hands one out), so "next week" vs "late June" was pure guesswork. We stamped the current Montréal date/time onto every tool result and taught the prompt to treat it as today.
  • Proved both fixes against the real code — ran the actual matching library, found a genuine silent-drop case ("San Lazaro"), and exercised find_units end-to-end with a fake database.
  • Deployed the config half to all 5 live lease assistants with update_lease_agents.py — and were honest that the backend half still needs a separate deploy before the fixes are fully live.
  • Hit and documented three dev-time surprises: a phonetic matcher silently returning 0.00 (wrong interpreter), a ZoneInfoNotFoundError crash (missing tzdata), and a KeyError from a test asserting a field the API doesn't expose.
🔑 Learning objectives

By the end of this lesson you will be able to:

  • Read a noisy, bilingual call transcript and extract a precise, ranked defect list from it.
  • Explain the difference between three kinds of fuzzy string matching — edit-distance (difflib / rapidfuzz) versus phonetic (Metaphone) — and when each rescues a garbled word the others miss.
  • Recognise the "two scorers disagree" anti-pattern, where a decision and its safety-question use different yardsticks, and fix it with a single shared score.
  • Understand why a language model cannot be trusted with the current date, and inject a real "now" as ground truth through a tool response.
  • Handle time correctly: UTC, offsets, DST, and the IANA tz database via Python's zoneinfo + tzdata.
  • Catch a measurement artifact (your test environment lying) and write fail-open initialization that can't take a route down.

1 · Transcript triage: turning a messy call into a defect list

Plain-English explanation. A call transcript is a timestamped script of who said what, plus markers for when the agent ran a tool. It's noisy: the speech-to-text mishears words, French comes out half-English, and the agent's own sentences can be garbled by the voice. Triage means reading that mess and sorting it into distinct, named problems — separating "the agent said something wrong" (behaviour) from "the agent couldn't find something" (data/logic) from "the voice sounded broken" (text-to-speech).

Why we need it (for CRM specifically). A partner's bug report is usually one sentence: "the French calls are bad." That's not actionable. Two of our three calls ended in a hang-up; if you treat "bad French" as one problem you'll fix the wrong thing. Triage converts one complaint into five separate, independently-fixable defects, each rankable by impact — so you fix the two that lose customers first.

How it works (analogy). It's an emergency-room triage nurse. Five patients arrive; the nurse doesn't treat them in arrival order — they sort by severity, so the heart attack is seen before the sprained ankle. We read the transcripts and tagged each symptom with a layer (data, logic, TTS, turn-taking) and a severity (did the caller hang up?).

Jargon decoder.

  • transcript — the machine's written record of a call: each line is a speaker + timestamp; tool runs appear as their own lines (e.g. Find Units — Completed successfully).
  • STT (Speech-To-Text) — the engine that converts the caller's audio into text. It is the source of "garble" — e.g. it heard "Saint-Lazare" as Saint-L'Ador.
  • TTS (Text-To-Speech) — the reverse engine that voices the agent's words. Bad TTS makes Max sound broken even when his text is fine.
  • defect / symptom / root cause — the symptom is what you observe; the defect is the wrong behaviour; the root cause is the underlying reason in the code/config.

The raw evidence. Here is the end of Transcript 3 (a French call). The caller is in Saint-Lazare; the STT wrote it Saint-L'Ador. Watch the contradiction in Max's reply:

User: Oui, allô, je à Saint-L'Ador présentement. Et j'ai vu que vous avez des unités. [ Find Units — Completed successfully ] Max: Un instant, je ne trouve rien à Saint-Lador pour le moment. Nous avons des logements à Château-Güey et à Saint-Lazar. Est-ce qu'un de ces secteurs vous convient? User: Uh, oui, bien, ça que je viens de dire, oui. # "that's what I just said" [ caller hangs up ]

In one breath Max says he found nothing in "Saint-Lador" and then offers "Saint-Lazar" as an option — the same town. That contradiction is the bug fingerprint: the system clearly knows about Saint-Lazare (it's in the offer list) but the matcher refused to connect the caller's word to it. 🔑 Key Concept — a contradiction in the output is a gift

When a system both denies something and reveals it in the same breath ("I found nothing in Saint-Lador… we have Saint-Lazar"), you've been handed the exact shape of the bug. It means the data exists and one specific code path failed to connect to it. Don't skim past contradictions — they collapse the search space faster than any log.

2 · Fuzzy string matching, three different ways

Plain-English explanation. "Fuzzy matching" answers: how similar are two pieces of text? as a number from 0 (nothing alike) to 1 (identical). But there is more than one way to be "alike," and they disagree:

  • Edit-distance similarity — how many single-character insert/delete/swap edits turn one string into the other. difflib (Python's built-in) and rapidfuzz (a fast C library) both measure this by spelling. "Saint-Lazare" vs "Saint-Lazaire" scores high (one extra letter); "Saint-Lazare" vs "San Lazaro" scores low (many letters differ).
  • Phonetic similarity — how alike two words sound, ignoring spelling. An algorithm like Metaphone converts a word to a rough "sound code" (vowels dropped, similar consonants merged), then compares the codes. "San Lazaro" and "Saint-Lazare" can sound nearly identical even though their letters differ a lot.

Our matcher takes the maximum of all three (rapidfuzz, Metaphone-phonetic, difflib). The intuition: a pair is "similar" if it's similar by any reasonable measure. The phonetic leg is the one that rescues French-accent garble that the spelling-based legs miss.

Why we need it (for CRM specifically). The STT renders French-accented audio as pseudo-English spellings — it writes down what it thought it heard, letter by letter. So "Saint-Lazare" comes back as Saint-L'Ador, Saint-Lador, even San Lazaro. By spelling these look wrong; by sound they're obviously the same town. Without the phonetic leg, every accented caller risks being told their own city doesn't exist.

How it works (analogy). Edit-distance is a proofreader comparing two printed words letter by letter. Phonetic matching is a friend on a noisy phone line who can't hear the spelling but recognises the sound of the name. For garbled speech, you want both in the room — and you believe whichever one is most confident.

Jargon decoder.

  • difflib — Python's standard-library text-comparison module; SequenceMatcher(...).ratio() gives an edit-similarity in [0,1]. Always available, no install.
  • rapidfuzz — a third-party library doing the same idea much faster (and a bit smarter); returns 0–100, which we divide by 100.
  • Metaphone — a phonetic algorithm: it maps a word to a string of sounds (e.g. drops most vowels, folds "z"/"s"). Provided here by the jellyfish library.
  • normalize — clean a string before comparing: lowercase it, strip accents (é→e), turn hyphens into spaces, expand "St"→"Saint". Done by normalize_place() so both sides are compared on equal footing.

Annotated code — the normaliser and the hybrid score. Both already existed (from Session 08); read them now because Fix #1 turns on which of these the matcher actually trusts.

def normalize_place(s: str) -> str:
    # Put both strings on equal footing BEFORE comparing them.
    if not s:
        return ""
    s = unicodedata.normalize("NFKD", s)                 # split accented chars into base + accent mark
    s = "".join(c for c in s if not unicodedata.combining(c))  # drop the accent marks: "é" -> "e"
    s = s.lower().replace("-", " ")                      # lowercase; treat hyphen as a space
    out = []
    for tok in s.split():
        tok = tok.strip(".,'")                           # shave stray punctuation off each word
        if tok in ("st", "st."):
            out.append("saint")                          # expand abbreviations so "St" == "Saint"
        elif tok in ("ste", "ste."):
            out.append("sainte")
        elif tok:
            out.append(tok)
    return " ".join(out)

def similarity(spoken: str, candidate: str) -> float:
    # Hybrid sound+spelling score in [0,1]. We trust whichever leg is MOST confident.
    a, b = normalize_place(spoken), normalize_place(candidate)
    if not a or not b:
        return 0.0
    return max(
        _rapidfuzz_score(a, b),     # fast edit-distance (0 if rapidfuzz not installed)
        _phonetic_ratio(a, b),      # Metaphone sound-code similarity (0 if jellyfish not installed)
        difflib.SequenceMatcher(None, a, b).ratio(),  # always-available edit-distance fallback
    )
⚠️ Warning — similarity() and city_matches() are NOT the same function

The codebase has two comparators. similarity() (above) is the strong hybrid. But there is also an older city_matches() that uses only difflib at a 0.82 threshold — no phonetic leg. They look interchangeable. They are not. Fix #1 is entirely about the fact that the match gate called the weak one while the "did you mean…?" ranker called the strong one. Two scorers, one decision, silent disagreement. (Full story in Bug 1.)

3 · Decision bands, and why a "gate" must never be weaker than its "ranker"

Plain-English explanation. Given a spoken city and the real cities a manager has, Session 09's rank_candidates() scores each candidate and returns one of three decisions:

  • AUTO_ACCEPT — one clear winner (top score ≥ 0.86 and it beats #2 by ≥ 0.08). Confident enough to use silently, no extra question.
  • CONFIRM — plausible but ambiguous (top ≥ 0.55 but not a clear winner). Ask the caller "did you mean X?" before proceeding. In the gray zone we lean to confirming, because a false accept costs the whole call while a false confirm costs one turn.
  • NO_MATCH — nothing close (top < 0.55). Fall back to listing the cities the manager actually has.

Now the trap. Two separate pieces of code were making decisions about the same city: the match gate (does this listing's city match the caller? → uses weak city_matches) and the disambiguation ranker (should I ask "did you mean…?" → uses strong rank_candidates/similarity). When the strong ranker said "AUTO_ACCEPT Saint-Lazare!" but the weak gate said "no match," the unit was dropped from the results and the ranker's confidence never turned into a returned unit. The result: "nothing found," for a city the system had just confidently identified.

Why we need it (for CRM specifically). The whole point of the phonetic matcher (Session 08) was to recognise garbled French cities. But that intelligence only ever ran in the "ask a question" path — never in the "actually return the units" path. Fix #1 makes the gate at least as strong as the ranker by reusing the ranker's verdict.

How it works (analogy). Imagine a bouncer (the gate) and a manager (the ranker) at a club door. The manager recognises a VIP by face. But the bouncer is only allowed to check IDs by spelling — and the VIP's ID is smudged. The manager shouts "that's definitely her, let her in!" and the bouncer, ignoring the manager, says "name doesn't match, no entry." Absurd — yet that's exactly what our two-comparator setup did. The fix: when the manager is certain (AUTO_ACCEPT), the bouncer defers to the manager.

Annotated code — the banded ranker (existing) and the thresholds.

T_HIGH   = 0.86   # a top score at/above this can be a "clear winner"
MARGIN   = 0.08   # ...but only if it beats #2 by at least this gap
T_CONFIRM= 0.66   # lowest top score still worth a "did you mean?" question
T_FLOOR  = 0.55   # below this: give up, list available cities instead

If two code paths must agree on the same judgement, they must compute it with the same function — or one will eventually drift weaker than the other and produce contradictions. The cleanest fix isn't "make the weak one stronger"; it's "compute the verdict once and share it." Fix #1 lifts the rank_candidates() call to the top of find_units and feeds its result to both the gate and the "did you mean…?" question. They can never disagree again because there's only one of them.

4 · Language models have no clock

Plain-English explanation. A language model (the "brain" behind Max) is a text predictor. It does not have a clock, a calendar, or any sense of the current moment. When you ask it about "today" or "next week," it guesses from patterns in its training data — and that guess can be months or years off. The only way it knows the real date is if you tell it, every call, as part of the input.

Why we need it (for CRM specifically). In Transcript 2, today was June 24. The caller wanted to move in "next week" (≈ June 29–July 5). The only unit was ready "late June" — which is within next week. The correct answer was "great, that lines up!" Instead Max said "I'm not finding anything available that quickly." He had no anchor for "now," so he couldn't reason that late June ⊆ next week. Note the deeper trap: the complaint agent (a different assistant) does get a date, because it calls Verify_phone_number, which returns one. But Max is forbidden from calling that tool (renters aren't existing tenants), so he had no source of "today" at all.

How it works (analogy). Imagine a brilliant assistant with total amnesia about what day it is — every morning they wake with no idea of the date. If you want them to schedule anything, you must staple today's date to the top of every memo. Our "memo" is the JSON each tool returns; we staple a now field to it.

Jargon decoder.

  • LLM (Large Language Model) — the text-prediction model that generates Max's words and decides which tools to call.
  • grounding — feeding a model real, current facts (here: the date) so it doesn't rely on its frozen training knowledge.
  • tool response — the JSON our backend returns when Max calls a tool; the model reads it before its next turn. The natural place to staple "now."
  • ISO 8601 — the unambiguous date/time text format YYYY-MM-DDTHH:MM:SS (e.g. 2026-06-24T07:11:04); sorts correctly and parses everywhere.

Where we put the clock. We picked the tool response over two tempting alternatives, for a concrete reason each: the agent's static "context block" is baked once when the assistant is created, so a date there would be frozen forever (stale within a day); and a VAPI template variable would only cover one spot, not flow into the reasoning. The tool response is fetched fresh on every call and is read right before Max reasons about dates — perfect.

5 · Time zones, UTC, DST, and the IANA tz database

Plain-English explanation. "What time is it?" has no single answer — it depends on where you are. To do dates correctly you need four ideas:

  • UTC (Coordinated Universal Time) — the world's single reference clock; everything else is an offset from it.
  • offset — how far a place is from UTC, e.g. Montréal is UTC−5 in winter.
  • DST (Daylight Saving Time) — the twice-a-year clock shift; Montréal becomes UTC−4 in summer. This is why you can't hard-code a single offset.
  • IANA tz database — the canonical dataset of every region's rules and DST history, keyed by names like America/Toronto. Software reads it so it never has to know the rules itself.

Montréal shares its rules with Toronto (both Canada/US Eastern), and the canonical IANA key is America/Toronto (the America/Montreal key is a deprecated alias). Python's zoneinfo reads the tz database; ZoneInfo("America/Toronto") gives a DST-aware zone that automatically returns −5 in winter and −4 in summer.

Why we need it (for CRM specifically). Our managers and renters are in Québec. If we stamped UTC onto the response, "now" would read 4–5 hours ahead of the caller's wall clock — enough to flip "today" to "tomorrow" late in the evening, breaking the very move-in reasoning we're adding. The date must be Montréal-local to match what the caller means by "today."

How it works (analogy). Hard-coding "Montréal is UTC−5" is like printing a train timetable that ignores the summer schedule — correct half the year, wrong the other half, and nobody remembers to fix it. The IANA database is the railway's official rulebook; ZoneInfo just looks up the right page for today's date.

Jargon decoder.

  • zoneinfo — Python's built-in (3.9+) module that turns an IANA key into a usable time zone.
  • tzdata — a pip package that ships the IANA database. Linux usually has it system-wide; Windows does not, so zoneinfo needs this package there (this caused Bug 4).
  • aware vs naive datetime — an "aware" datetime carries its zone; a "naive" one doesn't (and is a frequent source of off-by-hours bugs).

Annotated code — the Montréal clock helper (new).

from zoneinfo import ZoneInfo   # stdlib: turns an IANA key into a tz object

# Lease agents serve Quebec — anchor "today" to Montreal local time (Eastern, DST-aware)
# instead of the model's guessed date. tzdata is in requirements and Linux ships the tz DB,
# but fall back to a fixed offset rather than let a missing DB break module import.
try:
    MONTREAL_TZ = ZoneInfo("America/Toronto")    # Montreal == Canada/US Eastern (handles DST)
except Exception:
    MONTREAL_TZ = timezone(timedelta(hours=-4))  # fail-open: EDT-ish fallback, never crash

def _montreal_now() -> str:
    # ISO 8601 in Montreal local time, e.g. "2026-06-24T07:11:04" — the agent's "today".
    return datetime.now(MONTREAL_TZ).strftime("%Y-%m-%dT%H:%M:%S")

6 · variableExtractionPlan: how a response field reaches the model

Plain-English explanation. When Max calls a tool, our backend returns JSON. But the model doesn't automatically "see" every field — VAPI uses a variableExtractionPlan (a small schema attached to each tool) that declares which fields to pull out of the response and make available to the model's reasoning. If a field isn't in that plan, it's effectively invisible. So adding now to the JSON is only half the job; we must also declare now in the extraction plan.

Why we need it (for CRM specifically). This is the wiring that makes Fix #2 actually reach the brain. Backend returns now → extraction plan lists now → the model can read it → the prompt tells it to treat now as today. Miss any link and the date silently never arrives.

How it works (analogy). The backend mails a parcel with several items. The extraction plan is the customs form listing what's allowed through. Anything not on the form gets held at the border — present in the box, but never delivered to the recipient.

Annotated code — declaring now so the model can use it.

"variableExtractionPlan": {
    "schema": {
        "type": "object",
        "properties": {
            "found": {"type": "boolean"},     # was a unit matched?
            "count": {"type": "integer"},     # how many
            "now":   {"type": "string"},      # NEW: current Montreal date/time the model may read
            "units": { "type": "array", "items": { ... } },
            "available_cities": {"type": "array", "items": {"type": "string"}},
            "disambiguation": { ... },        # the "did you mean?" block
        },
    }
},
💡 Tip — three links, all required

For a tool field to influence behaviour you need: (1) the backend returns it, (2) the variableExtractionPlan declares it, and (3) the prompt instructs the model to use it. We did all three for now on both find_units and search_listings. Skipping (2) is the classic "I added the field but the agent ignores it" bug.

7 · Environment parity: when your test lies to you

Plain-English explanation. Code behaves differently depending on which Python interpreter and which installed packages it runs under. If you test in an environment that's missing a library production has, your test can show fake behaviour — and you'll "verify" the wrong thing. Environment parity means making sure your test environment matches production's installed dependencies before you trust a result.

Why we need it (for CRM specifically). Recall similarity() takes max(rapidfuzz, phonetic, difflib), and the two stronger legs return 0.0 when their library isn't installed. The first interpreter we tested in had neither rapidfuzz nor jellyfish — so similarity() silently collapsed to difflib-only, exactly the weak behaviour we were trying to study. Our "evidence" was an artifact of the test box, not of production. We only saw the real phonetic-powered behaviour after switching to the project's virtualenv (which has both). (Full story in Bug 3.)

How it works (analogy). It's tasting a recipe with the salt left out and concluding "this dish is bland by design." The recipe's fine; your test kitchen was missing an ingredient. Always cook with the production pantry.

Jargon decoder.

  • virtualenv (venv) — an isolated Python with its own installed packages, so each project has exactly the libraries it declares.
  • graceful degradation — code that still runs when an optional dependency is absent (here, returning 0.0). Convenient, but it can mask a missing library instead of shouting about it.
  • parity — sameness between environments (dev vs prod) in the things that affect behaviour.

8 · Fail-open initialization: don't let one missing thing crash a whole route

Plain-English explanation. Code that runs at import time (the moment Python loads a file, before any request) is dangerous: if it throws, the entire module fails to load and every endpoint in it goes dark. Fail-open means: for non-critical setup, wrap it so a failure degrades gracefully instead of taking everything down.

Why we need it (for CRM specifically). MONTREAL_TZ = ZoneInfo("America/Toronto") runs at import. If the tz database is missing (as on a bare Windows box), that line throws ZoneInfoNotFoundError — and because it's at module top level, the whole leasing.py route file refuses to import, killing every leasing endpoint, not just the date feature. Our VAPI endpoints are required to "always return 200," so a hard crash here is unacceptable. The try/except falls back to a fixed offset: the date might be an hour off in the rare failure, but the API stays up.

How it works (analogy). A single burnt-out bulb shouldn't trip the whole building's power. Fail-open is the fuse that isolates the fault: the bad bulb goes dark, the rest of the floor keeps its lights.

⚠️ Warning — fail-open is a judgement call, not a default

Fail-open is right for non-critical setup (a clock that can tolerate being an hour off). It is wrong for security or correctness-critical setup — you don't want auth to "fail open" and let everyone in. Ask: "if this silently degrades, is the degraded state safe?" For the Montréal clock, yes. For a payment check, never.

🐛 Bug 1 — "Nothing found in Saint-Lazare," for a city the manager serves

🚨 The Symptom

In two French calls, a caller in Saint-Lazare was told there was nothing there. The tell-tale contradiction from Transcript 3: "je ne trouve rien à Saint-Lador… Nous avons des logements à Château-Güey et à Saint-Lazar." — "I found nothing in Saint-Lador… we have units in Châteauguay and Saint-Lazare." Both callers hung up.

🔍 The Diagnosis

The contradiction localised it instantly: the city is in the manager's inventory (it's in the offer list), so the data and the backend are innocent — something in find_units failed to match the caller's word to the listing. Reading find_units, we saw it computes two things from the same city: a match gate (city_matches, difflib-only, threshold 0.82) and a disambiguation block (rank_candidates → similarity, which adds rapidfuzz + Metaphone phonetic). We then ran the real library on the STT garble (Step 3) and watched San Lazaro score 0.92 / AUTO_ACCEPT in the ranker but return [] from the gate. Proven.

🧠 The Root Cause

Two scorers, one decision (Concept 3). The intelligent phonetic matcher built in Session 08 was only ever wired into the "ask a question" path, never the "return the units" path. So when the ranker was confident enough to AUTO_ACCEPT a phonetically-garbled city, that confidence produced neither a returned unit (gate said no) nor a "did you mean?" question (AUTO_ACCEPT means "no question needed"). The unit fell into the gap between the two comparators and vanished. It was a class of bug, not a single typo: any city the strong scorer accepted but the weak one rejected would silently disappear.

🔧 The Fix

Compute the ranker once; when it AUTO_ACCEPTs, fold that city into the gate; share the one rank object with the question builder.

# BEFORE — gate uses ONLY the weak difflib comparator; ranker's confidence is ignored here
city_hit = bool(city_norm) and (
    city_matches(query_norm, city_norm)
    or any(city_matches(t, city_norm) for t in norm_tokens)
)

# AFTER — same weak legs PLUS: if the strong phonetic ranker auto-accepted this city, trust it
rank = rank_candidates(query, available_cities, field_name="city")   # computed ONCE, above the loop
accepted_city_norm = normalize_place(rank.top.value) if rank.decision == "AUTO_ACCEPT" and rank.top else ""
city_hit = bool(city_norm) and (
    city_matches(query_norm, city_norm)
    or any(city_matches(t, city_norm) for t in norm_tokens)
    or (bool(accepted_city_norm) and city_norm == accepted_city_norm)  # <-- the rescue
)
🛡️ The Lesson

If two code paths must agree on the same judgement, make them share one computation — or one will drift weaker and produce contradictions. When you build a smart matcher, audit every place a match decision is made and confirm they all call it. A "did you mean?" that's smarter than the actual lookup is worse than useless: it knows the answer and refuses to act on it.

🐛 Bug 2 — "Not available that quickly," when it actually was

🚨 The Symptom

Transcript 2 (English). Today is June 24. Caller wants to move in "next week." Max: "Next week, perfect — I'm not finding anything available that quickly right now. The 4½ we have in Saint-Lazar isn't ready until late June." But "late June" is inside next week — the unit fit, and Max said it didn't, then downgraded the lead.

🔍 The Diagnosis

We read Max's full system prompt and tool definitions. The move-in step asks the model to "compare the caller's date to the unit's available_from" — but nowhere is the model ever given the current date. We checked the complaint agent (which reasons about dates fine) and saw it gets a datetime back from Verify_phone_number. Then the key realisation: Max is explicitly forbidden from calling Verify_phone_number (renters aren't tenants). So Max literally has no source of "today" anywhere in his world.

🧠 The Root Cause

A language model has no clock (Concept 4). Asked to compare "next week" to "late June" with no anchor for now, it guessed — and guessed wrong. This isn't a prompt-wording bug; it's a missing input. No amount of "please reason carefully about dates" fixes a model that doesn't know the date.

🔧 The Fix

Give it the input. Stamp Montréal-local now onto every tool response, declare it in the extraction plan, and instruct the prompt to treat now as today (Steps 5–6). Montréal time specifically, because UTC would drift "today" by 4–5 hours.

# BEFORE — the response carried no notion of "now"
return {"count": len(listings), "listings": listings}

# AFTER — every return (incl. empty/except) carries the Montreal clock
return {"count": len(listings), "listings": listings, "now": _montreal_now()}
🛡️ The Lesson

When an LLM reasons wrongly about facts (dates, prices, inventory), first ask "does it even have that fact?" before rewriting the prompt. Models are amnesiac about the present moment; ground them with real data fetched per-call. And when the fact is time, get the zone right — local, DST-aware — or you'll trade one wrong date for another.

🐛 Bug 3 — The phantom phonetic score of 0.00 (a measurement artifact)

🚨 The Symptom

While proving Bug 1, our first probe printed every phonetic and rapidfuzz score as 0.00 — making similarity() look identical to plain difflib. By that reading there was no phonetic leg at all, and the "two scorers" story seemed to fall apart.

input difflib rapidf phon simil decision Saint Lezzare 0.88 0.00 0.00 0.88 AUTO_ACCEPT San Lazaro 0.82 0.00 0.00 0.82 CONFIRM
🔍 The Diagnosis

The numbers were too clean — exactly 0.00 for both stronger legs across every input. That's not "low similarity," that's "not running." We recalled the code: _rapidfuzz_score returns 0.0 if rapidfuzz isn't importable, and _phonetic_ratio returns 0.0 if jellyfish isn't. We were running the probe in the system Python, not the project venv. A quick check confirmed the system interpreter had neither library; the project's backend/.venv had both.

🧠 The Root Cause

Environment parity (Concept 7). similarity() gracefully degrades when optional libraries are missing — convenient in production, but in a test it silently masks the very behaviour you're measuring. The "bug" was in our test box, not the system. Re-running under backend/.venv/Scripts/python.exe immediately showed the real phonetic scores (San Lazaro → 0.92), and Bug 1's diagnosis held up.

🔧 The Fix

No code change — fix the environment. Run verification in the interpreter that matches production:

$ backend/.venv/Scripts/python.exe -c "import rapidfuzz, jellyfish; print('both present')" both present
🛡️ The Lesson

Suspiciously round results (all exactly 0.00, all exactly equal) usually mean your instrument is off, not the system. Before trusting a local test, confirm it runs in the same environment as production — same interpreter, same installed packages. Graceful-degradation fallbacks are great for uptime and treacherous for debugging.

🐛 Bug 4 — ZoneInfoNotFoundError: 'America/Toronto'

🚨 The Symptom

Importing the route to test it crashed at module load:

$ .venv/Scripts/python.exe -c "import app.routes.leasing" File ".../app/routes/leasing.py", line 25, in <module> MONTREAL_TZ = ZoneInfo("America/Toronto") zoneinfo._common.ZoneInfoNotFoundError: 'No time zone found with key America/Toronto'
🔍 The Diagnosis

The error is explicit: zoneinfo couldn't find the zone data. zoneinfo is the stdlib reader, but it needs the IANA database to read from. On Linux that's a system package; on Windows there isn't one — you must install the tzdata pip package, and this venv didn't have it. (We'd added tzdata to requirements.txt in Step 5, but the venv hadn't been re-installed yet.)

🧠 The Root Cause

Two compounding facts: (1) Windows has no system tz database, so zoneinfo depends on the tzdata package (Concept 5); and (2) the call ran at import time at module top level, so the failure didn't just disable the date feature — it made the entire leasing.py route refuse to load. A missing optional package was positioned to take down every leasing endpoint.

🔧 The Fix

Two parts. Install the data (and keep it in requirements so prod gets it too); and wrap the construction so it can never crash import — fail-open to a fixed offset (Concept 8).

# BEFORE — one bad import-time line takes the whole route file down
MONTREAL_TZ = ZoneInfo("America/Toronto")

# AFTER — degrade to a fixed offset instead of crashing module import
try:
    MONTREAL_TZ = ZoneInfo("America/Toronto")    # correct, DST-aware (needs tzdata)
except Exception:
    MONTREAL_TZ = timezone(timedelta(hours=-4))  # safe fallback: API stays up, date ~1h off at worst
$ .venv/Scripts/python.exe -m pip install "tzdata>=2024.1" $ .venv/Scripts/python.exe -c "import app.routes.leasing as L; print(L._montreal_now())" 2026-06-24T07:11:04 # UTC-4 (EDT) in June — DST handled correctly
🛡️ The Lesson

Anything that runs at import time is a single point of failure for the whole module — keep it bulletproof or lazy. And remember zoneinfo ≠ the tz data: the reader is built in, the database isn't (declare tzdata for cross-platform safety). Match the safety to the stakes: a clock may fail open; auth may not.

🐛 Bug 5 — KeyError 'city' in the functional test

🚨 The Symptom

The end-to-end find_units test (Step 7) blew up while printing results:

KeyError: 'city' print('cities matched:', [u['city'] for u in r['units']])
🔍 The Diagnosis

Quick — the traceback names the missing key. We re-read what find_units actually puts in each unit dict and saw it exposes a composed address string ("10 Rue Principale, Saint-Lazare, QC"), not a standalone city field. The test asserted a key the API never returns.

🧠 The Root Cause

The bug was in the test, not the code under test. We wrote the assertion from memory of the data shape instead of from the actual return contract. The API was correct; our expectation was wrong.

🔧 The Fix

Assert against the real contract — print address (which exists) instead of city (which doesn't):

# BEFORE — asserts a field find_units never returns in a unit
units = [u['city'] for u in r['units']]      # KeyError: 'city'

# AFTER — uses the field the unit dict actually exposes
units = [u['address'] for u in r['units']]   # "10 Rue Principale, Saint-Lazare, QC"
🛡️ The Lesson

A test failing doesn't mean the code is wrong — sometimes the test is. Write assertions from the actual return shape (read it, or print the dict once), not from memory. A trivial bug, but a real reminder: the test is also code, and it can lie.

🧯 Troubleshooting / Common Errors

ZoneInfoNotFoundError: 'No time zone found with key America/Toronto'

Cause: zoneinfo can't find the IANA database — typically on Windows, which has no system tz DB. Fix: pip install "tzdata>=2024.1" (it's in requirements.txt; re-install the venv). The fail-open try/except means the API stays up regardless, just with a fixed-offset clock.

All phonetic / rapidfuzz scores come back as 0.00

Cause: you're running in an interpreter that doesn't have rapidfuzz and/or jellyfish; similarity() degrades to difflib-only. Fix: run under backend/.venv/Scripts/python.exe, or install the libraries. Verify: python -c "import rapidfuzz, jellyfish".

ModuleNotFoundError: No module named 'fastapi' (when importing the route)

Cause: the venv you're using is partial. Fix: install the backend requirements into that venv (pip install -r backend/requirements.txt) or use the interpreter that has the full stack.

I added now to the response but the agent still ignores the date

Cause: one of the three links is missing (Concept 6). Fix: confirm (1) the backend returns now, (2) now is in the tool's variableExtractionPlan, and (3) the prompt's [Current Date - Reference] section is present. Also re-deploy the config with update_lease_agents.py and deploy the backend.

The fixes work locally but not on a real call

Cause: only the config surface was deployed; the backend (Render) still runs the old leasing.py. Fix: commit and push leasing.py + requirements.txt to the Render-tracked branch. A voice change needs both surfaces (Session 10).

The session HTML code blocks render garbled

Cause: a raw <, >, or & inside a <pre><code> block confuses the in-page tokenizer. Fix: HTML-escape them (&lt;, &gt;, &amp;) in the source — e.g. write &gt;= for >=.
