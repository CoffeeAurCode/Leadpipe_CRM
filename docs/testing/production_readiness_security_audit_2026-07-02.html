Leadpipe CRM — Production Readiness & Security Audit

Senior-dev review · Prepared 2026-07-02 · Target launch region: Canada · Branch: test

Verdict: NOT READY — DO NOT LAUNCH YET

The product is feature-rich and mostly well-structured, but it carries three critical, exploitable defects that break multi-tenant isolation and expose the entire database. Any one of them alone is a launch blocker. The good news: all three are fixable in roughly 2–5 focused days, and none require re-architecture. Once C-1, C-2, and C-3 are closed and re-tested, this is a reasonable MVP to pilot with a small set of building managers.

Critical Findings

C-1CriticalShared DB client + per-request JWT = cross-tenant leak

The anon Supabase client is a module-level singleton, and every authenticated request mutates its auth token in place before querying:

# db/session.py
_anon_client: Client = create_client(SUPABASE_URL, SUPABASE_KEY)   # one global instance

# dependencies/authenticated_db.py
async def get_authenticated_db(credentials, db=Depends(get_db)):
    db.postgrest.auth(credentials.credentials)   # mutates the SHARED client
    return db

All route handlers are async def and share one event loop. When requests from two managers overlap, Manager B's auth() call can overwrite Manager A's token in the window between A setting its token and A's query executing (any await yields the loop). A's query then runs as B — RLS resolves auth.uid() to the wrong user, and A reads/writes B's tenants, complaints, and leads.

Failure scenario

Two managers load their dashboards at the same moment. The parallel GET /tenants / GET /complaints calls interleave; one manager receives rows belonging to the other. In a multi-tenant CRM this is the single worst class of bug — silent, non-deterministic, and a privacy breach.

Fix
  • Create a fresh Supabase client per request inside get_authenticated_db (construct create_client(...) and call .postgrest.auth(token) on that instance), or
  • Pass the JWT as a per-call header (ClientOptions headers) rather than mutating shared state, or
  • Move to a request-scoped client via a dependency that never touches a singleton.

This must be load-tested with concurrent users of different managers before launch.

C-2CriticalLive secrets committed to the repository

Real, working credentials are checked into git (confirmed tracked, not gitignored):

FileSecret
tests/test_import.pySupabase anon key + service_role key (exp 2085)
tests/run_api_tests.pyLive user access-token JWT
tests/run_csv_tests.pySupabase key material

The service_role key bypasses all RLS — anyone with it has unrestricted read/write to the entire database of every manager and tenant. It is valid until 2085. The Supabase project ref (nfgnxndktecqeleabbip) is also exposed, so the endpoint is known.

Fix (do immediately, before anything else)
  • Rotate the Supabase service_role and anon keys now in the Supabase dashboard — assume they are compromised.
  • Remove the secrets from the files; load them from env vars instead.
  • Purge them from git history (git filter-repo / BFG) — deleting the file in a new commit is not enough; the keys remain in history and on GitHub forks/caches.
  • Add a secret-scanning pre-commit hook (e.g. gitleaks) so this can't recur.
C-3CriticalUnauthenticated, RLS-bypassing public endpoints

The VAPI/webhook endpoints use get_service_db (RLS bypassed) with no authentication and no signature verification. There is no VAPI signing-secret check anywhere in voice.py (only the outbound Vapi client token). Anyone on the internet who knows the URL can call them.

The most damaging are the ones that read or write tenant data with attacker-supplied identifiers:

EndpointAbuse
POST /flats/identify-callerSubmit any phone number → returns tenant name, flat, building, society, manager name + phone. Bulk PII enumeration.
POST /flats/verify-phoneProbe which flats exist / are occupied / vacant.
GET /appointments/view?flat_number=Read appointments for any flat number.
GET /leasing/find-units, /find-listing, /search, /search-listingsAccept manager_id as a query param → dump any manager's listings.
POST /voice/webhook, /voice/lease-lead-directInject fake complaints, leads, appointments and notifications against an arbitrary manager_id.
PATCH /appointments/update, /cancelReschedule/cancel appointments by flat number, unauthenticated.
Fix
  • Verify the VAPI request signature / shared secret on every voice endpoint (VAPI supports a server secret header — check it and reject mismatches while still returning HTTP 200 as the contract requires, or 401 for non-VAPI callers).
  • The Stripe webhook already does this correctly (construct_event + signature) — mirror that discipline for VAPI.
  • Stop trusting manager_id / property_group_id as free query params on read endpoints; derive them from the authenticated call context (assistant/number → manager mapping) instead of the caller.
  • Rate-limit these endpoints (see H-1) to blunt enumeration.

High Findings

H-1HighNo rate limiting

slowapi>=0.1.9 is in requirements.txt but is never imported or wired up (grep of all *.py returns nothing). There is no limiter on any route — including the unauthenticated service-role endpoints (C-3), the OpenAI-backed /chat, the Groq extraction path, and outbound-call initiation. This makes PII scraping, complaint/lead spam, and cost-amplification (each /chat and each outbound call costs money) trivial.

Fix Wire up slowapi with per-IP and per-user limits; apply the tightest limits to /voice/*, /flats/identify-caller, /leasing/find-*, /chat, and /voice/call/outbound.
H-2HighPII logged in plaintext

Handlers print caller phone numbers, tenant phone numbers, and full call transcripts to stdout (e.g. [DEBUG] verify_phone: ... phone_number=..., transcript handling in the voice webhook). On Render these land in retained log storage. For a Canadian launch handling tenant personal data, plaintext PII in logs is a PIPEDA exposure and an incident-blast-radius multiplier if logs leak.

Fix Replace print() with the standard logging module at appropriate levels; redact/mask phone numbers and never log full transcripts at INFO. Gate any verbose logging behind DEBUG.

Medium Findings

M-1MediumSubscription gate doesn't enforce trial expiry

require_active_subscription only checks status in ('trialing','active') and selects trial_ends_at but never compares it to now. If the Stripe customer.subscription.updated webhook is missed or delayed, a manager whose trial has actually ended keeps full access. Revenue leak, not a security hole.

Fix Reject trialing rows where trial_ends_at < now(), and/or reconcile subscription status on a schedule rather than relying solely on webhook delivery.
M-2MediumNo CI gate; unpinned dependency

No .github/workflows present — the pytest suite (backend/tests) and Playwright e2e (e2e/) exist but nothing runs them automatically, so regressions ship silently. Most Python deps are pinned, but openai>=1.0.0 is open-ended, which makes builds non-reproducible and risks a breaking minor.

Fix Add a CI workflow that runs lint + backend tests + e2e on PRs to test; pin openai to a known-good version.
M-3MediumCanadian compliance gaps
  • Call recording/transcription consent: the voice agent records and transcribes tenant calls. Canadian law generally requires the caller be notified of recording. Confirm the agent's first message discloses this; keep evidence of consent.
  • Data residency: tenant PII sits in Supabase, VAPI, Twilio, SendGrid, OpenAI, Groq, and Stripe — several are US-based. PIPEDA permits cross-border transfer but requires transparency about it. Confirm the Supabase project region and document processors in a privacy policy.
  • Retention/deletion: transcripts and leads accumulate with no visible retention policy or tenant deletion/right-to-access path.
Fix Add a recording-consent line to the agent script, publish a privacy policy listing sub-processors and residency, and define a retention + deletion process. Worth a short legal review before a Canadian launch.

Low Findings

L-1LowRepo hygiene
  • Stray files committed to the repo root (Transcript1–4.md, Render_logs.md, French_cere.md, Complaint_transcript.md, Lease_listing_*.csv) — violates the project's own "repo root is reserved" rule and Render_logs.md / transcripts may contain PII. Move to docs/ or delete.
  • Debug print() scattered through routes (see H-2).

What's already done well

Stripe webhook

Signature verified with construct_event and idempotency via stripe_events. This is the correct pattern — apply it to VAPI.

JWT validation

Proper ES256/JWKS with HS256 fallback, audience checked, expiry handled.

RLS as a model

Row-level security with manager_id keys is the right multi-tenant foundation — C-1 undermines it in the client layer, not the DB design.

CORS & uploads

CORS locked to configured origins; uploads enforce content-type and size limits.

DB error mapping

clean_db_error keeps raw Postgres errors from reaching the frontend.

Clean architecture

Consistent dependency-injection auth pattern, service vs. authenticated client separation, thorough CODEBASE_CONTEXT.md.
