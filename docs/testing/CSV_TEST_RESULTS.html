API Behaviour Observations

1created response shape — property imports

/import/properties returns created as a nested breakdown object, not a plain integer like the tenant endpoint: 

{"created": {"properties": 1, "buildings": 2, "flats": 3}, "skipped": [], "errors": []}

The test plan spec expected {"created": 3, ...}. Tenant imports do return a plain integer. The spec should be updated to document this format difference between the two endpoints.

2Mixed-case column headers — CP12 & CT12

Spec expected that Property_Name, Flat_Number, Name, Phone etc. would return needs_mapping: true and require an AI mapping round-trip. Actual: needs_mapping: false — the server normalises column names case-insensitively and handles underscore variants internally. The 2-step AI flow is only needed for genuinely unrecognised names (e.g. unit_id, block_name from CA04). This is better than the spec.

3File size vs row count check order — CP18 & CT16

Spec expected "File too large (max 5 MB)" for a 50k-row / 10k-row file. Both test files triggered the row-count limit first: {"detail": "Too many rows (max 1000)"}. The row check fires before the size check. Not a bug — both limits return HTTP 400. A file that is large but under 1000 rows would still trigger the size check.

4Sequential test state — CT09, CT11, CT13, CT17

Several tenant tests share flat numbers with earlier tests. Flats occupied in earlier tests cause later rows to be skipped rather than created. All skips are correct idempotent behaviour — occupied flats cannot receive a second tenant. The test plan should note these dependencies and recommend running against a clean dataset between runs.

5AI mapping quality — CA04

Groq llama-3.3-70b-versatile correctly inferred all 3 ambiguous headers in prop_weird_headers.csv (unit_id, block_name, street) without any hints. unmapped_required was empty — all required fields resolved. This confirms the AI mapping layer is reliable for real-world column name variations.
